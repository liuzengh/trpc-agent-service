# 跨后端数据迁移操作手册

> 状态：实现 + 文档（阶段 33，需求验收 A8）。
> 代码：`cmd/migrate/`（CLI）；`trpcservice/infra/storage/{sessions,memories}.go`（后端工厂）。
> 适用：Redis→SQL、SQL→Redis、本地→远端等跨后端搬迁；**不适用于** summaries/tracks
> 与超旧事件（保真边界见 §4）。

## 1. 用途与范围

把**一个租户**（AppName）下**若干用户**的会话状态/事件与记忆，从 source 后端
复制到 target 后端。source/target 支持平台全部后端组合：

| 数据 | 后端 |
| --- | --- |
| session | `inmemory` / `redis://URL` / `mysql://DSN` |
| memory | `inmemory` / `redis://URL` / `mysql://DSN`（与平台 `storage.backendTable` 一致） |

迁移只走框架 Service API（`session.Service` / `memory.Service`），不直读任何
后端的私有 schema，因此任何组合都能迁移。

## 2. 命令与参数

```
go run ./cmd/migrate \
  -src-session  redis://localhost:6379/0 \
  -dst-session  "mysql://root:pw@tcp(localhost:3306)/trpc_agent_service?parseTime=true" \
  -src-memory   redis://localhost:6379/0 \
  -dst-memory   redis://localhost:6379/1 \
  -tenant t1 -users u1,u2
```

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `-src-session` / `-dst-session` | 是 | 后端 spec：`inmemory` \| `redis://…` \| `mysql://DSN` |
| `-src-memory` / `-dst-memory` | 否 | 只给一端则跳过 memory；都给才迁移 |
| `-tenant` | 是 | 迁移的租户 id（= 框架 AppName） |
| `-users` | 二选一 | 逗号分隔用户列表 |
| `-auto` | 二选一 | 从 MySQL source 的 `session_states` 枚举该租户全部 user_id |

`-auto` 仅对 `-src-session mysql://…` 有效（SQL 枚举是 MySQL 私有能力；
Redis source 请显式 `-users`，Redis key 形态不提供稳定枚举）。

### 典型场景

- **Redis → MySQL（生产持久化）**
  ```
  go run ./cmd/migrate -src-session redis://r:6379/0 -dst-session "mysql://u:p@tcp(db:3306)/platform?parseTime=true" -src-memory redis://r:6379/0 -dst-memory redis://r:6379/1 -tenant t1 -auto
  ```
- **MySQL → 另一 MySQL（机房/环境搬迁）**：同上两端都用 mysql DSN。

## 3. 迁移语义

- **目标侧覆盖**：每个 session key 先 `DeleteSession` 再 `CreateSession(state)`，
  逐事件 `AppendEvent`；每个用户 memory 先 `ClearMemories` 再逐条 `AddMemory`
  （含 `kind/event_time/participants/location` 元数据，`main.go copyUser`）。
  因此**重复执行结果一致**（幂等）。
- 日志逐 session/逐 user 打印进度，结束时汇总 `sessions/events/memories` 计数。

## 4. 保真边界（务必阅读）

1. **事件窗口**：框架 v1.11.2 **未导出事件分页 API**（`EventPage` 无公开 builder），
   `GetSession` 各后端只返回“最近 N 事件”窗口。CLI 以 `WithEventNum(1<<30)` 取最大
   窗口（cmd/migrate/main.go `copyUser`），但后端自身仍可能截断超旧事件。
   **需要全量旧事件的 MySQL 源**，可在业务停写窗口内直拷
   `session_events`（补全模板，见 §5），再对拷贝的库执行迁移。
2. **summaries / tracks 不迁移**：框架无 Service 写入 API。目标库会话在继续对话
   时按需重新汇总（summary 是“压缩缓存”，可由后续会话重建；events 是真相）。
3. **一致性窗口**：删除重建期间目标 key 上有并发流量会丢写——建议迁移在低峰/
   停写窗口执行，或先迁移-校验-再切流（§6）。

## 5. MySQL 全量事件补全模板（可选）

在停写窗口把 MySQL source 的 events 直拷到目标库（表结构同源，前缀空）：

```sql
-- 目标库需先有 session 后端表（init 脚本 session mysql schema）。
INSERT INTO target.session_events
    (app_name, user_id, session_id, event_id, created_at, event_json, deleted_at)
SELECT app_name, user_id, session_id, event_id, created_at, event_json, deleted_at
  FROM source.session_events
 WHERE app_name = 't1' AND deleted_at IS NULL;
```

> 列名以实际 `session_events` schema 为准（`deployments/mysql/init/010_*.sql`
> 不含 framework 自有表；framework `session/mysql` 模块 `init.go`/`schema.sql`
> 是权威）。拷贝后 target 的 `session_states` 由 CLI 迁移生成，二者一致。

## 6. 上线步骤（建议）

1. 配置/启动 target 后端（MySQL 容器、Redis 实例）；
2. 低峰执行 CLI（先 1 个用户试跑 → 抽查 GetSession 对比 → 全量）；
3. 抽样校验：目标库 session state/events 条数与最近对话一致；
4. 灰度切换：改租户 `data_backend.session=mysql`（见《租户配置模型与数据后端路由
   设计》），旧 Redis 保留 1-7 天作为回退源；期间新消息双写靠 session 锁兜底
   （Redis 锁在 bus 层，与后端无关）。
