> 日期：2026-09-08 ｜ 环境：Docker Compose 全栈（backend:8080 / mysql / redis / milvus / jaeger / prometheus）
> 链路载体：admin `/chat`（与 IM 同管道）＋ Redis 总线直注。**全程不依赖真实 IM**。
> 完成后把「记录项」反馈给助手回归文档。

## 0. 准备：数据与冒烟

```bash
# 后端地址
BASE=http://localhost:8080
# mysql 直查（进容器）
MYSQL="docker exec deployments-mysql-1 mysql -uroot -ptrpc123 trpc_agent_service"
# redis 直查
R="docker exec deployments-redis-1 redis-cli"
```

1. 建租户
```bash
curl -s -X POST $BASE/tenants -H 'Content-Type: application/json' \
  -d '{"id":"t-demo","name":"演示租户"}' ; echo
```
2. 建模型端点（换成你的真实 key / base_url / model；明文 api_key 由后端自动转 secret 引用）
```bash
curl -s -X POST $BASE/endpoints -H 'Content-Type: application/json' -d '{
  "id":"e-demo","scope":"tenant","tenant_id":"t-demo","name":"main","type":"chat",
  "provider":"openai-compatible","base_url":"https://api.deepseek.com/v1",
  "model_name":"deepseek-chat","api_key":"<你的KEY>"
}'; echo
```
3. 建 Agent 并发布（挂时间工具；审批演示也用它）
```bash
curl -s -X POST $BASE/agents -H 'Content-Type: application/json' \
  -d '{"id":"a-demo","tenant_id":"t-demo","name":"演示Agent"}' ; echo
curl -s -X POST $BASE/agents/a-demo/publish -H 'Content-Type: application/json' -d '{
  "system_prompt":"你是助手。当用户请你查时间/日期时，你必须调用 get_current_time 工具。",
  "endpoint_id":"e-demo",
  "tool_ids":["get-current-time"],
  "approval_tool_ids":["get-current-time"]
}'; echo
```
4. 冒烟：发一条消息 → 拿 message_id
```bash
curl -s -X POST $BASE/chat -H 'Content-Type: application/json' \
  -d '{"tenant_id":"t-demo","agent_id":"a-demo","session_id":"s-smoke","text":"你好，用一句话自我介绍"}' ; echo
# 等 3~5s 后看回复（无 consumer group 直接读 outbound 流）
$R XRANGE stream:outbound - + COUNT 50 | grep -A2 "s-smoke" | head -20
```
> 记录项：回复文本是否正确出现（验证链路通）。

## A. 幂等（重复投递只回一次）

原理：worker 幂等键 = 消息 ID（`idem:{id}`，Redis SetNX）。HTTP 层 ID 是服务端生成的，重放要走**总线层**注入相同 ID 两条。

```bash
# 1) 直接向 inbound 流塞两条完全相同的消息（ID=dup-001）
DUP='id dup-001 trace_id t-1 tenant_id t-demo agent_id a-demo session_id s-dup channel admin user_id admin content {"role":"user","content":"现在几点"}'
$R XADD stream:inbound '*' $DUP
$R XADD stream:inbound '*' $DUP
# 2) 等 5~8s（worker 消费）
# 3) 看 outbound 里对 s-dup 的回复条数 —— 应为 1
$R XRANGE stream:outbound - + COUNT 100 | grep -c "s-dup"
# 4) 幂等键已存在
$R EXISTS idem:dup-001
# 5) 清场（避免污染后续）
$R DEL idem:dup-001
$R XDEL stream:inbound $( $R XRANGE stream:inbound - + COUNT 5 | grep -o '^[0-9-]*' | head -2 | tr '\n' ' ' )   # 清理本次注入(可选)
```
> 预期：第 3 步输出 `1`；audit_logs 中该会话 Decision=executed 仅 1 条。
> 记录项：XRANGE 条数、EXISTS=1、audit_logs 行数。

## B. 审批流（强制审批工具 → 通知 → 回复「批准」继续）

原理：发布 Agent 时挂 `approval_tool_ids:["get-current-time"]`（已在第 0 步配好）；模型一旦调用该工具，worker 先发审批通知并阻塞回合。

```bash
# 1) 发一条会触发工具调用的消息（新会话避免历史干扰）
curl -s -X POST $BASE/chat -H 'Content-Type: application/json' \
  -d '{"tenant_id":"t-demo","agent_id":"a-demo","session_id":"s-apr","text":"现在几点了？请调用工具回答"}' ; echo
# 2) 等 2~4s，在 outbound 里应看到审批通知（提示「回复「批准」允许执行」）
$R XRANGE stream:outbound - + COUNT 50 | grep -A3 "s-apr" | head -30
# 3) 同一会话回复「批准」
curl -s -X POST $BASE/chat -H 'Content-Type: application/json' \
  -d '{"tenant_id":"t-demo","agent_id":"a-demo","session_id":"s-apr","text":"批准"}' ; echo
# 4) 等几秒，再读 outbound → 应出现最终回答（含当前时间）；且只执行了一次工具
$R XRANGE stream:outbound - + COUNT 100 | grep -A3 "s-apr" | head -30
# 5) 看审批审计
$MYSQL -e "SELECT tenant_id,session_id,decision,latency FROM audit_logs WHERE session_id='s-apr' ORDER BY id;"
```
> 预期：先一条「需审批」通知，批准后出结果；audit 有 approved 记录。
> 备选：回复「拒绝」→ 工具不执行，回合以拒绝结束。
> 记录项：通知文本、批准后最终回复、audit 行数（应 2 条：executed 前/后 or approved）。

## C. 超时降级（模型端点黑洞 → 回合失败被兜底）

原理：模型 HTTP 超时 120s + 整轮 `runTimeout` 300s；失败回合不挂 worker、后续消息仍可处理、审计记 `error_type`。

```bash
# 1) 建一个指向黑洞的端点（同网络不可达端口 → 秒级失败）：
#    更狠可用 10.255.255.1:9（挂起到 120s 超时），演示选其一
curl -s -X POST $BASE/endpoints -H 'Content-Type: application/json' -d '{
  "id":"e-blackhole","scope":"tenant","tenant_id":"t-demo","name":"blackhole","type":"chat",
  "provider":"openai-compatible","base_url":"http://10.255.255.1:9/v1",
  "model_name":"x","api_key":"k"
}'; echo
# 2) 建临时 agent 挂黑洞端点
curl -s -X POST $BASE/agents -H 'Content-Type: application/json' \
  -d '{"id":"a-black","tenant_id":"t-demo","name":"黑洞"}' ; echo
curl -s -X POST $BASE/agents/a-black/publish -H 'Content-Type: application/json' \
  -d '{"endpoint_id":"e-blackhole"}' ; echo
# 3) 发消息（黑洞模式会等 ~120s 超时；拒绝模式秒级失败）
time curl -s -X POST $BASE/chat -H 'Content-Type: application/json' \
  -d '{"tenant_id":"t-demo","agent_id":"a-black","session_id":"s-to","text":"hi"}' ; echo
# 4) 期间观察后端日志（docker logs -f deployments-backend-1）应见 timeout/超时 Warn
# 5) 结束后查审计错误归类
$MYSQL -e "SELECT session_id,error_type,decision,latency FROM audit_logs WHERE session_id='s-to' ORDER BY id;"
# 6) 验证系统未受影响：再发一条正常消息（e-demo agent）仍能回复
curl -s -X POST $BASE/chat -H 'Content-Type: application/json' \
  -d '{"tenant_id":"t-demo","agent_id":"a-demo","session_id":"s-after","text":"还在吗"}' ; echo
```
> 预期：黑洞回合最终在审计里出现 error_type（timeout 或 run_error）；随后正常消息正常回复（worker 未被拖垮）。
> 记录项：黑洞回合耗时、error_type、随后正常消息是否成功。
> 注意：若选挂起模式请耐心等 ~120s；可并行观察日志。

## D. 简单压测（admin /chat 并发注入）

脚本：`scripts/loadtest/chat_load.go`（stdlib，无需装依赖）。每 goroutine 持一个独立 session，模拟 N 个并发会话。

```bash
cd /d/Develop/Git/trpc-agent-service
# 冒烟：8 并发 × 5 轮（40 条，真实模型，会消耗少量 token）
go run ./scripts/loadtest/chat_load.go \
  -url http://localhost:8080 -tenant t-demo -agent a-demo \
  -concurrency 8 -each 5 -text "hi"
# 试探拐点：16 / 32 并发（每次间隔 1 分钟以上，观察后端日志与 Redis 负载）
go run ./scripts/loadtest/chat_load.go -tenant t-demo -agent a-demo -concurrency 16 -each 5 -text "hi"
go run ./scripts/loadtest/chat_load.go -tenant t-demo -agent a-demo -concurrency 32 -each 3 -text "hi"
```

观测三组数据：
```bash
# ① 输出脚本的 throughput / p50/p95/p99/max / http_202 计数
# ② 用量落库（每轮回合的 token/tool 明细）：
$MYSQL -e "SELECT dimension,COUNT(*),ROUND(SUM(amount)) total FROM usage_records WHERE tenant_id='t-demo' GROUP BY dimension;"
$MYSQL -e "SELECT meta FROM usage_records WHERE tenant_id='t-demo' AND dimension='skill' ORDER BY id DESC LIMIT 2;"
# ③ 指标（Prometheus :9090 查询）：
#    platform_agent_run_duration_* 的 p95/p99（histogram_quantile）
#    platform_inbound_messages / platform_agent_run_errors
#    platform_model_call_duration 直方图
```

> 记录项：每档并发下的 throughput、p50/p95/p99/max、错误数；usage_records 各维度总量；
> Prometheus 端到端延迟 p95、error 计数。这些将回填 `docs/容量评估指南.md` 与 `详细设计文档 §14` 容量表。
> 说明：worker 并发上限 `consumeWorkers` 默认 16/节点；真实模型延迟是主要吞吐瓶颈；单 session 串行受会话锁保护，跨 session 并行。
