# 租户配置模型与数据后端路由设计

> 状态：设计定案（阶段 33，需求验收 A1/A6 取舍说明）。
> 关联：`CONTEXT.md`「分层架构」「数据访问与存储域」；`AGENTS.md` 阶段 18/32/33；
> 代码 `trpcservice/domain/tenant/tenant.go`、`trpcservice/infra/storage/router.go`。

## 1. 背景

需求验收清单 A1「租户模型含 tenant_id、应用/模型/工具权限/IM 通道/数据后端/审计策略」
与 A6「支持不同租户选择不同数据后端」检查时发现：字段并未全部堆在单个 `Tenant`
结构里，逐租户数据后端也只覆盖 session/memory 两域。本文说明这是**有意设计取舍**
而非缺口，并给出边界与扩展准则。

## 2. 租户 = 隔离与治理边界（不是配置聚合根）

`domain/tenant.Tenant`（tenant.go:36-43）只携带**运行时治理所必需**的字段：

| 字段 | 用途 |
| --- | --- |
| `id / name / status` | 身份、展示、启用/禁用 |
| `data_backend map[string]string` | 逐数据域的后端选择（session/memory） |
| `quota` | token 预算（治理） |
| `audit_policy` | 脱敏、IM 用户白名单、工具白名单、强制审批（治理） |

其余“租户的配置”是**以 `tenant_id` 隔离的独立管理域**，各自有生命周期与版本：

| 配置 | 管理域 | 隔离依据 | 代码位置 |
| --- | --- | --- | --- |
| 应用配置（Agent + RuntimeProfile） | `domain/agent` | agents/agent_versions 表 `tenant_id` | agentstore/agent_mysql.go |
| 模型配置（Endpoint + APIKeyRef） | `domain/llm` | model_endpoints 表 `tenant_id` | llmstore/llm_mysql.go |
| 工具权限（Scope + Grant） | `domain/tool` | tools 表 `tenant_id` + Registry.IsAllowed | tool.go |
| IM 通道绑定（channel+account+凭据引用） | `domain/channels`(binding) | bindings 表 `tenant_id` | bindingstore/binding_mysql.go |
| 会话数据后端路由 | 本 Tenant 的 `data_backend` | —— | 见 §3 |
| 审计策略 | 本 Tenant 的 `audit_policy` | —— | worker/policy.go |

> 注：建表 SQL（`deployments/mysql/init/001_tenants.sql`）另有 `model_config` 列，
> 是需求文档级全量设计；Go 运行时模型刻意不读它——模型配置实际由
> Agent 的 RuntimeProfile 挂 endpoint_id 表达（更贴近运行语义），避免双份真相。

**为什么这样分**：把 Endpoint/Agent/Binding 的增删改生命周期塞进 Tenant 聚合会产生
巨大的聚合根与级联写放大；这些资源独立管理、独立鉴权（例如 IM 账号先于租户绑定）。
治理策略（quota/audit_policy）与路由（data_backend）是**每次消息处理都要读**的
热数据，因此内联在 Tenant。

## 3. 数据后端路由：出现第二实现才纳入 Router

`infra/storage/router.go` 的 `Router.Sessions/Memories` 按 `Tenant.DataBackend`
（`DomainSession`/`DomainMemory`）逐租户解析后端实例（inmemory/mysql/redis，
router.go:18-101）。其余域为**全局单后端**：

| 数据域 | 路由方式 | 理由 |
| --- | --- | --- |
| Session | 逐租户（Router） | 需求明确要求 session 后端可换（inmemory/redis/mysql） |
| Memory | 逐租户（Router） | 同上（现支持 inmemory/redis，memories.go:20-31） |
| Knowledge 向量 | 全局（Milvus 或内存） | stores.go:36-45；向量检索无“会话热数据”逐租户诉求 |
| Artifact 对象存储 | 全局（MinIO） | stores.go:33-57；路径已按 tenant 前缀隔离 |
| Audit/Usage | 全局（MySQL） | 审计必须集中；条目带 tenant_id |

**扩展准则**（阶段 18 grill 已定）：Router 只在某个域出现**第二个实现**时才纳入；
当前每域至多一个生产实现 + 一个测试实现，逐租户路由是过度设计。当未来出现
“租户 A 用远端向量库、租户 B 用本地”时，把该域加进 `Tenant.DataBackend` 与
Router 的 switch 即可，域抽象（`tenant.Store`/`Sessions`/`Memories`）不需要动。

## 4. 租户级配置回滚与灰度（见独立文档）

配置回滚与灰度策略详见《灰度发布与配置回滚策略》——本设计只说明配置归属；
那篇说明如何安全变更这里的配置（tenant 版本快照 + rollback API、Agent 版本回滚）。

## 5. 成员与 RBAC（2 期预留，阶段 33 定案）

领域分层（用户拍板）：**tenant = 企业业务团队；member = 登录员工（login user）；
roles = 企业内授权**。`001_tenants.sql` 的 RBAC 四表
（tenant_members / roles / role_permissions / member_roles）当前**零代码使用**，
作为 2 期登录/SSO + 成员管理的地基**保留**并在 SQL 注释标注「预留」。

- 当前平台权限模型 = 租户级隔离 + agent↔tool 授权（agent_tool_grants）+ 治理白名单，
  无管理员登录概念（Admin API 无认证）；
- 登录体系落地时才接线 member 表（owner/admin/member 角色由 admin UI 维护，
  成员身份来自 IM/SSO user_id，001 中列注释已按此设计）。

## 6. 结论

- A1 字段语义完整落地（分散在管理域 + Tenant 热数据），非代码缺口；
- A6 session/memory 两域逐租户路由已实现；其余域按「第二实现才纳入」准则保持
  全局单后端，属既定收敛。
