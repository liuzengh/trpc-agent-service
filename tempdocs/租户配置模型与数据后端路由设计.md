# 租户配置模型与数据后端路由设计

> 状态：设计定案（阶段 33，需求验收 A1/A6 取舍说明）。
> 关联：`CONTEXT.md`「分层架构」「数据访问与存储域」；`AGENTS.md` 阶段 18/32/33；
> 代码 `trpcservice/domain/tenant/tenant.go`、`trpcservice/infra/storage/router.go`。

## 1. 背景

需求验收清单 A1「租户模型含 tenant_id、应用/模型/工具权限/IM 通道/数据后端/审计策略」
与 A6「支持不同租户选择不同数据后端」检查时发现：字段并未全部堆在单个 `Tenant`
结构里，逐租户数据后端也只覆盖 session/memory 两域。本文说明这是**有意设计取舍**
而非缺口，并给出边界与扩展准则。

## 2. 租户 = 隔离与治理边界（不是配置聚合根）

`domain/tenant.Tenant`（tenant.go:36-43）只携带**运行时治理所必需**的字段：

| 字段 | 用途 |
| --- | --- |
| `id / name / status` | 身份、展示、启用/禁用 |
| `data_backend map[string]string` | 逐数据域的后端选择（session/memory） |
| `quota` | token 预算（治理） |
| `audit_policy` | 脱敏、IM 用户白名单、工具白名单、强制审批（治理） |

其余“租户的配置”是**以 `tenant_id` 隔离的独立管理域**，各自有生命周期与版本：

| 配置 | 管理域 | 隔离依据 | 代码位置 |
| --- | --- | --- | --- |
| 应用配置（Agent + RuntimeProfile） | `domain/agent` | agents/agent_versions 表 `tenant_id` | agentstore/agent_mysql.go |
| 模型配置（Endpoint + APIKeyRef） | `domain/llm` | model_endpoints 表 `tenant_id` | llmstore/llm_mysql.go |
| 工具权限（Scope + Grant） | `domain/tool` | tools 表 `tenant_id` + Registry.IsAllowed | tool.go |
| IM 通道绑定（channel+account+凭据引用） | `domain/channels`(binding) | bindings 表 `tenant_id` | bindingstore/binding_mysql.go |
| 会话数据后端路由 | 本 Tenant 的 `data_backend` | —— | 见 §3 |
| 审计策略 | 本 Tenant 的 `audit_policy` | —— | worker/policy.go |

> 注：建表 SQL（`deployments/mysql/init/001_tenants.sql`）**已不再有** `model_config` 列
> （阶段 43 删除）。模型配置由 Agent 的 `RuntimeProfile.endpoint_id` 指向 `model_endpoints`
> 表达——两层引用，避免双份真相。映射关系见 `docs/架构设计文档.md §10.6`。

**为什么这样分**：把 Endpoint/Agent/Binding 的增删改生命周期塞进 Tenant 聚合会产生
巨大的聚合根与级联写放大；这些资源独立管理、独立鉴权（例如 IM 账号先于租户绑定）。
治理策略（quota/audit_policy）与路由（data_backend）是**每次消息处理都要读**的
热数据，因此内联在 Tenant。

## 3. 数据后端路由：出现第二实现才纳入 Router

`infra/storage/router.go` 的 `Router.Sessions/Memories` 按 `Tenant.DataBackend`
（`DomainSession`/`DomainMemory`）逐租户解析后端实例；`router_domains.go` 的三个包装器
（`NewRouterVectorFactory` / `NewRouterArtifactService` / `NewRouterAuditRecorder`）
对 Vector/Artifact/Audit 做同样的事。因此**五个域都可逐租户选择后端**：

| 数据域 | 路由方式 | 可选后端 | 理由 |
| --- | --- | --- | --- |
| Session | 逐租户（Router） | inmemory / redis / mysql | 需求明确要求 session 后端可换 |
| Memory | 逐租户（Router） | inmemory / redis / mysql | 同上（`backendTable` 已接 mysql） |
| Knowledge 向量 | 逐租户（包装器） | inmemory / milvus | 向量库有第二实现，纳入路由 |
| Artifact 对象存储 | 逐租户（包装器） | inmemory / minio | 同上；对象路径另按 tenant 前缀隔离 |
| Audit | 逐租户（包装器） | inmemory / mysql | 同上 |
| Usage 计量 | **不按租户路由** | 始终 MySQL（无 MySQL 时内存） | 用量要跨租户汇总做预算判断，落到租户私有内存后端会让预算失真 |
| Outbox / DLQ | **不按租户路由** | 始终 MySQL | 可靠投递与死信的底座 |

**扩展准则**：Router 只在某个域出现**第二个实现**时才纳入逐租户路由；纳入的代价是
一行 `backendTable` 记录（session/memory）或一个包装器分支（vector/artifact/audit）。

配置回滚与灰度策略详见《灰度发布与配置回滚策略》——本设计只说明配置归属；

## 5. 成员与 RBAC（已落地，阶段 37–42 完成）

领域分层：**tenant = 企业业务团队；member = 登录员工（login user）；roles = 企业内授权**。

- `tenant_members` 是**唯一**的成员/角色表；早期设计的 `roles` / `role_permissions` /
  `member_roles` 三张表**已在阶段 43 删除**（它们既无读者也无写者，留着只会误导），
  `001_tenants.sql` 留注释说明何时该补回；
- 权限模型 = 三角色（`owner` / `admin` / `member`）+ **行级作者规则**，全部由
  `app/web/permission.go` 从 `tenant_members.role` + 资产的 `created_by` 推导：
  认证走 JWT（`POST /auth/login`，bcrypt），路由级门禁走 `RequireRoutePermission`，
  资源级（按 id）越权统一返回 404；
- 成员身份只来自平台登录（member 全局 `user_id` 唯一，每个 member 只归属一个租户）；
  IM 用户身份不自动映射为 member。

## 6. 结论

- A1 字段语义完整落地（治理热数据内联 Tenant，业务配置是独立管理域）；
- A6 五域均可逐租户选择后端（session/memory 走 `backendTable`，vector/artifact/audit 走包装器）；
  Usage/DLQ/Outbox 刻意不按租户路由，理由见上表；
- RBAC 与登录体系已落地（不再是"2 期预留"）。
