## 1. 一页速览

### 1.1 一句话定位

把 **tRPC-Agent-Go** 的 Agent 编排能力（Runner / Session / Memory / Tool / Artifact / Knowledge / Plugin）
包装成**多租户、无状态可水平扩展、IM 可触达、数据后端可替换、全程可观测可审计**的生产级平台：
单一 Go 二进制 + `-role` 角色开关承载 Gateway / Worker / Admin 三种节点形态，配 Vue3 管理前端与
Docker Compose 全栈编排。

### 1.3 6 个「题目难点」的一句话答案（题目难点原文见 `README.md:76-83`）

| # | README 难点原文要点 | 一句话答案 | 展开节 |
| --- | --- | --- | --- |
| 1 | 多租户隔离不是只加一个 `tenant_id` 字段，还涉及配置、权限、密钥、数据、日志、工具和成本隔离 | `tenant_id` 是**四重物理边界**：SQL 列过滤、Redis key 前缀、框架 `AppName`（=tenant）、对象存储路径前缀；叠加三角色 RBAC + 行级作者规则 + 路由级门禁；密钥 AES-256-GCM 加密且日志正则脱敏；成本按 `usage_records` 五维度逐租户计量 | §5、§6 |
| 2 | Worker 要无状态，但 Agent 依赖 Session/Memory/Summary/工具上下文 | **所有状态外置**：Session/Memory 走 `storage.Router` 选出的共享后端（MySQL/Redis，同一实例跨节点共享），会话串行由 Redis Lua 会话锁保证，因此**不需要 sticky session**；Worker 只持有进程内的连接池与 Consumer 名称 | §3.3、§7 |
| 3 | IM 存在乱序、重复投递、响应超时、长度限制和身份映射问题 | 四层去重（adapter 内存 seen → `msg.ID=channel:platformMsgID` → Redis 两阶段幂等租约 → MySQL `idempotency_keys` 唯一键）+ 事件级幂等（`RequestID` + `resumeRecordedTurn`）；600ms 级审批之外的异步回复全部走 Outbox；出站按平台上限 rune 安全截断；`session_id` 内嵌 tenant+channel+chatType | §4、§9 |
| 4 | 不同后端一致性能力不同，不能用同一种同步策略 | 按域分工：Session/Memory 逐租户可换（Redis 低延迟 / MySQL 权威）；审计与用量强制 MySQL（跨租户汇总、合规）；向量 Milvus（Bounded 一致性，写后短暂不可见）；制品 MinIO（S3 语义、版本不可变、对象键内编码 revision）；总线与锁强依赖 Redis 原语 | §8、§7.6 |
| 5 | 执行链路含模型/工具/MCP/知识库/沙箱，监控审计必须跨组件串联 | 一条 `trace_id` 从 `im.callback` 贯穿到 `im.reply`：TraceID 存在 `bus.Message.TraceID`，Worker 用 `metrics.TraceContextFromID` 重建父 span，Session/Memory 有独立子 span；审计 11 字段 + 用量 5 维度，全部带 `trace_id`/`tenant_id` | §10 |
| 6 | 必须考虑灰度、回滚、租户级限流、成本控制和合规审计 | 灰度按**会话 id 稳定分桶**（`GrayBucket`，避免同一会话跨版本）；Agent 版本不可变 + 原子回滚；租户配置版本快照 + 回滚 API；IM 入站 Redis 固定窗口限流；租户 token 预算熔断；密钥加密 + 日志脱敏 | §5.6、§10 |

### 3.1 分层（`domain ← infra ← app`，依赖单向）

```

   │    ├─ storage         Router / sessions / memories / backends / artifact_minio / trace_* / <域>store
   │    ├─ bus             Redis Streams 总线 + outbox + DLQ + 跨节点状态（锁/幂等/路由/审批）
```

**为什么这样分（答辩可直接讲）**：

1. `domain` 零 IO 让领域规则可用纯单测覆盖（`domain/agent/gray_test.go` 等），也避免「MySQL 实现漂移成
   唯一实现」。MySQL 实现集中在 `infra/storage/<域>store/` 子包（`agentstore`/`llmstore`/…），
   领域包只导出 `Store` 接口 + 内存默认实现。
2. `infra` 拥有所有外部依赖；`app` 只做编排。因此「换一个 Session 后端」只动 `infra/storage/backends.go`
   一行，`app/worker` 一行不改。
3. `README.md:110` 明确写了这条依赖方向；`docs/存储与数据访问设计.md §1` 划清了「管理域（元数据，
   随 db 是否为 MySQL）」与「存储域（经 Router 路由）」的边界。

### 3.4 部署形态与 K8s 决策

- 阶段 17 grill 决策：**不实现 K8s Pod 执行后端**。用户确认生产形态是 Docker Compose/单机，
  平台自实现 `workspace.DockerExecutor`（docker CLI，容器级隔离）已覆盖。
- 阶段 25 决策：**删除 `deployments/k8s/` 全部清单**（单机 Compose 已覆盖，双份清单属 YAGNI）。
  未来上 K8s 集群时再补；届时 `codeexecutor.CodeExecutor` 窄接口天然支持 Pod 后端替换。
- 因此「最小可运行部署」= `COMPOSE_PROFILES= docker compose up -d`（4 服务）；
  「生产推荐」= `COMPOSE_PROFILES=full`（11 服务）。

### 3.5 节点水平扩展的物理约束（答辩加分点）

- 单节点并发回合受 `consumeWorkers`（默认 16）限制 —— 扩容 = **加节点**，不是调大这个值（调大只是
  提高单节点并发，后端延迟会先恶化）。
- **gateway 角色假定单节点**：`cursor:outbound` 是**全局一个 key**（`bus.go:83-91` 注释），
  两个 gateway 会为同一 bot 账号开竞争的长连接。要横向扩 gateway 必须按 binding 分片。
- worker 可以随意加：消费组 + 会话锁保证同一 session 只被一个节点处理。

### 4.2 `trace_id` 如何贯穿

| 跳 | 机制 | 代码 |
| --- | --- | --- |
| 1 | Gateway 开 `im.callback` span，取 `SpanContext().TraceID()` 写入 `bus.Message.TraceID` | `gateway.go:312-331` |
| 2 | Worker 用 `metrics.TraceContextFromID(ctx, m.TraceID)` 构造**远端父 span context** | `worker.go:533`、`metrics.go:174-187` |
| 3 | `agent.run` span 作为子 span；框架的 model/tool span 自动挂在其下 | `worker.go:534` |
| 4 | `session.*` / `memory.*` span 由装饰器开在同一个 ctx 上 → parent 是 `agent.run` | `infra/storage/trace_sessions.go:41`、`trace_memories.go` |
| 5 | 回复消息继承 `TraceID`（`worker.go:645`），Gateway 用它开 `im.reply` | `gateway.go:177-182` |

**注意（答辩易被追问）**：`im.callback` 的 span 表达式是
`tracer.Start(context.Background(), "im.callback", ...)`，随后立即 `cbSpan.End()` ——
它的作用是**生成一个 TraceID 并作为根**，而不是包住整条链路（整条链路是异步跨进程的，
不可能在一个 span 内）。`worker/admin chat` 走的是另一条根：`bus.Message.ID/TraceID` 由
`chat_handler.go:118-120` 直接 `uuid.NewString()` 生成。

### 4.3 去重（幂等）注册在哪一层（答辩常被追问）

| 机制 | 位置 | 为什么在这一层 |
| --- | --- | --- |
| adapter 内存 `Seen` | `base_adapter.go:140-148` | 平台重推同一 `platformMsgID` 时第一道拦截，零网络开销。只在进程内，重启失效 —— 所以后面还有两层 |
| `msg.ID = channel:platformMsgID` | `gateway.go:325` | 把「平台消息身份」变成「总线幂等键」，让后面两层与平台无关 |
| Redis 两阶段幂等 | `bus.go:665-701` | 跨节点、跨重启；**先租约后提交**（见 §7.2） |
| MySQL `idempotency_keys` 唯一键 | `outbox.go:137-144` | 与回复同一事务，是「已处理」的**权威记录**；崩溃恢复的判据 |
| 事件级幂等 | `worker.go:562`、`resumeRecordedTurn` | 崩溃发生在「模型跑完但回复未落库」时，避免重复调用模型、重复追加用户消息 |

> ⚠️ 文档不一致：`docs/架构设计文档.md:188` 与 `docs/数据同步与幂等策略.md §5.1/§5.2` 都写成

## 5. 多租户与权限

### 5.1 三角色定义（`app/web/permission.go:23-80`）

```
owner  ── 平台级：所有租户、所有权限（唯一能建 global 资产、能跨租户读写的角色）
admin  ── 单租户管理者：本租户内的一切（资产、成员、审计、用量、DLQ）
member ── 租户员工：创建/共享自己的资产、给自己的 Agent 授权工具、对话、读自己的用量
```

`rolePermissions` 的**真实取值**（逐条抄自代码，答辩时可直接背）：

| 权限 | owner | admin | member |
| --- | --- | --- | --- |
| `tenant:manage` / `tenant:read` | ✅ / ✅ | ❌ / ✅ | ❌ / ✅ |
| `member:manage` | ✅ | ✅ | ❌ |
| `agent:create` / `agent:read` / `agent:update` / `agent:delete` | ✅ / ✅ / ✅ / ✅ | ✅ / ✅ / ✅ / ❌ | ✅ / ✅ / ✅ / ✅ |
| `tool:manage` | ✅ | ✅ | ✅ |
| `kb:manage` / `skill:manage` / `channel:manage` / `endpoint:manage` | ✅ | ✅ | ✅ |
| `secret:manage` | ✅ | ❌ | ❌ |
| `audit:read` | ✅ | ✅ | ❌ |
| `usage:read` | ✅ | ✅ | ✅ |
| `chat` | ✅ | ✅ | ✅ |
| `dlq:manage` | ✅ | ✅ | ❌ |

**为什么 admin 和 member 的资产权限一模一样**：区别不在「能做什么动作」，而在「作用范围」
（admin = 整个租户；member = 只有自己写的行）。权限位表达不了「自己的行」，所以范围由
**行级规则**（§5.4）决定 —— 这条设计取舍写在 `permission.go:57-61` 的注释里，是答辩的加分点。

### 5.2 路由级门禁（粗粒度，`permission.go:302-393`）

`RequireRoutePermission` 是中间件链的一环：`web.CORS(authMW.Wrap(skipAuth, RequireRoutePermission(mux)))`。

- 先按路径+方法映射到一个权限位（`routePermission`）；映射为空 → 放行（交给 handler 自己判）。
- 需要权限位时：无 claims → **401**；有 claims 但角色没有该权限 → **403**。
- 关键映射：`/tenants`（GET→`tenant:read`，其它→`tenant:manage`）、`/members`→`member:manage`、
  `/secrets`→`secret:manage`、`/audit`→`audit:read`、`/usage`→`usage:read`、`/dlq`→`dlq:manage`、
  `/chat`+`/chat/stream`→`chat`、`/sessions`+`/history`→`agent:read`、`/agents/{id}/publish|rollback`→`agent:update`。
- **中间件顺序**：CORS 最外层（`main.go:362`）。理由写在 `main.go:351-355`：CORS 若在内层，
  401/403 响应不带 CORS 头，浏览器会把它当网络错误 —— 这正是阶段 39 那个「登录后无限刷新」的
  真实根因之一。

### 5.3 资源级（按 id）校验 —— 统一 404 而不是 403

阶段 40 的质量审查发现了一个真实缺口：**只知道 id 就能读到别的租户的资产**（列表已按租户过滤，
但按 id 的路由没有校验归属）。修复方式是一组可组合的原语（`permission.go`）：

| 原语 | 语义 | 代码 |
| --- | --- | --- |
| `ScopeTenant(claims, requested)` | **读**过滤：owner 用请求值（空=全部）；其他角色**一律钉死自己的租户**（即使省略参数也不会放宽） | `permission.go:102-107` |
| `ClaimTenant(claims, requested)` | **写**锚定：只有 owner 能指定别的租户；其他人写进自己的租户，无论请求体说什么 | `permission.go:112-120` |
| `TenantAccessible(claims, resourceTenant)` | 资源租户是否可达；空租户 = 平台共享，人人可达 | `permission.go:126-137` |
| `EndpointAccessible` | 全局端点人人可用；租户端点按租户 | `permission.go:142-150` |
| `WriteCrossTenant(w)` | 越权统一回 **404**（`ErrCrossTenant`） | `permission.go:253-255` |
| `WriteAssetDenied(...)` | 存在但不可读/改的资产也回 404（`ErrAssetDenied`），并**审计这次探测** | `permission.go:246-249` |

**为什么是 404 而不是 403（答辩必答）**：

1. 403 等于承认「这个 id 存在，只是你没权限」—— 对 ID 可猜测/可枚举的资源，这就是一个
   **存在性预言机**，攻击者可以逐个 id 探测别租户有多少 Agent、叫什么名字（配合别的报错差异）。
2. 404 让越权和「不存在」在响应上不可区分，不泄漏任何信息。
3. 这不是「掩盖错误」而是**刻意的安全语义**：真实原因只写进服务端日志与审计行
   （`recordAssetDenied`），运维仍能定位。

### 5.4 作者制 + 显式共享（`permission.go:152-240`）

租户资产（KB / Skill / IM 绑定 / 模型端点 / Agent）都是**作者制**：

| 规则 | 判定 | 代码 |
| --- | --- | --- |
| 可见 | `private` → 只有作者 + 租户管理者；`shared` → 全租户可见 | `CanReadAsset`（`permission.go:211-222`） |
| 可写 | 作者可改/删自己的行；租户管理者可改/删本租户任意行 | `CanManageAsset`（`permission.go:200-202`） |
| 全局资产 | 无租户的平台资产只有 owner 能建/改 | `GlobalAssetWritable`（`permission.go:226-228`） |
| 默认可见性 | 新建默认 `private`（`NormalizeVisibility`，`permission.go:175-180`） | 行级默认安全 |
| **老数据兜底** | `created_by` 为空 ⇒ **视为租户共享**（可见） | `permission.go:215-217` |

最后一条是**刻意的兼容决策**：作者制上线前创建的资产没有作者，如果按 `private` 处理会
「静默地从它所属租户里消失」。选择是「不造假作者、不跑 backfill，把无作者行当作共享」——
回归测试 `app/web/asset_sharing_test.go::TestLegacyAssetsWithoutAuthorStayVisible`。

行级规则的落地点在四个 handler 里成对出现（`readable` / `writable` 双闸），例如
`agent_handler.go`、`kb_handler.go`、`skill_handler.go`、`channel_handler.go`。

### 5.5 资产删除级联（`tenantstore/tenant_mysql.go:108-164`）

删租户是**单事务**，逐表策略明确：

| 表 | 动作 | 原因 |
| --- | --- | --- |
| `tenants` | 软删 `is_deleted=1` | 保留业务键以便审计 |
| `agents` / `model_endpoints(scope='tenant')` / `tools(scope='tenant')` / `skills(scope='tenant')` / `knowledge_bases` | 软删 | 有 `is_deleted` 列 |
| `channel_bindings` | **物理删** | `uk_channel_account(channel,account_id)` 不含 `is_deleted`，软删会导致同账号**无法重绑**（1062）—— 这是阶段 35 修的真实缺陷 |
| `chat_sessions` + `chat_messages` | 物理删 | 无软删列（业务账本） |
| `audit_logs` / `usage_records` / `tenant_config_versions` / outbox / idempotency / secrets | **保留** | 审计与计量必须能回溯（合规） |

### 5.6 灰度发布与租户配置回滚

**Agent 版本（不可变 + 原子回滚）**

- 发布 = 追加 `agent_versions` 行并切换 `agents.current_version`（`domain/agent/agent.go:196`）。
- `Resolve(ctx, id)` 取当前版本；`Rollback(ctx, id, version)` 切回指定版本（`agent.go:201`）。
- 「回滚本身也是一次写」，所以审计上「现在是什么版本」永远可查（`tempdocs/灰度发布与配置回滚策略.md §1`）。

**版本级灰度（按会话稳定分桶）**

```
agents.gray = {"version": N, "percent": P}
ResolveForSession(agentID, sessionID):
    if gray == nil || percent <= 0        → 当前版本
    if GrayBucket(sessionID) >= percent   → 当前版本
    else                                  → 解析第 N 版（失败则告警 + 回退当前版本）
GrayBucket(s) = fnv32a(s) % 100            // 确定性，非随机
```

- 代码：`agent.go:71-91`（`Validate` + `GrayBucket`）、`agent.go:251-280`（`ResolveForSession`）。
- 校验：`Version >= 1`、`1 <= Percent <= 100`、目标必须是**已发布**版本、不能等于当前版本。
- 生效版本写进 `agent.run` span 的 `agent_version` 属性（`worker.go:554`），Jaeger 里能直接对比灰度与基线。
- 测试：`domain/agent/gray_test.go`（分流比例与稳定性 / 清除后全量回当前 / 非法目标 / 版本消失回退）。

**为什么按会话分桶而不是按请求（答辩必答）**：IM 会话是多轮的状态机 —— Session 事件、
Memory、缓存都挂在会话上。同一个会话在第 2 轮换模型，会让上下文由 A 模型的输出喂给 B 模型，
出现「答非所问/风格突变」，而且**灰度实验本身被污染**（你无法区分差异来自版本还是来自会话中途切换）。
按会话哈希分桶后，一个会话全程固定版本，实验单元与会话单元对齐。

**租户配置版本与回滚**

- 每次 `PUT /tenants/{id}` 后把**更新后的完整租户 JSON** 快照进 `tenant_config_versions`
  （版本号单调递增，撞唯一键重试）。
- `GET /tenants/{id}/config-versions`（新→旧），`POST /tenants/{id}/config-rollback {version}`。
- 覆盖范围：`DataBackend`（换后端）、`Quota`（预算）、`AuditPolicy`（脱敏/白名单/强制审批）。
- **回滚立即生效**：治理策略每条消息从租户表重新解析（`resolveTenantPolicy`，无缓存）。

### 6.2 DDL / init 机制，以及那个必须记住的坑

```
deployments/mysql/init/001_tenants.sql … 013_member_single_tenant.sql
        │  仅当 MySQL **数据卷首次创建**时由 mysql 容器入口脚本按文件序号执行
        ▼
docker-entrypoint-initdb.d  ──▶  22 张表
```

**坑（答辩高频）**：`init` 目录只在**首次建卷**时执行。所以：

- 改了 DDL 后 `docker compose down && up` **不会**重建（卷还在）。要 `down -v`，
  或 `./begin.sh reset`（它精确删除 `<project>_mysql-data` 卷再重启）。
- 因此项目约定：**init 目录即全量 schema**，加列直接写进建表语句；对**已有数据卷**需要手写
  ALTER，这些 ALTER 语句作为注释放在对应 SQL 文件头部
  （例如 `008_channels_outbox.sql:13-18` 的 outbox `status`/`last_error`；
  `001_tenants.sql:56-57` 的 `DROP COLUMN model_config`）。
- `backend.healthcheck` 用 `mysqladmin ping` 会在 initdb **之前**就绪，中间有窗口期 →
  `begin.sh` 的 `wait_mysql()` 改为按 `information_schema` 表数 ≥20 判定真正跑完
  （`tempdocs/需求验收证据清单.md D5` 记录了这次修复）。

## 7. 数据同步与幂等

### 7.1 为什么不能只用一个 `SETNX`（答辩必答 ×2）

单个 `SETNX idem:{msg} EX 86400` 的问题在于**它把「正在处理」和「已处理完」写成了同一个状态**：

```
时间线（只有一层 SETNX）
  t0  worker A: SETNX 成功 → 开始跑模型
  t1  worker A 进程崩溃（OCI kill / 节点宕机）
  t2  消息被 XAUTOCLAIM 认领 → 但 idem 键还在（24h）
      → 新的 worker 认为「已处理」，直接 ack
  t3  用户永远收不到回复，消息从系统里消失
```

反过来把 TTL 调短（比如 30s）则会：模型跑了 5 分钟 → 键过期 → 另一个 worker 重跑整个回合并
**再回一次**（重复计费 + 重复回复）。

### 7.2 两阶段幂等（`bus.go:660-701`）

```
Idempotent(msgKey)   → SetNX(idem:{key}, "1", 90s)   ← 只是「租约」：我占着，还没干完
       │
       ├─ 处理中：startTurnHeartbeat 每 30s ExpireIdemLease 续租（幂等租约 TTL 90s）
       │
       ├─ 成功：CommitIdem(msgKey) → Set(idem:{key}, "1", 24h)   ← durable marker
       │
       └─ 失败：ClearIdem(msgKey) → Del(msgKey)                  ← 让重投能重新认领
```

- **租约 TTL 90s、刷新间隔 30s**：`idemLeaseTTL/3`（`bus.go:577-582`）。
- **心跳覆盖整个回合**：`startTurnHeartbeat`（`worker.go:166-225`）一个 ticker 同时续
  **会话锁**和**幂等租约**，间隔取两者较快者（`worker.go:169-172`）。心跳的刷新 context
  刻意用 `context.WithoutCancel(ctx)`（`worker.go:191`）：回合被取消后，**deferred 的释放还没跑**，
  此时让锁/租约提前过期就会发生并发执行。
- **锁丢失是被审计的治理事件**：`RefreshLock` 返回 false → Error 日志 + 审计
  `decision=failed, error_type=lock_lost`（`worker.go:197-205`、`worker.go:451`）。
- **`CommitIdem` 的位置**：在 `outbox.Append` **成功之后**（`worker.go:386-387`）。
  顺序是「回复持久化 → 提交幂等」，这样崩溃在两者之间只会导致一次「重复但被 MySQL 幂等键拦住」的重放。
- **测试**：`infra/bus/integration_test.go::TestBusIdempotencyIsATwoPhaseLease [I]`、
  `worker/idempotency_integration_test.go [I]`。

### 7.3 事件级幂等（`worker.go:460-524`）

第三种去重处理的是**「模型已经跑完，回复没落库」**这一种崩溃窗口：

```
[第 1 次尝试]  r.Run(..., WithRequestID(m.ID))
                   ↓ 框架把该轮的每个事件（含 assistant 文本）打上 RequestID=m.ID
                   ↓ 事件落 session_events
               outbox.Append  ← 崩在这里
[重投]  handle → Idempotent 租约过期后重新认领 → run()
                   ↓ resumeRecordedTurn(m)：从 session 读 RequestID==m.ID 的 assistant 文本
                   ↓ 命中 → 直接返回历史回复（不再调用模型、不再追加用户消息）
```

- 取的是**最后一个非 partial、非 tool-response 的 assistant 文本**（`recordedAssistantText`，`worker.go:504`）。
- **部分流式回答刻意不恢复**（`worker.go:514`）：交付被截断的回答比重跑更糟。
- **测试**：`worker/event_idempotency_test.go` 三例 —— 重放后用户轮次仍为 1、模型调用仍为 1、
  回复取自首次记录；partial 被忽略；别人的 RequestID 不会被误用。

### 7.4 Outbox 状态机（`bus/outbox.go`）

```
                  Append(msg, msgKey)  ← 单事务：INSERT idempotency_keys + INSERT outbox_events
                            │
                            ▼
                     status='pending'
                            │
        dispatcher 每 1s 拉一批（LIMIT 100，ORDER BY retries, created_at）
                            │
            ┌───────────────┴─────────────────┐
            │ outboxDue(age, retries)?        │
            │   retries == 0 → true（恒真）    │
            │   else → age ≥ backoff(retries) │
            └───────────────┬─────────────────┘
                   否 │           │ 是
                 deferred        ▼
                 （下一 tick）  PublishOutbound(stream:outbound)
                                  ├─ 成功 → status='sent'
                                  └─ 失败 → retries+1；retries ≥ 10 → status='dead' + last_error
```

- 退避：`outboxBackoff`（`outbox.go:38-53`）2s → 4s → 8s … 上限 60s；
  `DefaultMaxOutboxRetries = 10`（约第 10 次尝试落在 5 分钟左右，能吸收一次 Redis 重启）。
- **毒药 payload**：JSON 解析失败 → 直接 `park`（永远不会成功的事件不能无限重试）。
- **重试耗尽不是静默丢弃**：`status='dead'` + `last_error` 落库，日志里直接给出
  requeue SQL（`outbox.go:232-235`）：
  `UPDATE outbox_events SET status='pending', retries=0 WHERE event_id='...'`
- **`Run` 不因瞬态错误退出**（`outbox.go:282-311`）：出站派发是唯一的出口，一次 MySQL/Redis 抖动
  退出循环就等于「此进程余生不再投递」。

**时区/时钟一致性（真实缺陷，答辩很可能被问）**

```
现象：outbox 的 pending 事件永不派发，其余链路看起来完全健康。
根因（三个事实叠加）：
  1. created_at 由 MySQL 的 CURRENT_TIMESTAMP 写入 → 服务器会话时区（部署机 UTC+8）
  2. Go 的 mysql driver 把 DATETIME 按 cfg.Loc（默认 UTC）解析
  3. 旧的 due-check 拿这个「被误读的时间戳」和**进程时钟**比较
     → UTC+8 服务器上新写入的行被读成「8 小时后的未来」→ 永远不到期
修复：
  · OpenMySQL 给连接加 time_zone='+00:00'（仅当 DSN 保持驱动默认 UTC loc）
    → 服务器写的时间和 Go 写的时间表示同一个瞬时（此前同一行内两个来源差一个 offset）
  · due-check 改用**数据库自己算的年龄**：TIMESTAMPDIFF(SECOND, created_at, NOW())
    → 一个时钟、一次比较
  · retries == 0 恒为 due → 顺带治愈了修复前写入的历史行
```

证据：`infra/storage/mysql.go:33-72`、`infra/bus/outbox.go:55-78`，
红绿验证见提交 `77f9425` 的说明（「新加了 MySQL 时区用例，对旧 due-check 必然失败：
created_at 14:19:03 在进程时钟里读成 06:19:03」）。

**教训（答辩可以升华）**：时间戳只要跨越两个来源（应用 + 数据库），就必须**统一时钟与时区**，
否则会出现「逻辑正确、数据正确、行为错误」这种最难查的 bug。项目里还有第二处同类风险
（`cmd/migrate` 已改为用 `storage.OpenMySQL` 而不是裸 `sql.Open`，`cmd/migrate/main.go:139-141`）。

### 7.5 DLQ 与游标语义

**入站 DLQ（`infra/bus/dlq.go`）**

| 项 | 值 | 说明 |
| --- | --- | --- |
| 阈值 | `DefaultMaxDeliveries = 5` | 5 次**业务失败**（不是 XAUTOCLAIM 认领次数） |
| 认领窗口 | `XAUTOCLAIM MINIDLE = 30s` | 死消费者的消息 30s 后被认领 |
| 计数键 | `retry:{streamEntryID}` TTL 24h | 与幂等窗口对齐，避免陈旧计数 |
| 计数时机 | 只在 `fn` 返回错误时 `INCR` | `ErrRequeue`（锁争用）**不计入** —— 否则一个会话繁忙就能把健康消息推进 DLQ |
| 搬运动作 | XAdd 到 `stream:inbound:dlq` → sink 落 `dead_letters` → XAck + XDel → Del retry 计数 | **先写 DLQ 再从活流删除**：崩在中间只会重复（重放按信封 id 去重），不会丢失 |
| 成功清理 | `onSucceeded` → Del retry 计数 | 让后续重投从 0 开始 |

**出站游标（`ReadOutbound`，`bus.go:331-371`）**

- 无消费组、无 ack：多个读者可以各自跟随 outbound（gateway 分发 + admin SSE），互不影响。
- `"$"` 语义的坑（**答辩必答**）：

```
XREAD 每次调用都会把 "$" 重新解析成「此刻的流尾」。
聊天页的 SSE 循环大约每秒调一次 ReadOutbound —— 如果每次都传 "$"：
  t=0.0s  传 "$" → 解析为流尾 100-0 → 读到空
  t=0.5s  某条回复以 101-0 写入
  t=1.0s  又传 "$" → 这次解析为 101-0 → 于是 101-0 被**跳过**，浏览器永远看不到
修复：ReadOutbound 内部把 "$" 解析成具体 id 并作为 cursor 返回；
      所有调用方（chat SSE、gateway）**无条件用返回的 cursor 推进**
      （注意：不是「只有读到消息才推进」—— 第一次调用就要把 "$" 换成具体 id）
```

证据：`bus.go:331-347`、`app/web/chat_handler.go:179-184`、`infra/channels/gateway.go:151-155`，
以及 `front/e2e/chat.spec.ts`（真栈 e2e 断言回复在页面上实时出现）。

- `cursor:outbound` 持久化游标（`LoadOutboundCursor`/`SaveOutboundCursor`）让 **gateway 重启后仍
  投递停机期间产生的回复**；`SaveOutboundCursor` 忽略 `""`/`"$"`（不写无意义的尾标记）。

### 7.6 一致性取舍（README「说明不同后端的一致性取舍」）

| 后端 | 一致性模型 | 典型延迟（文档口径） | 成本 | 运维复杂度 | 本平台用它存什么 |
| --- | --- | --- | --- | --- | --- |
| MySQL | 强一致（ACID 事务） | ~10ms | 中 | 中 | 管理域、审计、用量、outbox、DLQ、配置版本、secret |
| Redis | 单线程原子命令（非事务、可丢） | ~1ms | 中 | 低 | 总线 Streams、锁、幂等、路由、审批、限流、session/memory 可选后端 |
| Milvus | Bounded（写后短暂不可见） | ~50ms | 高 | 高（etcd + MinIO 依赖） | 知识库向量（BM25 + embedding） |
| MinIO | S3 语义（对象不可变 + 版本化键） | ~20ms | 低 | 低 | 制品字节（artifact）、知识库原始文档 |
| InMemory | 进程内强一致 | <1ms | 零 | 零 | dev/test；也是 Milvus/MinIO/audit 不可用时的降级实现 |

**平台的策略性选择**（都有代码依据）：

1. **`RecordUsage` 恒走 MySQL**（`router_domains.go:127-132`）：用量要跨租户汇总做预算判断，
   落到租户私有内存后端会让预算失真。
2. **Audit 可逐租户**（`router_domains.go:110-121`，`inmemory` opt-in），但**读侧 admin API
   只在 MySQL 时注册**（`main.go:429-432`）。
3. **Artifact 逐租户**（`router_domains.go:60-69`）：MinIO 未配置时回落内存，且
   `main.go:536-550` 明确「没有 MinIO 就不启用该域」，不会假装成功。
4. **Session/Memory 是唯一同时有 MySQL 与 Redis 两个生产实现的域** → 只有它们支持
   「逐租户换后端」；其余域按「出现第二个实现才纳入 Router」的准则保持单后端。

### 8.5 Router 扩域准则

> **一个域只有在确实存在第二个后端实现时才纳入 `Router` 的逐租户选择。**

真实需求 + 连接池 + 运维手册 + 测试容器，预埋抽象只会放大测试与文档面。当前满足条件的是
session/memory（直连方法）与 vector/artifact/audit（包装 dispatcher）；
`Tenant.DataBackend` 是保留的扩展点。

阶段 44 还删除过一个反例：`storage.DataStores`（4 字段 0 方法的聚合 DTO）—— 它只是
「构造后立即拆包」的中间态，装配点本来就是 `main()`。

### 9.2 两种入站通路（同一套适配器）

```
长连接：平台主动连 ──WSS/WS──▶ Conn.Recv ─┐
回调：  平台被动收 ──HTTPS───▶ WebhookAPI ─┴─▶ Conn.events ──▶ Adapter.Start
        POST /webhooks/im/{binding_id}                │
                                                      ▼
                                       Inbound() ─▶ Gateway.pumpInbound ─▶ bus
```

**「同一通道二选一」是怎么保证的**（`infra/channels/manager.go` + `webhook.go`）：

| 机制 | 代码 | 作用 |
| --- | --- | --- |
| `WebhookChannelServed(channel)` | `webhook.go:130-135` | Manager 的 reconcile 跳过这些通道 → **不为它开长连接** |
| 惰性构建 | `Manager.webhookAdapter`（`webhook.go:196-247`） | 首次收到回调时才 build + attach，注册进 `m.conns` |
| 注册进 `m.conns` | 同上 | 出站路由（`adapterByBinding`）与优雅关停（`Close`）对两种模式完全一致 |
| 重复保护 | `HandleWebhook` 检查 `wh.Channels[b.Channel]`（`webhook.go:141-147`） | 长连接模式的绑定收到 HTTP 回调 → 直接拒绝，避免双投 |
| 构建串行化 | `m.whMu`（`webhook.go:222-228`） | 两个并发首回调不会建出两个适配器 |

**安全模型（fail-closed，每一条都要能讲）**：

| 检查 | 失败结果 | 代码 |
| --- | --- | --- |
| 端点是否启用 | 未启用 → `ErrWebhookUnsupported` → 501 | `webhook.go:118-121` |
| 绑定是否存在 | 不存在 → `ErrBindingNotFound` → **404** | `webhook.go:126-129` |
| 通道是否被 HTTP 服务 | 否 → 501 | `webhook.go:131-146` |
| 验证密钥引用是否配置 | 空 → `ErrWebhookUnauthorized` → **401** | `webhook.go:176-181` |
| 密钥能否解析到 | 解析失败/空 → 401 | `webhook.go:182-191` |
| 签名是否匹配 | 不匹配 → 401（**日志不说明原因**，避免签名预言机） | `feishu/webhook.go` `WebhookVerifier`、`app/web/webhook.go:86-90` |
| 适配器缓冲是否满 | 满 → `ErrWebhookBusy` → **503 + Retry-After** | `webhook.go:161-165` |
| body 是否过大 | > 1 MiB → 413 | `app/web/webhook.go:32,72-76` |

**启动期校验**：`im.webhook.channels` 里出现平台不支持的通道（企业微信）→ `exit 2`
（`main.go:617-623` + `webhookSelection`），而不是挂一个永远收不到请求的端点。

| --- | --- |

### 9.3 入站附件链路（阶段 45 补齐）

```
IM 附件消息
  │
  ├─[1] Adapter.Run → BaseAdapter.fetchMedia（base_adapter.go:95-130）
  │       · conn.DownloadMedia(ctx, att)：wecom 下载+AES 解密 / feishu message-resource
  │       · 上限 maxMediaBytes = 8 MiB、mediaFetchTimeout = 15s
  │       · 失败/超限/空 → 只写 att.FetchError（**不失败消息**）
  │
  ├─[2] Gateway.pumpInbound → buildUserContent（channels/media.go:35-76）
  │       · 图片 → msg.AddImageData(data, "", format)
  │            format 由**字节嗅探**决定（http.DetectContentType → png/jpeg/gif/webp）；
  │            嗅不出就退化为 AddFileData —— 否则会发出 `data:image/;base64` 这种坏 URL
  │       · 文件/语音 → msg.AddFileData(name, data, mime)
  │       · 文本追加「[附件清单]」，逐条写明名称/字节数/读取失败原因
  │       · bus.Message.Media = []MediaRef（**只有清单，没有字节**）
  │
  ├─[3] worker.handle → reportUnreadableMedia（worker/media.go:41-99）
  │       · 有失败附件 → audit(failed, error_type=attachment_unreadable)
  │       · + outbox 幂等回执（key = m.ID + ":media"）
  │
  └─[4] runner → session/externalization（worker.go:737-742）
          · AppendEvent 之前把内联字节存进 artifact 服务（MinIO）
          · 事件里只留 model.ContentRef{ArtifactRef: "artifact://name@ver",
                                       SizeBytes, SHA256, MimeType, ...}
          · 读会话时从制品回填（含 sha256 + 大小校验）
```

**为什么不把平台 URL 直接给模型**：企业微信的下载 URL 带 `AesKey` 且短时有效，飞书只给
`file_key` —— 外部模型服务**都拿不到**。所以统一「我们取回字节 + 内联给模型 + 归档到对象存储」，
模型看到的是内容，而不是一个它永远打不开的链接。

**为什么必须 externalization**：不做的话，用户每发一张图，base64 就内联进 `session_events` 的 JSON
—— 热表被图片撑大，且会话读取要拖着所有历史图片。externalization 是**框架自带机制**
（`session/externalization`），平台只是把它接上，没有自己重写一遍。

**证据**：`channels/media_test.go`（6 例：纯文本不变 / 图片内联+清单 / 未知编码退化文件 / 失败清单 /
纯图片不空 prompt / 生成文件名）、`worker/media_test.go`
（`TestExternalizeSessionContentArchivesInlineAttachments` 做真实归档 + 引用 + 回填断言）。

### 9.4 卡片审批链路（阶段 45）

```
worker.run → BeforeTool 命中需审工具
   │
   ├─ approvalNotice(m, tool, args)（approval.go:228-251）
   │     · CardActionCapable(channel) 为真（仅 feishu）→ KindCard
   │         Segments = [title, markdown, actions{批准/拒绝}]
   │         action.Value = {session_id, decision}
   │     · 否则 → 纯文本（正文仍写明「回复批准/拒绝」，按钮不可用时的兜底）
   │
   ├─ outbox.Append(notice, m.ID+":approval")   ← 幂等：重投不会重复通知
   ├─ SetPendingApproval(tenant, session, payload, ~5m10s)
   └─ 阻塞轮询 ApprovalResult（500ms 一次，超时 5 分钟自动拒绝）
                │
用户点按钮     ▼
   ├─ 长连接：OnP2CardActionTrigger → toCardActionEnvelope → conn.events
   └─ HTTP 回调：card.action.trigger → NormalizeWebhookCallback → cardActionEnvelope
                │
                └─ 适配器 decode 出「inbound 文本 = 批准/拒绝」
                            │
                       走与手工输入完全相同的路径：
                       adapter 去重 → msg.ID → 总线 → worker.handle
                            │
                       tryResolveApproval（**在拿会话锁之前**）
                            ├─ ResolveApproval(tenant, session, decision)
                            ├─ outbox 确认消息
                            └─ audit(DecisionApprove/Deny)
```

**关键点**：

- `tryResolveApproval` 必须在 `LockSession` **之前**（`worker.go:271-276` 有明确注释）：
  正在等待审批的那一轮**持有会话锁**，如果审批回复也要抢锁就会**死锁**。
- 为什么 `ConsumeInbound` 用有界并发池（16）而不是单 goroutine 顺序消费：同一个原因 ——
  阻塞的审批轮次不能挡住后续消息的投递。
- `bus.encode/decode` 必须序列化 `Kind`/`Segments`：否则卡片经 outbox 落地后**静默降级为纯文本**
  （按钮永远不出现，且无任何报错）。这是阶段 45 修的真实缺陷，回归测试
  `infra/bus/bus_test.go::TestMessageRoundTripPreservesCardAndMedia`。

### 9.7 绑定与凭据（binding 驱动，无 config IM 段）

```
前端通道页（ChannelListView.vue）
  ├─ 用户填 channel / tenant / agent / account_id / Secret /（飞书）Verification Token
  ├─ putSecret(`${tenantId}/${channel}:${account}:secret`, secret)   ← 加密入库
  ├─ putSecret(`${tenantId}/${channel}:${account}:verify`, token)     ← 飞书才写
  └─ POST /channels {binding…, credential_ref, verification_token_ref}
             │
             ▼
      ChannelAPI.SetManager → Manager.Reload（保存即连接，无需改 config / 重启）
             │
             ├─ 逐 binding：creds.Get(credential_ref) → buildAdapter → go supervise + gw.Attach
             └─ 删除的 binding：stop + 从 conns 移除
```

- **为什么 secret key 里带 tenant**：`{tenant}/{channel}:{account}:secret`。早期只用
  `{channel}:{account}` —— 两个租户绑同一个 account 时后写的会**覆盖**前者的密钥
  （阶段 41 修）。
- `ChannelBinding` 有 `UNIQUE(channel, account_id)`，因此账号全局唯一；这也解释了
  租户级删除必须**物理删** `channel_bindings`（§5.5）。
- 未绑定/无凭据的 binding 在 Reload 时 **Warn 跳过**，不会拉起一个连不上的适配器
  （`manager.go:112-115`）。

## 11. 故障恢复与运维

### 11.1 降级语义（**注意两者的不对称，这是有意设计**）

| 依赖 | 节点启动时 | 运行期 | /healthz |
| --- | --- | --- | --- |
| MySQL | 轮询 60s（`deps.go:47-65`）；仍失败 → **degraded**：无持久化/无审计/无 worker | **不自动重连**（进程内没有重连循环） | **503**（`health.SetDegraded`，`main.go:138`） |
| Redis | 轮询 60s（`deps.go:70-85`）；仍失败 → 数据面仍启动，命令自愈 | 每条命令独立重试；总线/派发/投递遇瞬态错误**不退出**；适配器断线退避重连 | **200**（只有告警日志） |

**为什么不对称（答辩必答）**：MySQL 的降级是「进程内不可恢复」的（连接对象在启动时就决定了
是否走内存实现），所以把 503 语义写准确；Redis 的降级是「命令级自愈」的，如果也粘 503，
一个 1 秒的 Redis 抖动就会让编排系统把健康节点摘掉 —— **误导比不报更糟**。
这条理由写在 `docs/风险清单.md R4` 与 `tempdocs/需求验收证据清单.md D1`。

### 11.2 各故障场景的处理矩阵

| 场景 | 行为 | 代码 |
| --- | --- | --- |
| Worker 节点宕机 | 消息保持 pending → `XAUTOCLAIM MINIDLE=30s` 被其它节点认领 | `bus.go:510-538` |
| 会话锁持有者崩溃 | 锁 30s 后自然过期（靠租约 + 心跳，不靠长 TTL） | `bus.go:544-548` |
| 模型挂起 | 单次 HTTP 120s（`domain/llm` `DefaultHTTPTimeout`）；整轮 300s（`worker.go:52`） | `worker.go:615` |
| 模型超时 | 审计 `error_type=timeout` + 消息重投 | `worker.go:451-454` |
| 工具运行时错误 | 非零退出归入 `Output` 回给模型自修复（不是工具 error） | `workspace/docker_exec.go` |
| 工具传输错误 | 返回 Runner → `run_error` → 审计 + 重投 | `worker.go:369` |
| outbox 发布失败 | 退避重试；10 次 → `dead` + `last_error` + 日志给出 requeue SQL | `outbox.go:229-256` |
| 派发循环遇到 DB 抖动 | 记 Warn（同一错误只记一次）并继续，不退出 | `outbox.go:289-311` |
| 消息反复失败 | 5 次 → DLQ（Redis 流 + `dead_letters` 表） | `dlq.go` |
| 记忆后端不可用 | 该轮降级为「无长期记忆」+ Warn，会话上下文不受影响 | `worker.go:672-676` |
| Session 后端不可用 | 该轮以无状态方式跑（不注入 session service）+ Warn | `worker.go:714-717` |
| MinIO 不可用 | 启动时 Error，制品域禁用（**不假装成功**） | `main.go:544-549` |
| Milvus 未配置 | Warn，KB 向量回落内存 | `main.go:167-169` |
| 卡在一个回合超过锁 TTL | `lock_lost` 审计 + Error 日志（并发执行可能） | `worker.go:198-205` |

### 11.3 优雅关停（`main.go:118-122, 363-381`）

```
SIGINT / SIGTERM
   │
   ├─ signal.NotifyContext 取消 runCtx
   │     ├─ worker.ConsumeInbound：break loop → close(jobs) → wg.Wait()（等在途回合结束）
   │     ├─ outbox.Run：ctx.Done() → return
   │     ├─ gateway.Run：ctx.Done() → return
   │     └─ imMgr.Close()（独立 goroutine 监听 runCtx.Done）→ 关闭全部 IM 长连接
   │
   ├─ http.Server.Shutdown(5s)  → 排空在途请求（SSE 连接随 ctx 结束）
   └─ defer：auditRec.Close()（flush 缓冲）→ telemetry cleanup
```

- 心跳 goroutine 用 `context.WithoutCancel` 拿刷新 ctx，保证**释放顺序**正确：
  先停心跳（`stopHeartbeat()`），再 `UnlockSession`（`worker.go:359-362`）。
- Runner 事件通道排空：`finalTextWithUsage` 一直 `range` 到 channel 关闭（`worker.go:830`），
  不会因为提前 return 而泄漏 goroutine。

> 每题给「简明答案」+「追问点」。标 ⭐ 的是任务里点名的必答项。

### 14.1 「为什么这样设计」

**Q1 ⭐ 为什么完全不接框架的 `server/*`（openai/agui/a2a/trpcagent）？**

- 简明答案：它们把 Runner **直接**暴露给调用方，因此**绕过平台的租户上下文、RBAC、配额、
  审批、审计**五道治理。要安全暴露就必须在外层重建一整套鉴权+配额层，等于把治理链复制一遍；
  而平台已有的 `/chat`（JWT + 租户 + 治理 + 审计）与 IM 通道已经覆盖了「外部输入 → Agent」。
  AG-UI 与平台自有的 REST+SSE 契约重复，a2a/trpcagent 缺少产品前提（跨平台 Agent 互调）。
- 追问点：**「那未来要提供 OpenAI 兼容接口怎么办？」** → 新增一个**薄适配层**，先过平台的
  鉴权/配额/审批，再交给 Runner；**不要**把框架的 server 直接挂上去。这个结论写在
  `docs/架构设计文档.md §10.5`。
- 追问点：**「这算不算少实现了一项？」** → 不算：README 要求的是「说明组件如何协作，
  **可对照** server/* 的职责划分」，是「对照」而不是「必须接线」。

**Q2 ⭐ 为什么不需要 sticky session？**

- 简明答案：Worker 进程里**没有任何会话状态**。Session/Memory 由 `storage.Router` 解析到
  **共享后端**（同一 backend id 一个实例，跨节点共享），隔离靠每次调用带的 `tenant_id`
  （框架 `AppName`）。同一会话的串行由 Redis 锁保证，所以任何节点都能处理任何会话。
- 追问点：**「那 L1/L2 缓存呢？」** → 平台在存储层没有进程内会话缓存（`Router` 只缓存
  **后端实例**，不缓存会话数据），所以不存在缓存不一致。
- 追问点：**「tool 上下文呢？」** → 工具是每轮按 `RuntimeProfile` 现场构建的
  （`BuildFromProfile` + `runner.NewRunner`），不跨轮持有。

**Q3 ⭐ 为什么用两阶段幂等而不是简单 `SETNX EX 86400`？**

- 简明答案：单一 SETNX 把「处理中」和「已处理」写成同一个状态 → 崩溃后消息永久丢失
  （见 §7.1 的时序）。两阶段把两者拆开：**租约**（90s，心跳续）+ **提交**（24h），
  崩溃时租约自然到期 → 重投重跑；成功时提交 → 永不重跑。
- 追问点：**「提交之后又崩溃在 outbox 写入之前呢？」** → 提交发生在
  `outbox.Append` **成功之后**（`worker.go:386`），顺序不会反。
- 追问点：**「那这不还是可能重复回复？」** → 可能，但被**第三层**兜住：
  MySQL `idempotency_keys` 唯一键 + **事件级幂等**（`resumeRecordedTurn` 从 session 取回已产出的回复）。

**Q4 ⭐ 为什么 outbox 不能直接发 Redis（为什么要一次落库 + 派发）？**

- 简明答案：**「先发 Redis 再落库」会在崩溃时丢回复**。outbox 的价值是让「回复存在」
  成为**单一事务里的持久事实**：`idempotency_keys`（这个入站消息处理过）+ `outbox_events`
  （这条回复要发）一起提交。之后崩溃，事件还在 `pending`，下一次派发继续投 —— 至少一次。
  另外 Redis Streams 没有「无限保留 + 事务」保证，不能当可靠性权威。
- 追问点：**「那为什么不直接在事务里 XADD？」** → 跨系统事务不存在（MySQL 事务提交了但 XADD
  失败，两边不一致）；outbox 把「投递」变成可重试的**幂等**动作（同一个 `event_id`）。

**Q5 ⭐ 为什么游标 `$` 不能反复传？**

- 简明答案：`XREAD` **每次调用**都把 `$` 重新解析成「此刻的流尾」。SSE 循环约每秒调一次，
  两次调用之间写入的消息会被**静默跳过**（§7.5 有时序图）。修法是
  `ReadOutbound` 内部把 `$` 解析成具体 id 并返回，调用方**无条件**用返回的 cursor 推进
  （注意不是「有消息才推进」——第一次调用就得把 `$` 换掉）。
- 追问点：**「如果我在 catch-up 时传 0 呢？」** → `0` 语义是「从头读」，用于补历史；
  正常跟随用「上次返回的 id」。

**Q6 ⭐ 时区/时钟一致性为什么危险？**

- 简明答案：因为它产生的是**「逻辑正确、数据正确、行为错误」**的 bug。真实事故：
  `created_at` 由 MySQL 会话时区（UTC+8）写入、Go driver 按 UTC 解析、due-check 又拿进程时钟比较
  → 新事件被读成「8 小时后的未来」→ outbox 永不派发，而其余链路全部健康（§7.4）。
- 追问点：**「怎么系统性防住？」** → 三条规矩：①**一个瞬时只用一个时钟**（让数据库算 age，
  或统一 `time_zone='+00:00'`）；②跨系统时间戳必须显式声明时区；③写一个「红-绿」回归测试，
  在旧实现上必然失败（`77f9425` 做到了）。
- 追问点：**「还有别处有同样风险吗？」** → 有：`cmd/migrate` 曾用裸 `sql.Open` 读 MySQL
  时间戳，已改成 `storage.OpenMySQL`。

**Q7 ⭐ 为什么资源级越权返回 404 而不是 403？**

- 简明答案：403 会**确认资源存在**，构成存在性预言机；404 让「越权」与「不存在」不可区分。
  真实原因只进服务端日志与审计（`recordAssetDenied`）。见 §5.3。
- 追问点：**「合法用户误配也回 404，会不会难排查？」** → 审计行里记了 `kind`/`id`/`actor`/原因，
  排查走审计与日志，不走响应体。

**Q8 ⭐ 为什么灰度按会话分桶而不是按请求？**

- 简明答案：会话是多轮状态机；按请求切会让 ①同一会话跨版本导致上下文错位；
  ②实验被污染（无法判断差异来自版本还是会话中途切换）。按会话 fnv32 哈希分桶后，
  会话是实验单元也是稳定单元。
- 追问点：**「那怎么保证灰度样本量足够？」** → 会话数量通常远大于请求数中「独立」的部分，
  对 IM 场景足够；不足时可提高 percent 或延长观察窗。

**Q9 ⭐ 为什么不建 summary 表？**

- 简明答案：**摘要不是平台资产**。框架 `session/mysql` 自己维护 `session_summaries`
  并按 `(app_name,user_id,session_id,filter_key)` upsert；平台再建一张同名表就是双份真相，
  而且没有写 API（框架不导出 summary 写入）→ 表会永远是空的。所以
  `tenants.data_backend` 里**没有 `summary` 键**，它随 session 后端。
- 追问点：**「那验收标准 2 要求数据模型能表达 summary 关系怎么办？」** →
  `docs/数据模型设计.md §1.4` 把框架表显式列出并标注隔离键与关键列 —— 关系表达完整。

**Q10 ⭐ 为什么 `agents.model_config` 被删？**

- 简明答案：它**没有读者也没有写者**。模型配置的真实载体是
  `Agent 版本 → RuntimeProfile.endpoint_id → model_endpoints(provider/base_url/model_name/api_key_ref)`，
  改模型 = 改端点，不必改 Agent（也不需要 republish）。保留一个没人读的列就是第二份真相。
- 追问点：**「那需求说租户模型含『模型配置』怎么办？」** → 是**映射关系**而非缺失：
  配置实体是 `model_endpoints`（带 `tenant_id`），租户的模型配置 = 该租户的端点集合。
  写在 `docs/架构设计文档.md §10.6`。
- 追问点：**「删列怎么迁移已有库？」** → `001_tenants.sql:56-57` 给了
  `ALTER TABLE tenants DROP COLUMN model_config;`。

**Q11 ⭐ 装饰器为什么会「吞掉」框架的可选接口能力？**

- 简明答案：Go 的**能力由方法集决定**。框架用类型断言探测能力
  （`inv.SessionService.(session.WindowService)`）。一个只实现 `session.Service` 的装饰器
  方法集里没有 `GetEventWindow` → 断言失败 → 框架走「没有窗口能力」的回退分支 →
  **后端本来有的能力被静默丢弃**。更糟的是 `externalization.Wrap` 会**从被包装者重建**
  自己的可选接口组合，所以能力是在整条链上丢的。
- 追问点：**「怎么修得既保能力又不撒谎？」** → 两种包装类型 + 运行期探测：
  后端三者齐备 → 返回 `tracingSessionsFull`（嵌入 `sessionCaps` 转发三个方法）；
  否则返回基础版（**不宣称**能力）+ Warn。见 §10.4。
- 追问点：**「框架那个接口是未导出的，你怎么转发？」** → Go 接口满足是**结构化**的：
  定义同名同签名的方法，框架自己的断言就会成功（`trackEventReader`）。

**Q12 为什么单一二进制 + 角色标志，而不是拆多个服务？**

- 简明答案：三者共享绝大部分初始化（配置、MySQL、Redis、Router、secret、audit），
  拆成三个镜像会**复制组装代码**并让版本漂移；角色标志让「同一份构建产物」按部署拓扑
  开不同能力，也让「角色语义」成为可测试的纯函数（`planFor` + `role_test.go`）。
- 追问点：**「安全边界呢？」** → 角色同时决定**注册哪些 API** 和**运行哪些循环**，
  一个只连 IM 的 gateway 节点不暴露任何管理面（阶段 44 修过语义倒挂）。

**Q13 为什么会话锁 TTL 只有 30s，而一回合可能跑 300s？**

- 简明答案：**长 TTL 会让崩溃的节点阻塞会话数分钟**。选择短 TTL + **心跳续租**：
  liveness 由持有者证明（还在工作就续），而不是靠一个猜出来的长 TTL。
  心跳间隔取「锁 TTL/3」与「幂等租约/3」的较小者。
- 追问点：**「锁丢了怎么办？」** → 审计 `lock_lost` + Error 日志（并发执行是可能的，
  必须让人看见，而不是在数据里事后发现）。

**Q14 为什么限流默认是关的？**

- 简明答案：限流阈值强烈依赖业务（`rate_limit.per_minute`），默认开一个拍脑袋的值
  会**误伤正常业务**（且 IM 平台本身没有硬性频率限制）。所以做成「默认关 + 显式开启 +
  失败 fail-open」：限流器后端挂掉时选择可用性，同时 Warn。
- 追问点：**「fail-open 不是安全风险吗？」** → 是取舍：限流是**防滥用**而非**认证**，
  真正的访问控制在 JWT/RBAC/IM 白名单（这些是 fail-closed）。

**Q15 为什么把 `usage_records` 恒定为 MySQL？**

- 简明答案：用量要**跨租户汇总**来判预算，也要给运营出报表。落到租户私有的内存后端会让
  预算视图失真（每个租户只看到自己那份碎片）。审计可以逐租户（合规口径不同），
  但记账必须集中。
- 追问点：**「那内存模式下呢？」** → 无 MySQL 时回落 `MemRecorder`（dev/test 语义）。

### 14.2 「如果让你改会怎么改」

**Q16 现在让你支持第三个 IM 通道（例如 Telegram），要动哪些地方？**

- 需要：①新建 `infra/channels/telegram/`（实现 `Conn` + 复用 `BaseAdapter` 的 `Run(decode)`）；
  ②`buildAdapter` 加一个 case；③若是 webhook 模式，加 `Verifier` 并注册进 `webhookChannels()`；
  ④`channels.go` 加 `ChannelTelegram` 常量 + `maxTextLen` 加上限；
  ⑤前端通道页的下拉白名单。
- **不需要**动：总线、Worker、Outbox、DLQ、Session/Memory、审计、指标、前端对话页。
  这正是 Adapter 契约的价值。

**Q17 现在让你支持 PostgreSQL 作为 Session 后端？**

- 照 §8.3 六步：`backendTable` 加一行（**session + memory 都要**，否则 `backends_test.go` 失败）
  + 配置字段 + 前端可选项 + 一个集成测试。预期约 15 行。

**Q18 gateway 要横向扩展，怎么改？**

- 现状障碍：`cursor:outbound` 是全局单 key，且同一 bot 两个节点会开竞争长连接。
- 改法：①`cursor:outbound:{binding_id}` 分片；②manager 按 binding 做**租约**（Redis SETNX）
  保证一个 binding 只被一个 gateway 持有；③`imroute:` 已带 session，天然可跨节点。
- 代价：把「一个 bot 的可用性」从「任一节点活着」收紧为「租约持有者活着」，
  所以租约 TTL 与续期策略要设计好。

**Q19 出站媒体（Agent 发图）怎么补？**

- ①`OutboundMessage.Segments` 已经能表达 `{Type:"image", URL}`；
  ②适配器实现上传：飞书 `im/v1/images`（拿 image_key）+ `Create`；企微素材上传；
  ③worker 侧需要一个「把 artifact 转成可发送 URL」的通道（现在 artifact 在 MinIO，
  需要签名 URL 或先下载再上传）；
  ④`base_adapter.Send` 加一个按 segment 类型分发的分支。

**Q20 迁移 CLI 的 memory+mysql 不一致怎么修？**

- 删掉 `cmd/migrate/main.go:107-110` 的特判，把 `MySQLDSN` 传进 `MemoryConfig`。
  `storage.NewMemories` 本来就支持 mysql（`backends.go` 的 mysql memory 构造器已存在）。
  同时更新手册 §1 的后端表。

**Q21 想让「脱敏规则」可按租户配置，怎么做？**

- `AuditPolicy` 加 `redact_patterns []string`（租户级正则）；
  `redactionPlugin(policy)` 里若配置非空则用它构建 `RedactionFilter`，否则用内置三类。
  风险：错误的正则（过宽/过窄）会漏脱敏或误脱敏 → 需要在保存时做**编译校验**并在页面提示。

**Q22 现在要接 K8s，需要改什么？**

- 部署层：按角色拆 Deployment（gateway/worker/admin），镜像同一份 + `-role` 参数。
- 代码层：①`workspace.DockerExecutor` 在 Pod 内没有 docker socket → 需要 Pod 执行后端
  （实现 `CodeExecutor` 窄接口即可）；②gateway 需要 leader election（见 Q18）；
  ③`/healthz` 已具备（503 degraded），可直接做 readiness。
- 不需要改：Worker 无状态、锁/幂等/路由都在 Redis、审计在 MySQL。

**Q23 如果模型供应商要求「每次调用带租户维度密钥」，怎么改？**

- 现状已是两层引用：端点 `APIKeyRef` → secret store。要按租户隔离密钥，
  只需在 `normalizeCredentials` 里把 key 命名从 `endpoint:{id}` 改成
  `{tenant}/endpoint:{id}`（与 IM 凭据的做法一致），并在 `KeySource` 实现里透传 tenant。
  注意 `Resolve` 的调用链要能拿到 tenant（现在 `llm.Registry` 是按端点解析的，
  最简单是在端点实体上带 tenant 前缀）。

### 14.3 「出了问题怎么定位」

**Q24 用户说「发了消息没回复」，你怎么查？**

按链路顺序二分（每步都有日志或状态可查）：

1. **有没有 `started adapter`** → 没有：binding 没建/凭据没入库/secret 未解析
   （`channels: binding has no credential, skipping`）。
2. **有没有 `channels: publish inbound` 错误** → 有：Redis 有问题。
3. **`XLEN stream:inbound` / `XPENDING`** → 消息在流里但没被消费：worker 没起或消费组异常。
4. **`idem:{channel}:{msgid}` 是否存在** → 存在且是 24h TTL：处理过（看 outbox）。
5. **`outbox_events` 里 status** → `pending` 且 `retries>0`：投递在重试，
   看日志里的 `bus: outbox publish failed`；`dead`：看 `last_error` 与 requeue SQL。
6. **`XLEN stream:outbound`** → 有但用户没收到：gateway 侧问题（
   `channels: no route for session` / `adapter send failed`）。
7. **`idempotency_keys` 里有没有该 msg_key** → 有：处理过并落库了（否则看 session 事件）。

**Q25 聊天页「消息发出去了但回复不显示」，怎么查？**

这是**真实修过的三连 bug**（提交 `77f9425`），排查顺序：

1. **SSE 是否 401** → `curl -N -H "Authorization: Bearer $TOKEN" '.../chat/stream?session_id=s1&cursor=$'`。
   客户端用 `EventSource` 时**无法带 Authorization** → 必然 401（现在改成 fetch + Bearer）。
2. **outbox 是否派发** → `SELECT status,retries,created_at FROM outbox_events`。
   若全是 pending 而 `created_at` 看起来还没到时间 → **时区问题**（§7.4）。
3. **cursor 是否被跳过** → 看 `stream:outbound` 的长度是否 > 页面收到的消息数；
   若循环每次都传 `$`，两次轮询之间的消息会被跳过。
4. **前端去重是否误删** → 按 `message_id` 去重（`ChatView.vue:141`），
   若后端复用了 message_id 会误判。

**Q26 「审计里出现很多 deny，但没有报错」，怎么定位？**

按 `decision=deny` 拉出 `error_type`/`channel`/`user_id` 分布，对照代码里的 deny 点：
- `tenant mismatch` → agent 与消息不同租户（构造/配置问题）。
- IM 用户不在白名单 → 检查 `tenants.audit_policy.im_allow_users`。
- 审批拒绝/超时/取消 → 检查审批链路；`error_type` 会区分（`approval timed out` 写在日志里，
  审计只留 coarse 分类）。

**Q27 抓到一个「同一个消息回复了两次」，怎么定位？**

1. 两份回复的 `ReplyTo` 是否同一个 `m.ID` → 是：说明同一入站消息被跑了两次。
2. 检查 `idempotency_keys` 是否有该 `msg_key` → 没有：两阶段幂等的提交没发生
   （看是否 `commit failed` 或有 worker 重启）。
3. 检查是否发生 `lock_lost` 审计 → 是：会话锁在回合中途丢了（回合超过心跳能力/
   Redis 抖动）→ 两个 worker 并发执行了同一会话。
4. 检查 `resumeRecordedTurn` 是否被跳过 → 若 session 后端当时不可用，事件级幂等失效。

**Q28 「某个租户的模型调用特别慢」，怎么定位？**

- Prometheus：`platform_model_call_duration{tenant_id=...}` 的 p95（**按回合累计**的模型耗时）。
- Jaeger：按 `tenant_id` 过滤 `agent.run`，看子 span 是模型还是工具慢。
- 注意 `session_latency` 只测 Router 解析后端，**不是** Session I/O 耗时 → Session I/O 看
  `session.*` span。

**Q29 「DLQ 里堆了 5 条同一个会话的消息」，怎么定位？**

- 大概率是**会话锁争用被误计**？不会：`ErrRequeue` 不计数（`bus.go:491-496`）。
- 看 `dead_letters.fail_reason`：如果是 `worker: run agent ...` → 模型侧持续失败
  （端点错了/被限流/超时）；如果是 `session lock lost` → 心跳跟不上回合长度。
- 处置：修因后 `POST /dlq/{id}/replay`。

**Q30 「/healthz 返回 503」，怎么定位？**

- `body.reason` 直接说明（`health.SetDegraded("mysql unavailable")`）。
- 当前唯一的 degraded 触发点是**启动时 MySQL 等不到**（60s 轮询后）。
- 注意：Redis 挂掉**不会**让 /healthz 变 503（§11.1 的有意设计）。

**Q31 「前端按钮点了没反应 / 一直跳登录页」，怎么定位？**

- 先看是不是 **403/401 噪音**：member 角色可能请求了无权限的接口。
- 历史事故（阶段 39）：`/login ↔ 受保护页` 死循环 —— 根因是 `api/index.ts` 硬跳转 +
  CORS 顺序错误导致 `/auth/me` 必然失败。现在的收敛逻辑在 `router/guard.ts`
  （纯函数 + 9 个单测），判断「有权限的页面集合」用的是 `hasPermission`。
- 定位手段：浏览器 Network 看文档加载次数（>1 次/秒说明有重载循环）。

**Q32 「租户 B 能看到租户 A 的资产」，怎么定位？**

1. 列表泄漏还是按 id 泄漏？列表 → 检查 `ScopeTenant` 用了吗；
   按 id → 检查 `readable`/`writable` 双闸。
2. 会不会是 `created_by` 为空的**老数据**？按设计它被视为租户共享
   （`CanReadAsset` 第一条分支）—— 这是**有意的兼容行为**，不是 bug。
3. 用 `app/web/tenant_isolation_test.go` 的模式写一个回归用例复现。

**Q33 「灰度设了 30% 但实际没生效」，怎么定位？**

1. `GET /agents/{id}` 看 `gray` 字段是否是 `{"version":N,"percent":30}`。
2. 目标版本必须是**已发布**且 ≠ `current_version`，否则接口直接 400。
3. 看 `agent.run` span 的 `agent_version` 属性（Jaeger 里能直接看实际生效版本）。
4. 分桶是**会话级**：想快速看到效果，用多个不同 `session_id` 试。

**Q34 「迁移跑完了但目标会话少了旧事件」，是 bug 吗？**

- 不是代码 bug，是**框架能力边界**：v1.11.2 没有公开的事件分页 API，
  `GetSession` 各后端只返回「最近 N 事件」窗口。要全量旧事件，需在停写窗口用
  `session_events` 直拷模板（手册 §5）。这条在 `docs/数据同步与幂等策略.md §4.1`
  与 `cmd/migrate/main.go:11-17` 都如实标注了。

## 16. 演示脚本（5 分钟，可现场走通）

> 前置：`./begin.sh up`（或 `up core`）已跑完，`curl localhost:8080/healthz` 返回 200，
> 前端 `http://127.0.0.1:5173` 可访问，管理员 `admin/admin123`（compose 默认）。
> 演示可以全部走 UI；下面的 curl 只是给你**兜底**（避免现场点错）。

### Step 0（10s）健康与初始化

```bash
curl -s localhost:8080/healthz          # {"status":"ok"}
bash scripts/verify_init.sh             # ✅ 所有 22 个核心表已成功创建
```

讲一句：**22 张平台表 + 7 张框架自建表**；init 只在首次建卷时执行，所以改 DDL 要 `begin.sh reset`。

### Step 1（20s）登录 + 看角色

```bash
TOKEN=$(curl -s -X POST localhost:8080/auth/login -H 'Content-Type: application/json' \
  -d '{"user_id":"admin","password":"admin123"}' | jq -r .token)
curl -s -H "Authorization: Bearer $TOKEN" localhost:8080/auth/me
```

讲一句：JWT 里带 `tenant_id` + `role`；owner 可以跨租户，admin/member 被钉死在自己的租户
（`ScopeTenant`）。UI 侧边栏的可见项就是 `hasPermission` 的结果。

### Step 2（40s）建模型端点

UI：**模型端点 → 新建**：名称 `demo-endpoint`、类型 `chat`、协议按你的供应商、
Base URL + 模型名 + API Key（**API Key 会加密进 secret store，不回显**）。

```bash
curl -s -X POST localhost:8080/endpoints -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"demo-endpoint","type":"chat","provider":"openai","base_url":"https://api.example.com/v1","model_name":"gpt-4o-mini","api_key":"sk-xxx"}'
```

讲一句：端点还分 `type=embedding`；知识库只能选 embedding 端点
（`RegistryEmbedderFactory` 会校验，否则会出现「embedding 返回 text/html」那类事故）。

### Step 3（40s）建知识库（可选，快）

UI：**知识库 → 新建** → 选 embedding 端点 → 摄入一段文本 → **检索演示** 输入问题看命中。

讲一句：元数据在 MySQL，向量在 Milvus（v2.5+ 才能用 BM25）；一致性是 Bounded
（写后短暂不可见属正常）；collection 名做了 `sanitizeName`（数字开头的租户 id 要加前缀）。

### Step 4（60s）建 Agent 并发布

UI：**Agent 配置 → 新建** → 填名称 → **发布** 对话框里勾选：端点 `demo-endpoint`、
工具（内置目录里的 `echo`（名称 `echo`）与 `get-current-time`（名称 `get_current_time`））、
知识库、Skill、（可选）需要审批的工具。

> 注意：`RuntimeProfile.tool_ids` 用的是**工具定义 ID**（`echo` / `get-current-time` /
> `code-exec`），不是工具的调用名（`echo` / `get_current_time` / `execute_code`）。
> 审批判定用的是**调用名**（`FunctionTool.Name`），这个映射在
> `toolResolver.fromProfile` 里完成 —— 答辩时容易被追问。

```bash
curl -s -X POST localhost:8080/agents -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"name":"演示 Agent"}'
curl -s -X POST "localhost:8080/agents/<agent_id>/publish" -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"endpoint_id":"<endpoint_id>","system_prompt":"你是演示助手","tool_ids":["echo","get-current-time"]}'
curl -s -H "Authorization: Bearer $TOKEN" "localhost:8080/agents/<agent_id>/versions"   # v1
```

讲一句：发布 = **追加不可变版本 + 原子切换指针**；回滚就是切指针，改模型 = 改端点。
注意工具要**授权**（工具页 → 授权）才会真正挂载：目录 → 授权 → 发布挂载 → 运行时 RBAC。

### Step 5（60s）对话，看「实时回复」

UI：**Agent 对话** → 选租户（owner 可选）/ Agent / 新会话 → 输入「你好，介绍一下你自己」→ 发送。

- **要看的**：用户气泡立刻出现 → 助手气泡**通过 SSE 实时出现** → 右上角 `● 已连接`。
- 刷新页面 → 从会话下拉里选回刚才那个会话 → 历史还在（来自 `chat_messages` 账本）。

讲一句（这是最近修的三连 bug 的现场验证）：
① 回复流用 **fetch + Bearer**（`EventSource` 不能带 header，过去必然 401）；
② outbox 的 due-check 用**数据库算的年龄**（否则 UTC+8 服务器上事件永远不到期）；
③ 游标 `$` 只解析一次（否则两次轮询之间的回复被跳过）。

### Step 6（40s）审计 / 用量

UI：**审计日志** → 看到 `executed` 行（tenant/channel/user/session/agent/tools/decision/latency/cost/trace_id）
→ 用「操作者/决策/来源」筛选。
**用量** → 五个维度卡片 + 明细（tool×n、skill 快照）。

讲一句：审计 11 字段里 `cost` 是 **token 数**（没有价目表，不折算金额）；
`usage_records` 的 record_id 是 `sha256(msgID:dim)` 前 32 hex —— 因为列宽 36，
用 `msgID:dim` 会截断撞键、静默丢行。

### Step 7（40s）Jaeger

打开 `http://127.0.0.1:16686` → Service 选 `trpc-agent-service` → 找刚才那轮：
`im.callback → agent.run → session.* / memory.* / tool.* → im.reply`，点进去看
`agent_version`、`tenant_id`、`session.id`、`event.request_id` 属性。

讲一句：`session.*`/`memory.*` 是**真实子 span**（parent = `agent.run`），
不是「并入当前 span」；装饰器还刻意**保住了框架的可选接口能力**。

### Step 8（40s）IM 通道绑定（讲，不必真的连）

UI：**IM 通道 → 新建**：channel `feishu`、租户、Agent、Account ID（App ID）、
Secret（App Secret）、Verification Token。保存后**立即连接**（看后端日志
`channels: started adapter`）。

讲一句：①连接由 **binding 驱动**，不需要改 config、不需要重启；
②Secret 用 `{tenant}/{channel}:{account}:secret` 做 key，避免跨租户覆盖；
③另一个入站通路是 HTTP 回调（`im.webhook.enable`，飞书事件订阅模式），
默认关、fail-closed 验签；企业微信 AI-bot 只有 WSS，所以配它会**启动失败**。

### Step 9（20s）收尾：说清楚边界

主动说三句：**出站媒体未接线**、**流式是占位+终稿**、**真实 IM 收发需账号手测**；
再补一句「已实测的容量数值在 `tempdocs/容量评估指南.md §4.1`：入队 p50 3–5 ms，
端到端 p50 4–5 s，单节点 16 槽约 0.33 回合/s」。
