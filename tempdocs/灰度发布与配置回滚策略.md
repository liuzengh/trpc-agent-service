# 灰度发布与配置回滚策略

> 状态：**已实现**（阶段 33 起，阶段 44 补齐真实灰度分流）。
> 代码：Agent 不可变版本发布/回滚（`domain/agent` + `agent_versions` + `POST /agents/{id}/rollback`）；
> **Agent 版本级灰度**（`agents.gray {version,percent}` + 会话稳定分桶 + `PUT|DELETE /agents/{id}/gray`）；
> 租户配置版本历史 + 回滚（`tenant_config_versions` + `GET /tenants/{id}/config-versions` +
> `POST /tenants/{id}/config-rollback`）；数据后端切换可回滚。
> 本文描述的每条都有测试：`domain/agent` 的灰度分桶单测、`web` 的 gray/rollback handler 用例。

## 1. 两级可回滚对象

| 对象 | 粒度 | 机制 | 回滚 |
| --- | --- | --- | --- |
| **Agent 运行配置** | 单 agent | 不可变版本：发布即生成 `agent_versions` 新版本（draft→published），原子切换 `agents.current_version` | `POST /agents/{id}/rollback {version}`；历史版本全量保留 |
| **租户配置** | 单租户 | 每次 `PUT /tenants/{id}` 生成配置快照 | `GET /tenants/{id}/config-versions` + `POST /tenants/{id}/config-rollback {version}`；表 `tenant_config_versions`（011 SQL） |

回滚动作本身也是"写"，会生成新的头部版本（Agent 回滚到 v1 会产生 v3 状态；租户同理），
因此审计上"现在是什么版本"永远可查，历史也不会被回滚动作覆盖。

## 2. 租户配置回滚 API

每次 `PUT /tenants/{id}` 成功后，`Manager.Update` 把**更新后**的完整租户 JSON 写入版本表
（`SnapshotConfig`）；版本号每租户单调递增（MySQL 用 `COALESCE(MAX(version),0)+1`，撞唯一键重试）。

- `GET /tenants/{id}/config-versions` → 历史（新→旧，含 config 与 created_at）；
- `POST /tenants/{id}/config-rollback {version}` → 校验存在 → 应用该快照 → 落新版本 → 返回恢复后的租户。

影响面：`DataBackend`（切换数据后端）、`Quota`（预算）、`AuditPolicy`（脱敏/白名单/强制审批）
全部可回退。**回滚后 worker 下一轮消息自动按新策略运行**——治理策略每条消息从租户表重新解析
（`worker/policy.go resolveTenantPolicy`），没有进程内缓存需要失效。

## 3. Agent 版本级灰度（按会话稳定分桶）

`agents.gray` 存 `{"version":N,"percent":P}`。命中灰度的会话走第 N 版，其余走 `current_version`：

- **分桶键是会话 id，不是请求**：`fnv32(sessionID) % 100 < P`。同一会话在整个生命周期内
  固定使用同一版本——IM 多轮对话的上下文/记忆必须自洽，按请求随机切版本会让同一会话
  在版本间跳变；
- **目标必须是已发布版本，且不能等于当前版本**，否则接口直接报错（不做静默 no-op——
  静默忽略会让操作者以为自己灰度生效了）；
- **清除灰度**（`DELETE /agents/{id}/gray`）即回滚到 `current_version`，无需重新发布；
- **可观测**：实际生效版本写进 `agent.run` span 的 `agent_version` 属性，可在 Jaeger 里
  按属性对比灰度组与基线的延迟/错误率。

**发布与回滚语义**：`Publish` 生成不可变版本并原子切换指针，`Rollback` 同样原子切换；
运行中的回合已经拿到自己的 Agent 实例，不受切换影响（下一轮生效）。

## 4. 为什么灰度的粒度是"会话"而不是"租户整体"

- 会话级分桶让**同一租户内**也能做小流量验证（`percent` 可以是 5%），比"整租户切换"
  更安全：出问题时受影响的会话数有上界；
- 同时又保留了"整租户灰度"的能力——把 `percent` 设为 100 即该租户全量切到新版本；
- 反面做法（按请求随机切）会破坏会话连续性，因此明确不做。

## 5. 操作建议

1. **发布新版本** → 先把 `percent` 设小（如 5）观察 Jaeger 的 `agent_version` 分组与错误率；
2. 稳定后逐步提高 `percent`，最后 `Publish` 成 `current_version` 并 `DELETE /agents/{id}/gray` 清除灰度；
3. 出问题时 `DELETE /agents/{id}/gray` 立刻止血（已命中灰度的会话在**下一轮**回到当前版本）；
4. 改租户治理配置前先 `GET /tenants/{id}` 保存当前值，或直接用 config-versions 的版本号回滚；
5. `agent_versions` 保留全部历史版本，勿清理最近 N 个，以便快速回滚。
