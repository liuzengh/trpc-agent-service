# Agent 平台产品化改造计划

状态：本轮 P0—P6 产品化改造已完成。代码、构建与交付归档、升级/回退核对、日常数据库备份与 schema 24 升级、真实模型网页调试均已完成；2026-09-09 用户分别确认 Telegram 和企业微信消息 MCP 收到升级后的回复。企业微信测试群的历史补读进度经用户明确授权恢复，操作已审计。现有 Agent 发布版本、IM 授权范围和模型凭据保持不变；未 push。此结论不代表生产容量、云端灾备或企业合规验收。

基线：`0ce285f`（`0.2.0-rc.10`，数据库 schema 23）。保留现有 tRPC-Agent-Go 执行内核和已验证的后端能力，重点解决配置、调试、发布与排错需要人工串联的问题。实施时先检查工作区和运行版本，不覆盖此后已有的用户修改。

## 1. 改造目标与完成标准

目标使用流程：部署者首次配置凭据和授权后，操作员在浏览器中选择 Agent、修改常用配置、调试对话、批准工具、发布版本、查看失败原因；不需要手写 JSON、编排版本编号或为了每次调试新建 Telegram Topic。

本轮完成必须同时满足：

1. 模型、提示词、工具、Skill、知识库、记忆的常用配置都有可理解的表单，JSON 只作为高级入口。
2. 草稿、调试快照、已发布版本明确区分；保存草稿不会改变线上 Agent。
3. 调试真实经过平台 Runtime、Runner、权限、预算、审批与执行记录，不另写一个直接调用模型的演示接口。
4. 已知配置冲突在调试或发布前指出，运行错误由平台提供结构化原因，不依赖模型解释。
5. 普通操作员可以从请求列表进入运行详情，不必先去日志里寻找 request_id。
6. 编译、类型检查、现有回归和隔离运行检查通过后，集中安排必要的真实模型、IM 联调，不让用户反复完成整套验收。按后续要求不另建一批测试脚本或过程文档。

这些是本轮的产品验收标准，不代表完成生产容量、云端灾备或企业合规验收。

## 2. 范围与参考原则

### 保留什么

- tRPC-Agent-Go LLMAgent / Runner，以及现有多租户、Session 协调、持久任务、消息去重、Storage Router。
- Telegram、企业微信通道与既有绑定；工具白名单、精确 Secret grant、审批、Tool Journal、Docker 沙箱。
- 已有版本和会话固定关系。新发布默认只影响新会话，不强行迁移旧会话。
- 现有 `.env`、数据库、知识库、附件、备份与历史审计；不为方便开发重置环境。
- Admin API 的自动化使用方式。新增浏览器能力不要求已有 API 客户端立即升级。

### 本轮不扩展什么

- 不替换执行框架，不复制完整 Coze/Dify，不增加拖拽工作流、Graph/多 Agent 编排。
- 不新增 IM 类型或存储类型，不把任意脚本上传、Skill 商店、虚拟机沙箱列为前置条件。
- 不新增公开注册、企业 SSO 或完整账户管理系统；沿用已有 Admin Principal 与 RBAC。
- 不在网页提供宿主机 shell、Docker 管理、任意 URL 探测或任意 Secret 写入。
- 不自动启动模型、Tunnel 或真实 IM 轮询，不自动发送外部消息，不 push。

## 3. 技术方案

### 前端与构建

- 采用 React + TypeScript + Vite，使用 Ant Design 的表单、导航、表格、弹窗等组件；统一布局、文案、空状态、加载状态与错误展示，不复制其他产品的外观。
- 源码放在 `trpcservice/web/console/`；构建产物放入 `trpcservice/admin/ui/dist/`，由 Go 内嵌，仍通过 `/admin/ui/` 提供同源服务。开发服务器仅用于开发。
- 使用 npm 与一份锁文件；实施时选取相互兼容的稳定版本并锁定，不依赖每次拉取 latest。[Vite 文档](https://vite.dev/guide/)和 [Ant Design 文档](https://ant.design/docs/react/introduce)用于核对构建、组件与样式方案。
- 沿用根目录 `build.sh`、`start.sh`、`stop.sh` 等入口，不再增加一批包装脚本。源码构建需要 Node/npm；运行编译好的 Go 服务不需要 Node。
- 构建必须包含前端，缺少依赖或构建失败就明确报错，不静默嵌入陈旧页面。源码包包含前端源码与锁文件，不包含 node_modules、私有环境或运行数据；Docker 使用多阶段构建。
- 动态资源采用构建清单和严格静态路径限制。CSP、同源检查和静态文件安全测试必须保留；组件样式优先采用静态提取，必要的动态样式使用 nonce，不直接放宽脚本策略。

### 登录、角色与凭据

- 继续使用部署者已有 Admin Token/Principal 完成首次认证；增加短期浏览器登录会话，刷新页面不必重新粘贴长期 Token。
- 登录会话使用服务端保存的随机不透明凭据，数据库保存其摘要并设置到期时间；多 Admin 节点共享状态。浏览器使用 HttpOnly、SameSite Cookie，HTTPS 下启用 Secure，仅本机 HTTP 开发允许明确例外。
- Cookie 写接口同时验证 Origin 与 CSRF Token；登录限流、注销、过期、Principal/Token 变更后的失效规则纳入测试。长期 Admin Token 不进入 localStorage、日志或 URL。
- 调试执行和运行内容读取分别授权；普通只读审计角色不因能看元数据就自动获得执行权限或聊天正文。租户切换清理前一租户页面状态，后端再次校验全部资源归属。

### 复用后端，而不是旁路调用

- 配置和发布复用 `admin` / `controlplane`，通过草稿与聚合查询 API 补齐用户流程。
- 调试复用 `agent.Runtime`、`RevisionCompiler`、Worker、队列、审批及 Journal；Admin-only 节点只管理和提交任务，不获得模型执行或 Docker 权限。
- 不把 `/chat` 直接开放给 Admin Token，也不让前端自行拼接可信 tenant/user/session/approval Scope。
- 运行详情从持久化事实和有界事件构建，不以模型回复文字判断审批、取消或工具成功；不展示模型内部推理内容。

### P0：补发布检查与错误契约

实现入口：[统一预检](../trpcservice/admin/validation.go)、[平台反馈](../trpcservice/governance/feedback.go)。创建/发布/灰度和浏览器预检共用服务；自动化覆盖不写入、不调用模型、权限、过期观测、预算反馈、幂等与真实 Docker 执行。依赖观测当前提供只读快照契约和本地沙箱禁用事实，远端探测与完整系统状态在 P5 接入；显式模型检测沿用现有检查命令，不伪造已验证状态。

改动：

- 将创建、调试、发布、灰度共用的配置检查收敛为同一服务，返回错误码、字段位置、严重程度和修正建议。
- 检查模型配置、Secret 引用授权、工具白名单、Skill 版本/checksum、后端配置与能力依赖。静态校验默认不请求模型或执行工具。
- 对本平台“加载后执行 Skill”的路径，正数工具预算小于 2 时阻止新调试/新发布，并说明原因；默认建议值可以是 4，但必须由用户明确保存，不能暗中放宽权限。保留现有 `0` 表示不设该次数上限的语义，并显示风险提示。
- 沙箱、后端等可用性由执行节点提供有限时效的探测结果；无法观测显示“未知”，不伪造通过。模型生成测试是单独的显式操作，提示可能产生费用。
- 为 `tool_budget_exceeded`、`approval_required`、`sandbox_unavailable` 等提供稳定平台错误，保留 request_id；先保证结构化事实，不只换一句报错文案。

验收：Skill 加载与执行预算冲突可在调用模型前定位到字段；旧版本不会被静默改写；越权、缺少 Secret、旧 checksum、不可用 Worker 的测试都有确定结果。

### P1：建立组件化控制台与登录会话（已实现）

改动：

- 搭建前端工程、统一 API 客户端、导航、租户切换、权限展示、表单组件和错误边界。
- 一级入口收敛为“概览、Agent、资源、通道、运行记录、系统状态”，避免先让用户理解底层表结构。
- 接入安全登录会话；迁移现有列表/创建、租户策略、通道更新、后端注册和审计功能，不以重做页面为由丢失旧能力。
- 所有页面处理加载、无数据、无权限、请求失败、会话过期和并发修改；敏感字段只显示引用或状态。

验收：登录、刷新、注销、租户切换和只读角色通过浏览器测试；新页面连接真实 Admin API；构建后仍只需启动 Go 服务，不启动单独前端服务。

### P2：Agent 工作台、结构化配置与草稿（已实现）

改动：

- Agent 详情页集中展示“配置、调试、发布记录、运行记录、通道”；模型、提示词、工具、Skill、知识库和 Memory 使用专门表单。
- 模型和 Secret 只选择当前租户已获授权的配置；现有复杂 MCP、Guardrail 等字段先提供可校验的高级编辑，不能因表单未覆盖而丢字段。
- 增加独立草稿，记录来源版本、草稿版本号和修改人；保存使用乐观锁，冲突时展示差异，不覆盖他人修改。
- 已发布版本只读，“编辑为草稿”“保存草稿”“发布”是不同动作；不再让一个“查看”页面同时隐式承担复制和发布语义。
- ID 由服务端生成，版本序号在生成不可变版本时由数据库事务分配；用户不填写内部版本编号。保留旧 API 的合法显式 ID 用法。

验收：可以从已有 Agent 创建草稿、修改常用配置而不手写 JSON；原配置、授权引用和线上版本保持不变；两个浏览器并发保存不会丢更新。

### P3：页面内调试、审批与执行过程（已实现）

改动：

- 将草稿冻结为服务端不可变调试快照；调试会话固定快照，修改草稿后由“开始新调试”显式使用新快照，不改变正在执行的任务。
- 提供发送、历史消息、清空并开始新调试、取消和审批按钮。服务端生成可信身份；不同管理员、租户和调试会话相互隔离，不冒用 Telegram/企业微信用户。
- 使用独立调试 Session/Memory/Artifact 命名空间，默认不写正式记忆、不发送 IM；知识库只读且仍受租户授权限制。外部写工具默认不开放，必须有明确测试目标与授权；沙箱 Skill 仍需审批。
- 经专用任务类型/队列交给支持调试的 Worker；复用预算、Session 协调、审批参数哈希、执行 Journal、幂等、超时和取消。不能直接绕过这些机制调用 Model 或 shell。
- 展示排队、执行、等待审批、完成、失败、取消请求中、已取消和未知结果；审批后的继续执行与原请求关联。审批批准不展示为执行成功，取消不展示为副作用回滚。
- 先实现可靠的持久状态查询和有界事件，再提供基于 fetch 的事件流。连接断开不重新执行任务，重连使用事件游标；缺少进度事件时显示等待，不伪造流式进度。
- 原始调试输入/输出仅对授权用户可见，设置大小限制、保留期与清理规则；审计仍只记录必要元数据和摘要。

验收：关闭 Tunnel 后仍能在页面完成真实 Runner 的多轮对话和 Skill 审批；自动测试验证审批前零执行、批准后一次执行、重复点击不重做、断线不重跑、取消排空事件和回收 goroutine。先使用合成模型及隔离 Docker 完成，不依赖用户发 IM 消息。

### P4：版本差异、发布检查与回滚（已实现）

改动：

- 提供草稿与稳定版本差异，列出模型、指令、工具权限、Skill、知识/记忆、预算等实际变更。
- 发布前执行 P0 检查，展示本次调试使用的快照及结果；明确区分“未测试”“测试通过”“依赖未知”，不能把静态检查写成真实联调通过。
- 使用幂等提交、期望草稿版本和期望 App 版本：并发发布不产生重复序号或覆盖他人发布；检查后配置变化必须重检。
- 发布后显示稳定版本、发布时间、发布人和影响范围；回滚重新检查当前授权及依赖，不能仅切指针就绕过安全策略。
- 页面明确说明旧会话继续使用原版本；本轮不提供批量强制迁移旧会话，调试通过新会话入口解决。

验收：新建 Agent 可以完成“草稿 → 调试 → 发布 → 再修改 → 回滚”；无手写 ID；旧会话不变、重复提交幂等、并发冲突可理解、授权撤销后不能借回滚恢复权限。

### P5：运行记录、资源与依赖诊断（已实现）

改动：

- 请求列表按 Agent、时间、通道和状态查询，展示版本、耗时、Token/成本及失败摘要；点击进入详情，无需手动复制 request_id。
- 将工具许可、审批、执行 Journal、后台任务和 IM 出站结果串联；分别展示执行成功与消息投递成功，不混为一个绿色状态。
- 资源页可选择和查看授权模型、Skill、知识库及后端；明确区分“配置已保存”“依赖可用”“最近测试成功”。不为了页面完善开放 Secret 原文或危险数据库编辑。
- 通道页展示启用状态、最近接收/投递、已记录的拒绝原因和回调配置提示；只读取获授权范围，不主动读取新群或重发消息。
- 系统状态显示 Admin、Worker、队列、Session 后端、沙箱和模型配置状态，注明观测来源与时间。按组件角色解释缺少本地进程，不把远端 Worker 误报成未启动。
- Tunnel 的进程状态只在有受控本机诊断来源时显示；没有来源则显示未知。公网探测与模型生成检测必须显式触发、限时限流且只能使用部署者允许的目标，不提供任意 URL 探测。

验收：工具预算不足能直接看到“上限、已用次数、受阻工具”；同租户跨应用及跨租户读取都做归属检查；无权用户看不到正文或敏感配置；依赖不可用、不可观测和探测超时有不同提示。

### P6：回归、升级与交付收尾（本轮已完成）

改动：

- 已将前端类型检查和构建加入现有回归入口；先生成嵌入资源，再执行 Go 检查。按后续要求不扩建组件/浏览器测试套件，使用隔离浏览器检查补充现有 Go race、权限、恢复、迁移和 Docker 检查；如需无人值守 UI 回归，仍需另补。

## 5. 后端与数据改动清单

下表对应当前代码接口；需部署新版 Admin/Worker 并应用 schema 024 后使用。原 Bearer API 保留，网页使用 Cookie/CSRF。

| 能力 | 已实现接口（省略 `/admin`） | 核心约束 |
| --- | --- | --- |
| 登录会话 | `/login`、`GET /session`、`/logout` | 不返回长期 Token，Cookie/CSRF 与原 Bearer API 分开验证 |
| Agent 工作台 | `/workspace`、`/apps/onboard`、`/apps/settings`、`/resources/list` | 后端裁剪租户范围；只返回凭据引用 |
| 草稿 | `/drafts/get`、`/drafts/save`、`/drafts/reset` | expected_version；修改人由认证身份确定；页面按配置组比较与合并 |
| 配置检查 | `/revisions/validate`、`/drafts/readiness` | 静态有效、依赖观测与同配置调试记录分开展示；显式模型检测沿用 CLI 或网页调试 |
| 调试 | `/debug/sessions`、`/latest`、`/send`、`/get`、`/events`、`/live`、`/cancel`、`/decision`（后七个也在 `/debug` 下） | 后端生成 Scope；独立任务和数据命名空间；幂等提交 |
| 发布 | `/drafts/publish`、`/releases/list`，复用 `/revisions/publish`（含回滚）、`/apps/rollout`（灰度）和版本查询 | 事务分配序号、CAS、幂等键；同事务审计与统一校验 |
| 运行查询 | `/runs/list`、`/runs/get`、`/jobs/list` | 元数据与正文权限分离；有界分页和明确的请求关联 |
| 状态诊断 | `/system/status`、`/system/probe`、`/channel-bindings/diagnostics` | 默认只读已有记录，公网探测显式触发且目标固定；不主动读取新群或重发 |

schema 024 新增 `admin_session`、`agent_draft`、`debug_snapshot`、`debug_session`、`debug_run`、`debug_event`、`debug_tool_execution`、`debug_tool_approval`、`debug_approval_decision`、`console_worker`。它们记录租户/应用归属、Principal、版本、时间及保留期。登录表单独授权，Worker 不读取浏览器凭据摘要；调试 Tool Journal/审批不放宽原 IM 表外键。调试快照不进入普通版本列表，也不能由通道或发布接口引用。

运行列表优先复用现有 Inbox、任务、审批、Journal 和审计的事实，不维护第二份“人工成功状态”。跨请求的审批继续任务保留关联 ID；状态汇总可以是读模型，但不得覆盖原始执行事实。

升级策略：先做增量 schema 与兼容 API，再部署支持新任务的 Worker/Admin，最后启用新控制台。调试使用隔离队列/明确能力版本，旧 Worker 不能误领新任务。阶段性开关只切换新入口，不改线上 Agent 的稳定版本。

回退时先停止接收新调试任务、处理在途执行，再关闭新入口；数据库保留新增表，不自动执行破坏性 down migration。旧程序是否支持新 schema 必须先测试，不能仅凭“增量迁移”承诺旧二进制一定可直接回退。若不兼容，应交付保留新 schema 读取能力的回退构建。未知工具结果不得因回退自动重放。
