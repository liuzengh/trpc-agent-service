## 1. 风险清单

| # | 风险 | 影响 | 缓解措施 | 状态 |
|---|---|---|---|---|
| **R1** | **Admin API 未授权访问** | 管理接口暴露导致租户数据泄露或误操作 | JWT 登录（`POST /auth/login`，bcrypt 口令）+ 外层 auth 中间件（`/healthz`、`/auth/login` 之外的路径一律要 Bearer，IM 回调前缀只认平台签名）+ 路由级权限门禁 + **资源级（按 id）租户归属校验**（越权统一 404，不确认外部资源存在）+ 行级作者规则；生产模式 `server.production=true` 缺签名密钥直接拒绝启动 | 已实现 |
| **R2** | **模型超时导致 Worker 阻塞** | 长尾请求（10–15% ~300s）占用 Worker 槽位，降低吞吐 | 单次模型 HTTP 120s；整回合 300s 硬超时（`context.WithTimeout`）；`consumeWorkers` 有界并发（默认 16）；超时后取消 context，goroutine 正常退出并审计 `timeout` | 已实现 |
| **R3** | **IM 消息重复投递** | 同一消息被多次处理，导致重复回复或重复计费 | **五层幂等**：①`Message.ID = channel:platformMsgID`；②adapter 内存 seen 集；③**Redis 两阶段租约**（90s 租约 + 心跳续期，回复落 outbox 后才 `CommitIdem` 24h；失败 `ClearIdem` / 崩溃由租约到期释放）；④MySQL `idempotency_keys` 唯一键（与 outbox 同事务）；⑤**事件级幂等**（`RunOptions.RequestID=msgID` + `resumeRecordedTurn` 复用已产出回复，不再二次调用模型） | 已实现 |
| **R4** | **Redis 不可用** | 消息总线、锁、幂等、路由、outbound 跟随全部受影响 | 生产建议 Sentinel/Cluster；节点启动**等待 Redis 就绪**（60s 轮询）后再起数据面；运行期消费循环与 IM 出口跟随者由 `health.Supervisor` 托管：**失败即退避重连（1s→30s）**，依赖**沉默 >5s** 即 `/healthz` 503，**总线重新应答一次读的瞬间自动清除**（`RedisBus.SetConsumeReady` / `Gateway.SetReady` → `Attached`）；其余命令各自重试，出站派发不因瞬态错误退出。实测：停 Redis 30s → t+21s 转 503、恢复后 ≤6s 回 200、进程不重启、消息零丢失（《部署与运维手册》§2.5）；**降级原因是按生产者命名的议题集合，互不覆盖**（MySQL/消费者/网关各自独立） | 已实现（自愈 + 可观测降级） |
| **R12** | **崩溃恢复把在途消息当成已处理**（故障演练暴露的真实缺陷，已修） | 节点被 SIGKILL 后，`XAUTOCLAIM` 在死者的 90s 幂等租约仍有效时把消息交给存活节点，存活节点把"标记存在"误读为"已处理"→ **ack 丢弃**。症状极具欺骗性：`lag=0`、`pending=0`、`/healthz` 200，消息却凭空消失（演练实测丢 3/20） | `Idempotent` 由布尔值改为**三态**（认领成功 / 进行中 / 已完成）；**进行中一律 `ErrRequeue` 保持 pending，绝不 ack**——对方提交后下次看到"已完成"再 ack，对方已死则租约到期后真正执行。回归测试 `TestBusIdempotencyDistinguishesLeaseFromCompletion`、`TestWorkerLeavesAnInFlightMessagePending`；演练脚本 `scripts/faults/node-failure.ps1` 可复现 | 已实现（代价：崩溃消息恢复上限约 2 分钟 = 租约 90s + 认领窗口 30s） |
| **R14** | **超时失败被记成普通运行错误**（故障演练暴露，已修） | 回合被平台自己的 300s 护栏切断时，框架用自己的措辞报告"模型调用被取消"，`errors.Is(err, context.DeadlineExceeded)` 为假 → 审计写 `run_error`，与"上游返回错误"无法区分；运维无法判断该找上游还是该调预算。实测：stall 上游把回合拖到 ~283s 被切断，审计却是 `run_error` | `run()` 的错误出口统一经 `timeoutAware(runCtx, err)`，把平台 deadline 与框架错误**同时**包装（`fmt.Errorf("%w: %w", …)`），审计因此记为 `timeout`；回归 `TestTimeoutAwareKeepsThePlatformDeadlineVisible`；演练脚本 `scripts/faults/model-timeout.ps1`（黑洞地址=连接层失败→`run_error`，stall 上游→`timeout`，两种分类可区分） | 已实现 |
| **R13** | **优雅停机丢掉"已完成回合"的记账**（故障演练暴露，已修） | SIGTERM（滚动重启）会取消消费 context，而回合的账本/用量写入用同一 context：模型已答完、回复已进 outbox，但账本行、用量行、幂等提交全部失败（日志 `usage metering skipped ... context canceled`）→ 会话历史缺回合、成本少计 | 回合收尾的**记账类写入改为脱离取消的限时 context**（`shutdownSafe` = `context.WithoutCancel` + 5s 超时）：已经产生回复的工作，其账本/用量/幂等提交必须活过打断它的那次停机。回归测试 `TestShutdownSafeSurvivesCancellation`；演练中断言"每条消息有耐久处理凭证 + 账本行齐全" | 已实现 |
| **R15** | **软删端点后同名无法重建**（故障演练暴露，已修） | `model_endpoints` 的唯一键 `uk_endpoint_scope_tenant_name(scope, tenant_id, name)` 不含 `is_deleted`：软删一行后，同一 scope/tenant 下再建同名端点会永远返回 409（演练里临时端点 "drill hanging endpoint" 就这样卡住了下一次演练；`004_tools.sql` 的 `uk_tool_scope_tenant_name` 是同一模式，工具表当前只有读路径故未改） | 软删时把 name 改写为 `LEFT(name,80) + '#deleted#' + endpoint_id`（墓碑唯一，零 DDL 变更），删除行仍以 `endpoint_id` 标识 | 已实现 |
| **R5** | **租户数据泄露** | SQL 查询缺少 `tenant_id` 过滤导致跨租户访问 | 所有 Store 查询强制 `WHERE tenant_id = ?`；Redis 键内嵌 tenant；框架 Session/Memory 以 `AppName=tenant_id` 隔离；**资源级**按 id 的越权校验（跨租户统一 404）；worker 侧校验 agent 与消息同租户；集成测试覆盖隔离 | 已实现 |
| **R6** | **密钥明文泄露** | IM token、模型 API key、数据库密码出现在日志或 trace 中 | 统一日志脱敏（key 含 password/secret/token/dsn/api_key 等自动 `***`，含嵌套 group 与 URL 凭据）；审计错误只落粗粒度分类；Secret Manager 用 AES-256-GCM，主密钥从环境变量注入且不落库；端点凭据写库前转成密钥引用，明文被拒绝落盘 | 已实现 |
| **R7** | **DLQ 消息积压** | 死信消息未被及时发现和处理 | `platform.dlq_total` 指标告警；`GET /dlq` 按租户筛选；`POST /dlq/{id}/replay` 先 `ClearIdem` 再重投，`replayed_at` 防重复重放 | 已实现 |
| **R8** | **后端迁移数据丢失** | 切换租户后端时旧数据未迁移 | `cmd/migrate` CLI 支持 Session/Memory 跨后端迁移（幂等：delete-then-create）；迁移前可快照租户配置（`tenant_config_versions`）；向量库可离线重建；对象存储可整体搬迁 | 已实现 |
| **R9** | **RBAC 表未接线**（已消解，保留作历史） | 早期 `roles`/`role_permissions`/`member_roles` 三表既无读者也无写者，易误导 | **阶段 43 已删除这三张表**（`001_tenants.sql` 留注释说明何时补回）；现行权限模型 = 三角色（owner/admin/member）+ 行级作者规则，全部由 `app/web/permission.go` 从 `tenant_members.role` + `created_by` 推导，并有 `rbac_matrix_test.go` / `tenant_isolation_test.go` 回归 | 已消解 |
| **R10** | **IM 平台限制** | WeCom 2000 rune / Feishu 4000 rune 截断；卡片/流式形态、非文本消息（图片/文件/语音）在各平台支持度不一 | 出站文本自动截断（`truncateText` 按通道上限）；WeCom 流式占位（先发"正在处理…"再在同一 stream.id 原位替换）；**卡片有生产者**：审批通知在具备按钮回调的通道（Feishu）渲染为交互卡片，按钮 `behaviors.callback` 把 批准/拒绝 与 session 一起回传，回调经 `CardActionToInbound` 复用与"回复批准/拒绝"完全相同的链路；WeCom 无按钮回调降级为文本；**非文本消息已落地**：适配器按平台 API 取回附件字节（WeCom 下载 + AES 解密 / Feishu message-resource），网关内联为 `ContentParts`；字节由框架 `session/externalization` 落 MinIO 制品；读取失败的附件**明确回执** + 审计 `attachment_unreadable`；`KindStream` 仍无生产者（WeCom 用占位+终稿，Feishu 无原生流式） | 已实现（流式为占位方案） |
| **R11** | **数据库与应用时钟不一致**（真实事故复盘） | 服务端写的时间戳被应用按另一种时区解读，导致基于时间的判定全部失真——曾使 outbox 每条新事件都被判为"未到期"，**所有回复静默停在 pending**，而链路其余部分看起来完全正常 | 规则：**任何涉及"是否到期"的判断只用一个时钟**。outbox 到期改用数据库自己算的年龄（`TIMESTAMPDIFF(SECOND, created_at, NOW())`），且从未尝试过的事件永远立即到期；`OpenMySQL` 把连接会话时区钉为 `+00:00`，使 DB 写的 `CURRENT_TIMESTAMP` 与驱动读写的时间戳表示同一时刻；集成测试用 `+08:00` 会话显式复现偏差（`TestOutboxDeliversWhenServerZoneDiffersFromTheDriver`）。**遗留**：修复前写入的行其 DB 侧时间戳仍是本地时区，展示上会差一个偏移（不影响投递，因为首投已不依赖时间比较） | 已实现（历史数据的展示偏移已记录） |
