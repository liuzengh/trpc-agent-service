## 3. Versioned reply routing payload

Sender 只接受 `ReplyOutboxPayload`，当前 schema 为 `2`，sender routing version 为 `1`：

```go
type ReplyOutboxPayload struct {
    SchemaVersion        int
    Kind                 string
    TenantID             string
    SessionID            string
    JobID                string
    ExecutionID          string
    RequestID            string
    MessageID            string
    TraceID              string
    Channel              string
    DestinationType      string
    DestinationID        string
    ReplyText            string
    FinishType           string
    SenderRoutingVersion int
}
```

durable payload 是 execution result 的小 projection，只包含 delivery 所需 identity、routing 和 reply text。不会复制 Prompt、History、Provider response/body、token usage、Authorization、Cookie、DSN、token 或原始错误文本。JSON decoder 拒绝 unknown fields；payload、reply text、identity、destination 和 finish type 均有 byte 上限；encode 和 decode 都执行完整校验。

reply Outbox identity 保持确定性：

- `Kind = agent.reply`；
- `AggregateID = execution_id`；
- `TenantID = tenant_id`；
- `ID = reply-{execution_id}`；
- tenant-scoped `DedupKey` 与 P0-09F 规则一致；
- provider-facing `Idempotency-Key` 从 tenant/execution/kind 的稳定 hash 生成，跨 Outbox retry 不变。

`DecodeReplyOutboxMessage` 还校验 durable message tenant、kind、aggregate、ID 和 dedup identity，防止 payload 被挂载到其他 tenant 或 execution。

## 4. Tenant、channel 和 destination 边界

`RoutingFromTenantContext` 只从已解析的 `TenantContext` 生成 routing，不发明 fallback destination：

- Telegram 必须使用 `chat` destination，且 destination ID 必须是 canonical int64 字符串；
- Web 和 WeCom 允许已解析的 `chat` 或 `user` destination；存在 chat 时优先使用 chat；
- 缺 channel、缺 destination、空白/控制字符、超长 identity 和不支持的 destination type 均被拒绝。

`Registry` 在构造时拒绝空 adapter、重复 channel、未知 channel policy 和重复 policy entry。构造后不暴露或修改内部 map；`Lookup` 和 tenant policy check 可安全并发读取。`NewRegistryWithPolicy` 可显式限制 tenant 能使用的 channel；HTTPSender 在任何 HTTP transport 调用前执行该检查。

## 5. Adapter 和 transport contract

`SenderAdapter` 只负责：

1. 接受已校验的 `OutboundMessage`；
2. 构造 bounded provider-neutral `OutboundRequest`；
3. 校验 provider success response 的最小结构。

当前 builder 只输出以下字段：

| Channel | Path | Body projection |
| --- | --- | --- |
| Web | `/replies` | `destination_type`、`destination_id`、`text` |
| Telegram | `/sendMessage` | `chat_id`、`text` |
| WeCom | `/message/send` | `msgtype`、`text.content`、`touser` 或 `chatid` |

`HTTPSender` 通过注入的 `HTTPDoer` 执行请求。endpoint 只允许显式 `http/https`、host、无 userinfo、无 query、无 fragment；request body 和 response body 有边界。sender 自己不保存 repository，也不调用 `MarkCompleted`、`MarkRetry` 或 `MoveToDLQ`。测试只使用 fake HTTPDoer，endpoint 使用不可连接的保留域名，因此没有真实 Provider 调用。

## 6. 四类 outcome 映射

- `OutcomeDelivered`：2xx 且 adapter 明确确认最小成功字段，才允许 Dispatcher 选择 `MarkCompleted`；
- `OutcomeRetryableFailure`：429、5xx、timeout、明确可重试的 transport failure，使用有限 code；
- `OutcomePermanentFailure`：无效 payload/destination、unknown channel、未配置 endpoint、4xx rejection、malformed success response；
- `OutcomeUnknown`：连接可能在远端接受后中断、不可判定的 transport 结果或空 sender 状态，统一为 `delivery_outcome_unknown`。

Dispatcher 的 `ClassifyOutcome` 再次将 code 归一到有限 allowlist。原始 Provider error、response body、Authorization、token、URL query 和 DSN 不进入 durable `last_error` 或 DLQ reason。unknown 不会被报告为成功，也不会立即 DLQ；它按现有 bounded at-least-once policy retry，达到上限后才 DLQ。

## 7. Dispatcher 接线和 durable 证据

适配路径为：

```text
PostgreSQL Outbox Claim
  -> Decode/Validate reply routing payload
  -> Tenant/channel policy check
  -> Channel Adapter BuildOutbound
  -> HTTPDoer seam
  -> safe SenderOutcome
  -> existing RetryPolicy
  -> MarkCompleted / MarkRetry / MoveToDLQ
```

`outbox.ChannelSender` 只做 package contract adaptation，不持有 Outbox Repository。Fake/in-process 测试验证：

- delivered channel reply 只在 durable `complete` transition 后计为完成；
- rate limited reply 进入 retry；
- connection interruption 进入 unknown retry；
- retry 的 provider idempotency key 保持相同；
- outcome code 不会绕过 Dispatcher 的 durable policy。

真实 PostgreSQL test 使用隔离 schema 和真实 `OutboxRepository`，验证已提交 pending channel reply 被 database claim、channel-aware HTTP sender 调用、完成 transition 和 idempotency key。另有真实 PostgreSQL existing Outbox lifecycle、竞争 claim、expired-lock reclaim/fencing、retry/DLQ、tenant isolation、Docker restart recovery 验证。
