## 3. Queue Schema 和 Migration

migration `000004_job_queue` 新增 `job_queue` 表：

- `tenant_id`、`job_id`、`execution_id`、`schema_version`、`payload jsonb`；
- `status`：`queued`、`in_flight`、`acked`、`discarded`；
- `available_at`、`delivery_id`、`last_delivery_id`、`leased_until`；
- `attempt`、`delivery_count`、`acked_at`、`created_at`、`updated_at`；
- 主键 `(tenant_id, job_id)`；
- 唯一约束 `(tenant_id, execution_id)` 和非空 `delivery_id`；
- `tenant_id` 外键引用 `tenant`；
- `in_flight` 状态必须同时有 `delivery_id` 和 `leased_until`，其他状态不能保留 active delivery；
- ready partial index `(available_at, created_at, job_id)`；
- expiry partial index `(leased_until)`。

Queue 只保存已验证的 AgentJob snapshot，不强制 Session 外键；Session/Lease 事实源由后续 Execution 编排负责。Queue migration 与 P0-09A 的 `000003_execution_result` 顺序一致。

真实 migration acceptance 验证了干净 Up、重复 Up、checksum/missing/unknown version fail-closed、失败 migration rollback、并发 Up、Down 4 步回退到空 schema，以及 Up after Down。Down 只在独立测试 schema 中执行，未操作生产数据库。

## 4. Enqueue 事务语义

`PostgresQueue.Enqueue`：

1. 检查调用 context 和 Queue 本地关闭状态。
2. 使用当前时间和 Queue `MaxJobAge` 执行 `AgentJob.ValidateAt`。
3. 将 AgentJob 序列化为独立 JSON payload；调用方之后修改原对象不会改变数据库记录。
4. 在 PostgreSQL transaction 中插入 `job_queue`，使用 `ON CONFLICT DO NOTHING`。
5. 相同 tenant/job、相同 execution、相同 JSON payload 的重复 Enqueue 返回确定性的 accepted receipt，不生成第二行。
6. 相同 tenant/job 的不同 payload、或 execution identity 冲突返回 `ErrEnqueueConflict`。
7. 只有 transaction commit 成功后才返回 `QueueReceipt{Accepted:true}`。
8. 数据库或 commit 错误返回错误，不返回 accepted；commit 错误按 `ErrQueueOperationAmbiguous` 保留不确定结果分类，底层错误链仍可定位。

重复 payload 使用 JSON 语义比较，避免 PostgreSQL `jsonb` 规范化格式造成错误冲突。receipt ID 对同一 Job 稳定，不依赖进程内计数器。

## 5. Receive / Claim 事务语义

`Receive` 不依赖进程内 mutex 防止重复领取。每次 claim 使用一个数据库 transaction：

1. 将 `status='in_flight' AND leased_until <= clock_timestamp()` 的记录恢复为 `queued`，清空旧 token/lease，增加 `attempt`。
2. 使用 `status='queued' AND available_at <= clock_timestamp()` 条件，按可用时间排序并执行 `FOR UPDATE SKIP LOCKED LIMIT 1`。
3. 在同一 transaction 内生成新的 delivery token，条件更新为 `in_flight`，设置 `leased_until`，并增加 `delivery_count`。
4. 只有 claim transaction commit 成功后才返回 `Delivery`。
5. 返回的 Delivery 包含 JobEnvelope、恢复后的完整 AgentJob、当前 `Attempt`、`DeliveryID`、`ReceivedAt` 和 `VisibleUntil`。
6. 没有 ready Job 时按 bounded polling 等待，并尊重 context cancel/deadline；Queue Close 会在短 polling interval 内唤醒等待者。

同一 Job 的两个独立 pgx pool 并发 Receive acceptance 断言只有一个成功 delivery、一个 active token 和 `delivery_count=1`。数据库行锁和条件更新是跨连接的同步边界。

## 6. Ack 事务语义

Ack 在 transaction 内按 `(tenant_id, job_id)` 锁定 Queue 行，并重新验证：

- tenant；
- JobID；
- 当前状态为 `in_flight`；
- delivery token 等于当前 `delivery_id`；
- `leased_until > clock_timestamp()`。

成功 Ack 将状态提交为 `acked`，清除 active token/lease，保存 `last_delivery_id` 和 `acked_at`。相同 token 的重复 Ack 返回 nil；旧 token、错误 tenant、已 Nack、已过期或已完成 delivery 返回稳定拒绝错误。`RowsAffected()!=1` 不会被当作成功。

Queue Ack 没有与 P0-09A Execution Commit 组成跨资源事务，Commit/Ack 跨进程原子性仍 deferred。

## 7. Nack 事务语义

Nack 首先验证 `NackOptions`，再在 transaction 内锁行并重新验证当前 delivery holder 和 visibility：

- `Requeue=true`：状态回到 `queued`，`available_at` 持久化为当前时间加 `RetryAfter`，清除 token/lease，`attempt` 增加 1；
- `Requeue=false`：状态进入明确终态 `discarded`，不再 Receive；
- 旧 token 不能影响当前新 delivery；
- 数据库提交成功后才返回 nil；affected rows 为 0 不视为成功。

当前 Queue contract 没有 DLQ/permanent reason 读取接口，因此 Queue 不持久化 `NackOptions.Reason`。Worker 仍使用 R2 的安全稳定 reason 分类；Queue 不写入原始 `cause.Error()`、Prompt、Authorization、Provider body 或 URL query。Retry/DLQ 产品策略保持 deferred。

## 8. ExtendVisibility 和 Close

ExtendVisibility 在 transaction 内按 tenant、JobID、delivery token 和未过期条件更新 `leased_until`。只有当前 holder 可以延长，extension 必须为正且不超过 Queue 配置上限。Ack/Nack 与 ExtendVisibility 的竞争由同一行锁和状态条件决定。

`Close` 是 Queue 实例的本地生命周期操作：停止新的 Enqueue/Receive，并唤醒本地 polling；不关闭调用方拥有的 pgx pool，不删除数据库 Job，也不改变未完成 Job 的状态。Queue Close 后，另一个 Queue 实例仍可在 visibility 到期后接管该 Job。

## 9. Tenant Isolation 和安全证据

- Enqueue 的 tenant 来自已验证 `AgentJob.Tenant.TenantID`。
- Queue 主键和唯一约束均包含 tenant；相同 JobID/ExecutionID 可在不同 tenant 独立存在。
- Ack、Nack、ExtendVisibility 的 SQL 均带 tenant 和 Job 条件。
- 错误 tenant 的 delivery action 在真实 PostgreSQL 中无法读取目标行，原 owner 的 action 不受影响。
- payload 只保存 Job DTO；AgentRef 不包含 provider、secret 或 mutable runtime object。
- 测试输出只包含状态、计数、错误分类和 token 是否变化，不输出完整 payload、History 或凭据。

`TestPostgresQueueTenantIsolationForActionsAndSharedIDs` 真实验证了两个 tenant 使用相同 JobID/ExecutionID 时各自独立，并验证错误 tenant Ack 被拒绝。

## 10. Visibility Expiry 和 Crash Recovery 证据

真实 PostgreSQL acceptance 覆盖：

- visibility 到期后旧 in-flight 行恢复为 queued；
- 新 Queue client 获得新 delivery token 和递增 attempt；
- 旧 token 的 Ack/Nack/ExtendVisibility 全部被拒绝；
- 新 token 可以继续 Ack；
- Queue Close 不删除未完成 Job；
- 一个独立 pgx pool 领取 Job 后关闭连接，另一个 pgx pool 在 visibility 到期后成功接管；原始 Job body、History、Trace 和 tenant 信息保留。

这提供了数据库连接关闭和独立客户端 recovery 证据。没有执行真实 OS 进程 fork/kill 或生产 Worker 进程测试，因此不能把它外推为完整生产进程恢复、Worker SIGTERM 或 framework goroutine 退出证明。

## 11. Rollback、错误链和 Migration 证据

`TestPostgresQueueEnqueueDatabaseFailureDoesNotAccept` 在 isolated schema 中通过 PostgreSQL trigger 注入 INSERT 错误，验证：

- Enqueue 返回 `ErrQueueBackend`；
- `errors.As` 仍可取得 `*pgconn.PgError`；
- receipt 不 accepted；
- transaction rollback 后没有半持久化 Queue row。

migration acceptance 验证 broken version 的 DDL 和 metadata 不会半提交。所有 Queue action 的 commit error 都返回 error，不伪造成功 receipt 或 action nil。

## 15. Fake 与真实 PostgreSQL 证据边界

- **FakeQueue：** 快速验证现有 Job/DTO/visibility/Ack/Nack/Close contract，不证明持久化或跨连接 claim。
- **PostgreSQL Queue：** 真实数据库表、事务 claim、`SKIP LOCKED`、token fencing、expiry recovery、rollback、tenant isolation 和独立 pool/连接关闭 evidence。
- **Worker：** 本阶段只做既有 in-process Worker regression；没有把 Queue test 描述成 Worker 全链路生产证据。
- **Execution Repository：** P0-09A 独立 fenced result commit；Queue Ack 不参与同一事务。
- **跨进程：** 独立数据库连接/pgx pool证明数据库边界行为；没有 OS 进程级 crash、生产部署或服务入口证明。
