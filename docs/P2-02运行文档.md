# P2-02 运行文档：本地 PostgreSQL 逻辑备份/恢复与有界会话事件回放

本文档描述 P2-02 交付的离线恢复演练边界。它只覆盖**本地** PostgreSQL
logical backup/restore、有界 session-event replay/recovery drill 与
Compose 恢复门禁，不代表生产 DR、PITR/WAL 归档、云备份、跨 Region
恢复、生产切换、RPO/RTO 或任何 production rollout。

## 1. 范围与边界

- 权威计划对 P2-02 的最小映射：`备份恢复和事件回放`。
- 两个相互区分的子边界：
  - **A. PostgreSQL logical backup/restore**：`cmd/trpc-recovery`
    （backup/verify/restore/replay 子命令）；custom/data-only archive；
    schema 与 role/policy/function 由当前 release migrations 恢复，
    archive 永远不是可执行 schema 的替代来源。
  - **B. Session event replay**：只读既有 `session_event`；默认 dry-run
    （零写入、确定性 SHA-256 摘要）；唯一允许的可选修复是把偏低且其余
    全部合法的 `session.last_event_seq` 单调提升到已验证连续 max sequence。
- NOT INCLUDED（禁止外推）：
  `Production backup scheduling/retention/encryption/off-site replication:
  NOT IMPLEMENTED`；`Production PITR/WAL archiving: NOT IMPLEMENTED`；
  `Production restore cutover/failback and RPO/RTO: NOT PROVEN`；
  `Object Storage byte backup/restore: NOT INCLUDED`；
  `Secret Manager value backup/restore: NOT INCLUDED`；
  `Milvus index backup: NOT INCLUDED; rebuild only`；
  `Whole-system event sourcing/replay: NOT IMPLEMENTED`；
  `External side-effect replay/exactly-once: NOT PROVEN`。

## 2. 事实源矩阵（演练结论）

| 事实域 | 载体 | 进入 archive？ |
| --- | --- | --- |
| 业务/协调/发布/vector task+rebuild 事实（24 张 tenant 表） | PostgreSQL | 是（TABLE DATA only） |
| migration 目录 | `schema_migration`（owner-only） | 否（manifest 记录 version/name/checksum + digest） |
| 临时协调状态 | Redis | 否（fresh empty Redis 证明 PostgreSQL authority） |
| 派生向量索引 | Milvus | 否（由 PostgreSQL facts + P1-06E rebuild 重建） |
| Artifact bytes | Object Storage | 否（metadata 恢复，bytes 由 reconciliation 识别 missing/failed/expired） |
| Secret 明文 | SecretRef 之外的 Secret Manager / env | 否（SecretRef 恢复，value 需独立供给） |
| `session_event` 记录了什么 | 8 类事件、sequence/attempt/parent/payload | 是，但它**不是**完整生产事件日志 |
| `session_event` 没有记录什么 | tenant/binding/job/execution/outbox/configpub/Memory/Artifact bytes/外部发送结果 | 不能据此重建上述任何事实 |

## 3. 前置条件

- Docker daemon 与 `docker compose`；本轮在 Docker 29.7.2、Compose v5.5.0
  验证。
- 固定 tag+digest 基镜像：
  - `postgres:16-alpine@sha256:cf78e76683b9ca8c5733cbbdce6c9262b45b6767934dd0a95e671f9a0fc20685`
    （source/target/恢复工具客户端环境）
  - `redis:7-alpine@sha256:ff02b58f971e7d7d156a1267e283fcbbeee91773b6aa36c49dac28ecfe28eadf`
    （全新空 Redis；不从备份恢复）
  - `golang:1.26.3-alpine`（builder，与业务镜像一致）
- 宿主机 PATH 的 pg_dump/pg_restore **不要求**匹配；设置
  `P202_CLIENT_IMAGE`（tag+digest）即可让工具用钉定客户端包裹执行。

## 4. 构建镜像

```bash
docker build -f Dockerfile -t p109-deploy-app:local .
docker build -f Dockerfile.recovery -t p202-recovery-tool:local .
```

`p202-recovery-tool:local` 运行时层 = 钉定的 `postgres:16-alpine@digest`
+ `trpc-recovery`、`trpc-migrate`、`/app/migrations` 与 wrapper 脚本；
**不进入**业务运行镜像，也不进入任何启动/readiness 路径。

## 5. Secret 与 env

```bash
RUN_ID=p202-recovery-$(date +%s)
mkdir -m 700 -p /tmp/$RUN/secrets
printf '%s' '<local-owner-password>'     > /tmp/$RUN/secrets/p202_pg_password
printf '%s' '<local-runtime-password>'   > /tmp/$RUN/secrets/p202_pg_runtime_password
chmod 600 /tmp/$RUN/secrets/*
cat > /tmp/$RUN/env <<ENV
P202_RUN_ID=$RUN
P202_SECRET_DIR=/tmp/$RUN/secrets
P109_RUN_ID=p202-gate
P109_SECRET_DIR=/tmp/$RUN/secrets
P109_APP_IMAGE=p109-deploy-app:local
P202_APP_PORT=18082
ENV
```

- 密码只经 Docker secret（`/run/secrets/p202_pg_password`、
  `/run/secrets/p202_pg_runtime_password`）进入容器；wrapper 在容器内
  组装 DSN 进环境变量（从不出现在 argv/日志/manifest）。
- 工具进程内密码只落地为 0600 `PGPASSFILE`（0700 临时目录），退出即删。
- 环境变量：`P202_SOURCE_URL`、`P202_TARGET_URL`、
  `P202_REPLAY_RUNTIME_URL`、`P202_OUTPUT_DIR`、`P202_BACKUP_DIR`、
  `P202_MIGRATIONS_DIR`、`P202_TIMEOUT`（默认 30m，1s..2h）、
  `P202_ALLOW_REPAIR=yes`（repair 门槛）、`P202_CLIENT_IMAGE`。

## 6. Compose 恢复演练（默认关闭的 recovery profile）

```bash
export P202_RUN_ID=<run-id> P202_SECRET_DIR=<0700 dir> \
       P109_RUN_ID=p202-gate P109_SECRET_DIR=<same dir> P109_APP_IMAGE=p109-deploy-app:local

# 0) 启动隔离 source/target/全新空 Redis（均为 recovery profile，默认不启动）
docker compose --profile recovery up -d recovery-source recovery-target recovery-redis

# 1) source schema 初始化 + runtime 角色供给（trpc-migrate, 版本 1..11）
docker compose run --rm recovery-migrate migrate-source

# 2) operator 以 owner 身份播种代表性事实（psql, 占位数据）
docker compose exec -T recovery-source psql -U trpc_app -d trpc_agent < seed.sql

# 3) 备份：一致性快照（pg_export_snapshot）+ data-only custom archive + manifest + COMPLETED 标记
docker compose run --rm recovery-tool backup
#    → stdout JSON: {"backup_dir":"/backups/p202-backup-...","archive_sha256":...,"rows_total":N}

# 4) 校验：marker/manifest/0600/SHA-256/TOC 审计（仅 TABLE DATA×24）
docker compose run --rm -e P202_BACKUP_DIR=/backups/<backup-dir> recovery-tool verify

# 5) target 初始化（migrations + runtime 角色）——restore 自身也会先跑 migration gate
docker compose run --rm recovery-migrate migrate

# 6) 恢复：单事务、exit-on-error、不禁用 constraint/trigger；目标必须为空业务表
docker compose run --rm -e P202_BACKUP_DIR=/backups/<backup-dir> recovery-tool restore

# 7) 有界回放（dry-run 默认；repair 需 P202_ALLOW_REPAIR=yes 且仅限隔离目标）
docker compose run --rm recovery-tool replay
docker compose run --rm -e P202_ALLOW_REPAIR=yes recovery-tool replay --mode repair

# 8) 以目标 runtime 角色启动真实服务（recovery-app → recovery-target + 空 Redis）
docker compose --profile recovery up -d recovery-app
#    /healthz 200、/livez 200（loopback 18082）；不执行生产切换

# 9) 清理（owner-scoped）
docker compose --profile recovery down -v --timeout 20
```

## 7. 直接使用二进制

`trpc-recovery backup|verify|restore|replay` 亦可在宿主机直接运行；
`pg_dump/pg_restore` 从 PATH 取（须与服务器 major 匹配），或设
`P202_CLIENT_IMAGE=postgres:16-alpine@sha256:<digest>` 由工具以
`docker run --network host --user <uid>:<gid>` 包裹执行。退出码：

```
0 成功; 2 invalid_config; 3 dependency_unavailable; 4 integrity_mismatch;
5 forbidden_state; 6 replay_integrity_violation; 7 restore_failed;
8 backup_failed; 9 timeout_or_cancelled
```

stderr 只输出 `recovery failed category=<category>` 一行；stdout 只输出
非敏感 JSON（计数、digest、路径）。

## 8. Replay 语义

- 读取：`(tenant_id, session_id, sequence)` 稳定顺序、keyset 分页、
  有界 batch；租户枚举仅由 recovery owner 完成，逐租户经 runtime 角色
  的 P2-01 tenant 事务执行；tenant 值只进摘要哈希，从不落日志。
- 校验类别（全部 fail-closed，不修改任何行）：
  `sequence_gap`、`event_type_unknown`、`payload_invalid`、
  `payload_decode_failed`、`field_invalid`、`identity_mismatch`、
  `parent_missing`、`parent_future`、`event_id_duplicate`、
  `watermark_high`、`watermark_low`、`session_event_limit`。
- 摘要：每事件一行规范内容进 SHA-256 链（session→tenant→全局），重复
  执行结果一致；dry-run 数据库零变化。
- repair：仅当事件从 1 连续、全部合法且 `last_event_seq < max` 时，以
  CAS（`AND last_event_seq = 旧值 AND last_event_seq < max`）单调提升；
  watermark 偏高 fail closed，绝不降低；幂等可重跑；cancel 即回滚。

## 9. 恢复状态机与失败处理

```
verify OK → target preflight（特权角色≠trpc_runtime / major 一致 / ≠source）
          → migration gate（1..11 与 manifest 完全一致）
          → catalog/schema fingerprint/空业务表检查
          → pg_restore --data-only --single-transaction --exit-on-error
          → 事实审计（counts/约束/FK/RLS/definer/runtime probes/migration 目录不变）
          → ready（不切换流量）
任一步失败 → 目标保持"仅 migrations、业务表为空"，可清理后重试
```

拒绝清单（稳定类别 `forbidden_state`/`integrity_mismatch`）：原地覆盖
source、source==target、非空业务目标、migration 版本/名称/checksum 不
一致、未知 future migration、PG major 不一致、archive/manifest 损坏或缺
COMPLETED、TOC 含非 TABLE DATA/未知对象、schema/表集合漂移、非特权或
runtime 恢复角色。

## 10. 清理

无论 PASS/FAIL/timeout/cancel：`docker compose --profile recovery down -v`
移除本轮 source/target/redis 容器、网络、卷与备份卷；工具镜像按需保留或
`docker rmi p202-recovery-tool:local`；PGPASSFILE 由工具退出即删；备份
产物属验收材料，验收后删除。禁止 prune 或触碰历史资源。
