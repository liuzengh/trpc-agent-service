## 4. Dispatcher 接口和生命周期

Dispatcher 构造器为：

```go
func NewDispatcher(
    repository storage.OutboxRepository,
    sender Sender,
    config Config,
) (*Dispatcher, error)
```

Sender 接口为：

```go
type Sender interface {
    Send(context.Context, storage.OutboxMessage) SenderOutcome
}
```

`Config` 要求稳定的 `OwnerID` 和一个或多个已验证的 tenant context。Claim batch size、并发数、claim interval、shutdown timeout 和 lock guard 都有配置上限；默认值也是有界的。Dispatcher 不使用进程内 mutex 代替数据库 claim，进程内状态只用于控制生命周期、并发容量、计数和诊断。

`Run(ctx)` 按 tenant context 调用 Repository `ClaimBatch`。Repository 返回的消息必须是当前 owner、processing 状态、有 lock expiry、attempt 为正；只有 ClaimBatch 完成后才启动 Sender。每条消息单独处理，单条 mutation 失败不污染同 batch 的其它消息。

发送截止时间为 `LockedUntil - LockGuard`。Dispatcher 没有为 P0-09D 增加 lock renewal 接口；发送超过该边界时不伪造完成。成功、retry、DLQ mutation 都使用当前 owner，并通过 Repository 的 durable fencing 条件完成。

`Stop(ctx)` 先设置 stopping、取消 Run 的 claim context、等待 Run 退出，再等待 active work 到配置 deadline。Stop 后不会发起新的 claim 或 Sender 调用。active Sender 在 deadline 前返回时，Dispatcher 可以按 outcome 继续执行当前 durable mutation；deadline 已到或 Sender 不合作时，Dispatcher 返回 `ErrShutdownTimeout`，并且后续迟到的 Sender 返回不会产生新的 durable 状态变化。Run 在 Stop 驱动的退出路径以 `context.Canceled` 结束。

## 5. RetryPolicy 规则和边界

`RetryPolicy.Decide(attempt, outcome, now)` 是无副作用、由调用方提供当前时间的纯策略：

- Delivered：返回 `Complete`，不生成 next attempt。
- RetryableFailure：attempt 小于 `MaxAttempts` 时返回 `Retry`；否则返回 `DeadLetter`。
- PermanentFailure：始终返回 `DeadLetter`。
- OutcomeUnknown：默认按 at-least-once 的有限 retry 处理；attempt 小于上限时返回 `Retry`，达到上限后返回 `DeadLetter`。
- 退避是有界指数退避，超过 `MaxDelay` 时固定为 `MaxDelay`。
- `MaxAttempts` 为 1 到 100；`MaxDelay` 不超过 24 小时；负 duration、反向 delay、零 attempt、零 clock 和时间溢出均返回 `ErrInvalidPolicy`。

attempt 语义与 P0-09D Repository 一致：初次 claim 是 attempt 1，`MarkRetry` 或 expired processing reclaim 按现有 Repository 语义推进 attempt。P0-09E 没有引入 provider-specific retry heuristic，也没有使用进程内计数作为 retry 事实源。

## 6. Sender 四类 outcome 和安全 code

- `Delivered`：Sender 明确确认远端已交付，Dispatcher 才选择 `MarkCompleted`。
- `RetryableFailure(code)`：Sender 明确知道本次未交付且可再次尝试，Dispatcher 选择 `MarkRetry`。
- `PermanentFailure(code)`：Sender 明确知道本次未交付且不应继续尝试，Dispatcher 选择 `MoveToDLQ`。
- `OutcomeUnknown(code)`：Sender 无法判断远端是否已经接受，Dispatcher 既不 `MarkCompleted`，也不直接 `MoveToDLQ`。

分类会归一到有限稳定 code：`sender_unavailable`、`sender_timeout`、`sender_rate_limited`、`sender_invalid_payload`、`sender_rejected`、`delivery_outcome_unknown`、`repository_lock_lost`、`repository_unavailable` 等。任意外部错误文本只用于 Sender 自己分类，不能作为 durable `last_error` 或 DLQ reason。

## 7. Unknown durable policy

本阶段默认选择有限 at-least-once retry：第一次未知结果持久化 `delivery_outcome_unknown`，设置由 RetryPolicy 计算的 next attempt，释放当前 processing lock；到达最大 attempt 后才进入已有原子 DLQ transition。未知结果绝不直接表示“已发送”，也不被简单当作永久失败。

这种策略承认可能重复投递。真实 Sender 必须在后续阶段提供 provider message key、dedup 或幂等能力；没有这些能力时，unknown retry 可能重复触达。这个限制已写入本报告和背景文档。

## 8. Complete/Retry/DLQ 调用映射

处理顺序固定为：

```text
ClaimBatch
  -> Sender.Send
  -> ClassifyOutcome / safe code
  -> RetryPolicy.Decide
  -> MarkCompleted / MarkRetry / MoveToDLQ
  -> 记录 mutation 成功或稳定失败分类
```

只有 Repository mutation 返回成功，Dispatcher 才增加 `Completed`、`Retried` 或 `DeadLettered` 计数。`MarkCompleted` 失败不会被报告为发送成功；repository backend unavailable、transaction outcome unknown、stale owner 和 expired lock 都保留在明确的 mutation error/lock-lost 计数中。下一次 durable reclaim 仍由 PostgreSQL Outbox 状态决定。

## 9. 并发、fencing 和 recovery 证据

- Fake Dispatcher competing test 与真实 PostgreSQL 两个独立 pool test 均证明同一条 pending message 只有一个 active Sender owner。
- 真实 PostgreSQL expired-lock test 先用数据库时间使 processing lock 过期，再由新 owner reclaim；旧 owner 的 completion 被拒绝。
- overlap test 让旧 owner 的 Sender 保持阻塞，数据库过期后新 owner reclaim 并保持 Sender barrier；旧 owner 先执行 mutation，得到 `ErrOutboxLockLost`，新 owner 随后成功完成。旧 owner 的 `Completed` 计数保持 0。
- batch 中一条 permanent failure 进入 DLQ，不影响另一条 Delivered 消息完成。
- Docker recovery test 使用现有隔离 `DockerLab` 创建的本轮资源：PostgreSQL stop/restart 后重建 endpoint 和 pool，expired processing 被新 Dispatcher reclaim 并完成。

Docker restart 只证明隔离 PostgreSQL service stop/restart 和 Outbox repository recovery，不证明完整 OS crash、生产集群故障、进程 kill、SIGTERM 或 framework global Wait/Done。

## 10. Shutdown 证据和非合作 Sender 边界

Fake tests 使用 channel barrier、active work channel、claim/send counters 和 context cancellation；没有使用固定几十毫秒 sleep 作为并发或 lease 证据。cooperative sender 在 Stop deadline 内结束后按 unknown policy 进入 retry；Stop 后 claim/send counters 不再增加。

非合作 Sender 测试让 Sender 忽略 context 并阻塞。Stop 在 `ShutdownTimeout` 到达时返回 `ErrShutdownTimeout`，并记录 bounded shutdown 边界；它不能强制终止外部调用，也不等待不可控 Sender 无限期退出。Sender 之后释放并返回时，Dispatcher 检查 shutdown deadline，不再调用 durable mutation。该测试不声称外部 Sender 已被终止。

P0-09E 只提供可构造 Dispatcher 和 Sender interface。没有 SIGTERM 到整个生产进程的装配，也没有 tRPC-Agent-Go framework 私有 channel、私有字段或内部 global Wait/Done。

## 11. 安全和事实源边界

安全 failure code 在 Dispatcher 分类和 P0-09D PostgreSQL Repository 两侧均受限制。测试确认包含 authorization、token、provider body、完整 URL query 等敏感文本的 Sender code 不会进入 durable `last_error`。Dispatcher 内存诊断只保留分类和计数；报告不输出测试数据库连接值。

PostgreSQL 是 Outbox durable 状态事实源。Redis 不是 Outbox 事实源，本阶段没有把 payload、retry 或 DLQ 状态写入 Redis。P0-09A/B/C 的生产逻辑没有改变；Atomic Completion 也没有在本阶段接线到 Outbox。
