# 数据同步与幂等策略

## 可靠消息处理

1. Gateway 先验证通道请求并解析租户、绑定、用户和平台消息标识。
2. Inbox 以 `(tenant_id, binding_id, platform_message_id)` 唯一键写入。重复消息返回成功 ACK，
   不创建第二次执行。
3. Worker 通过 MySQL 租约领取可处理消息；fencing token 防止旧 Worker 在失去租约后提交。
4. Worker 在一个事务内写入会话事件、状态、执行结果、审计和 Reply Outbox。
5. Delivery 独立领取 Reply Outbox，向 IM 发送并记录尝试结果。

这种 Inbox → Worker → Outbox 结构将“已接收”“已执行”“已投递”分为可恢复的状态，避免
IM 回调超时或进程退出造成消息丢失。

## 会话一致性

同一会话需要按顺序执行。可靠模式使用租约、会话版本和 fence 保护提交；Gateway 可使用 Redis
协调锁减少并发竞争。Redis Session 投影是最终一致读模型，版本只能单调增加，不能覆盖 MySQL
中更新的会话状态。

## Memory、摘要与知识库

- 会话事件和状态提交后，摘要任务按覆盖序号异步生成；摘要不能覆盖更高版本的状态。
- Memory 与知识库先在 MySQL 记录事实状态，再通过任务写入 Qdrant；向量索引失败时条目不会标记为可用。
- Artifact 先写对象存储，再在 MySQL 保存元数据和关联关系。

## 迁移与重建

`-migrate-sessions` 支持将 legacy Redis 会话迁移到 MySQL，可用 `-dry-run` 预览；迁移按会话和
事件标识幂等，可重复运行。`-reindex-kb` 将指定知识库的已就绪文档重新放入索引任务，用于更换
embedding 模型或向量库后的重建。

## 一致性取舍

| 数据 | 策略 |
| --- | --- |
| Inbox、Session、Execution、Outbox | MySQL 事务强一致。 |
| Redis 会话投影 | 最终一致，可由 MySQL 重建。 |
| Qdrant 向量索引 | 最终一致，状态机避免未完成索引参与检索。 |
| IM 投递 | 至少一次尝试；使用 Outbox、条件更新和平台消息标识降低重复。 |
