## 1. 多节点并发写入同一 Session 的一致性

**问题**：多个 Worker 节点可能同时处理同一 Session 的消息（例如 IM 重投导致同一消息被两次消费，或群聊中多条消息同时到达）。

**实现方案**：

1. **Redis 分布式锁**：`lock:session:{tenant}:{session}`（30s TTL），Worker 在 `handle()` 中获取锁后才能执行 `run()`。
2. **Lua CAS 解锁**：`UnlockSession(lockToken)` 使用 Lua 脚本比较 token 后删除，防止误删其他 Worker 的锁。
3. **自动续期**：在审批等待等长时操作中，`RefreshLock(lockToken)` 定期续期。
4. **Session 后端原子性**：
   - **Redis**：Lua 脚本保证 event append + state update 原子性
   - **MySQL**：事务保证 event insert + state update 一致性（`SELECT ... FOR UPDATE`）
   - **InMemory**：互斥锁（仅单节点场景）

**结论**：通过 Redis 锁序列化 + 后端原子操作，保证同一 Session 的并发写入安全。

## 2. Session Event / State / Summary 更新顺序

由 tRPC-Agent-Go 框架 `session.Service` 内部管理，平台层不直接操作。框架保证：

1. **Event 先落**：每条消息（user/assistant/tool）以单调递增 `seq` 写入
2. **State 更新**：Session 状态（如 `last_message_at`、`turn_count`）在 Event 写入后更新
3. **Summary 增量**：当 Event 数量超过窗口阈值时，框架按 `seq` 水位增量生成 Summary

平台层通过 `Router.Sessions(tenantID)` 获取正确后端的 `session.Service` 实例，传入 Runner 即可。

## 3. Memory 写入后的跨节点可见性

**实现方案**：

- **Redis 后端**：Memory 写入 Redis（原子 Lua），所有 Worker 节点立即可见
- **MySQL 后端**：Memory 写入 MySQL 事务提交后，其他节点通过 `Router.Memories(tenantID)` 读取
- **InMemory 后端**：仅单节点可见（适用于开发/测试）

**关键点**：`storage.Router` 按 `backendID` 缓存后端实例，同一租户的所有 Worker 节点共享同一后端实例，保证可见性。

## 4. 跨后端数据迁移方案

### 4.1 Session / Memory 迁移

**工具**：`cmd/migrate` CLI

**流程**：

1. 读取源后端 Session/Memory 数据
2. 转换为目标后端格式
3. 幂等写入目标后端（delete-then-create）

**限制**：

- 框架 v1.11.2 无 Event 分页 API，仅迁移最近窗口
- Summary 和 Tracks 不迁移（由框架在目标端重建）

### 4.2 向量库迁移

**方案**：离线重建

1. 从 MinIO 或原始数据源重新抽取文档
2. 使用相同 embedding 模型重新向量化
3. 写入新 Milvus 实例

### 4.3 对象存储迁移

**方案**：整体搬迁

1. MinIO 支持跨实例复制（`mc mirror`）
2. 对象键布局不变（`{tenant}/{user}/{session}/{filename}/{revision}`）

### 4.4 租户级后端切换

**流程**：

1. 更新 `Tenant.DataBackend` JSON（如 `{"session":"mysql"}` → `{"session":"redis"}`）
2. `tenant.Manager.Update()` 自动快照到 `tenant_config_versions`
3. 下次请求时，`Router.Sessions()` 自动解析新后端
4. 旧数据仍保留在原后端（需手动迁移或清理）

## 5. IM 消息重复投递的幂等处理

### 5.1 三层幂等保障

| 层级 | 机制 | 说明 |
|---|---|---|
| **Gateway** | Redis SETNX `idem:{channel}:{platformMsgID}` | 24h TTL，快速拦截重复消息 |
| **Worker** | `Idempotent(msgKey)` 检查 | 消费时再次校验（Redis + Outbox 双重检查） |
| **Outbox** | MySQL `idempotency_keys` UNIQUE 约束 | `Append()` 事务中插入，重复返回 `ErrDuplicateIdem` |

### 5.2 去重流程

```
Gateway.pumpInbound()
  → msgKey = "channel:platformMsgID"
  → Redis SETNX idem:{msgKey} EX 86400
  → 成功 → PublishInbound()
  → 失败 → 忽略（已处理）

Worker.handle()
  → Idempotent(msgKey) 再次检查
  → 成功 → 处理消息
  → 失败 → 确认消费（不重投）

Outbox.Append()
  → BEGIN
  → INSERT idempotency_keys (msg_key)
  → INSERT outbox_events (payload)
  → COMMIT
  → 冲突 → ErrDuplicateIdem → 忽略
```

### 5.3 DLQ 重放去重

DLQ 重放时，`ClearIdem(msgKey)` 释放幂等键，然后重新 `PublishInbound()`。如果重放成功，新的 `idem` 键会阻止重复处理；如果再次失败，重新进入 DLQ（append-only，新行）。

## 6. 不同后端的一致性取舍

| 后端 | 一致性模型 | 读写延迟 | 成本 | 运维复杂度 | 适用场景 |
|---|---|---|---|---|---|
| **MySQL** | 强一致（ACID 事务） | 中等（~10ms） | 中 | 中（主从复制、备份） | 审计日志、用量计量、配置管理、DLQ |
| **Redis** | 最终一致（单线程模型） | 极低（~1ms） | 中 | 低（持久化可选） | Session 热数据、消息总线、分布式锁、幂等键 |
| **Milvus** | 最终一致 | 中等（~50ms） | 高 | 高（etcd + MinIO 依赖） | 知识库向量检索 |
| **MinIO** | 强一致（S3 语义） | 中等（~20ms） | 低 | 低 | 制品文件、大对象存储 |
| **InMemory** | 强一致（进程内） | 极低（<1ms） | 零 | 零 | 开发/测试、单节点演示 |

**平台策略**：

- **审计日志**：MySQL 为默认生产后端（强一致、合规）；InMemory 为开发/测试后端（零依赖）
- **Session/Memory**：租户级可选，Redis 适合高并发低延迟，MySQL 适合强一致要求
- **Vector/Artifact**：全局单后端（Milvus/MinIO），InMemory 为降级选项
- **Usage 计量**：`RecordUsage()` 始终路由到 MySQL（全局预算控制），不受租户 audit 后端选择影响
