## 1. 多节点并发写入同一 Session 的一致性

**问题**：多个 Worker 节点可能同时处理同一 Session 的消息（例如 IM 重投导致同一消息被两次消费，或群聊中多条消息同时到达）。

**实现方案**：

1. **Redis 分布式锁**：`lock:session:{tenant}:{session}`（30s TTL），Worker 在 `handle()` 中获取锁后才能执行 `run()`。
2. **Lua CAS 解锁**：`UnlockSession(lockToken)` 用 Lua 比较 token 后删除，防止因 TTL 过期而误删他人的锁。
3. **单 ticker 续期**：一次回合最长 `runTimeout=300s`，审批等待再叠加 5 分钟，而锁 TTL 只有 30s、
   幂等租约 90s。`startTurnHeartbeat` 用**一个** ticker（按较快者取间隔）同时续锁与租约，
   并在丢失锁时告警——两个独立定时器会漂移，曾经正是 TTL 与回合时长失配导致"回合中途锁失效"。
4. **会话内串行、会话间并行**：同一会话的消息被锁串行化；不同会话由 `consumeWorkers`（默认 16）并发处理。
5. **Session 后端原子性由框架保证**：平台不直接操作存储。
   框架 MySQL 后端在状态/清理路径上使用事务与 `SELECT ... FOR UPDATE`；
   Redis 后端使用 Lua/单命令；InMemory 用互斥锁（仅单节点场景）。

**结论**：Redis 锁序列化 + 幂等三层兜底 + 后端自身原子性，三者叠加保证同一 Session 的并发写入安全。
即使锁因故障失效（节点被 kill -9），幂等键仍能保证"只回复一次"，只是可能多花一次模型调用。

## 2. Session Event / State / Summary 更新顺序

由 tRPC-Agent-Go 框架 `session.Service` 内部管理，平台层不直接操作存储，只负责**选后端**与**注入 Runner**：

1. **Event 落库**：每条消息（user/assistant/tool）与部分事件按会话顺序写入；每条事件携带
   `RequestID`——平台把入站消息 id 作为 `RunOptions.RequestID`，因此"这一次请求产生了哪些事件"
   在存储里是可查的（幂等第 ⑤ 层就靠它）；
2. **State 更新**：App/User/Session 三级 state 由框架随事件更新；
3. **Summary**：由框架的会话摘要机制维护（`session_summaries` 表），平台不提供独立摘要域/API；
4. **附件外置**：平台在会话服务外面套了框架的 `session/externalization`，
   在事件落库**之前**把内联图片/音频/文件字节存进制品库，事件里只留 `artifact://名字@版本`
   （带 sha256 与大小），读取时回填——否则一张用户图片就会以 base64 形式永久留在
   `session_events` 这类热表里。

平台层通过 `Router.Sessions(tenantID)` 获取正确后端的 `session.Service`（已带 span 装饰器）传入 Runner。

## 3. Memory 写入后的跨节点可见性

**写入路径（工具驱动，无自动抽取）**：平台把框架 `memory.Service.Tools()` 挂进该轮工具集，由模型显式调用 `memory_add / memory_update / memory_search / memory_load` 写入与检索；平台**未配置 Extractor**，因此不存在"后台自动提取记忆"的异步写路径。读路径是 `runner.WithMemoryService` + `llmagent.WithPreloadMemory(N)`：每轮按 `memory.preload_count` 预算把该 `<tenant, user>` 的记忆注入系统提示词。

**实现方案**：

- **Redis 后端**：Memory 写入 Redis（原子 Lua），所有 Worker 节点立即可见
- **MySQL 后端**：Memory 写入 MySQL 事务提交后，其他节点通过 `Router.Memories(tenantID)` 读取
- **InMemory 后端**：仅单节点可见（适用于开发/测试）

**关键点**：

1. `storage.Router` 按 `backendID` 缓存后端实例，同一租户的所有 Worker 节点共享同一后端实例，保证可见性；
2. 记忆隔离维度是框架的 `<AppName, userID>`，平台把 `AppName` 固定为 `tenant_id`（`runner.NewRunner(m.TenantID, ...)`），`UserID` 为消息触发者；跨租户不可见由 AppName 保证；
3. 后端不可用（Redis/MySQL 未就绪）时该轮**降级为无长期记忆**并告警，不影响会话上下文与回复（可用性优先）；
4. 摘要（Summary）不是独立域：它随框架 session 存储（即租户的 `session` 后端）维护，`tenants.data_backend` 中没有 `summary` 键。

## 4. 跨后端数据迁移方案

### 4.1 Session / Memory 迁移

**工具**：`cmd/migrate` CLI

**流程**：

1. 读取源后端 Session/Memory 数据
2. 转换为目标后端格式
3. 幂等写入目标后端（delete-then-create）

**限制**：

- 框架 v1.11.2 无 Event 分页 API，仅迁移最近窗口
- Summary 和 Tracks 不迁移（由框架在目标端重建）

### 4.2 向量库迁移

**方案**：离线重建

1. 从 MinIO 或原始数据源重新抽取文档
2. 使用相同 embedding 模型重新向量化
3. 写入新 Milvus 实例

### 4.3 对象存储迁移

**方案**：整体搬迁

1. MinIO 支持跨实例复制（`mc mirror`）
2. 对象键布局不变（`{tenant}/{user}/{session}/{filename}/{revision}`）

### 4.4 租户级后端切换

**流程**：

1. 更新 `Tenant.DataBackend` JSON（如 `{"session":"mysql"}` → `{"session":"redis"}`）
2. `tenant.Manager.Update()` 自动快照到 `tenant_config_versions`
3. 下次请求时，`Router.Sessions()` 自动解析新后端
4. 旧数据仍保留在原后端（需手动迁移或清理）

## 5. IM 消息重复投递的幂等处理

重复投递在这个平台上是**常态**而非异常：企业微信 AI-bot 在回调未及时 ack 时会重推，
Redis 的 `XAUTOCLAIM` 会把死消费者留下的 pending 消息交给别的节点，
Worker 崩溃后租约到期也会重投。因此幂等不是"加一层 SETNX"，而是**五层各管一段**：

| 层 | 机制 | 位置 | 管什么 |
| --- | --- | --- | --- |
| ① 消息标识 | `Message.ID = channel:platformMsgID` | `channels/gateway.pumpInbound` | 让同一条平台消息在任何地方都有**同一个**幂等键 |
| ② 适配器内存去重 | `Seen(platformMsgID)` | `channels/base_adapter.Run` | 进程内重推的第一道拦截（成本最低） |
| ③ Redis 两阶段租约 | `Idempotent`(**三态**：认领成功 / 进行中 / 已完成, 租约 90s) → `CommitIdem`(24h) / `ClearIdem` / `ExpireIdemLease` | `worker.handle` + `bus` | 跨节点互斥 + "崩溃不吞消息"（见下） |
| ④ MySQL 唯一键 | `idempotency_keys.msg_key` UNIQUE，与 outbox 事件**同事务** | `bus.Outbox.Append` | 最终一致的"已处理"凭证；重复 Append 返回 `ErrDuplicateIdem` |
| ⑤ 事件级幂等 | `runner.Run(RequestID = msgID)` + `resumeRecordedTurn` | `worker.run` / `worker/resume.go` | 重放时**复用已产出的回复**，不再二次调用模型 |

**两阶段租约（③）为什么不是一次 SETNX 到底**：如果只 SETNX 24h，进程在回合中途崩掉，
这条消息就永远被"标记为已处理"而实际上没人回复——用户看到的是"消息已读不回"。
所以第一次只拿 **90s 租约**（工作期间由心跳续期），只有 **outbox 事务提交成功后**才
`CommitIdem` 成 24h 的持久标记；失败路径显式 `ClearIdem` 让重投能重新处理。

**为什么必须区分「进行中」和「已完成」**（阶段 45 故障演练暴露的真实缺陷）：
`Idempotent` 早期只返回布尔值，于是这两种情况看起来一样。节点被 SIGKILL 时它的在途消息
留在 PEL，30s 后 `XAUTOCLAIM` 把它们交给存活节点，而**死者的 90s 租约仍然有效**——
存活节点读到"标记存在"，当成"已经处理过"直接 ack，`lag=0`、`pending=0`、`/healthz` 200，
**消息却凭空消失了**（演练实测丢 3/20）。现在 `Idempotent` 返回三态：

| 状态 | 含义 | Worker 动作 |
| --- | --- | --- |
| `IdemClaimed` | 本次抢到租约 | 正常处理 |
| `IdemInFlight` | 别的尝试持有租约（并发重投，或刚崩的节点租约未到期） | **`ErrRequeue`，绝不 ack**：对方提交了 → 下次看到「已完成」再 ack；对方死了 → 租约到期后下次真正执行 |
| `IdemCompleted` | 已完成（24h 标记） | ack 丢弃（并记一条 `delivery already completed` 日志，便于与"处理过"区分） |

代价与边界（如实）：崩溃节点的在途消息**恢复延迟 = 幂等租约（90s）+ 一次认领窗口（30s）**，
上限约 2 分钟；这段时间消息一直 pending、不丢。回归测试：
`TestBusIdempotencyDistinguishesLeaseFromCompletion`、
`TestWorkerLeavesAnInFlightMessagePending`，演练脚本 `scripts/faults/node-failure.ps1`。

### 5.1 三条路径的实际行为

```
正常：
  Worker: Idempotent(msgID)=认领成功（租约 90s，心跳续期）
        → run() → Outbox.Append(reply, msgID)   ← 事务：idempotency_keys + outbox_events
        → CommitIdem(msgID)（24h）→ ack

平台重推（消息已处理过）：
  Adapter.Seen(platformMsgID) 命中 → 直接丢（进程内）
  未命中（重启/别的节点）→ PublishInbound(同一 ID) → Worker: Idempotent=已完成 → ack 丢弃

回合中途崩溃：
  消息留在 PEL → 30s 后 XAUTOCLAIM → 重投
  Worker: Idempotent=进行中（死者租约未到期）→ ErrRequeue（保持 pending，不丢）
  租约到期后再认领：Idempotent=认领成功
    → resumeRecordedTurn：查本 RequestID 是否已产出回复
       有 → 复用回复，不再调用模型
       无 → 正常重跑
    → Outbox.Append：唯一键冲突（此前已成功写过）→ 视为已处理 → ack
```

### 5.2 锁竞争为什么不进死信

会话锁被占用时 `handle` 返回 `bus.ErrRequeue`，消息**留在 pending 等下一次
XAUTOCLAIM，且不计入失败次数**。否则一个繁忙会话（用户连着发几条）就会把健康消息
推到 5 次阈值、进 DLQ。这条规则是阶段 44 修的：当时 `XAUTOCLAIM` 的重复投递被当成
业务失败计数，造成"越忙越容易丢消息"。

### 5.3 DLQ 重放去重

`POST /dlq/{id}/replay` 先 `ClearIdem(原 msgKey)` 释放幂等占用，再
`PublishInbound(原信封)`；重放成功则新的幂等键阻止再次处理，再次失败则重新入 DLQ
（append-only，新行，`replayed_at` 防重复重放）。

## 6. 不同后端的一致性取舍

| 后端 | 一致性模型 | 读写延迟 | 成本 | 运维复杂度 | 适用场景 |
|---|---|---|---|---|---|
| **MySQL** | 强一致（ACID 事务） | 中等（~10ms） | 中 | 中（主从复制、备份） | 审计日志、用量计量、配置管理、DLQ |
| **Redis** | 最终一致（单线程模型） | 极低（~1ms） | 中 | 低（持久化可选） | Session 热数据、消息总线、分布式锁、幂等键 |
| **Milvus** | 最终一致 | 中等（~50ms） | 高 | 高（etcd + MinIO 依赖） | 知识库向量检索 |
| **MinIO** | 强一致（S3 语义） | 中等（~20ms） | 低 | 低 | 制品文件、大对象存储 |
| **InMemory** | 强一致（进程内） | 极低（<1ms） | 零 | 零 | 开发/测试、单节点演示 |

**平台策略**：

- **审计日志**：MySQL 为默认生产后端（强一致、合规）；InMemory 为开发/测试后端（零依赖）
- **Session/Memory**：租户级可选，Redis 适合高并发低延迟，MySQL 适合强一致要求
- **Vector/Artifact**：租户级可选（Milvus / MinIO 为默认，InMemory 为降级选项）
- **Usage 计量**：`RecordUsage()` **不按租户路由**，只要有 MySQL 就走 MySQL——
  用量需要跨租户汇总来做预算判断，落到某个租户私有的内存后端会让预算失真；
  无 MySQL 时（dev/test）回落内存实现。写入是幂等的 `INSERT IGNORE`，
  键 = `sha256(msgID:dimension)` 前缀（36 列长度约束下的碰撞安全做法）
- **Outbox / DLQ / 配置 / 密钥**：始终 MySQL（它们是可靠性与合规底座，不允许按租户漂移到内存）

## 7. Outbox 状态机与出站可靠性

回复**不直接写 Redis**，而是先落 MySQL 的 outbox 事件（与幂等键同事务），再由 dispatcher 发到
`stream:outbound`。原因：Redis Streams 的写入不在 MySQL 事务里——若先发 Redis 再写幂等键，
进程在两行之间崩溃就会出现"回复已发出但消息被判定未处理"，重投后再发一次；反过来则可能
"标记已处理但回复丢失"。Outbox 把"回复已产出"和"消息已处理"绑成一个原子事实。

```
            Append（单事务，与 idempotency_keys 一起提交）
                          │
                          ▼
                     [ pending ] ──发布成功──▶ [ sent ]（终态，不再扫描）
                          │
                          ├─ 发布失败：retries++，2s→4s→…→60s 指数退避，下次到期再试
                          └─ 用尽 10 次预算 ──▶ [ dead ] + last_error（终态，人工重新入队）
```

**到期判断由数据库算**：dispatcher 取 `TIMESTAMPDIFF(SECOND, created_at, NOW())`，
只在"年龄 ≥ 该事件重试次数的退避"时才尝试，并且**从未尝试过的事件永远立即到期**。
这是为一条真实事故加的防线：驱动把 DATETIME 按 UTC 解析，而 MySQL 会话时区是宿主本地（UTC+8），
"服务端写的 created_at vs 进程时钟"这一比较会让每条新事件都显示为"尚未到期"，
于是所有回复静默停在 pending，而链路其余部分（模型、审计、账本）看起来一切正常。
**同一时刻只能有一个时钟说了算**，这里选了数据库。配套地 `storage.OpenMySQL` 把连接会话时区
钉为 UTC（`time_zone='+00:00'`），使 DB 写的 `CURRENT_TIMESTAMP` 与 Go 写的 `time.Time`
表示同一时刻（修复前同一行里两者相差 8 小时）。回归测试
`TestOutboxDeliversWhenServerZoneDiffersFromTheDriver` 用 `+08:00` 会话复现过该偏差。

**出站游标**：`stream:outbound` 的跟随者（IM 网关、SSE）用游标推进。Redis 的 `$` 表示
"**本次调用时刻**的流尾"，反复传 `$` 会跳过两次调用之间产生的消息（SSE 循环约每秒一次，
这曾让"已发布"的回复永远到不了浏览器）。因此 `bus.ReadOutbound` 把 `$` 解析一次并作为具体游标返回，
所有跟随者都用返回值推进；同理，`LoadOutboundCursor` 恢复的持久化游标让网关重启后
仍能补发停机期间产生的回复。
