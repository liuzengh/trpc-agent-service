# trpc-agent-service 验证与发布技术规范

本文定义服务的验证分层、故障场景、外部 Provider 验证边界和发布准入条件。验证用于证明技术契约成立，不承担项目进度记录功能。

## 1. 验证原则

1. 单元测试验证局部规则，不能替代共享后端和进程故障测试。
2. InMemory 与生产适配器必须复用同一 contract suite；测试替身不得放宽租户、版本、幂等或错误分类。
3. PostgreSQL、Redis、S3-compatible ObjectStore、Scanner 和 Provider 分别验证；一个后端通过不能推导其他后端正确。
4. 所有消息链路按 at-least-once 验证，断言目标是“允许重复传输，不允许重复业务效果”。
5. 未提供真实凭据时，外部 Provider 测试必须显式跳过；fixture 或 WebUI 结果不得标记为真实 Provider 通过。
6. 生产准入同时要求功能、安全、恢复、可观测和回滚证据。

## 2. 静态与构建门禁

| 门禁 | 约束 |
|---|---|
| 格式 | 所有 Go 源码通过 `gofmt`，Shell 脚本通过语法检查 |
| 文档引用 | 所有仓库内 Markdown 相对链接与标题锚点通过 `bash scripts/ci/check-doc-links.sh` 校验 |
| 依赖 | `trpc-agent-go`、Feishu SDK、AWS SDK 与 Smithy 版本满足固定边界；禁止导入上游 `internal` 和未获批产品模块 |
| 编译 | 所有生产 role 与测试包在固定 Go toolchain 下可构建 |
| 静态检查 | `go vet ./...` 无错误 |
| 单元测试 | `go test -count=1 ./...` 通过 |
| 竞争检查 | `go test -count=1 -race ./...` 通过 |
| Compose | Compose 配置可解析，secret 文件不写入镜像或普通环境模板 |

仓库 CI 固定使用 Go 1.25.x，并以一次性 `GOMODCACHE`/`GOCACHE` 执行
build、vet、unit 与 race 门禁；不得用开发机缓存作为通过依据。PostgreSQL
16、Redis 7、Qdrant 和 Vault 的最小后端验证使用 digest 固定的 Compose
镜像和独立项目名。该 smoke 不需要企业账号，也不替代真实 Provider 或集群验收。

本地常备验证使用真实 PostgreSQL/Redis 适配器执行两个租户的 Worker 切片、
跨租户状态拒绝、依赖短断后的 readiness 恢复，以及 PostgreSQL 迁移的重复执行
与回滚测试。它们不需要企业账号，也不替代真实 Provider 验收。

真实 DeepSeek、S3/ClamAV/DLP、Feishu/WeCom 与 OTEL smoke 属于显式 opt-in
操作：未提供真实凭据时必须显式跳过，状态只有 `SKIPPED`、`BLOCKED` 或
`READY`，绝不把缺资源或未授权写成通过；凭据只允许从 owner-only 配置或
绝对路径凭据文件读取。未启用的外部能力按能力边界文档显式关闭。

## 3. 契约测试

### 3.1 控制面

- Tenant、Agent App、Config 和 Profile 的 CAS、不可变版本、跨租户引用拒绝。
- 发布、回滚、状态变化与 Audit/Outbox 的事务原子性。
- 严格 schema、digest、SecretRef generation 和 capability 校验。

### 3.2 Runtime 与 Session

- `PrepareDispatch` 只分配一次 `input_seq`。
- 同 Session 仅有效 fence 可以提交；旧 lease、旧 fence 和旧 version 永久拒绝。
- `CommitTurn` 对事件、状态、终态和 Outbox 原子且幂等。
- cancel、park/wakeup、confirmation 和重投不会越过 next-input 门禁。

### 3.3 Channel 与 Delivery

- callback 验签前不解析 Tenant；候选能力一次性且有过期边界。
- 重复 callback 只形成一个 Inbox、payload 和 PreprocessJob。
- Reply Queue 重投、consumer reclaim 和 sender 超时不产生重复业务效果。
- Delivery Ledger 覆盖 sent、retryable、permanent 和 ambiguous 分类。
- Feishu、WeCom、WebUI 与 fake adapter 复用公共 Channel contract。

### 3.4 ObjectStore 与媒体

- Put 的幂等条件、冲突后 compare、digest/size 校验和精确 version 删除。
- upload intent、orphan 回收、引用保留、lease/CAS 和 quarantine 状态机。
- ClamAV 与 DLP 对 clean/rejected/unknown/backend unavailable 的 fail-closed 行为。
- 原始媒体引用不得直接进入模型；执行只接受已扫描的 PreparedInput ArtifactRef。

## 4. PostgreSQL 与 Redis 集成验证

PostgreSQL 验证在随机临时数据库执行完整 schema apply、重复 apply、rollback、空库再 apply 和 repository contract。验证不得复用生产数据库。

Redis 验证使用 Redis 7，覆盖：

- Broker publish/consume/ACK/reclaim。
- Worker control、wakeup 和 reply stream 的 consumer group 隔离。
- publish 成功但 mark 失败、ACK 前进程退出和 pending reclaim。
- 环境、tenant、shard、account 维度的 stream key 隔离。

<a id="runtime-slice"></a>

## 5. 端到端 Runtime Slice

标准 slice 使用两个 Tenant、PostgreSQL、Redis、至少两个 Worker 和确定性模型，覆盖：

```text
Gateway/Channel
→ durable payload + Inbox/PreprocessJob
→ PrepareDispatch + Dispatch Outbox
→ Redis Broker
→ Worker lease/fence + Runner
→ CommitTurn + Reply Outbox
→ Reply Queue + Delivery Ledger
→ Channel Adapter
```

必须注入以下故障：

- Worker 在模型调用前后退出。
- Relay 在 publish 与 mark 之间退出。
- Delivery consumer 在 Provider effect 后、ACK 前退出。
- lease 到期后由另一 owner reclaim。
- 同一 callback、request、reply 重复提交。
- 不同 Tenant 使用相同外部 ID、Session ID 或 Artifact ID。

验收断言包括：终态唯一、有效 fence 唯一、Session 顺序单调、回复业务效果唯一、跨租户不可见。

## 6. WebUI 本地链路验证

WebUI 是普通 `channel.Adapter`，用于在无企业 IM 凭据时验证 provider-neutral 主链。它必须经过公共 callback、identity/session、Preprocess、Worker、Reply Queue、Delivery Ledger 和加密 ResultStore，不得建立平行状态机。

WebUI 验证覆盖：

- HMAC 请求、timestamp/nonce、防重放和 route/binding 匹配。
- DeepSeek 模型调用和结果持久化。
- 容器重启后的 readiness 恢复。
- reclaim 或重复轮询不会新增 Execution、Delivery Ledger 或 mailbox 业务记录。

WebUI 通过只证明内部 Channel/Runtime/Delivery 语义，不证明 Feishu 或 WeCom 外部 API、权限和限流行为。

<a id="real-im-verification"></a>

## 7. 真实 IM Provider 验证

真实 Provider smoke 是显式 opt-in 操作，会发送可见消息。凭据只允许从 owner-only 绝对路径文件读取。

- Feishu：使用 App ID/App Secret 获取凭据，并对授权的现有消息执行 Reply API。
- WeCom：使用 Corp ID/Corp Secret/Agent ID 获取 token，并向应用可见测试用户发送 Agent 消息。
- 单 Provider 和双 Provider 均使用同一入口；只有所有选中 Provider 返回有效消息 ID 才通过。
- 测试错误必须脱敏，不能输出 token、secret、原始响应体或 credential 文件内容。

WebUI、mock server 和协议 fixture 不能替代本节。

## 8. 健康与重启验证

每个生产 role 必须分别验证：

- 依赖健康时 `/livez` 与 `/readyz` 返回成功。
- 依赖不健康或 generation 不匹配时保持 live、ready=false。
- SIGTERM/SIGINT 立即进入 draining，拒绝新的外部工作。
- 已领取工作只在有效 lease/fence 和 drain deadline 内完成。
- 重启后依靠 PostgreSQL/Redis 恢复，不依赖进程内缓存事实。

## 9. 发布准入

发布候选必须同时满足：

1. 静态、单元、race、契约、PostgreSQL 和 Redis 门禁通过。
2. 所有生产 role 的依赖、readiness、drain 和恢复行为通过。
3. 迁移具备重复执行、回滚和 schema 一致性证据。
4. Secret canary、跨租户负向测试和未知 verdict fail-closed 通过。
5. 已启用的外部 Provider 具有真实凭据 smoke 证据；未启用 Provider 在能力声明中明确关闭。
6. 启动、停止与本地故障处置操作记录在本地 runbook；集群级回滚、隔离和凭据轮换操作属于生产运维边界，随相应运维资源引入后另行建设。
7. 工作区可从固定依赖与部署清单重复构建。
