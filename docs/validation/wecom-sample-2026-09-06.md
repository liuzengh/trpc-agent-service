# 企业微信 MCP 消息取样记录

日期：2026-09-06。分三轮执行：私聊查询、另行授权的测试群查询、单独授权的机器人发送。结果是**群聊已读到用户测试正文，发送接口返回成功，用户已确认群中看到机器人测试回执**。机器人回复在固定窗口回读中仍为空，私聊空结果原因未明；这些未明项不改变本次客户端已收到消息的事实。未启用后台接收器或完整 Agent 回复链路。

## 第一轮：私聊查询

用户明确授权：已发送 `TRPC-WECOM-TEST-001`，允许读取测试会话。

1. 调用一次 `message_aibot_sessions_list`。返回 `errcode=0`、`sessions_count=1`，唯一会话为 `chat_type=single`，`last_msg_time=2026-09-06 15:31:20`。
2. 对该唯一会话调用 `chat_messages_list`，参数时间窗口固定为 `2026-09-06 15:29:20` 至 `2026-09-06 15:33:20`。没有指定翻页游标。
3. 原样复核一次相同会话、相同时间窗口。

两次正文查询均返回：

```json
{"errcode": 0, "errmsg": "ok", "has_more": false, "messages_count": 0}
```

因此**没有取得测试消息正文，也没有取得成功消息的输出字段结构**。会话列表时间有更新，不等同于消息读取成功。不能据此断言用户没发消息、接口不支持私聊，或自动把它标为已完成收发联调。

本轮没有发送消息、下载附件、订阅事件、遍历其他会话、补拉历史或开启后台接收器。接口没有说明时间参数的时区；没有尝试把时间平移八小时后查询其他时段。公开检索也没有找到能确认该精确接口私聊读取语义的文档，原因仍待定位。

### 私聊阶段确认的响应字段

会话列表有 `sessions[]`，条目包含 `chat_id`、`chat_name`、`chat_type`、`last_msg_time`。返回还带有 `extra_identity_context`；它不是聊天正文，不应拼入 Agent prompt。新取样代码不保存该附加身份上下文或会话名称。

空消息响应仅确认 `errcode`、`errmsg`、`has_more`、`messages_count`。这一阶段未确认消息 ID、发送者、消息类型、正文及发送回执的具体结构。

## 第二轮：授权测试群查询

用户明确授权：“群消息已发送，允许读取该测试群”。本轮只读取该群，不发送回复、不下载附件、不遍历其他群。

1. 调用一次 `message_aibot_sessions_list`，返回两个会话：一个群聊，最后消息时间 `2026-09-06 15:59:38`；另一个是前轮的私聊，时间没有变化。
2. 只选择唯一群聊，调用一次 `chat_messages_list`，固定窗口为 `2026-09-06 15:57:38` 至 `2026-09-06 16:01:38`，不带游标。
3. 原样复核一次相同群、相同窗口。两次的消息记录及状态一致。

两次均返回 `errcode=0`、`messages_count=1`、`has_more=false`。消息类型为 `text`，发送时间为 `2026-09-06 15:59:38`，正文带有 @，包含测试标记 `TRPC-WECOM-TEST-001`。虽然建议发送的是 `TRPC-WECOM-GROUP-001`，实际沿用了私聊标记，但这里选择的是独立群会话，足以确认群聊读取成功，无须重发。

此次消息条目实际只有以下字段：

```json
{
  "msg_type": "text",
  "send_time": "2026-09-06 15:59:38",
  "text": {"content": "@synthetic-bot TRPC-WECOM-TEST-001"},
  "user_name": "synthetic-user",
  "userid": "synthetic-user-id"
}
```

上例替换了成员身份与 @ 名称，保留真实字段层级；完整脱敏样例见 [group_messages.json](../../trpcservice/channels/wecommcp/testdata/group_messages.json)。没有返回 `id`、`msgid`、`msg_id` 或 `message_id`，也没有 `is_bot`、独立的 @ 元数据或翻页游标。不能给样例补造这些字段。

这两次读取能证明该测试消息在相同窗口内可重复读取；不能证明所有消息完整可见、没有读取副作用、时间边界/时区已明确或发送已可用。之前私聊为空的原因仍未确认。

## 第三轮：单次机器人发送

用户回复“发”，授权仅向前述测试群发送一次 `TRPC-WECOM-REPLY-001`，并查询发送附近的短时间窗口。不调用模型、不启用自动回复。

1. 重新读取一次最近会话列表：仍为一个群聊和此前私聊，群的最后消息时间仍为 `2026-09-06 15:59:38`，只选择该群。另做一次元数据发现，复核机器人发送工具的输入参数。
2. 在本地持久化单次尝试记录后，于本地时间约 `16:10:07` 调用一次 `message_aibot_send`。参数为该群 ID、`msg_type=markdown`、`markdown.content=TRPC-WECOM-REPLY-001`。没有调用其他身份的 `message_send`。
3. MCP `is_error=false`，实际业务响应为：

   ```json
   {"errcode":0,"errmsg":"ok","success":true}
   ```

   该响应没有消息 ID。样例见 [group_reply.json](../../trpcservice/channels/wecommcp/testdata/group_reply.json)。该回执本身只证明接口报告成功；客户端展示另由下述用户反馈确认。
4. 对同一群查询固定窗口 `2026-09-06 16:09:07` 至 `2026-09-06 16:12:07`，之后原样复核一次；两次均返回 `errcode=0`、`messages_count=0`、`has_more=false`。没有重发，也没有扩大窗口、平移八小时或切换会话。
5. 在询问测试群是否看到 `TRPC-WECOM-REPLY-001` 后，用户明确回复“看到了”。因此这次固定消息的实际送达已由用户确认，群聊读取及单次发送验证完成，无需重做。

读取窗口按实际发送尝试时刻构造，UTC+8 与之前群消息样例及操作者本地时间对应；这属于本次测试的时区假设，不冒充官方时区契约。回读为空的原因未确认，不能断言该接口永远不返回机器人消息。本次消息已在客户端显示，说明不能把“回读为空”直接当作发送失败并触发重发。

## 有界采样与发送探针

新增独立命令 `cmd/trpc-wecomsample`，必须显式传 `-authorized`。原来的 `check-wecom.sh` 仍然只做初始化与工具列表，不能调用任何业务工具。

传输只允许预先选定的工具、精确参数和一次调用；改变会话 ID、正文、时间窗口、切换工具或在同一实例追加调用都会被拒绝。只读采样不因新增发送探针而获得发送权限。

- `-mode messages` 只接受唯一近期私聊，不读取群。
- `-mode group-messages` 用于单独授权的专用测试群，只接受会话列表中恰好一个群，允许列表同时存在私聊，但不读取私聊。
- 有多个群时不自动选择“最新群”；过期快照、无可靠时间、缺失或不匹配的 MCP 配置指纹均拒绝查询。
- 两种消息模式均使用会话列表中时间的原始表示构造前后各两分钟窗口，不平移时区、不补拉历史、不翻页。`-authorized` 是操作者的授权确认，不会自动替代与群成员约定的访问范围；不应在有多个未识别业务群的账号上盲目使用。
- `-mode group-reply` 还必须单独传 `-allow-send`，仅允许固定标记 `TRPC-WECOM-REPLY-001`，不接受任意正文、媒体、私聊目标或多个候选群。
- 发送前通过独占创建和文件/目录同步持久化 `0600` 尝试记录，只含配置/群的指纹、标记及时间，不含原始凭据或群 ID。同一配置、群和标记的再次尝试在联网前拒绝；无论超时、响应丢失还是保存结果失败，都不删除记录或自动重试。这是同一本地数据目录下的测试保护，不是企业微信提供的幂等保证，也不是分布式 Sender。
- `-mode group-reply-read` 只读取该尝试时间前一分钟、后两分钟的窗口，并检查群/配置指纹与记录有效期；不会发送。不能用旧群消息时间代替发送时间。

原始响应暂存为本地 `0600` 临时文件，用于字段确认，完成后清理，不保留原文备份；仅保留脱敏证据和必要的单次发送尝试记录（不进入 Git）。尝试记录不能当作普通采样文件清理，否则会失去本机防重复发送保护。未删除任何企业微信会话或消息。日志/工具输出没有完整地址、API Key、会话名称或成员 ID。

自动测试覆盖：默认采样禁用、发现命令仍不能执行工具、采样工具/参数白名单、单次预算、私有文件权限、身份字段最小化、私聊/群聊选择隔离、歧义/过期窗口拒绝、MCP 配置绑定、基于脱敏消息结构的响应处理及输出脱敏；发送还覆盖单独授权、固定正文/目标、并发独占尝试、成功或结果不明后的重复调用阻断，以及绑定发送尝试的读取窗口。

本轮 `go test -race ./...`、`./lint.sh`、采样命令构建及 `git diff --check` 均通过。自动测试使用本地假服务与脱敏 fixture；真实接口结果来自上述单独执行的授权采样，不混淆两类证据。

## 下一步

群聊读取、单次发送及客户端收到回执均已确认，不再要求重发测试消息。随后平台通道集成代码已实现，见[独立开发记录](wecom-runtime-2026-09-06.md)。本记录描述的实际访问仍仅为授权采样与单次发送；没有在真实账号启用自动 Agent 服务，单条消息授权不等于持续读取或自动回复。

正式接收器不能照搬 Telegram 的消息 ID 去重：这个非空样例没有唯一 ID。若采用“会话 + 发送者 + 秒级时间 + 正文”的指纹，两条同一用户同一秒发送的相同文本可能被合并；它不是平台提供的唯一消息 ID，也不是 exactly-once 保证。需要确认可用的源标识/分页契约，或明确指纹降级语义后再接入 Inbox，并对危险工具保持额外业务幂等与审批限制。

机器人自身消息的识别、分页游标、延迟可见性、发送失败格式及超时重试语义仍需实证；成功回执只确认上述布尔结果，不能补造 `ProviderMessageID`。本轮没有创建 Binding、调用模型、写入业务 Inbox 或重启现有 Telegram 服务。
