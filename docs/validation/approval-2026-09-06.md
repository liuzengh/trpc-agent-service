日期：2026-09-06。真实 Telegram `current_time` 验收已另行记录并随提交 `66f7a7e` 保存；本记录只描述后续审批阶段。

## 代码修正

- 批准/拒绝必须匹配原 Session，修复同一用户跨群或 Topic 批准的边界。
- 不可重试的审批错误记录 `approval_rejected` 后确认回调，不进入普通 Agent 执行；基础设施错误仍要求 IM 重试。
- 重复的过期决策统一返回过期语义；Memory 和 PostgreSQL 对同一 decision_message_id 不能决定两张审批单的行为保持一致。
- 审批审计增加恢复请求 ID 和重复标记；提示明确要求在 Telegram 群中使用“回复”操作发送严格的批准/拒绝命令。
- 真实预检发现 BeforeTool 在权限检查前触发，会使等待审批的请求被误记为 running；将执行预留移至权限允许之后，保持重复执行拦截和 AfterTool 结果审计。

## 确定性平台回执修正

为解决上述缺陷，新增平台直接回复路径：在同一事务中写入 Inbox、completed 的平台控制记录和 Outbound，不创建队列任务、不调用模型。回复记录标记为 `platform-control`，有独立的 `receipt_request_id`；批准的 Agent continuation 保留原标识，避免重放旧审批时重复执行。

- 非规范审批/取消消息：只返回“本条消息没有更改审批状态”的帮助，不推断用户已批准或拒绝。
- 有效拒绝：数据库变为 denied 后直接生成固定回执，不创建恢复任务；这与上面的旧版历史不同。
- 有效批准：固定回执只确认批准与提交任务；最终执行消息根据 Tool Journal 生成，不转发模型对审批状态的自行判断。
- 同一会话还有待批记录时，Worker 用真实待批提示替换模型回复，覆盖未被命令识别器捕获的自然语言拒绝。
- 提示中的批准/拒绝命令独占一行，不再使用容易被一并复制的前缀。

新增回归测试故意让模型输出错误的取消/成功声明，验证这些文字没有被发给模拟 Telegram；同时检查格式错误和拒绝均不增加模型调用次数、工具次数，重复消息不增加回执。

PostgreSQL 隔离测试验证了直接回复与审批状态、审计的关联，以及 Outbound 插入失败时整个直接回复事务回滚。Migration 010 为按会话查找 pending approval 增加索引。自动测试、race、静态检查与构建通过；确定性回执修正后的真实 Telegram 收发仍待用户复验。
