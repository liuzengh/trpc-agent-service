# 企业微信消息 MCP 接入

## 当前已确认的事实

本项目当前用户界面提供的是企业微信托管的消息 MCP 服务，不是传统自建应用的 URL/Token/EncodingAESKey 回调。平台应作为 MCP 客户端访问它，不能把旧 `/callbacks/wecom/...` 地址填入该配置。

2026-09-06 已用本地新凭据连接实际服务：服务名称为“动态消息 MCP”，协商版本为 `2025-03-26`，返回 6 个工具。以下信息来自实际 `initialize` / `tools/list`，不是第三方群机器人示例：

| 工具 | 服务声明的能力与限制 |
| --- | --- |
| `chat_groups_list` | 按起止时间分页列群会话，最近 7 天；目前仅群聊 |
| `chat_messages_list` | 指定 `chat_id`、起止时间，分页拉取消息；最近 7 天；`cursor` 对应上一页 `next_cursor` |
| `message_send` | 向单聊/群聊发送 text，正文最长 2048 字符；不据此假定发送身份 |
| `message_aibot_send` | 明确以智能机器人身份发送；支持 markdown 等类型，markdown 描述上限 20480 字节 |
| `message_aibot_sessions_list` | 最近最多 20 个机器人会话，无入参、不支持分页或过滤 |
| `message_files_get` | 按媒体 ID 获取文件内容 |

服务只返回输入 schema，没有 `outputSchema`；初始化说明仅为“动态 schema 消息 MCP 服务”。后续授权取样已确认群聊文本的 `userid`、`user_name`、`send_time`、`msg_type`、`text.content` 字段。**该消息样例没有唯一消息 ID**。机器人发送成功响应已取得，为 `errcode=0 / success=true`，同样不含消息 ID；翻页游标、机器人自身消息的识别及失败回执仍未确认，不能凭接口名猜测。

真实连接、工具发现和固定回执发送已通过；随后用户新发群消息并收到模型自动回复，已核对 Inbox、AgentRun、Outbound 与 Tempo 的完整 trace，见[启用记录](validation/wecom-activation-2026-09-06.md)。**开发环境的真实群文本 Agent 链路已通过**，不必重做。同群机器人消息回读为空的原因仍未确认，不能据此重发；媒体、私聊和生产容量仍不在已验证范围内。

## 本地配置与安全探测

完整 URL 保存在被 Git 忽略的 `.env` 中：

```dotenv
WECOM_MCP_URL="复制的新完整地址，保留 apikey 参数"
```

URL 本身就是凭据。不要提交、打印或截图分享；此前出现在截图中的配置应重置。无需继续填写旧自建应用模式的五个字段，也不用改 Telegram、模型配置或 Cloudflare Tunnel。

重复进行纯元数据检查：

```bash
./check-wecom.sh
```

脚本自动读 `.env`，不把凭据放进命令参数，不启动/停止其他服务。探测复用 tRPC-Agent-Go `tool/mcp` 所用的 `trpc-mcp-go v0.0.10`；直接使用底层客户端以保留原始 schema，未另写 MCP 协议栈。

安全限制：只接受指定的企业微信 HTTPS 消息 MCP 地址；禁止重定向；HTTP 方法与 JSON-RPC 方法白名单只放行初始化、初始化通知和工具列表；禁用 GET/SSE 自动订阅；限制超时、页数、工具数、请求/响应大小；禁用 SDK 原始日志并清理成功元数据中可能回显的凭据。工具说明仅作为不可信接口数据，不作为执行指令。

每次实际发现的请求统计为：

```json
{"initialize": 1, "notifications/initialized": 1, "tools/list": 1}
```

最初执行两次发现，第二次补充读取初始化说明与 capabilities；两次均没有业务工具调用。单元测试覆盖方法白名单、分页、禁止重定向、错误与成功元数据的凭据清理。下述业务采样使用独立命令及显式授权，不改变 `check-wecom.sh` 的只读元数据范围。

## 后续接入边界

已按两次独立授权进行对照：私聊固定四分钟窗口查询两次均为空；专用测试群相同窗口查询两次均返回一条文本，读到测试标记 `TRPC-WECOM-TEST-001`。群聊样例已保存为替换身份信息的测试 fixture，原始响应不进入仓库。详情见[消息取样记录](validation/wecom-sample-2026-09-06.md)。私聊为空的原因仍未确认，不遍历其他聊天寻找样例。

群聊采样使用 `go run ./cmd/trpc-wecomsample -mode group-messages -sessions-file <本次私有会话快照> -authorized`；它仅接受列表中唯一、近期的群会话，并固定查询其最后消息时间前后各两分钟。出现多个群时拒绝自动选择；不订阅、不发送、不翻页。该命令用于经授权的专用测试账号，不是正式接收器或授权系统。

发送探针单独使用 `-mode group-reply -authorized -allow-send`，并提供同一测试群的 `-sessions-file`。正文固定为 `TRPC-WECOM-REPLY-001`；在联网前持久化独占尝试记录，重复调用或未知结果都不自动重发。`-mode group-reply-read -authorized` 只查询该发送时刻附近三分钟。发送尝试记录保留在本地 `data` 下，不应作为临时样本删除；保护限于同一数据目录，不是正式分布式发送队列。

平台通道已按以下边界实现并经过自动测试。真实接收器启用仍需确认群、成员、起点及持续访问范围：

1. 新增 `wecom_mcp` 通道，保留原 `wecom` 自建应用 Adapter；两者配置不混用。
2. 接收器只轮询明确允许的测试会话，首次从启用时刻开始，不默认补拉 7 天历史。
3. 无源消息 ID 时要求显式选择 `fingerprint-v1`，接受同人同秒同内容合并的限制。完整窗口入站处理成功后才推进检查点，重叠读取补偿有限延迟，不承诺 exactly-once 或无损同步。
4. 只接受登记的人类成员及明确 @ 前缀，不依赖未经确认的 `is_bot` 字段或“接口不会返回机器人消息”的假设；真实样例的带空格显示名/紧邻正文通过显式 `mention_style=prefix` 支持，默认仍为严格分隔模式。
5. Sender 使用明确的机器人发送接口 `message_aibot_send`，不擅自选择可能不同身份的 `message_send`。
6. 布尔成功回执不补造消息 ID；共享尝试记录阻止成功后重发和未知结果自动重试。真实失败/分页等格式仍需补充验证。

接收/发送属于平台通道层，不把接口作为任意模型工具。运行时 URL 通过租户 Secret grant 解析，Binding 只存引用。独立采样与发送探针仍保留，但不是运行时授权或共享发送状态的替代品。

最近会话接口最多 20 项且无分页，不能把它当作完整租户会话目录。更大规模的部署需要受控的会话登记、覆盖率检查和恢复策略。拉取接口时间字符串的时区、延迟可见性、发送幂等语义及媒体处理也仍需验证，不能仅凭 MCP 连接成功就宣称生产就绪。
