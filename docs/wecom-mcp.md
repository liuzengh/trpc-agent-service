# 企业微信消息 MCP 接入

## 当前已确认的事实

本项目当前用户界面提供的是企业微信托管的消息 MCP 服务，不是传统自建应用的 URL/Token/EncodingAESKey 回调。平台应作为 MCP 客户端访问它，不能把旧 `/callbacks/wecom/...` 地址填入该配置。

2026-09-06 已用本地新凭据连接实际服务：服务名称为“动态消息 MCP”，协商版本为 `2025-03-26`，返回 6 个工具。以下信息来自实际 `initialize` / `tools/list`，不是第三方群机器人示例：

| 工具 | 服务声明的能力与限制 |
| --- | --- |
| `chat_groups_list` | 按起止时间分页列群会话，最近 7 天；目前仅群聊 |
| `chat_messages_list` | 指定 `chat_id`、起止时间，分页拉取消息；最近 7 天；`cursor` 对应上一页 `next_cursor` |
| `message_send` | 向单聊/群聊发送 text，正文最长 2048 字符；不据此假定发送身份 |
| `message_aibot_send` | 明确以智能机器人身份发送；支持 markdown 等类型，markdown 描述上限 20480 字节 |
| `message_aibot_sessions_list` | 最近最多 20 个机器人会话，无入参、不支持分页或过滤 |
| `message_files_get` | 按媒体 ID 获取文件内容 |

服务只返回输入 schema，没有 `outputSchema`；初始化说明仅为“动态 schema 消息 MCP 服务”。因此尚未确认实际消息 ID、发送者、时间戳、正文、翻页游标及发送回执的 JSON 层级。这些字段不能凭接口名猜测。

这证明了真实连接和工具发现成功，**不等于平台已完成企业微信收发**。本轮没有调用任何 `tools/call`，没有列出业务会话、拉取聊天消息、下载附件或发送回复，也没有创建 Binding 或启用后台接收器。

## 本地配置与安全探测

完整 URL 保存在被 Git 忽略的 `.env` 中：

```dotenv
WECOM_MCP_URL="复制的新完整地址，保留 apikey 参数"
```

URL 本身就是凭据。不要提交、打印或截图分享；此前出现在截图中的配置应重置。无需继续填写旧自建应用模式的五个字段，也不用改 Telegram、模型配置或 Cloudflare Tunnel。

重复进行纯元数据检查：

```bash
./check-wecom.sh
```

脚本自动读 `.env`，不把凭据放进命令参数，不启动/停止其他服务。探测复用 tRPC-Agent-Go `tool/mcp` 所用的 `trpc-mcp-go v0.0.10`；直接使用底层客户端以保留原始 schema，未另写 MCP 协议栈。

安全限制：只接受指定的企业微信 HTTPS 消息 MCP 地址；禁止重定向；HTTP 方法与 JSON-RPC 方法白名单只放行初始化、初始化通知和工具列表；禁用 GET/SSE 自动订阅；限制超时、页数、工具数、请求/响应大小；禁用 SDK 原始日志并清理成功元数据中可能回显的凭据。工具说明仅作为不可信接口数据，不作为执行指令。

每次实际发现的请求统计为：

```json
{"initialize": 1, "notifications/initialized": 1, "tools/list": 1}
```

本轮执行两次发现，第二次补充读取初始化说明与 capabilities；两次均没有业务工具调用。单元测试覆盖方法白名单、分页、禁止重定向、错误与成功元数据的凭据清理。

## 后续接入边界

后续已按用户授权进行了私聊取样：唯一机器人私聊的最后消息时间有更新，但两次固定四分钟窗口查询均为 `errcode=0 / messages_count=0`，没有取得测试文本。详情见[私聊取样记录](validation/wecom-sample-2026-09-06.md)。原因未确认，下一步需要另行授权的无业务内容群聊对照；不遍历其他聊天寻找样例。

真正拿到非空消息样例后的实现路线：

1. 新增 `wecom_mcp` 通道，保留原 `wecom` 自建应用 Adapter；两者配置不混用。
2. 接收器只轮询明确允许的测试会话，首次从启用时刻开始，不默认补拉 7 天历史。
3. 使用稳定消息 ID 去重；完成一个查询时间窗口的全部分页、可靠写入 Inbox 后才推进检查点；重叠窗口处理延迟消息。
4. 排除机器人自己的回复，避免接收→回复→再接收的循环。
5. Sender 使用明确的机器人发送接口 `message_aibot_send`，不擅自选择可能不同身份的 `message_send`。
6. 验证回执和业务错误格式后再开放发送；发送超时不能假定无副作用，需沿用不确定结果治理。

接收/发送属于平台通道层，不把这些接口作为任意模型可调用的工具暴露出去。URL 应由租户 Secret grant 解析，Binding 只存引用；当前探测是本机部署者命令，不是多租户运行时授权的替代品。

最近会话接口最多 20 项且无分页，不能把它当作完整租户会话目录。更大规模的部署需要受控的会话登记、覆盖率检查和恢复策略。拉取接口时间字符串的时区、延迟可见性、发送幂等语义及媒体处理也仍需验证，不能仅凭 MCP 连接成功就宣称生产就绪。
