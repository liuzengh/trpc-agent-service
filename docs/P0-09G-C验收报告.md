# P0-09G-C 验收报告

## 状态

P0-09G-C 状态为 `verified (production async assembly boundary)`。

本轮使用测试进程提供的 `TEST_DATABASE_URL` 建立唯一 PostgreSQL schema，直接通过 CMD 使用的同一 production composition root 验证 Lark 和 Telegram 的异步装配。Provider transport 是本地 deterministic fake；本轮真实外部 Lark/Telegram send 次数为 0。

P0-09G-D、P0-09G-R 未启动。

## 证据门禁与范围

- `TEST_DATABASE_URL` 缺失时，联合证据必须停止并报告：`blocked; TEST_DATABASE_URL is required to close P0-09G-C evidence`。
- 测试内部临时绑定 `DATABASE_URL=TEST_DATABASE_URL`，使用唯一 schema、tenant、binding、owner、message 和 execution identity；不访问生产数据库，不使用默认 schema，不修改已应用 migration。
- 测试结束只删除本测试创建的 schema；DSN、Token、App Secret、Chat/Receiver ID、Authorization、Provider body、Prompt 和 History 不写入报告或测试输出。
- `assembleProduction` 的默认路径继续构造真实 PostgreSQL pool、Queue、Atomic Completion、Outbox、Worker、Dispatcher 以及真实 Lark/Telegram Sender constructors。
- 仅 `assembleProductionWithDependencies` 的内部测试 seam 可以替换 deterministic AgentFactory、recording channel Sender 和事件同步 hook；不替换 Queue、Outbox、completion 或 PostgreSQL Repository。

## 联合链路

Lark 与 Telegram 分别通过 HTTP handler 验证以下链路：

```text
verified synthetic webhook
  -> server-owned bootstrap Binding/TenantContext
  -> PostgreSQL Claim
  -> PostgreSQL durable Queue
  -> real Worker/Executor
  -> deterministic fake Runner reply
  -> PostgreSQL atomic result + Queue Ack + reply Outbox
  -> PostgreSQL Outbox claim
  -> channel-specific recording Sender
  -> Delivered
  -> Dispatcher MarkCompleted
```

Lark fixture 独立构造官方 callback contract 的 challenge/事件 JSON、AES-CBC `IV || ciphertext` 和签名；fixture 不调用生产解密或验签 helper。Telegram fixture 验证合成 `X-Telegram-Bot-Api-Secret-Token`、numeric `update_id`、numeric chat ID 和 `message_thread_id`。

持久事实断言包括：Claim/Queue/Execution/Outbox 使用同一 tenant 和 binding；只有一个逻辑 Job、execution result 和 reply Outbox；Worker 最终 Ack；execution result 带 owner/epoch/fence；result、Ack、Outbox 由同一 completion transaction 提交；Outbox 先为 `pending`，Dispatcher 后为 `completed`；Lark 只调用 Lark recording Sender，Telegram 只调用 Telegram recording Sender；每个事件的 recording Sender 逻辑调用一次。

## Ingress 失败窗口

当前顺序仍为 `Claim -> Queue Submit -> Claim Complete`。本轮新增确定性 PostgreSQL 测试覆盖：

- Claim 成功、Queue Submit 失败：HTTP 不返回 accepted；移除数据库失败触发器后 replay 安全恢复。
- Queue Submit 成功、Claim Complete 失败：replay 使用稳定入站 Job/Execution identity，不创建第二个逻辑 Job、execution 或 Outbox。
- Claim Complete 成功、HTTP ACK 丢失：replay 返回 duplicate accepted，不重复执行。
- pending Claim 被新 owner takeover：旧 owner 的 fencing completion 被拒绝。
- duplicate concurrent webhook：两个请求均得到 bounded accepted response，但只有一个逻辑 Job、execution result、Outbox 和 Runner 调用。

稳定 identity 位于 Gateway/Ingress durable boundary；普通 Gateway `Submit` 仍保持随机 Job/Execution identity。没有使用固定 sleep、无限 polling、retry-until-success、goleak 或吞错。

## Readiness 与兼容性

已验证：

- 缺少必需 bootstrap identity 或 SecretRef 时 assembly 失败。
- 数据库连接/迁移失败时 assembly fail-closed，不回退 Memory Queue 或 Fake Sender。
- production readiness 同时要求 migration、pool、durable Queue、Worker、Dispatcher 存在并可用。
- runtime `Start` 前 `/healthz` 为 not ready，显式 `Start` 后 ready；显式 `Stop` 进入 draining 后不 ready。
- `/livez` 与 readiness 分离；draining 不影响 liveness。
- `POST /api/chat` 仍通过同步 MemoryStore/Runner 返回，不创建 PostgreSQL Queue Job、execution result 或 reply Outbox。
- constructor error path 在返回前关闭已创建 pool；本轮只验证显式 Start/Stop hook，没有宣称 OS SIGTERM、process restart 或完整 drain。
