# 存储设计与多后端数据库支持：按 PR 序号

## 总结和观察

多数 PR 采用 **SQL 保存关键记录、Redis 承担队列与协调、向量库和对象存储按需接入**的组合。主要差异在于：租户能选择什么、已有数据能否迁走，以及故障后能否保持一致。

- **数据库选择范围不同。** #23 接入了 MySQL、MongoDB、ClickHouse 等多种会话后端；#24 的 `sql` 实际仅指 PostgreSQL。配置名称和 SDK 支持列表都需要核对实际实现。
- **租户选择的粒度不同。** #6、#25 可分别选择会话和长期记忆后端；#18 主要开放会话切换；#27 的可靠模式固定使用 MySQL。
- **迁移能力差距明显。** #20、#25 已有双写、复制校验和切换门禁；#19 的长期记忆迁移停在校验阶段。部分其他 PR 仅提供设计或停写复制工具。
- **部分能力尚未进入业务链路。** #3 只有方案；#4 的向量/对象适配仅用于 smoke 测试；#15 当前只交付会话后端。
- **可靠性仍需分项验证。** 多个实现存在过期执行者继续写入的窗口；已有测试也未覆盖所有数据库组合及迁移故障。支持的数据库种类多，不能直接说明恢复能力完整。

以下表格列出各 PR 的具体实现、限制和源码依据。
