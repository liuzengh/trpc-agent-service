## 实际实现

- `tenant.ChannelBinding` 仅允许 Lark/Telegram，具有 tenant、binding、provider identity、SecretRef、目标类型、enabled/status、version、更新时间和过期字段。
- `tenant.RegistryResolver` 只根据服务端 channel/provider identity 查找 Binding；caller tenant/binding override 被拒绝。
- `tenant.Identity` 以 tenant/channel/binding/external user 形成稳定内部映射；内部 ID 由服务端确定，external user 不原样进入错误或 Audit。
- private、group/supergroup 和 Telegram topic scope 被区分；Telegram thread 进入 thread-aware session identity，无 thread 的既有 session ID 规则不变。
- `tenant.EnvironmentSecretResolver` 只解析 `env://` reference；空引用、plaintext、未知 scheme、格式错误和缺失值返回有限错误类别。云 Secret Manager、KMS、Vault 和生产 IAM 未实现。
- Binding metadata、Identity metadata 和 Binding Audit 使用 PostgreSQL；Redis 不是事实源。更新要求 version/CAS，跨租户读取按 tenant context 拒绝。
- Ingress 顺序保持 verification/challenge、server-owned Binding/TenantContext、Identity、Claim、durable enqueue、Claim completion、ACK。body 的 tenant、channel 和 Binding 覆盖被拒绝。
- production composition 构造 PostgreSQL TenantRegistry、唯一 Identity resolver 和唯一 startup SecretResolver；disabled optional Binding 不注册 webhook/sender，也不阻塞启动。动态 reload deferred。
- Audit 只写有限 metadata 和不可逆 fingerprint；Audit 写入失败不会绕过安全拒绝。完整 Tool Policy、Guardrail、审批、预算和统一脱敏属于 P1-05。

## P1-04-R Final Closure Investigation

### Queue 执行路径与失败时间线

`newPostgresQueueFixture` 为每个测试创建 `context.WithTimeout(context.Background(), 60*time.Second)`，base pool `MaxConns=8`，使用 UnixNano 唯一 schema；schema pool 使用相同 `SearchPath`，fixture cleanup 关闭 queue/pool、drop schema、关闭 base pool 并 cancel context。`newIndependentQueue` 为两个 receiver 各创建独立 pool，`MaxConns=2`。目标测试在 fixture enqueue 后创建两个 receiver goroutine，原实现仅用 `close(start)` 广播，修改后先用 `ready` channel 等待两个 goroutine 到达启动点，再 release；测试始终使用 `WaitGroup` 等待两个 Receive 返回后才关闭 results、检查状态并进入 cleanup。修改后的目标测试没有 fixed sleep。

每个 receiver 使用 `context.WithTimeout(..., 350*time.Millisecond)`，调用 `Receive(ctx, 2*time.Second)`。`Receive` 循环检查 context/closed 状态，进入 `claim`；`claim` 开始 transaction，设置 local `lock_timeout=5s`、`statement_timeout=15s`，执行 expired delivery recovery UPDATE，再执行 `SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1`，decode 后执行 conditional claim UPDATE/RETURNING，最后 commit；所有非 commit 路径由 deferred rollback 收尾。目标 test 的 loser 只应等待到自己的 350ms deadline。

历史首次 full race failure 保留如下：test=`TestPostgresQueueConcurrentReceiveHasOneActiveDelivery`，stage=`claim candidate`，category=`database transport i/o timeout`，last_stage=`Postgres concurrent Receive write`，deadline=`true`，`DATA RACE=false`。源码和重复证据显示不是 row lock/deadlock、statement/lock timeout、schema collision 或 durable claim correctness failure；pgx 在 receiver context 已耗尽时可能把 socket deadline 表现为 wrapped `net.Error.Timeout()`，而不是 `context.DeadlineExceeded`。full suite 会并行运行多个 PostgreSQL-heavy package，350ms test budget 对 race/full-suite scheduling 敏感。

第一次 test-only barrier/分类修复后，full race 暴露了同类 failure：test=`TestPostgresQueueExtendVisibilityUsesConditionalLease`，stage=`requireNoDurableDelivery/claim candidate`，category=`deadline-coupled database transport timeout`，deadline=`true`，`DATA RACE=false`。该 helper 也只接受 `context.DeadlineExceeded`，未接受“自身 context 已过期且错误链明确为 `net.Error.Timeout`”。随后同样以 test-only 方式修正，并增加 pool `total/idle/acquired` 安全诊断。中间一次诊断改写造成 `undefined: err` 的 test compile failure，stage=`build`，category=`test-only diagnostic scope error`，deadline=`N/A`，`DATA RACE=false`；已修正，未进入 runtime。

## P1-04 Functional Boundary Checklist

1. Supported channel bindings are limited to Lark and Telegram.
2. Binding-to-tenant ownership is determined server-side.
3. Caller input cannot override tenant, binding, channel, or destination.
4. Provider identity lookup is performed server-side.
5. Disabled, expired, invalid, unknown, or secret-failing bindings are rejected before Claim/enqueue.
6. External Identity maps by tenant, channel, binding, and external user.
7. Private, group/supergroup, and Telegram topic/thread scopes are distinct.
8. Cross-tenant, cross-channel, cross-binding, and chat/thread scope conflicts fail closed.
9. Identity is resolved before Claim.
10. Identity failure never enters Queue.
11. Binding updates use version/CAS concurrency semantics.
12. PostgreSQL is the durable Binding/Identity metadata fact source.
13. Redis is not the sole Binding/Identity metadata fact source.
14. SecretRef persistence stores references only, never plaintext secrets.
15. `env://` has a real EnvironmentSecretResolver.
16. `secret://` is format-validated only and remains `validated-but-unresolved`.
17. `secret://` is not represented as cloud Secret Manager, KMS, Vault, or IAM integration.
18. Enabled bindings fail closed when required SecretRef metadata or secret values are missing.
19. Disabled optional bindings create no adapter/sender and do not block startup.
20. Current production configuration is a startup snapshot.
21. Dynamic reload, rotation, and automatic reconciliation remain deferred.
22. Audit records are limited metadata/fingerprints.
23. Audit contains no webhook body, prompt, history, provider body, Authorization, DSN, token, or raw secret.
24. Audit failure cannot bypass Binding/Identity rejection.
25. `/api/chat` remains synchronous `MemoryStore -> platform.Runner -> EchoResponder`.
26. Ingress does not directly call Runner, Model Provider, or Sender.
27. Existing Lark/Telegram Sender and Dispatcher boundaries are unchanged.

P1-04 functional boundary: VERIFIED. This does not mean full production identity management, cloud secret management, dynamic rotation/reload, Admin API, or project security remediation is complete.
