# P0-03/P0-04 实施计划完整性审核

**审核对象**：将当前任务中的占位符解释为 `P0-03 Session/Event/Memory/Summary/Artifact/Audit 模型` 与 `P0-04 ID、幂等键和存储契约`。

**审核结论**：现有实施计划的架构方向和任务边界基本正确，但按当前仓库状态还不能直接称为“可完整实施”。主要缺口是：计划中的目标包全部尚不存在；P0-04 的 Repository 契约没有明确 Fake 实现和可执行的租户校验方式；`SessionKey` 算法与现有 `channels.SessionID` 不兼容但迁移策略不在原任务验收中；`Summary`、`Lease`、`OutboxMessage` 和统一错误契约定义不够具体；旧 `platform` 类型与新领域类型之间的兼容边界需要锁定。

本审核仅进行只读分析，没有修改仓库文件，也没有运行会写出 `coverage.out` 或构建产物的命令。

## 2. 需求与现有代码的差距

### P0-03 差距

1. **领域实体缺失**：Session、SessionEvent、Memory、Summary、Artifact、AuditLog 尚不存在。
2. **状态规则缺失**：当前只有 Tenant 状态，没有 Session 和 Artifact 状态迁移。
3. **版本语义缺失**：现有 `platform.Event.Sequence` 是进程内切片长度，无法表达 Session CAS 或 Summary 单调更新。
4. **事件元数据缺失**：没有 EventType、ExecutionID、ParentEventID、Attempt、TraceID 等字段。
5. **审计脱敏缺失**：现有 `platform.Audit` 仅保存字段，没有统一 Metadata 脱敏规则。
6. **Artifact 安全约束缺失**：没有对象 key、MIME、大小、SHA256 和过期状态，也没有 `tenants/{tenant_id}/...` 校验。
7. **领域包边界未落地**：实施计划要求不暴露 tRPC-Agent-Go 类型，但当前没有新领域包来承载该边界。

### P0-04 差距

1. **ID 规则未统一**：计划规定 `v1 + tenant + channel + binding + scope`，现有通道代码仍使用旧 hex 算法。
2. **Topic 隔离无法实现**：当前 `channels.Incoming` 没有 `MessageThreadID`，P0-04 可以定义字段，但不能要求本阶段修改 Telegram Adapter。
3. **幂等契约不完整**：现有 `Store.Claim` 无法返回重复请求的持久化回复引用，也没有处理中、完成、失败、租约过期等状态。
4. **租约/Fencing 契约未定义**：P0-04 提到 `Lease`，但没有明确 Owner、FenceToken、过期时间和旧 token 拒绝语义。
5. **Repository 接口缺少可执行测试对象**：只声明接口不足以验证租户过滤、CAS、Summary 单调更新和跨租户拒绝。
6. **Outbox 接口欠缺模型**：只列出 `OutboxRepository`，没有定义 `OutboxMessage` 的租户、状态、Attempt、下一次执行时间和幂等字段。
7. **错误分类不统一**：后续 Redis、PostgreSQL、Worker 需要基于 `errors.Is` 判断冲突、租户错配、Lease 丢失和 Fence 拒绝，当前没有统一错误。
8. **旧接口兼容边界不明确**：如果直接修改 `platform.Store` 或 `channels.SessionID`，会影响 `web`、`cmd/trpc-service` 和已有测试；如果完全不建立转换边界，后续 P0-05/P0-08 无法接入新契约。
9. **接口签名存在文档冲突**：`implementation-plan-p0.md` 中的 `TenantResolver.Resolve(ctx, channel, externalAppID)` 与当前已实现的 `Resolve(ctx, ResolveRequest)` 不一致。P0-03/P0-04 不应重新修改 P0-02 的接口，应沿用当前 `ResolveRequest` 签名。

### 完整性判断

现有计划可以作为方向性计划，但必须补充以下执行决策后才完整：

- 新领域类型的确切字段、枚举和校验规则。
- `SessionKey`、`DedupKey` 的规范化和版本化算法。
- Legacy Session ID 的兼容读取策略。
- Fake Repository 及契约测试范围。
- `Lease`、`Claim`、`OutboxMessage` 和错误类型的完整定义。
- 新领域包与旧 `platform` 类型之间的单向转换边界。

## 3. 详细实施步骤

### P0-03-A：Session 和事件模型

1. 新建 `trpcservice/session/`。
2. 定义 `Session`、`SessionState`、`SessionEvent`、`EventType` 和 `Summary`。
3. 定义 Session 初始版本、事件 Sequence、Summary 覆盖 Sequence 的规则。
4. 实现 `Session.Validate()`、`Session.Transition()`、`SessionEvent.Validate()`、`Summary.Validate()`。
5. 禁止新包依赖 `platform` 和 tRPC-Agent-Go。
6. 事件 Payload 使用领域层可控的结构，不直接暴露模型框架对象。

推荐 Session 状态迁移：

```text
active -> paused
active -> completed
paused -> active
paused -> completed
completed -> archived
```

禁止从 `archived` 返回其他状态。

### P0-03-B：Memory、Artifact、Audit 模型

1. 新建 `trpcservice/memory/`，定义 Memory Scope、Kind、Version、SourceSeq、Deleted。
2. 新建 `trpcservice/artifact/`，定义对象引用、MIME、大小、SHA256、状态和过期时间。
3. 新建 `trpcservice/audit/`，定义审计 ID、Trace/Request/Execution ID、Decision、Latency、Cost 和脱敏 Metadata。
4. 实现所有实体校验。
5. 实现 `audit.RedactMetadata()`，返回新 Map，不修改输入 Map。
6. Artifact 校验强制要求对象 key 以 `tenants/{tenant_id}/` 开头，并拒绝绝对路径及 `..`。

### P0-04-A：SessionKey

定义：

```go
type SessionKey struct {
    TenantID        string
    Channel         string
    BindingID       string
    Scope           string
    MessageThreadID string
}
```

算法固定为：

```text
base64url(SHA-256("v1|" + tenant_id + "|" + channel + "|" + binding_id + "|" + scope + "|" + message_thread_id))
```

实现：

```go
func NewSessionKey(tenantID, channel, bindingID, scope, threadID string) (SessionKey, error)
func (k SessionKey) ID() string
func (k SessionKey) String() string
```

要求：

- 空值、长度、非法字符拒绝。
- 同输入必然生成同 ID。
- 不同租户、Binding、Scope、Topic 不发生逻辑碰撞。
- `String()` 不应在日志中暴露原始用户或群 ID，优先使用稳定脱敏表示。

### P0-04-B：Legacy ID 兼容

现有 [channels/channels.go](C:/Documents/trpc-agent-service/trpcservice/channels/channels.go) 的算法不得静默改变。

计划应明确：

- 新增 `session.LegacySessionID()` 或等价兼容函数。
- 新数据只使用 `v1` ID。
- 旧数据继续按 legacy 算法读取。
- P0-04 不修改 Adapter 和 Web 路由。
- Telegram Topic 字段只在新 Key 契约中预留，实际解析留到 P1-02。

### P0-04-C：DedupKey 和 Claim

定义：

```go
type DedupKey struct {
    TenantID          string
    Channel           string
    BindingID         string
    ExternalMessageID string
}

type ClaimStatus string

const (
    ClaimAcquired  ClaimStatus = "acquired"
    ClaimInFlight  ClaimStatus = "in_flight"
    ClaimCompleted ClaimStatus = "completed"
)

type Claim struct {
    Key         DedupKey
    Status      ClaimStatus
    OwnerID     string
    Attempt     int
    FenceToken  uint64
    ResponseRef string
    ClaimedAt   time.Time
    ExpiresAt   time.Time
}
```

接口：

```go
type IdempotencyRepository interface {
    Claim(ctx context.Context, tc tenant.TenantContext, externalMessageID string, ttl time.Duration) (Claim, error)
    Complete(ctx context.Context, tc tenant.TenantContext, key DedupKey, responseRef string, fenceToken uint64) error
    Fail(ctx context.Context, tc tenant.TenantContext, key DedupKey, fenceToken uint64, retryable bool) error
}
```

必须固定：

- Claim 唯一键为 `(tenant_id, channel, binding_id, external_message_id)`。
- 重复完成请求返回 `ResponseRef`，不得重新执行 Agent。
- Claim 过期才能接管。
- 新 Owner 必须获得新 Attempt 和 FenceToken。
- 旧 FenceToken 的 Complete/Fail 必须返回 `ErrFenceRejected`。

### P0-04-D：Repository 契约

定义：

```go
type SessionRepository interface {
    Get(ctx context.Context, tc tenant.TenantContext, id string) (session.Session, error)

type SummaryRepository interface {
    UpsertIfNewer(ctx context.Context, tc tenant.TenantContext, s session.Summary) error

type ArtifactRepository interface {

    PresignedURL(ctx context.Context, tc tenant.TenantContext, id string, ttl time.Duration) (string, error)

type AuditRepository interface {
    Append(ctx context.Context, tc tenant.TenantContext, a audit.AuditLog) error

```

定义 Lease：

```go
type Lease struct {
    SessionID  string
    OwnerID    string
    FenceToken uint64
    ExpiresAt  time.Time
}
```

每个 Repository 实现必须：

- 校验 Context 存在且 `TenantContext.Validate()` 通过。
- 校验资源 TenantID 与 `tc.TenantID` 相等。
- 不允许调用方覆盖向量搜索的 Tenant filter。
- 限制 Search limit，例如 `1..100`。
- 使用 `errors.Is` 返回统一错误。

### P0-04-E：Outbox 契约

```go
type OutboxMessage struct {

    ID          string
    Kind        string
    AggregateID string
    Payload     []byte
    Status      string
    Attempt     int
    NextAttempt time.Time
    LockedBy    string
    LockedUntil time.Time
    LastError   string

```

接口至少包括：

```go

    MarkRetry(ctx context.Context, workerID, id string, nextAttempt time.Time, errorType string) error
    MoveToDLQ(ctx context.Context, workerID, id, reason string) error

```

P0-04 只定义契约和 Fake 行为，不实现 SQL `SKIP LOCKED`、Redis Lua 或真实 DLQ。

### P0-04-F：Fake Repository 和契约测试

新增内存 Fake 仅用于 P0-04 测试，不能替代 `platform.MemoryStore`，也不能宣称为生产实现。

Fake 必须验证：

- 同一幂等键并发 Claim 只有一个 Owner。
- 跨租户 Get/Put/Search/Append 被拒绝。
- Session expectedVersion 冲突返回 `ErrVersionConflict`。
- Summary 旧版本或旧 CoveredSeq 不覆盖新版本。
- Artifact 跨租户 PresignedURL 被拒绝。
- Lease 和 FenceToken 具备基本旧 Token 拒绝行为。
- Outbox Claim 具备 Owner 隔离。

`build.sh` 会写入 `bin/trpc-service`，应在实施完成后的独立验证阶段运行。

验收不应要求：

- PostgreSQL 容器
- Redis 容器
- tRPC-Agent-Go 真实模型凭据
- 修改 Web/IM 行为
- 修改生产数据库

这些属于 P0-05 及之后任务。

## 7. 风险和回滚方案

### 领域模型与旧类型重复

**风险**：新旧 `SessionEvent`、`AuditLog` 和 `platform.Event` 语义漂移。

**缓解**：新领域包作为唯一未来生产契约；旧 `platform` 类型只保留开发兼容；增加单向转换测试；不要在 P0-03 同时重写 Runner。

**回滚**：删除新领域包和新测试，保留现有 `platform`、`tenant` 和 `config` 实现。

### Session ID 算法变更

**风险**：直接替换 `channels.SessionID` 后历史 Session 无法读取，且同一用户产生新会话。

**缓解**：新算法带 `v1` 语义并增加 Legacy 读取函数；P0-04 不修改 Web/Adapter 调用路径。

**回滚**：停用新 Key 生成入口，恢复 Legacy ID 读取；不删除已有数据。

### 分隔符歧义和输入碰撞

**风险**：使用简单 `|` 拼接时，字段内容包含分隔符会形成歧义。

**缓解**：对字段做严格字符/长度校验，或使用长度前缀/结构化编码后再 Hash；在测试中覆盖边界输入。

### 租户边界遗漏

**风险**：Repository 只使用传入 ID，不校验 `TenantContext`。

**缓解**：所有接口第一参数固定为 `TenantContext`；Fake 契约测试覆盖跨租户访问；统一 `errors.Is` 判断。

### Payload 和审计泄密

**风险**：事件 Payload 或 Audit Metadata 写入 API Key、Authorization、Prompt 或文件内容。

**缓解**：领域层提供脱敏函数；测试使用典型敏感字段；Repository 后续实现再次保护性脱敏。

### 版本和 Sequence 语义不一致

**风险**：领域模型允许非单调版本，导致后续 SQL CAS 或 Summary upsert 无法正确实现。

**缓解**：在实体校验和 Fake Repository 中同时验证版本单调；明确 `expectedVersion` 是 Session state version 还是 event sequence，不能混用。

### P0-04 过度实现后端

**风险**：在本任务中引入 pgx/Redis 客户端、迁移或真实 Lease，扩大提交边界并阻塞独立回滚。

**缓解**：P0-04 只实现接口、错误、Fake 和契约测试；真实后端严格留给 P0-05/P0-06。

**回滚**：删除新 `storage` 包及其测试，不触碰现有数据库或服务入口。

### 当前用户修改冲突

**风险**：修改 `tenant`、`web` 或平台文件时覆盖工作树中的未提交改动。

**缓解**：P0-03/P0-04 只新增目录和必要的独立契约文件；如必须修改既有文件，先逐段阅读当前工作树内容并保持最小改动。

## 最终完成标准

P0-03/P0-04 只有在以下条件全部满足时才算完整：

1. 新领域包可以独立编译，不依赖 tRPC-Agent-Go 和具体数据库客户端。
2. Session、Event、Memory、Summary、Artifact、AuditLog 均有字段校验和错误语义。
3. Session 状态、事件 Sequence、Summary Version/CoveredSeq 的单调规则有测试。
4. Artifact 对象 key 和 Audit Metadata 具备租户隔离及脱敏测试。
5. SessionKey 使用版本化算法，并保留旧算法兼容策略。
6. DedupKey 精确表达租户、Channel、Binding 和外部消息 ID。
7. Repository 接口全部接收 `TenantContext`，并明确 CAS、Lease、FenceToken、Claim 和 Outbox 语义。
8. Fake Repository 契约测试验证跨租户拒绝、并发 Claim、版本冲突和旧 FenceToken 拒绝。
9. 现有 tenant/config/platform 测试继续通过。
10. `go test ./...`、`go vet ./...`、格式检查和指定 race 测试通过。
11. 未修改数据库、Redis、Web、IM 协议和生产运行入口。
12. P0-03 和 P0-04 可分别独立提交、构建、验证和回滚。
