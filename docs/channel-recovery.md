# 企业微信 MCP 异常隔离与检查点恢复

本阶段代码和隔离测试已覆盖异常记录处理、权限检查及恢复事务。没有为了测试向真实群发送媒体，也没有跳过日常群的任何消息。

## 单条异常不再阻塞后面的正常文本

MCP 响应分两层校验：

- 页级异常（错误码、条数不符、缺失/重复游标、响应不完整、超时、页数上限）仍使整个窗口失败，不推进检查点。
- 单条不支持的媒体、格式异常或过大文本进入 `channel_message_rejection`。只保存指纹、原因枚举、窗口、时间和 trace，不保存原文、文件、姓名或密钥。

接收器必须先持久化全部隔离记录，再接收正常文本，最后推进检查点。隔离存储失败仍会停在原窗口，不静默丢弃。重叠读取不会重复创建同一隔离记录；已进入 Inbox 的正常文本仍按原来的 seen/Inbox 唯一键去重。

隔离不是媒体处理能力：不会下载、分析图片或文件，也不会把隔离内容交给模型/审批；未可靠识别 @ 信息时不主动给群发提示。拒绝记录本身是持久化审计事实，统一 audit 中的 `channel_message_quarantined` 为辅助索引。

授权操作者可通过 `POST /admin/channel-rejections/list` 查看指定 `tenant_id + binding_id` 最新最多 100 条记录。Auditor 只能查看，不能恢复检查点。

## 检查点查询与恢复

`POST /admin/channel-checkpoints/list` 返回指定租户/绑定的群指纹、配置指纹、窗口位置、读取下界和版本，不返回原始群 ID 或消息正文。

恢复必须先通过既有 Admin API 禁用 Binding，再提交 `POST /admin/channel-checkpoints/recover`：

```json
{
  "tenant_id":"tutorial-tenant",
  "binding_id":"wecom-mcp-tutorial",
  "chat_hash":"复制检查点查询中的群指纹",
  "expected_binding_version":2,
  "expected_version":10,
  "action":"rewind",
  "from":"2026-09-06T17:00:00+08:00",
  "acknowledge_gap":false
}
```

版本和时间都必须使用当前真实值，不能直接执行示例。起点精确到秒，必须在配置允许的范围、源保留期内，不能是未来。

| 动作 | 行为与限制 |
| --- | --- |
| `rewind` | 只向后补查，不接受配置变化；保留 seen、Inbox 和发送记录，因此不会强制重执行已处理消息 |
| `resume` | 从明确的新起点恢复，可采纳调整后的配置；必须 `acknowledge_gap=true`，承认可能跳过历史或改变读取范围 |

PostgreSQL 恢复会锁定 Binding/Checkpoint，重新检查禁用状态及版本，原子更新检查点并写入 `channel_checkpoint_recovery`。恢复审计写失败会回滚位置更新；旧读者的 CAS 无法覆盖新版本。新读取下界设为显式起点，避免重叠窗口重新越过操作者选择的边界。

没有删除 seen、Inbox、出站尝试的接口，未知发送不能通过检查点恢复变成自动可重发。收到超时或失败响应时先查询当前版本，不能假定数据库一定没有执行。内存后端仅供单进程测试，不提供持久恢复审计保证。

恢复后检查配置与新检查点，再使用最新 Binding 版本重新启用。新加入的群若没有检查点，应先设置明确的 `start_at`；不能利用新增绑定绕过幂等。

## 迁移、测试和限制

迁移 `015_channel_recovery.sql` 增加读取下界、异常隔离表与恢复审计表。部署权限生成器已同步新增 Gateway 写入、Admin 查询/恢复所需权限，不授予删除权限。

自动测试覆盖媒体夹在正常消息中、隔离存储故障、重放去重、跨租户拒绝、Auditor 拒绝恢复、启用中绑定拒绝恢复、版本过期、显式跳过确认、恢复审计失败回滚。原始源仍没有唯一 ID，指纹碰撞及有限延迟补偿的限制没有消失；真实媒体/分页格式仍应在受控群联调后再扩展能力。
