- 方法：读取既有评审的可观测性证据，并复核冻结源码、启动接线和相关测试。本次没有启动观测栈或重跑业务测试。“有实现”“作者测试已有执行记录”“评审方独立端到端验证”分别表述；设计声明、跳过测试和健康检查不算完整业务验证通过。
- Trace 分析链路覆盖、异步上下文、父子关系和隐私；Metric 分析指标语义、标签基数、计费与多节点聚合；Log 分析结构、关联和脱敏；Audit 单列持久化、查询及失败语义；同时记录采集、告警与运维缺口。

- 证据列 T/M/L/A 分别对应 Trace/Metric/Log/Audit，链接直接指向冻结源码或项目说明。测试源码说明断言范围；既有测试执行情况来自本批次评审记录。

## 总结与设计观察

1. **异步连续性是关键差异。** 只保留 request_id/trace_id 能检索相关记录，仍需持久父上下文和实际 span 才能还原队列、重试、存储提交、最终发送的因果关系。现有批次没有取得覆盖全部要求环节的独立完整 IM trace 核验结果；局部传播测试仍有价值。
2. **聚合指标与计费账本需要分开。** 处理尝试数、唯一请求数、完成数和外部发送成功数不同；模型流式累计 usage 需去重，缺失 usage/价格须显式表达未知或估算。重启后累计指标、共享库 gauge 和多币种费用也不能直接相加。
3. **低基数需要控制取值数量。** 不把 request/session/user ID 放入标签只是起点；tenant/model/tool 即使经过哈希，数量仍可增长。限制白名单/映射到固定类别有利于控制采集成本，租户明细可由授权账本查询提供。
4. **脱敏需要覆盖实际出口。** 结构化字段、自由文本错误、嵌套对象、SDK 自动 span 和导出器异常各有独立边界。删除 payload 能降低泄漏面，也会减少诊断细节；仅有脱敏函数不能证明所有调用点接入。
5. **审计失败语义直接影响业务。** 有的实现允许队列满丢弃，有的用持久 Outbox/spool 或写失败阻断操作。应明确哪些记录可丢、哪些必须持久化，并验证幂等 ID；审计冲突也可能使管理请求失败。
6. **运维闭环需要观测用户结果和采集系统自身。** 有入站却无完成/回复、最老积压、unknown、审计失败及遥测丢弃都值得监测。提供 Dashboard/规则文件说明有部署资产，不代表外部采集、告警通知和故障处置已经独立验收。
