### S1：真实 Tool 注册、调用和事件桥接

**目标**：让模型产生的 Tool Call 真正调用平台 `ToolInvoker`，并把一次 Tool 生命周期映射到稳定平台事件。

**修改边界**：

- `trpcservice/agent/agent.go`
- `trpcservice/agent/runtime.go`
- `trpcservice/agent/tool.go`
- 必要时新增 `trpcservice/agent/tool_bridge.go`
- `trpcservice/agent/agent_test.go` 及同包 Tool 测试
- 不修改 `tenant`、`storage`、`channels`、`web`

**固定数据边界**：

```go
type ToolRequest struct {
    TenantContext tenant.TenantContext
    Agent         AgentSpec
    ToolName      string
    Arguments     map[string]any
}

type ToolResult struct {
    Content string
    IsError bool
}

type ToolInvoker interface {
    Invoke(context.Context, ToolRequest) (ToolResult, error)
}
```

框架类型只出现在 `trpcservice/agent` 的 bridge 中。bridge 在创建本次 framework agent/runner 时注册一个或多个真实 Tool 定义：

1. Tool schema、ToolName 和 Tool Policy 来自当前 `AgentSpec`/本次执行配置，不来自模型自由输出的租户字段。
2. 框架 Tool callback 将名称和参数解析为平台 `ToolRequest`，使用本次 Runtime 固定的 TenantContext 和 AgentSpec 副本。
3. 调用 `ToolInvoker` 时传递原始 Context，使取消和 deadline 下传。
4. 成功返回框架接受的 Tool result；`ToolResult.IsError` 和 Go error 使用框架规定的错误结果协议。
5. Tool callback 不能修改共享 Provider、全局租户状态或其他请求的 metadata。
6. Tool started/completed/failed 事件由 request-scoped execution state 记录，或从 framework Event 可靠转换；不能使用全局 slice/map。

Tool 事件最少包含：Sequence、Type、Role、ToolName、Content/ErrorType。事件序列必须满足：`tool.started` 先于对应的 `tool.completed` 或 `tool.failed`；同一次调用只能有一个终态事件。

**错误语义**：

- 非取消 Tool error：`ErrToolFailure` 包裹原始 error。
- Tool Context 取消：保留 `context.Canceled` 或 `context.DeadlineExceeded`，同时事件为 `tool.failed`，ErrorType 为稳定分类。
- Tool 参数解析或未知 Tool：`ErrInvalidInput` 或 `ErrToolFailure`，不得调用 invoker。
- Tool 错误不得被压缩为只含 `response.Error.Message` 的字符串。

**S1 测试**：

- Fake framework agent 产生 Tool Call，验证真实 callback 被调用一次。
- callback 收到正确 TenantID、AgentAppID、ConfigVersion、ModelConfigRef、ToolPolicyRef 和防御性复制的参数。
- Tool 成功：事件顺序为 started -> completed，模型能继续完成本轮响应。
- Tool 返回 sentinel error：事件为 started -> failed，返回错误同时满足 `errors.Is(err, ErrToolFailure)` 和 `errors.Is(err, sentinel)`。
- Tool Context canceled/deadline：下游收到取消，不能生成 completed 事件。
- 未注册 Tool、未知 Tool、畸形参数和 nil invoker 均 fail closed。
- 两个租户并发使用同名 Tool，invoker 收到的 Context/Agent 不串用。
- `go test ./trpcservice/agent -run 'Test(Tool|Event|FrameworkTool)' -count=1 -v`
- 对应 targeted `-race` 必须执行。

**S1 关闭条件**：

- `rg` 能找到从 framework Tool 注册对象到 `ToolInvoker.Invoke` 的生产调用链。
- 测试不是只直接调用 `invokeTool`；至少有一项从 framework Tool callback 进入 invoker 的测试。
- Tool 事件和原始错误链测试全部通过。

### S2：Request-scoped execution handle、producer pump 和取消收敛

**目标**：修复当前只 drain Event channel、没有 producer completion 的生命周期缺口。

**设计固定如下**：

为每次 `AgentRuntime.Run` 创建一个内部 execution handle，至少包含：

```go
type execution struct {
    events       <-chan *frameworkevent.Event
    done         <-chan struct{} // Adapter pump 已停止
    runErr       <-chan error
    stopOnce     sync.Once
    stopErr      error
    producerDone atomic.Bool
}
```

具体实现规则：

1. 调用 framework `Run` 后，不把 framework-owned channel 直接交给业务 drain。创建一个 Adapter-owned pump channel。
2. pump 负责从 framework channel 读取事件、按顺序转发到 Adapter-owned channel，并在 framework channel 关闭后关闭自己的 channel、记录 producer error、关闭 `done`。
3. Adapter 不关闭 framework-owned channel；只关闭自己拥有的 pump channel。
4. Runtime drain 只消费 Adapter-owned channel。正常路径必须同时看到 pump channel close 和 `done`。
5. 父 Context 取消时，先通过 `stopOnce` 调用 `ManagedRunner.Cancel(requestID)`；`ErrRunNotFound` 只有在已知 producer 已完成时才可视为无害，否则作为生命周期诊断保留。
6. Cancel/Stop 使用 `StopTimeout`；停止调用超时不能伪造 producer 完成。超时后调用 framework Close 作为最后的 bounded cleanup，并记录 Close error。
7. 取消后继续 drain 一个明确的 grace window；不得用无界 `context.Background()`。grace 结束时，如果 `done` 未关闭，返回 `ErrProducerIncomplete`/`ErrDrainTimeout`，并标明 `producerDone=false`。
8. Event channel close 不等于所有 framework 内部 goroutine 都已退出。方案只把 Adapter pump completion 作为可证明的本地生命周期边界；如果 v1.11.2 没有更强的 framework completion API，最终报告必须明确该剩余限制，不能声称“零 goroutine 泄漏”已经被证明。
9. 任何 producer completion 未到达的路径不能返回成功结果，也不能进入 Platform assistant commit。
10. `fw.Close()` 只执行一次，Close error 用 `%w` 保留；已存在的取消、drain 或 producer error 使用 `errors.Join` 保留所有可判断 cause。

**错误优先级**：

- 参数/配置错误在启动 framework 前返回。
- Provider/Tool/framework 执行错误先记录，不提前停止 drain。
- 主 Context canceled/deadline 优先保留对应 context cause。
- drain timeout 或 producer incomplete 追加稳定 sentinel。
- Close error 作为 secondary cause 加入 error chain。
- 只有 channel close、pump done、无执行错误、结果有效且 Context 未取消时才算成功。

**S2 测试**：

- 正常 producer：发送多个事件、关闭 framework channel，验证事件顺序、pump done、producerDone 和单次 Close。
- framework Run 返回 error 但 channel 仍有事件：先 drain，再保留原始 Run error。
- 主动取消：Provider 收到 Context 取消，ManagedRunner.Cancel 调用一次，pump drain 完成，Runtime 返回前 `done` 已关闭。
- deadline exceeded：与主动取消可区分，StopTimeout 和 DrainTimeout 诊断稳定。
- producer 取消后继续发送尾部事件：pump 不丢事件、不阻塞，最终正常关闭。
- framework channel 永不关闭：在 bounded timeout 内返回 `ErrProducerIncomplete`/`ErrDrainTimeout`，不返回成功；测试明确检查 `producerDone=false`。该测试不允许用 skip。
- Stop 返回 `ErrRunNotFound` 的已完成和未完成两种情况分别验证。
- Stop 永久阻塞：Runtime 在 StopTimeout 内返回生命周期错误；不得等待无界时间。
- Close 返回 sentinel error：`errors.Is` 可判断 `ErrFrameworkFailure` 和原始 sentinel。
- `go test ./trpcservice/agent -run 'Test(Execution|Producer|Drain|Cancel|Deadline|Stop|Close)' -count=1 -v`
- 对应 targeted `-race` 必须通过。

**S2 关闭条件**：

- 生产调用链存在明确的 execution/pump `done` 证据。
- 当前代码中没有“drain 返回即视为 producer 完成”的路径。
- 永不关闭 channel 的故障路径有明确 bounded return 和未完成状态，不能被普通成功测试掩盖。

### S3：Provider 错误链和模型配置隔离

**目标**：修复 provider response error、framework error 和 main 全局配置 resolver 的语义缺口。

**修改边界**：

- `trpcservice/agent/provider.go`
- `trpcservice/agent/runtime.go`
- `trpcservice/agent/agent.go`
- `cmd/trpc-service/main.go`
- `trpcservice/agent/*_test.go`
- `cmd/trpc-service/main_test.go`
- 只有实际 import 需要时才调整 `go.mod`/`go.sum`，不升级 tRPC-Agent-Go 版本

**Provider 错误模型固定如下**：

定义内部稳定错误类型，而不是只返回字符串：

```go
type ProviderResponseError struct {
    Type    string
    Code    string
    Message string
}

func (e *ProviderResponseError) Error() string
```

- OpenAI model 的 transport/auth/network/config error 使用 `%w` 包裹原始 error。
- streamed response 中的结构化 response error 转换为 `*ProviderResponseError`，使用 `%w` 继续包在 `ErrProviderFailure` 下；Type、Code、Message 作为结构化字段保留。
- framework error 使用 `%w`，禁止 `fmt.Errorf("...: %v", err)` 丢链。
- `classifyResultEvents` 不再只返回 `ErrProviderFailure: <string>`；如果 Event 只有结构化错误字段，构造并返回 `ProviderResponseError`，如果 execution state 已记录原始 cause，优先返回该 cause。
- 错误文本脱敏，不包含 API key、Authorization、完整请求消息或完整响应 body。

**配置隔离固定如下**：

- `ModelConfigResolver` 必须按 `(TenantID, AgentAppID, ConfigVersion/AgentVersion, ModelConfigRef)` 查找配置，并拒绝任何 key 不匹配的返回值。
- `SecretResolver` 必须接收同一 TenantContext 和 SecretRef；ProviderFactory 不能把一个租户解析出的 secret 缓存到全局或跨请求可变字段。
- ProviderFactory 每次 Build 创建 request-scoped provider/client，或者返回明确不可变、只绑定当前 config key 的 client；不允许用一个全局 Provider 保存可变 tenant/model 状态。
- 现有 `RuntimeDependencies.Provider` 兼容字段必须移除生产入口。现有 fake 测试迁移到测试专用 `StaticProviderFactory`，避免 NewFactory 继续允许共享 Provider 作为生产依赖。
- `main` 的 env resolver 只能作为明确的单租户开发 bootstrap：捕获 `DEFAULT_TENANT`、默认 Agent ID 和 `MODEL_CONFIG_REF`，仅在请求三元组完全匹配时返回配置；不能声称一个全局 env 配置支持多租户生产隔离。
- 多租户配置的生产解析接口保留为 `ModelConfigResolver`，真实 Registry/Secret Manager 不在 P0-07 实现；没有配置匹配时必须 fail closed，不回退 Echo。

**S3 测试**：

- transport sentinel error：`errors.Is` 能取到原始 error，同时 `errors.Is(err, ErrProviderFailure)` 为真。
- response error：`errors.As` 能取到 `ProviderResponseError`，Type/Code/Message 保留。
- framework error、Tool error、context canceled、deadline、drain timeout 互不混淆。
- tenant-a/agent-a/ref-a 和 tenant-b/agent-b/ref-b 返回不同 endpoint/model/secret ref；并发执行的 Provider 请求不能交叉。
- 错误 ConfigRef、跨租户 ConfigRef、空 secret、错误 provider 名称全部 fail closed。
- env bootstrap 只接受绑定的 TenantID/AgentAppID/ConfigRef；其他请求不能复用 env provider。
- 旧静态 Provider 测试迁移后，生产 `NewFactory` 不再接受共享 Provider 作为隐式 fallback。

**S3 关闭条件**：

- `rg` 能确认所有 framework/provider error 映射使用 `%w` 或明确的 typed error。
- `errors.Is`/`errors.As` 测试覆盖 transport 和 response 两类错误。
- 两个配置 key 的并发隔离测试通过。
- 未实现真实 Registry/Secret Manager 的部分明确记录为后续阶段，不把 env bootstrap 伪装成多租户配置中心。

第一条边界扫描必须无输出。第二条扫描不能代替行为测试，但必须证明：

- Tool helper 存在生产调用链，而不是孤立定义。
- execution pump 有 producer completion 状态。
- Provider response typed error 存在并被使用。
- ModelConfigRef 参与 resolver key 校验。

**最终矩阵必须全部为 `passed` 或明确的范围外限制**：

- Tool 注册/实际调用/事件顺序/错误链：`passed`。

- Provider 原始错误和结构化 response error：`passed`。
- 两租户/两 ConfigRef 并发隔离：`passed`。
- runner actual adapter 成功路径：`passed`。

- 全量 test/race/vet/gofmt：`passed`。
- framework 内部 completion 若 v1.11.2 没有公开 API：必须在关闭报告中明确“已证明 Adapter pump completion，未证明 framework 内部所有后台资源 completion”，并将剩余风险列入 backlog；如果该限制影响 P0-07 的目标验收，则 P0-07 保持 `not verified`，不能强行关闭。
