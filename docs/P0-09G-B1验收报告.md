## 3. 官方 Lark API contract

本阶段以官方 Open Platform 文档和官方 Go SDK 生成 request model 固定 contract：

- Tenant access token：
  `POST /open-apis/auth/v3/tenant_access_token/internal`。
  request body 只由服务端 binding 的 `app_id` 和 SecretRef 解析出的 `app_secret` 构成；成功响应要求 `code == 0`、非空 `tenant_access_token` 和正的 `expire`。
- 文本消息：
  `POST /open-apis/im/v1/messages`，`receive_id_type` 是 query 参数；Authorization 使用内存中的 `Bearer tenant_access_token`。
  request body 只包含 `receive_id`、`msg_type=text`、JSON 字符串形式的 `content={"text":"..."}` 和官方 request model 的 `uuid`。
- receiver type：binding 服务端固定为 `open_id`、`user_id`、`union_id`、`email` 或 `chat_id` 之一；user destination 不允许 `chat_id`，chat destination 必须使用 `chat_id`。
- 最小成功响应：HTTP 2xx 且 JSON `code == 0`，并且 `data.message_id` 非空。只有满足全部条件才返回 Delivered。
- 相关官方页面：
  - Tenant access token：`https://open.feishu.cn/document/server-docs/authentication-management/access-token/tenant-access-token`
  - Create message：`https://open.feishu.cn/document/server-docs/im-v1/message/create`
  - Request URL validation：`https://open.feishu.cn/document/server-docs/event-subscription-guide/event-subscription-configure-/request-url-configuration/validation-of-url`
  - 官方 SDK request model：`https://github.com/larksuite/oapi-sdk-go/blob/main/service/im/v1/model.go`

Webhook challenge、签名/时间戳/nonce、加密事件、event ID/message ID 去重和生产 path/config tenant 映射没有在本阶段接入 `web.Server`；官方 webhook 页面只作为后续 contract 参考，不是生产入口已接入证据。

## 4. Config、SecretRef 和 Binding contract

`channels/lark.Binding` 是服务端不可变 binding 配置：

```go
type Binding struct {
    TenantID       string
    BindingID      string
    Channel        string // lark
    AppID          string
    SecretRef      string
    ReceiverIDType string
    Enabled        bool
}
```

`SenderConfig` 接收 binding 列表、`TokenResolver`、HTTP client、固定 base URL、request timeout 和 response limit。binding ID 由服务端 map 解析，payload 只能引用已提交的 BindingID，不能指定 URL、app secret、tenant 配置或 token。

Secret 只通过：

```go
type SecretResolver interface {
    Resolve(context.Context, string) (string, error)
}
```

`HTTPAccessTokenResolver` 使用 binding 的 AppID 和 SecretRef 取得短期 tenant access token；secret 和 token 只在内存请求期间存在。resolver 的原始错误被转换为有限 sentinel，Sender 不返回、记录或持久化原始错误。

base URL 只允许精确的 HTTPS `open.feishu.cn` 或 `open.larksuite.com` host，不能有 userinfo、query、fragment 或任意 path。Outbox payload 没有 endpoint、SecretRef、app secret、token 或 Authorization 字段。

## 5. Routing、Tenant 和 destination

`ReplyOutboxPayload` 当前为 schema v3，新增必需 `binding_id`：

- `tenant_id`、`binding_id`、`channel=lark`、execution/reply identity 和 destination 都必须存在并有界；
- execution sink 只从已解析 `TenantContext` 生成 BindingID 和 destination；
- `RoutingFromTenantContext` 已支持 Lark 的 user/chat destination；
- Lark Sender 要求 payload BindingID 在 server-owned binding map 中存在、binding tenant 等于 payload tenant、binding channel 是 Lark 且 enabled；
- destination ID 非空、不得包含控制字符且受长度限制；
- receiver ID type 只能来自 binding，不能来自 payload；
- 未知 binding 或 disabled binding 返回稳定的 `lark_sender_not_configured`；tenant/binding/type 不一致在发请求前返回 `lark_sender_invalid_destination`；
- 不从 payload 重新读取 Prompt、History、Agent runtime、Provider request 或任意用户可控 tenant identity。

PostgreSQL 的 Outbox identity/dedup 仍沿用 P0-09F/G-A 的 tenant-scoped execution identity。BindingID 是 routing contract 字段，不改变既有 Outbox ID 或 dedup key。

## 6. Request、success 和 response limits

消息发送 request 的固定 path、method、body projection 和 query 由 Lark package 生成；payload 不含 URL。官方 `uuid` 从已有稳定 external idempotency identity 派生为确定性 UUID，不使用随机数、当前时间或 Secret。

request timeout 和 response body 都有上限。response body 只在内存中 bounded read：超过上限返回 `lark_sender_malformed_response`，读取中断返回 `lark_delivery_outcome_unknown`；空 response 或无法判断是否被接受也返回 unknown。HTTP response/body 不进入 `last_error`、DLQ reason、日志或指标。

`Retry-After` header 被安全忽略，不写入 SenderOutcome、retry durable state 或 sleep。既有 Dispatcher `RetryPolicy` 负责 bounded retry timing，不让 Sender 因 provider hint 占住 Outbox lock。

## 7. Outcome 分类

- `Delivered`：HTTP 2xx、JSON `code=0` 且 `data.message_id` 非空。
- `RetryableFailure(lark_sender_rate_limited)`：HTTP 429。
- `RetryableFailure(lark_sender_unavailable)`：HTTP 5xx；token endpoint 的 5xx 也转换为有限 unavailable。
- `RetryableFailure(lark_sender_timeout)`：context deadline/cancellation 或 transport timeout。
- `RetryableFailure(lark_sender_unavailable)`：transport 明确证明请求未发出。
- `PermanentFailure(lark_sender_auth_failed)`：HTTP 401 或 token resolver/auth failure；2xx provider `code != 0` 在无法由官方 contract 明确解释时统一归入 rejected。
- `PermanentFailure(lark_sender_forbidden)`：HTTP 403。
- `PermanentFailure(lark_sender_rejected)`：其它明确 4xx、provider `code != 0` 的未知业务拒绝、invalid schema 或 Sender config rejection。
- `PermanentFailure(lark_sender_invalid_destination)`：tenant/binding/receiver type/destination mismatch。
- `PermanentFailure(lark_sender_not_configured)`：binding 缺失或 disabled。
- `PermanentFailure(lark_sender_malformed_response)`：2xx response 缺少合法 success contract 或超过 bounded body limit。
- `OutcomeUnknown(lark_delivery_outcome_unknown)`：nil response/body、空 response、response read interruption、plain connection error 或 transport 证明请求可能已经被 Provider 接受。

`outbox.ChannelSender` 将 Lark outcome 适配为现有 `outbox.SenderOutcome`；unknown 不变成 Delivered，Dispatcher 的 existing RetryPolicy 不会第一次直接 DLQ。

## 8. Provider idempotency 结论

官方 Lark message create request model 包含 `uuid` 字段，本阶段按官方字段发送稳定 provider UUID。该值由 tenant/execution/kind 的既有稳定 identity hash 派生，Outbox retry 和 OutcomeUnknown retry 使用相同值；SDK 字段存在不等于服务端去重语义已被本阶段证明。

本地 PostgreSQL dedup 与 Lark provider dedup 是两个独立层次。当前没有授权真实租户，因此没有验证 Lark 服务端实际去重效果；不能宣称 exactly-once。即使使用稳定 `uuid`，OutcomeUnknown 仍可能在 provider 去重未生效、窗口过期或服务端语义不同的情况下导致重复发送。后续真实验收必须单独记录 provider-side dedup/reconciliation 证据。

## 9. Dispatcher 和 PostgreSQL Outbox

接线路径保持：

```text
committed PostgreSQL Outbox
  -> ClaimBatch
  -> DecodeReplyOutboxMessage
  -> Lark binding/tenant/destination validation
  -> token resolver
  -> fixed Lark request
  -> SenderOutcome
  -> existing RetryPolicy
  -> MarkCompleted / MarkRetry / MoveToDLQ
```

Lark Sender 不持有 `storage.OutboxRepository`，不调用 `MarkCompleted`、`MarkRetry`、`MoveToDLQ`，不 Ack Queue，也不提交 execution result。只有 Dispatcher 负责 durable mutation。

新增 `TestPostgresDispatcherClaimsCommittedLarkReply` 使用真实 PostgreSQL Outbox repository、Fake HTTP transport 和内存 token resolver；它验证 committed pending Lark payload 可以 claim、发送后由 Dispatcher 完成。该 test 在本机缺少 `TEST_DATABASE_URL` 时 SKIP，因此本轮没有真实 PostgreSQL Lark integration PASS。既有 PostgreSQL Outbox/DLQ/reclaim/expired-lock 组件证据保持独立，不能外推为真实 Lark Provider 证据。

## 10. Sensitive data 证据

- durable payload 只含 bounded execution/reply/routing projection；不含 Prompt、History、Provider body、app secret、token、Authorization、DSN 或 raw provider error；
- response body、Authorization 和 token 只保留在一次内存 HTTP request/response 生命周期；
- token resolver 错误被转换为 sentinel；transport error 的 `Error()` 不返回底层原文；
- SenderOutcome 只有有限 class 和 safe code；Outbox `last_error` 只接受既有安全 token allowlist；
- unit tests 验证 SecretRef 调用、credential failure redaction、provider response 不进入 outcome/error 和 response body limit；
- 没有日志、metrics 或生产装配改动；真实 gated test 仅使用临时进程环境变量发起受控 Lark 请求，未持久化凭据或请求敏感字段。

## 13. 真实证据收口轮（gated real test）

本轮按 P0-09G-B1 收口要求新增 `trpcservice/channels/lark/lark_real_test.go`，提供唯一、显式门禁的真实 Provider 证据入口，未修改任何生产代码：

- 门禁：只有 `LARK_B1_REAL=1` 时才允许发起真实请求；否则测试 SKIP，默认不向真实群发送任何消息。
- 配置来源：`LARK_B1_APP_ID`、`LARK_B1_APP_SECRET`（`env://LARK_B1_APP_SECRET`）、`LARK_B1_RECEIVER_ID`（`env://LARK_B1_RECEIVER_ID`）只做存在性与本地格式校验；不实现从 Outbox payload、命令行参数或报告读取 Secret 的路径。
- Binding：`tenant-lark-b1` / `binding-lark-b1` / `lark` / `chat_id` / enabled，仅存在于内存。
- 路径：`lark.HTTPAccessTokenResolver` + `lark.Sender` + 真实 `http.Client` + `https://open.feishu.cn`；token 与消息请求 contract（method/path/query、`receive_id_type=chat_id`、`msg_type=text`、JSON 字符串 content、`uuid`）在内存 transport 层校验，token 只存在于单次请求生命周期。
