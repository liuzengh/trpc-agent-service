# P0-09F Atomic Completion + Outbox Enqueue 验收报告

## 1. 状态

P0-09F 状态：`verified (Atomic Completion + Outbox enqueue boundary)`。

本阶段证明：execution result、Queue delivery Ack 和 reply Outbox enqueue 在同一个 PostgreSQL `pgx.Tx` 中提交，三者全部成功或全部 rollback；durable Worker 已强制使用带 Outbox 的 completion contract。

本阶段不证明真实 Sender、真实 IM/Provider、Web/CMD async assembly、生产 SIGTERM orchestration、framework global Wait/Done 或完整业务 Repository。P0-09G 尚未开始。

## 3. Contract 和 reply payload

新的 request 形状为：

```go
type AtomicCompletionRequest struct {
    Commit   ExecutionCommitRecord
    Delivery DeliveryAckRecord
    Outbox   *OutboxMessage
}
```

兼容语义如下：

- `Outbox == nil`：明确表示旧 P0-09C 的 execution result + Queue Ack 两项 contract，不声称包含 durable reply。
- `Outbox != nil`：要求 result、delivery 和 reply Outbox 三项 identity 一致；PostgreSQL coordinator 只接受三项同事务首次提交，或三项已一致提交后的幂等读取。
- 带 Outbox 的请求遇到 result-only、result+ack without outbox、outbox-only、outbox before Ack 或 identity conflict 时返回 conflict/partial，不在普通 retry 中猜测补写。

reply payload 是 `ReplyOutboxPayload` 的有限 JSON projection：

- `schema_version`、`kind`、`tenant_id`、`session_id`、`job_id`、`execution_id`；
- `request_id`、`message_id`、`trace_id`；
- `reply_text`、可选 `finish_type`。

不写入 Prompt、完整 History、Provider response/body、token usage、Authorization、Cookie、DSN 或未定义 provider metadata。事件内容和 metadata 不复制到 payload。payload 经过 JSON 校验和 1 MiB 限制，构造是确定性的，调用方之后修改 `AgentResult` 不影响已构造 bytes。

Outbox identity：

- `Kind = agent.reply`；
- `AggregateID = execution_id`；
- `TenantID = tenant_id`；
- `ID = reply-{execution_id}`；
- `DedupKey = tenant_id + "|" + execution_id + "|agent.reply"`（canonical key 超过 256 字节时使用 `reply-sha256-{hex}` 的确定性 fallback）。

同一 execution retry 生成相同 identity 和 payload；PostgreSQL 的 tenant-scoped unique dedup 保证不同 tenant 可以使用相同业务后缀而不冲突。

## 4. PostgreSQL transaction boundary

`AtomicCompletionCoordinator` 从同一个 pool acquire 一个连接和一个 `pgx.Tx`。当前顺序为：

1. 配置 transaction lock/statement timeout。
2. 按 tenant/job `SELECT ... FOR UPDATE` 锁定 Queue delivery，并从 durable job payload 校验 job、execution、tenant、session identity。
3. 读取当前 execution result 和 reply Outbox；带 Outbox 请求先拒绝已有 partial state。
4. Queue 处于活动 delivery 时，按 tenant/session `SELECT ... FOR UPDATE` 锁定 session lease，重新校验 owner、epoch、fencing token 和数据库时钟下的 lease expiry。
5. result 不存在时插入 `execution_result`；已存在时只接受完全一致的 identity/result JSON。
6. 带 Outbox 请求插入 `outbox_message`，初始为 `pending`、`attempt=1`、无 lock；duplicate ID、dedup 或 payload 不一致返回 conflict。
7. 以 tenant/job/status/delivery token/visibility 条件更新 `job_queue` 为 `acked`。
8. `tx.Commit` 明确成功后才返回 nil。

Coordinator 不调用 `ExecutionResultRepository.CommitExecution`、Queue runtime `Ack` 或 `OutboxRepository.Enqueue`。Outbox 入队和 Queue Ack 使用 transaction 内部 SQL，Redis 不是 Outbox 事实源。

## 5. Rollback、idempotency 和 conflict

真实 PostgreSQL trigger 故障注入通过：

- result insert failure：result、Outbox 均不存在，Queue 仍为 `in_flight`；
- Outbox insert failure：已执行的 result insert 和 Queue Ack 一起 rollback；
- Queue Ack failure：result、Outbox 一起 rollback，Queue 不进入 `acked`。

重复请求语义：

- 相同 tenant、job、execution、session、fence、delivery token、result JSON、Outbox identity/payload：幂等成功，不生成第二条 result 或 Outbox；
- 相同 dedup key 不同 Outbox ID/payload：稳定 `ErrConflict`；
- 相同 execution 不同 result：稳定 conflict；
- tenant、session、job、execution、aggregate 或 payload identity 不一致：拒绝；
- 旧 P0-09C result+ack 无 Outbox 状态：带 Outbox request 返回 `ErrCompletionPartial + ErrConflict`，不隐式补写；旧 nil Outbox request 保持两项兼容读取。

Fake coordinator 对 result、Outbox、Ack fault 采用相同 all-or-nothing 状态模型；Fake 不替代真实 PostgreSQL 证据。

## 6. Fence、delivery 和 Worker

真实 acceptance 覆盖：

- tenant mismatch、session/job/execution mismatch；
- owner、epoch、fence token mismatch；
- expired delivery、discarded delivery 和 reclaimed old delivery token；
- session lease takeover 后旧 owner 被拒绝；
- 两个独立 PostgreSQL pool 同时提交同一 completion，最终最多一条 result 和一条 Outbox；
- durable Worker 使用 `NewWithAtomicCompletion`，执行路径为：

```text
Receive -> Lease/ExecuteWithCompletion -> BuildReplyOutboxMessage
        -> CommitResultAndAck(result + outbox + queue Ack) -> Release
```

成功前不释放 lease。Worker 不回退到独立 `Commit -> Ack -> Enqueue`；coordinator 缺失时 `NewWithAtomicCompletion` 直接返回配置错误。Provider/runtime failure 和 fence loss 都不会写三项事实。

## 7. Unknown outcome reconciliation

commit 附近连接关闭使用现有 test-only seam，真实 PostgreSQL 返回 `ErrCompletionOutcomeUnknown`，不返回 clean success，也不执行 Ack/Nack/Retry/DLQ。只读 reconciliation 同时读取 result、Queue 和 Outbox，并区分：

- `all_committed`；
- `none_committed`；
- `result_only`；
- `result_and_ack_without_outbox`；
- `outbox_only`；
- `result_and_outbox_only`；
- `ack_only`；
- `partial_conflict`；
- `delivery_token_taken_over`；
- `unknown`（reconciliation 自身不可用）。

三项正常事务只应得到 all committed 或 none committed。partial outcome 只表示 P0-09C 历史状态、故障注入或外部破坏，不能隐藏为成功。unknown retry 或后续 Dispatcher 发送仍依赖 Outbox/provider dedup；本阶段没有证明外部发送不会重复。

## 8. Migration 和事实源

没有新增 migration。复核确认 `000001` 的 `outbox_message` 已有 tenant、identity、payload、status、attempt、lock 和 dedup 字段，`000005_outbox_repository` 已有：

- attempt positive；
- processing lock consistency；
- payload/identity/error size bounds；
- ready 和 processing-expiry partial indexes。

P0-09F 只复用已有 `000005` schema，没有修改已应用 migration。PostgreSQL Outbox 仍是 durable 事实源；Redis 不是 Outbox 事实源。

## 10. 证据边界和 deferred

本报告不把 Docker PostgreSQL restart 解释为完整 OS crash、生产集群 failover 或 framework global Wait/Done。P0-09F 也不证明：

- 真实 Sender 或外部 IM/provider outcome；
- Web/CMD async assembly；
- 生产 SIGTERM orchestration；
- 完整业务 Repository/Unit of Work；
- 真实进程 crash 后的 framework goroutine 收敛；
- unknown 后的 provider-side dedup、重复发送消除或全链路 exactly-once。

P0-09A/B/C 的核心边界保持不变，P0-09D Outbox Repository 和 P0-09E Dispatcher/Retry/DLQ contract 保持通过。P0-09G 尚未开始，必须等待新的明确指令。
