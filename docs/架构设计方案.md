# 架构设计方案

## 目标与边界

平台面向多个租户、多个 Agent 应用和多个 IM 入口。每个租户拥有独立的模型配置、
通道绑定、工具权限、知识库、会话数据和审计策略。平台复用 tRPC-Agent-Go 的
Runner、Session、Tool、Memory、Knowledge、Artifact、Guardrail 与 OpenTelemetry 能力，
新增多租户控制面、通道适配、可靠执行和运营接口。

本项目实现了可运行的最小闭环；设计中的灰度发布、租户周期预算、危险工具审批、
KMS 提供方和全量租户级后端选择仍是后续扩展点，详见[代码实现说明](代码实现说明.md)。

## 组件职责

| 组件 | 职责 |
| --- | --- |
| Gateway | 验签、租户识别、消息归一化、幂等、会话串行化和回复输出。 |
| Channel Adapter | 对接企业微信、微信客服和 WebChat 的收发协议。 |
| Worker | 运行 Agent，调用模型和受控工具，提交会话事件、状态和回复。 |
| Delivery | 从 Reply Outbox 读取待投递回复并调用通道发送接口。 |
| Jobs | 执行摘要、知识库索引、Memory 索引和 Redis 投影等异步任务。 |
| Control Plane | 管理租户、应用、修订、模型、后端、工具和通道绑定。 |
| Storage | 提供 Session、MySQL、Redis、Qdrant、MinIO 等存储能力。 |
| Telemetry | 输出 trace、指标和审计记录。 |

## 多租户隔离

请求入口构建租户上下文，后续所有存储查询、缓存键、通道绑定、工具绑定和审计记录
均携带 `tenant_id`。控制面数据库使用 tenant-scoped 联合唯一键和外键，阻止跨租户引用。
Redis Session 使用租户前缀；Qdrant 点位和 MinIO 对象键包含租户范围；技能和工作目录
按租户目录隔离。

密钥以引用形式存储，运行时仅允许从受控 `env:` 或 `file:` 来源解析。结构化日志会对已知
环境变量密钥进行脱敏，业务回复不回传上游内部错误。

## 节点与会话

Gateway 和 Worker 可采用无状态部署。可靠模式把会话、Inbox、执行记录、Outbox 和审计
写入 MySQL，Worker 通过租约和 fencing token 领取工作；Redis 可保存会话投影和跨实例
协调锁。正常情况下共享协调锁保证同一会话串行，Worker 故障后租约过期即可由其他
Worker 接管。

不依赖 HTTP sticky session：会话状态在共享后端中恢复。消息路由键由租户、通道、用户或
群聊标识构成；单聊和群聊不会共享会话。

## IM 与治理

企业微信采用验签、AES 解密和主动发送消息；微信客服先记录回调通知，再拉取消息并投递；
WebChat 用于本地对话验证。输入 Guardrail 在模型调用前执行，输出 Guardrail 对流式文本
执行截断。工具按发布修订固定绑定，并对 HTTP URL、方法、参数、密钥引用和调用次数执行
控制。

审计记录 `tenant_id`、通道、用户、会话、Agent、工具、决策、延迟、错误、Token、成本和
`trace_id`。OpenTelemetry 将 IM 回调、Gateway、模型调用和工具调用串联。

## 故障处理

模型请求受 `context.Context` 超时约束；失败时向用户返回安全的通用提示并记录审计。Reply
Outbox 把执行提交与外部 IM 投递分离；投递失败可重试，副作用不确定的工具调用会阻塞会话并
等待人工处置。健康检查区分存活和就绪，依赖后端不可用时就绪检查失败以便编排系统摘流量。

最小部署使用 Docker Compose；生产部署使用 Kubernetes 的 Deployment、Service、HPA、PDB
和 Ingress 清单。
