## 3. 官方 Telegram API contract

已直接核对官方页面 `https://core.telegram.org/bots/api`：

- Bot API 支持 GET/POST；本实现固定使用 POST。
- `getMe` 不需要参数，成功返回 `User`。
- `sendMessage` 成功返回 `Message`；最小请求只含 `chat_id` 和 `text`，topic 时增加 `message_thread_id`。
- `chat_id` 官方允许 Integer 或 String；本项目 routing contract 固定为 canonical numeric int64 字符串，拒绝 `@username`。
- `text` 是 UTF-8 文本；本阶段 plain text 上限按官方 1-4096 字符执行，使用 deterministic rejection，不截断、不静默改写、不分片。
- `Message` 使用 `message_id`、可选 `message_thread_id`、可选 `from`、必需 `chat` 和可选 `text`；`Chat` 使用 numeric `id` 和 `type`；`User` 使用 numeric `id`。
- `Update.update_id` 是递增的唯一标识，官方明确说明 webhook 场景可用它忽略重复 update；本包只生成稳定 dedup key，不持有 PostgreSQL dedup repository。
- `setWebhook.secret_token` 为 1-256 个字符，仅允许 `A-Z`、`a-z`、`0-9`、`_`、`-`；Telegram 会在每次 webhook 请求中发送 `X-Telegram-Bot-Api-Secret-Token`。
- 官方 response envelope 使用 `ok`、成功时 `result`、失败时 `error_code`/`description`，限流可带 `parameters.retry_after`。Sender 只读取有限结构，不保存原始 body、description 或 header。
- `sendMessage` contract 没有本项目所需的 outbound idempotency key 或 dedup key。未向请求 body 添加 `uuid`、`idempotency_key` 或其他未定义字段。

## 4. Binding、routing 和 webhook

Binding 至少表达：

```text
TenantID
BindingID
Channel=telegram
BotTokenSecretRef
enabled
```

Webhook 配置另外要求服务端提供 `WebhookSecretRef` 对应的已解析 secret。`EnvironmentSecretResolver` 只接受显式 `env://NAME`，当前真实测试代码约定的本机变量名为 `TELEGRAM_B2_BOT_TOKEN`、`TELEGRAM_B2_CHAT_ID`、`TELEGRAM_B2_WEBHOOK_SECRET`；真实 gate 只从进程环境读取所需值，报告不记录任何值、长度或 hash。

Sender 只从 server-owned Binding map 取得 Bot Token SecretRef，不从 Outbox payload 读取 token。Outbox payload 只含 tenant、binding、channel、destination、reply 和稳定内部 identity；不含 endpoint、token、Authorization、SecretRef、Prompt、History 或 provider response。

`ReplyOutboxPayload` schema v4 的 `message_thread_id` 是显式可选字段，来源是服务端已验证 `TenantContext.ExternalThreadID`。旧 schema v3 payload 仍可解码；旧 Web/Lark payload 不要求 thread 字段。

支持范围：

- private chat：numeric positive chat ID；已测试；
- group：numeric negative chat ID，chat-level 发送/解析已测试；
- supergroup：numeric negative chat ID，chat-level 发送/解析已测试；
- topic/thread：private 和 supergroup 的正 `message_thread_id` 已正式投影并测试；group 的 thread 被明确拒绝，因为官方字段 contract 不适用于普通 group；
- username/string target：拒绝；
- channel/non-text update：当前 parser 明确拒绝；
- webhook production entry、快速 ACK、Queue 投递、Worker、Outbox reply 和 production Dispatcher registration：deferred to P0-09G-C。

不信任 Update body 中的 tenant ID；parser 不产生 tenant identity，服务端应由 webhook path/config Binding 映射 tenant。

## 5. Sender request 和 outcome

生产 Base URL 固定为：`https://api.telegram.org`。Sender 只构造：

```text
POST https://api.telegram.org/bot<token>/getMe
POST https://api.telegram.org/bot<token>/sendMessage
Content-Type: application/json
```

`sendMessage` body 只包含：

```json
{
  "chat_id": "<server-validated numeric chat id>",
  "text": "<bounded plain text>",
  "message_thread_id": 123
}
```

第三个字段仅在服务端 routing contract 提供 topic/thread 时存在。没有 parse mode、Markdown/HTML、link preview、reply markup、inline keyboard 或未定义 idempotency 字段。Token 只出现在内存 HTTP request URL path；transport error、SenderOutcome、Dispatcher durable error 和 DLQ reason 都不会返回或写入 URL。

安全分类：

| Provider/transport 情况 | Sender outcome |
| --- | --- |
| HTTP 2xx、`ok=true`、`result.message_id` 为合法正整数 | `Delivered` |
| HTTP 429，或 envelope `error_code=429` | `RetryableFailure(telegram_sender_rate_limited)` |
| HTTP 5xx，或 envelope `error_code>=500` | `RetryableFailure(telegram_sender_unavailable)` |
| 请求明确未发出且 timeout | `RetryableFailure(telegram_sender_timeout)` |
| 请求明确未发出的一般 transport failure | `RetryableFailure(telegram_sender_unavailable)` |
| 请求可能已到达、plain network error、已发出 timeout/cancel、response body read interruption、response nil/body nil | `OutcomeUnknown(telegram_delivery_outcome_unknown)` |
| HTTP 401 或 envelope `error_code=401` | `PermanentFailure(telegram_sender_auth_failed)` |
| HTTP 403 或 envelope `error_code=403` | `PermanentFailure(telegram_sender_forbidden)` |
| HTTP 400、其他明确 provider rejection | `PermanentFailure(telegram_sender_rejected)` |
| text 超过 4096 字符 | `PermanentFailure(telegram_sender_message_too_long)` |
| HTTP 2xx malformed envelope/result/message_id | `PermanentFailure(telegram_sender_malformed_response)` |
| username、tenant/binding/destination/thread mismatch | `PermanentFailure(telegram_sender_invalid_destination)` |
| unknown/disabled Binding | `PermanentFailure(telegram_sender_not_configured)` |

`retry_after` 不使 Sender sleep、不占用 Outbox lock、不进入 durable error；现有 bounded RetryPolicy 决定下一次 retry。Telegram Sender 不持有 Outbox Repository，不调用 MarkCompleted/MarkRetry/MoveToDLQ、Queue Ack 或 execution commit；Dispatcher 是唯一 durable mutation owner。

## 6. Dispatcher 和 PostgreSQL

链路保持：

```text
committed PostgreSQL Outbox
  -> ClaimBatch
  -> decode/validate Telegram routing payload
  -> Telegram Sender
  -> SenderOutcome
  -> existing RetryPolicy
  -> MarkCompleted / MarkRetry / MoveToDLQ
```

Fake/in-process evidence：

- Delivered 由 Dispatcher 完成；
- 429 由 Dispatcher retry，Telegram safe code 保留；
- OutcomeUnknown 首次不完成、不直接 DLQ；
- invalid/disabled Binding fail closed；
- 一个失败消息不污染同批其他消息；
- Stop 不启动新的 Telegram request，in-flight request 遵守现有 bounded shutdown boundary。

Telegram + PostgreSQL Dispatcher integration：`PASS`。新增测试 `TestPostgresDispatcherClaimsCommittedTelegramReply` 使用真实 PostgreSQL Outbox Repository、Fake HTTP transport 和内存 token resolver；验证 committed pending Telegram payload 可以 claim、调用 sender、完成 durable Outbox。此项不是真实 Telegram + PostgreSQL combined evidence。

## 7. Provider dedup 结论

Telegram `sendMessage` 没有本项目可依赖的官方 outbound idempotency/dedup 字段或 reconciliation lookup contract。本项目保留稳定 PostgreSQL Outbox ID、tenant-scoped dedup key、execution identity 和 internal routing identity，但这些不是 Telegram provider dedup。

结论：`provider-side dedup: not supported or not demonstrated`；`exactly-once: not supported`；delivery semantics 是 at-least-once with duplicate-send risk。OutcomeUnknown 重试可能重复发送，不能 MarkCompleted；多片发送未实现，也不声称 exactly-once。
