# solution 对照赛题 Review（2026-09-11）

初次审查结论：主要模块、设计交付和最小消息链路已覆盖，但不能认定“所有功能已实现且可生产验收”。初次发现的三个运行时问题已在随后修复；下文 R1–R3 保留原始发现以便追溯。

## 修复状态（2026-09-11）

- **R1 已修复**：每次实际权限检查分配独立审计事件 ID，包含 turn/revision 作用域；SQL/spool 对同一已保存事件继续使用原 ID 与正文。真实重新执行会记录新事件，canonical replay 不重新检查权限。新增真实 PostgreSQL 回归验证两轮相同参数产生两条工具审计，第三次重放不新增审计。
- **R2 已修复**：Worker 输出安全检查使用 `OutputCandidateKey(message, revision, text)`，同一候选输出可复用决策，新正文必须独立检查；不改写旧安全记录，不需要更改 009 migration。新增事务回滚后不同回复的成功/拦截回归，以及跨节点 PostgreSQL 候选决策测试。
- **R3 已修复**：Registry 发布前调用连接 reconcile，新增/替换连接先认证再安装；失败关闭暂存客户端，保留旧映射及配置。reload、控制面发布和本地 rollback 均经过此门禁；禁用会关闭客户端。每批准备限时 10 秒，单次握手限时 5 秒。同一 binding 的 canary 不支持切换机器人身份/凭据引用，需 full release。初始启用的机器人同样必须完成认证，不能以占位凭据启动后宣称就绪。
- **验证时附带修复**：离线 smoke 禁用外部企微长连接；HAProxy 将 `/healthz` 交给独立 liveness 上游，避免数据库故障使所有 readiness 失败后存活探针也错误返回 503。

新增回归位于 `worker/review_regression_test.go`、`contentsafety/postgres_integration_test.go`、`aibotbridge/reconcile_test.go`、`tenant/publication_test.go`。企微连接生命周期测试使用受控客户端工厂；本轮没有向真实企微发送消息，也没有以真实 Bot 凭据验证轮换。原先列出的 DLP、多媒体等未实现能力不因这次修复被标记为完成。

修复后已通过：全量 Go 测试、全量 race、go vet、build.sh（三个二进制与前端嵌入）、HTTP smoke，以及隔离临时 PostgreSQL 的 14 包 race/no-cache 门禁（无 SKIP）。生产 Compose 的双副本、断连、提交确认丢失、安全检查、RBAC、Secret 与 trace 门禁通过，见 [生产验收记录](../evidence/production/summary-trpc-prod-acceptance-242229407.txt)。smoke 中仅可选 promtool 语义检查因本机未安装而跳过。

## 原始问题（已修复）

### R1 / P1：工具权限审计 ID 跨轮次冲突，SQL 审计导致后续消息失败

位置：`trpcservice/worker/service.go:933–935`；关联 `trpcservice/log/audit_sql.go:133–140`、`worker/service.go:707`。

权限审计 ID 仅由 tenant、session、tool、参数 hash 和 decision 派生，没有 TurnID、真实调用身份或配置版本。同一个用户在同一会话两次调用相同参数（例如再次计算 2+2）会产生相同 ID，但 Timestamp、RequestID 等审计正文不同。PostgresSink 对相同 ID 的不同正文返回 ErrAuditConflict；Worker 记录该错误，并在 Runner 完成后返回错误，无法正常提交回复。一次运行里重复检查相同调用、失败后重新执行也可能命中。

临时探针直接调用实际 observeToolDecision，使用两个不同 RequestID/TurnID，确认输出相同 AuditID、不同正文。SQL 冲突和 Worker 失败传播通过源码确认，本轮没有将该场景连接真实 PostgreSQL 重跑。

修复要求：按稳定 turn 和具体工具调用/权限事件生成身份，并规定重试时如何重放已保存审计正文；只在 ID 里加时间戳会破坏幂等。回归至少覆盖跨轮同参、同轮重复调用和故障重放。

### R2 / P1：输出安全决策先落库，事务回滚后不同回复无法重新通过检查

位置：`trpcservice/contentsafety/safety.go:186–190`；关联 `worker/service.go:730–745`、`worker/service.go:803–807`。

输出检查以 tenant/message/phase/policy 为唯一身份，首次通过即独立持久化 content_hash。随后 Session/Inbox/Outbox 组合提交若回滚，尚无 canonical replay；重试必须再次运行模型。模型返回不同文字时，旧安全记录因 hash 不同返回 ErrInvalid，Worker 将其转换成可重试 ErrUnavailable。此后重试仍受旧 hash 限制，可能反复调用模型并最终进入死信，无法恢复原消息。

临时探针使用实际 MemoryChecker，先检查 first answer，再对相同消息检查 retry answer，确认返回 ErrInvalid；PostgreSQL 路径具有同样的 hash 拒绝分支。该探针证明冲突条件，不等于真实进程崩溃/事务故障演练。

修复要求：输出审批应绑定具体候选输出身份（如 attempt/content hash），提交时验证所提交正文对应的 allowed 决策；或先持久保存可重用候选输出，使重试不重新生成。不能简单接受旧 allowed 决策放行新正文。补充“输出检查完成→提交回滚→不同输出重试”的集成测试。

### R3 / P2：企微智能机器人连接没有参与配置发布与回滚

位置：`trpcservice/aibotbridge/bridge.go:88–136`；关联 `cmd/trpc-service/main.go:161–162,304`。

Start 只在进程启动时遍历 binding，解析 BotID/Secret 并建立连接。控制面的 Apply 仅 PublishControlState；Manager 没有配置 reconcile 路径。新增机器人 binding 后不会连接，修改 BotID、Secret 引用或 WebSocketURL 后仍持有旧连接，回滚也不恢复对应连接。Registry 更新只能改变已有回调的路由，不能创建或替换 WebSocket 客户端。

修复要求：把连接的准备、认证、替换和关闭接入 release 生命周期，成功后再 ACK；若暂不支持，则显式拒绝此类热更新，并要求重启，不能将配置生效等同于通道已生效。需要覆盖新增、轮换、禁用、回滚和失败保留旧连接。
