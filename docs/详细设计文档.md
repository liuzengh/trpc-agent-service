## 1. 设计总纲与核心决策

| 决策项 | 结论 |
| --- | --- |
| 租户层级 | **Tenant → Agent 两级** |
| 共享资源 | ModelEndpoint、Skill（GLOBAL/TENANT）、知识库均为租户级共享资产 |
| 部署形态 | 单一二进制 + 角色标志（gateway/worker/admin/all） |
| Worker 状态 | 无状态 + 共享 Session/Memory 后端 |
| 消息总线 | Redis Streams + Consumer Group |
| 数据库 | MySQL（强一致权威）+ Redis（缓存/队列/锁） |
| 向量库 | Milvus（复用 `storage/milvus`） |
| 对象存储 | MinIO（复用 `storage/s3` S3 兼容） |
| Admin API | RESTful（框架无通用 REST CRUD） |
| 模型接入 | 自建 ModelEndpoint 归一化层 |
| Skill | 组织级四级资产模型（复用框架 SKILL.md 格式 + 注入） |
| 租户级后端 | 数据域（session/memory/summary/artifact/vector/audit）逐域可选后端，Storage Adapter 按租户路由 |

## 2. 数据模型：MySQL 表结构

> 表结构覆盖 README 要求的最小数据模型：tenant、agent、session、event、memory、**summary**、channel binding、audit log，并补充 model endpoint、tool、knowledge、skill、artifact、usage。
>
> **权威建表语句**：最终 SQL 见 `deployments/mysql/init/*.sql`（已评审借鉴参考 DDL 后定稿：BIGINT 物理行 ID + UUID 业务键防枚举 + 软删 + 账本 turn/status 流）。本节为设计概要，字段以 SQL 为准。

### 2.1 租户与成员

```sql
CREATE TABLE tenants (
  tenant_id    VARCHAR(36) PRIMARY KEY,   -- UUID
  name         VARCHAR(128) NOT NULL,
  status       ENUM('active','disabled') DEFAULT 'active',
  model_config JSON,                       -- 默认模型端点引用 {endpoint_id, model_name}
  data_backend JSON,                       -- 租户级数据后端选择，见 §5.8（session/memory/summary/artifact/vector/audit 逐域指定）
  audit_policy JSON,                       -- 审计策略：记录粒度/保留期/脱敏规则

  created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE tenant_members (
  tenant_id    VARCHAR(36) NOT NULL,
  user_id      VARCHAR(64) NOT NULL,
  role         ENUM('owner','admin','member') NOT NULL DEFAULT 'member',

```

## 3. Redis Key 设计

| Key | 类型 | 用途 | TTL |
| --- | --- | --- | --- |
| `stream:inbound` | Stream | 统一消息总线（IM → Worker） | 持久 |
| `stream:outbound` | Stream | 回复回流（Worker → IM） | 持久 |
| `route:{tenant_id}:{session_id}` | String | session → agent 路由表 | 7d |
| `lock:session:{tenant_id}:{session_id}` | String(NX) | 会话并发串行化锁 | 30s |
| `idem:{msg_key}` | String(SETNX) | 消息幂等去重 | 24h |
| `mem:{tenant_id}:{user_id}` | Hash | Memory 缓存（跨节点可见） | 持久 |
| `sum:{tenant_id}:{session_id}` | String | 摘要缓存 | 10m |
| `runtime:{agent_id}:{version}` | String | 运行时画像缓存 | 10m |
| `endpoint:{endpoint_id}` | String | ModelEndpoint 元数据缓存 | 10m |

命名统一前缀 `{tenant_id}:` 保证租户隔离；global 资源用 `global:` 前缀。

## 4. 核心 Go 接口定义

```go
// Package storage defines backend abstractions. (注释英文)
package storage

// SessionStore is the shared session backend enabling stateless workers.
type SessionStore interface {
    Get(ctx context.Context, tenantID, sessionID string) (*session.Session, error)
    AppendEvent(ctx context.Context, tenantID, sessionID string, seq int64, ev *model.Message) error
    UpdateState(ctx context.Context, tenantID, sessionID string, state []byte) error
}

// MemoryStore persists cross-node-visible memory entries.
type MemoryStore interface {
    Get(ctx context.Context, tenantID, userID, key string) ([]byte, error)
    Put(ctx context.Context, tenantID, userID, key string, value []byte) error
}

// SummaryStore persists rolling conversation summaries keyed by session.
type SummaryStore interface {
    Get(ctx context.Context, tenantID, sessionID string) (string, int64, error) // text, seq
    Put(ctx context.Context, tenantID, sessionID string, seq int64, text string) error
}

// ArtifactStore stores artifact metadata; files live in MinIO.
type ArtifactStore interface {
    Create(ctx context.Context, a *Artifact) error
    Get(ctx context.Context, tenantID, artifactID string) (*Artifact, error)
    ListBySession(ctx context.Context, tenantID, sessionID string) ([]*Artifact, error)
}

// AuditStore appends immutable audit records.
type AuditStore interface {
    Append(ctx context.Context, e *AuditEvent) error
    Query(ctx context.Context, tenantID string, filter AuditFilter) ([]*AuditEvent, error)
}

// Router selects a backend implementation per (tenant, data-domain).
// This is the tenant-level backend selection & routing layer.
type Router interface {
    Session(tenantID string) SessionStore
    Memory(tenantID string) MemoryStore
    Summary(tenantID string) SummaryStore
    Artifact(tenantID string) ArtifactStore
    Audit(tenantID string) AuditStore
}
```

```go
package channel

// Adapter is the unified IM adapter contract for WeCom and Feishu.
type Adapter interface {
    Name() string
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
    // Inbound returns the channel of normalized inbound messages.
    Inbound() <-chan *InboundMessage
    // Send pushes an outbound message (text/card/stream) to the IM platform.
    Send(ctx context.Context, msg *OutboundMessage) error
}

// InboundMessage is a normalized message from an IM platform.
type InboundMessage struct {
    PlatformMsgID string // original platform message id, for dedup
    TenantID      string
    AgentID       string
    SessionID     string
    UserID        string
    ChatType      string // single | group
    ChatID        string
    Content       string
    MsgType       string // text | image | file | event(撤回/失败)
}

// OutboundMessage is a normalized reply (text / stream / card).
type OutboundMessage struct {
    Inbound  *InboundMessage
    Kind     string // text | stream | card
    Segments []Segment
    // Stream is set when Kind == stream; consumer drains the channel.
    Stream <-chan string
}
```

## 5. 租户隔离机制（含租户级后端选择）

1. **上下文传递**：Gateway 鉴权后把 `tenant_id` 注入 `context.Context`，经消息总线 → Worker → Runner 全程透传。
2. **SQL 强制过滤**：仓储层统一加 `tenant_id` 过滤（所有查询带租户条件，杜绝跨租户查询）。
3. **Redis 隔离**：key 统一 `{tenant_id}:` 前缀；global 资源 `global:` 前缀。
4. **对象存储隔离**：MinIO 路径 `{tenant_id}/{...}`，双向不可读（借鉴参考 PR 思路）。
5. **向量库隔离**：Milvus collection/partition 按 `tenant_id` 隔离。
6. **密钥隔离**：密钥走 Secret 引用（`credential_ref`/`api_key_ref`），运行时经 Secret 服务注入，日志/trace 全脱敏。
7. **工具权限隔离**：模型只能调用 Agent 白名单内工具，授权由后端可信上下文判定。
8. **成本隔离**：usage/audit 均带 `tenant_id`，配额（quota）按租户计，超限熔断。

### 5.8 租户级数据后端选择与路由

- **数据域**：`session`、`memory`、`summary`、`artifact`、`vector`（知识库）、`audit` 六个数据域逐域可选后端。
- **可选后端**（复用 tRPC-Agent-Go 多后端实现，平台层包装）：
  - session：`inmemory` / `redis` / `mysql`（框架已提供 `session/redis`、`session/mysql`、`session/inmemory`）
  - memory：`redis` / `mysql`
  - summary：`mysql`（权威）+ `redis`（缓存）
  - artifact：元数据 `mysql` + 文件 `minio`（`storage/s3`）
  - vector：`milvus`（`storage/milvus`）
  - audit：`mysql`（可扩展 ES，需用户确认）
- **选择机制**：`tenants.data_backend` JSON 逐域指定；`storage.Router` 按 `tenant_id` 解析并缓存实现，运行时路由，无需改代码即可替换后端。
- **默认值**：未配置时全平台默认（session=redis、memory=redis、summary=mysql、artifact=minio、vector=milvus、audit=mysql）。

## 6. 会话路由与粘性策略

- **无状态 Worker**：Worker 不持有会话本地状态，任意节点可处理任意会话。
- **session_id 生成规则**：
  - 单聊：`{tenant}:{channel}:user:{openId}`
  - 群聊：`{tenant}:{channel}:group:{chatId}`
  - 跨群/跨租户天然隔离（session_id 含 tenant + channel + 会话对象）。
- **路由表**：`route:{tenant}:{session}` → agent_id，Redis 缓存 + MySQL 权威。
- **粘性判定**：**不需要 sticky**。同一会话的并发消息用 Redis 锁 `lock:session:{tenant}:{session}` 串行化，保证事件顺序。

## 7. 跨节点数据同步与多后端一致性

| 场景 | 方案 | 理由 |
| --- | --- | --- |
| 消息入队/消费 | Redis Streams + Consumer Group（XADD/XREADGROUP/XAUTOCLAIM） | Redis 已强制，避免额外 MQ；XAUTOCLAIM 支持故障认领 |
| 可靠投递 | MySQL Outbox（先写库 → 再发 Stream，消费后标记 sent） | 借鉴参考 PR 思路，MySQL 强一致兜底 |
| 多节点并发写 session | Redis 会话锁 + `session_events` 单调 seq + MySQL 事务 | 保证事件顺序，避免覆盖 |
| event/state/summary 更新顺序 | event 先落（seq 递增）→ state 更新 → summary 按 seq 水位增量更新 | 摘要水位单调，任意节点读到一致快照 |
| Memory 跨节点可见 | 写 Redis Hash（原子 Lua）+ 异步落 MySQL，读走 Redis | Redis 共享缓存天然跨节点 |
| 后端迁移（Redis→SQL） | 双写过渡 + 回填脚本 + 灰度切换 | 平滑迁移，可回滚 |
| 向量库迁移（本地→远端 Milvus） | 文档元数据在 MySQL，向量离线重建 + 双写切换 | 向量可重建，元数据不丢 |
| 对象存储迁移 | 元数据在 MySQL，文件跨桶复制 + 签名 URL 重定向 | 文件可整体搬迁 |
| IM 消息重复投递 | `idem:{msg_key}` SETNX + MySQL idempotency_keys 唯一键 | exactly-once 语义 |

**一致性取舍（四类后端）**：

| 后端 | 一致性 | 读写延迟 | 成本 | 运维复杂度 |
| --- | --- | --- | --- | --- |
| MySQL（SQL） | 强一致 | 中 | 中 | 低 |
| Redis | 最终一致（可调 AOF） | 低 | 中 | 中 |
| Milvus（向量） | 最终一致 | 低-中 | 高 | 高 |
| MinIO（对象） | 强一致（S3） | 中-高 | 低 | 低 |

跨节点共享状态以 MySQL 为权威、Redis 加速；向量与对象存储仅承载其专属数据域，不参与会话一致性。

## 8. IM 适配器接口与实现要点

### 8.1 统一接口与两条通道

- 统一接口：见 §4 `channel.Adapter`。
- **企业微信**（微信系，满足「至少含微信/企业微信」）：`wss://openws.work.weixin.qq.com` 客户端 WSS 模式（借鉴 aibot-node-sdk 协议，Go 实现）；回调验签（token + AES 解密）、消息去重、身份映射；群聊用平台原生群投递。
- **飞书**：官方 v3.7.2 `ws.Client` + `EventDispatcher`，订阅 `im.message.receive_v1`；群聊需 `@机器人` 精确提及过滤；Markdown 归一化。

### 8.2 消息转换与回复

- **入站**：IM 消息 → 解析出 `platformMsgID` / 用户 / 会话 → 校验身份映射 → 归一化为 `InboundMessage` → 转 `model.Message`（role=user）→ 投递消息总线 → Worker 调用 `runner.Runner.Run`。
- **出站**：Agent Event 流 → 按事件类型映射：
  - `message.delta` → 流式回复（`OutboundMessage.Kind=stream`）
  - `final output` → 文本回复（`Kind=text`）
  - `tool.*` / `approval.*` → 卡片消息（`Kind=card`，用于审批通知）
  - `artifact.created` → 附带产物卡片 + 短期签名下载链接。

### 8.3 账号绑定、验签与身份映射

- **绑定**：`channel_bindings` 表绑定「渠道 + 账号 + 租户 + Agent」，凭证走 `credential_ref`。
- **验签**：企业微信回调验签（signature/timestamp/nonce）；飞书事件校验。
- **去重**：`idem:{msg_key}` 幂等。
- **身份映射**：IM openId/userId → 平台 user_id，群成员跨租户校验（隔离策略）。

### 8.4 IM 平台限制

| 限制 | 应对 |
| --- | --- |
| 消息长度 | 超长截断 + 卡片/文件续传 |
| 频率限制 | 租户/渠道级限流 + 异步排队 |
| 异步回复 | 消息总线解耦，回复走 outbound stream |
| 图片/文件消息 | 入站解析为附件/产物；出站上传 MinIO 后回传 URL |
| 撤回 | `MsgType=event` 识别撤回，触发对应处理 |
| 失败重试 | 有界重试 + DLQ |

## 9. 工具权限与治理模型（RBAC + Guardrail）

- **工具注册**：`FunctionTool` 封装内置工具 + 支持 MCP 工具动态加载。
- **权限层次**：全局工具（global）→ 租户可见（tenant）→ Agent 白名单（`agent_tool_grants`）→ 模型实际可调用。
- **治理（复用 `plugin`）**：
  - 工具白名单：Agent 级白名单，未授权工具调用直接拒绝。
  - 敏感信息脱敏：输出/日志/trace 统一脱敏（Secret Masking）。
  - 预算限制：`RuntimeProfile.Budget` 每 Run token/工具调用上限，超限熔断。
  - 危险工具二次确认：`tools.risk_level=high` 触发 `plugin/guardrail/approval`。
  - IM 用户权限校验：入站消息先校验 IM 用户是否属于该租户/Agent 的授权用户集。
- **授权原则**：模型参数只表达意图，授权由后端基于 tenant/user/agent 可信上下文判定。

## 12. 监控指标与追踪埋点

- **追踪**：OpenTelemetry SDK + Jaeger；span 贯穿 Channel → Dispatch → Worker → Runner → Governance → Tool → Session/Memory 读写 → Reply，`trace_id` 全链路透传（入站生成，随 `bus.Message.TraceID` 传递，跨节点经 traceparent 注入）。
- **指标（Prometheus）**：会话数、消息数、模型/工具延迟、IM 投递成功率、错误率、token 消耗、每租户成本、队列积压、审批等待时长、Session 后端延迟。
- **审计**：§11。

## 13. 故障恢复与容错设计

- **节点故障**：Redis Streams XAUTOCLAIM 认领未确认消息；Outbox 补偿重发。
- **IM 重试**：幂等表去重 + 有界重试 + DLQ。
- **数据库短暂不可用**：连接池重试 + 熔断 + Outbox 兜底。
- **模型超时**：`context.Context` 取消 + Runner 事件通道排空 + goroutine 生命周期管理（defer 关闭、WaitGroup），避免泄漏。
- **工具失败**：返回结构化错误给模型，模型可换方案；记录审计。
- **灰度/回滚**：Agent 不可变版本发布，回滚即切换版本指针（Worker 无感）。

## 14. 容量评估

| 指标 | 估算方法 | 示例（中规模） |
| --- | --- | --- |
| 每节点并发 session | 受 goroutine 与内存限制，模型延迟/token 吞吐主导 | 200~500 并发 session/节点 |
| 平均 token 消耗 | 单会话消息数 × 单次上下文 token | 按模型计费，见 usage_records |
| Redis QPS | session 读写 + 消息总线 + 锁 | 峰值 ~5k QPS（Stream 为主） |
| SQL QPS | 审计/配置/outbox 写入 | 峰值 ~1k QPS（写多读少） |
| IM 回调峰值 | 企业微信/飞书平台 QPS 限制 + 租户限流 | 单渠道 ~100 msg/s 缓冲 |

容量瓶颈优先在模型调用（外部）与 Session 后端延迟，Worker 无状态可线性扩展。

## 15. 部署方案

### 15.1 最小可运行（Docker Compose）

```yaml
services:
  app:        # 单二进制 --role=all，含 Gateway + Worker + Admin
  mysql:      # 业务/会话/审计/outbox
  redis:      # 消息总线/锁/缓存
  milvus:     # 向量库（含 etcd + minio 依赖）
  minio:      # 对象存储（产物）
  jaeger:     # 追踪
  prometheus: # 指标
```

### 15.2 生产推荐（Kubernetes）

- **Deployment**：`gateway`（对外，含 Admin API + IM WSS）、`worker`（多副本，消费 Stream）。
- **Service/Ingress**：gateway ClusterIP + Ingress；worker 无对外入口。
- **HPA**：worker 按 Redis Streams 积压 + CPU 伸缩。
- **ConfigMap/Secret**：配置与密钥分离。
- **健康检查/滚动更新**：liveness/readiness 探针 + RollingUpdate。
- 沙箱若启用：独立 Deployment + NetworkPolicy 隔离（阶段 10 细化）。
