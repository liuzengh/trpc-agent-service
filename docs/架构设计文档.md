## 1. 平台概述

本平台基于 **tRPC-Agent-Go v1.11.2** 构建，以单一 Go 二进制承载 Gateway、Worker、Admin 三种角色，支持：

- **多租户隔离**：配置、数据、工具权限、密钥、审计、成本六个维度独立隔离
- **多 IM 通道**：企业微信（WeCom WSS）、飞书（Lark WebSocket）、Admin Chat（HTTP/SSE）
- **无状态 Worker**：Agent 执行层不持有本地状态，Session/Memory/Summary 统一由共享后端管理
- **可插拔数据后端**：Session、Memory、Vector、Artifact、Audit 五个域均支持逐租户选择后端
- **可靠消息投递**：Redis Streams + MySQL Outbox + 死信队列（DLQ）三级保障

**技术栈**：Go 1.26 · `net/http` + `gorilla/mux` · `database/sql` 手写 SQL · Redis Streams · MySQL 8.0 · Milvus v2.5.6 · MinIO · OpenTelemetry + Jaeger · Prometheus · Vue3 + Vite + Pinia + Element Plus

## 3. 多租户隔离模型

### 3.1 租户数据结构

```go
type Tenant struct {
    ID          string            // 唯一租户标识 (UUID)
    Name        string            // 显示名称
    Status      string            // "active" | "disabled"
    DataBackend map[string]string // 逐域后端选择: session/memory/vector/artifact/audit
    Quota       *Quota            // 租户级 Token 预算 (0=无限制)
    AuditPolicy *AuditPolicy      // 治理策略
}
```

`DataBackend` 域键定义（代码常量 `tenant.Domain*`）：

| 域        | 键          | 可选后端                           |
| -------- | ---------- | ------------------------------ |
| Session  | `session`  | `inmemory` / `redis` / `mysql` |
| Memory   | `memory`   | `inmemory` / `redis` / `mysql` |
| Vector   | `vector`   | `inmemory` / `milvus`          |
| Artifact | `artifact` | `inmemory` / `minio`           |
| Audit    | `audit`    | `inmemory` / `mysql`           |

Summary 不独立路由——框架 `session/mysql` 在保存 Session 时自动维护 summary。

### 3.2 六维隔离机制

| 隔离维度        | 实现方式                                                                                                     |
| ----------- | -------------------------------------------------------------------------------------------------------- |
| **配置隔离**    | 每个租户的 Agent、Endpoint、Tool、Channel Binding 独立存储，由 `tenant_id` 关联加载                                        |
| **数据隔离**    | 所有 MySQL 查询按 `tenant_id` 过滤；Redis 键按 `{tenant}:` 前缀隔离；Session/Memory 通过框架 `AppName` 隔离                   |
| **工具权限隔离**  | Agent 级工具白名单（`agent_tool_grants` 表）；租户级 `ToolWhitelist` + `ForceApprovalTools`                           |
| **密钥隔离**    | AES-256-GCM 加密存储（`secrets` 表），引用键由 `credential_ref` 绑定到租户；日志自动脱敏（正则匹配 password/secret/token/dsn/api_key） |
| **审计与日志脱敏** | `audit_logs` 按租户分片；日志中敏感字段自动替换为 `***`；错误类型为粗粒度分类（timeout/run_error），不泄露原始错误内容                            |
| **成本隔离**    | `quota.token_quota` 逐租户 Token 预算；`usage_records` 按维度（token/tool/sandbox/artifact/skill）幂等计量；预算耗尽触发熔断     |

### 3.3 审计策略字段

```go
type AuditPolicy struct {
    Redact            *bool    // PII 脱敏开关 (nil=默认开启)
    IMAllowUsers      []string // IM 用户白名单 (空=允许全部)
    ToolWhitelist     []string // 工具白名单 (空=不限制，knowledge_search 豁免)
    ForceApprovalTools []string // 强制人工审批的工具 (与 agent 级列表取并集)
}
```

### 4.3 多节点水平扩展

**Worker 无状态设计**：Worker 不持有本地 Session 状态，所有状态由 Redis Streams + 共享存储后端管理。

**不需要 Sticky Session**：理由如下：

1. **Session 后端共享**：`storage.Router` 根据 `Tenant.DataBackend` 解析到共享的 Redis/MySQL Session 服务；所有 Worker 节点操作同一后端实例
2. **Redis Streams 天然扇出**：Consumer Group 确保每条消息只被一个 Worker 消费
3. **Session 锁序列化**：`lock:session:{tenant}:{id}`（30s TTL + Lua CAS）保证同一 Session 同一时刻只有一个 Worker 处理

**并发控制**：`consumeWorkers` 信号量（默认 16）限制每节点同时处理的 Session 数，避免连接池耗尽。

### 4.4 用户消息路由到正确租户和 Session

```
IM 消息 → Adapter.Inbound() → Gateway.pumpInbound()
         → Resolve binding(account_id) → 获取 tenant_id + agent_id
         → BuildSessionID(tenant, channel, chatType, platformUserID)
         → bus.Message{TenantID, SessionID}
         → stream:inbound → Worker.handle()
         → LockSession(tenant, session) → Runner.Run()
         → 回复通过 Outbox → stream:outbound → Route(tenant,session) → 原 Adapter.Send()
```

## 5. 消息流转链路

完整消息链路（以企业微信为例）：

```
用户发送 → WeCom WSS → Adapter.Inbound()
  → Gateway: BuildTraceID("im.callback"), IdempotentCheck, SetRoute
  → RedisBus: PublishInbound → stream:inbound
  → Worker: XReadGroup → handle()
    → IdempotentCheck → GovernancePolicy → LockSession
    → run():
      → Router.Sessions/Memories (逐租户)
      → runner.Run(model, tools, session, memory)
        → Model.Call() → Tool.Execute() → Model.Call()
      → Session.Save() → Memory.Add()
      → Audit.Record() → UsageMeter.RecordUsage()
    → Outbox.Append(reply, msgKey) (事务: idempotency_keys + outbox_events)
  → Outbox Dispatcher: drain → PublishInbound → stream:outbound
  → Gateway: ReadOutbound → Route(tenant,session) → 文本截断
  → WeCom Adapter: Send(text reply) → 用户收到回复
```

**trace_id 贯穿链路**：

1. Gateway 生成 `im.callback` span（根 trace）
2. `bus.Message.TraceID` 透传给 Worker
3. Worker 通过 `metrics.TraceContextFromID(traceID)` 重建父 span
4. Runner 执行产生子 span（模型调用、工具调用）
5. Session/Memory 读写自动合并到当前 span
6. `im.reply` span 共享同一 TraceID

## 6. 数据层设计

### 6.1 五域路由架构

`storage.Router` 是数据层统一入口，根据 `Tenant.DataBackend[domain]` 解析后端实现：

```
storage.Router
  ├─ Sessions(tenantID) → SessionConfig → backendID → Sessions 实例
  ├─ Memories(tenantID) → MemoryConfig  → backendID → Memories 实例
  ├─ VectorFactory(tenantID) → VectorStoreFactory
  ├─ ArtifactService(tenantID) → artifact.Service
  └─ AuditRecorder(tenantID) → audit.Recorder
```

每个后端实例按 `backendID` 缓存，跨租户共享；隔离通过每次调用传入的 `tenantID` 实现。

### 6.2 各后端适配职责

| 后端           | 存储内容                                    | 适用场景          |
| ------------ | --------------------------------------- | ------------- |
| **Redis**    | Session 热数据、消息总线（Streams）、分布式锁、幂等键、路由缓存 | 高频读写、低延迟要求    |
| **MySQL**    | Agent 版本、工具定义、租户配置、审计日志、用量计量、DLQ、Outbox | 强一致、复杂查询、合规审计 |
| **Milvus**   | 知识库向量（BM25 + embedding）                 | 语义检索、相似度计算    |
| **MinIO**    | 制品文件（artifact）、知识库原始文档                  | 大文件存储、S3 兼容   |
| **InMemory** | 开发/测试模式全量后端                             | 无外部依赖、快速启动    |

### 6.3 DataStores 聚合结构

```go
type DataStores struct {
    Router    *Router              // session/memory 逐租户路由
    Knowledge *knowledge.Manager   // KB 元数据 + Milvus 向量
    Artifacts artifact.Service     // MinIO / inmemory
    Auditor   audit.Recorder       // MySQL async batch / inmemory
}
```

Worker 构造时接收 `DataStores`，在 `run()` 中根据上下文调用对应域的后端。

## 7. IM 通道接入

### 7.1 Adapter 统一接口

```go
type Adapter interface {
    Name() string
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
    Inbound() <-chan *InboundMessage
    Send(ctx context.Context, msg *OutboundMessage) error
}
```

### 7.2 企业微信 vs 飞书接入差异

| 维度   | 企业微信 (WeCom)                              | 飞书 (Feishu)                         |
| ---- | ----------------------------------------- | ----------------------------------- |
| 协议   | WSS (`wecom-aibot-go-sdk`)                | WebSocket (`larksuite/oapi-sdk-go`) |
| 连接   | `aibot.NewConn` 建立 WSS 长连接                | `ws.Client` + `EventDispatcher`     |
| 群聊过滤 | 处理所有群消息                                   | 须 `@bot` 提及（按 `botOpenID` 过滤）       |
| 消息长度 | 2000 rune                                 | 4000 rune                           |
| 回复方式 | `CreateTextReplyBody` + `SendMessage` API | `im/message` Create API             |
| 签名验证 | SHA1 + AES                                | SHA256                              |
| 流式占位 | 先发"正在处理…"再原位替换                            | 逐条 send 分片                          |

### 7.3 Session ID 生成规则

```
单聊: {tenant}:{channel}:user:{platformUserID}
群聊: {tenant}:{channel}:group:{chatID}
```

### 7.4 IM 消息去重

- **幂等键**：`idem:{channel}:{platformMsgID}`（Redis SETNX 24h TTL）
- **数据库唯一键**：`idempotency_keys.msg_key`（MySQL UNIQUE）
- **双层保障**：Redis 快速拦截 + MySQL 最终一致

## 9. 故障恢复与运维

### 9.1 降级策略

| 故障场景          | 降级策略                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| **MySQL 不可用** | 启动时检测，进入 degraded 模式（Healthz 返回 503，管理 API 只读，Worker 无法处理新消息）          |
| **Redis 不可用** | Worker/Outbox/Gateway 不启动；已有消息由 Redis 消费者重投                            |
| **模型超时**      | 300s 硬超时（`context.WithTimeout`），context 取消，goroutine 正常退出              |
| **工具执行失败**    | 错误返回 Runner，Worker 分类为 `run_error`，记录审计，消息重投                           |
| **IM 回复失败**   | Outbox 重试（retries 递增），超阈值标记为已发送（日志记录）                                  |
| **DLQ 死信**    | 5 次业务失败后移入 DLQ（`stream:inbound:dlq` + `dead_letters` 表），Admin API 支持重放 |

### 9.2 Goroutine 生命周期与资源泄漏防护

- `context.WithCancel` + `signal.NotifyContext`：SIGINT/SIGTERM 触发全局取消
- HTTP Server：5s drain 期
- Audit Batch Writer：`Close()` 等待缓冲区写完
- Outbox Dispatcher：`ctx.Done()` 退出循环
- IM Manager：`Stop()` 关闭所有 Adapter WSS 连接
- Runner 执行：`ctx.Done()` 时 Runner 取消，事件通道排空

### 9.3 灰度发布与配置回滚

**Agent 级**：每次 publish 创建不可变版本（`agent_versions` 表），回滚通过原子切换 `agents.current_version` 指针，Worker 无感知。

**租户级**：每次更新快照到 `tenant_config_versions` 表（含版本号），`RollbackConfig` 恢复历史版本。

**不支持流量百分比分流**：IM 会话上下文要求同一会话全程使用同一 Agent 版本，灰度通过逐租户原子切换实现。

### 9.4 容量评估参考

| 指标            | 参考值                                       |
| ------------- | ----------------------------------------- |
| 单节点并发 Session | 16（`consumeWorkers` 默认值）                  |
| 单节点吞吐         | ~0.33 turns/s（p50 端到端 4-5s，15% 尾延迟 ~300s） |
| 入站 Redis 延迟   | p50 ~3-5ms                                |
| 模型调用延迟        | 依上游 API，平台设 300s 硬超时                      |
| 线性扩展          | 吞吐与 Worker 节点数线性正相关                       |

### 10.3 记忆与摘要：复用边界（诚实表述）

平台**不自建**记忆与会话摘要，两者都复用框架能力，且复用方式必须说清楚：

| 能力 | 复用方式 | 平台做了什么 | 平台**没有**做什么 |
| --- | --- | --- | --- |
| 会话上下文（短期） | `runner.WithSessionService` + `session/{redis,mysql,inmemory}` | 按租户经 `Router.Sessions(tenantID)` 选择后端并注入 Runner | 不另建会话表、不改框架事件模型 |
| 长期记忆 | `memory.Service`（`memory/{redis,mysql,inmemory}`）+ `runner.WithMemoryService` + `llmagent.WithPreloadMemory(N)` | ①按租户经 `Router.Memories(tenantID)` 选择后端；②把 `memory.Service.Tools()` 挂进该轮工具集（**工具驱动模式/Agentic**：由模型显式调用 `memory_add/search/load/update` 写入）；③按 `memory.preload_count` 预算把已有记忆注入系统提示词 | **未配置 LLM Extractor**：平台不做自动抽取，记忆只由 Agent 显式工具调用产生（`delete/clear` 沿用框架默认关闭）；不另建 `memories` 表（框架 MySQL 后端自建） |
| 会话摘要（Summary） | 框架 session 存储内的摘要（`session/*`） | 按租户沿用会话后端选择 | 平台**无**独立摘要域/表/API：摘要不是平台资产，`tenants.data_backend` 中也没有 `summary` 键 |

记忆的隔离维度是框架的 `<AppName, userID>`，而平台把 `AppName` 固定为 `tenant_id`（`runner.NewRunner(m.TenantID, ...)`），因此记忆天然按租户隔离；`UserID` 为消息触发者（IM 用户 / 成员 id）。

**开关**：`memory.preload_count` 是该能力的唯一开关（0 = 关闭：不解析记忆后端、不挂记忆工具；-1 = 全量注入；N>0 = 自适应预算，记忆条数 ≤N 全量注入，否则注入与当前问题最相关的前 N 条）。默认 10。

### 10.4 灰度发布（版本级分流）

`agents.gray` 存 `{"version":N,"percent":P}`：按**会话 id 稳定分桶**（`fnv32(sessionID) % 100 < P`）把 P% 的会话路由到第 N 版，其余走 `current_version`。

- 同一会话全程固定版本，不会中途切换（分桶键是会话，不是请求）；
- 目标必须是**已发布**版本，且不能等于当前版本（否则接口直接报错，不做静默 no-op）；
- 清除灰度（`DELETE /agents/{id}/gray`）即回滚，无需重新发布；
- 实际生效版本写入 `agent.run` span 的 `agent_version` 属性，便于在 Jaeger 中对比灰度与基线。
