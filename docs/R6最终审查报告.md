### Medium

1. **R5 的 Stop 返回边界必须保持为残余限制。**
   - 位置：`trpcservice/worker/worker.go:697-731`、`worker.go:736-743`。
   - 实际行为：强制分支在 `consumerDone` 尚未完成时启动 `finishStopAfterWorkers()`，随后记录 Stop 结果并返回；finalizer 等待 Worker/action 退出，再执行 recovery 和 `Queue.Close`。测试 `TestWorkerStopReportsIncompleteCleanupWhenVisibilityIgnoresCancel` 明确验证 Stop 返回时 action 仍 active、Queue 未关闭，action 释放后才关闭。
   - 影响：`Stop` 返回不是“所有外部 Queue action 已退出”的证明。对违反 context cancellation 合同的 Queue，action 可能在 Stop 返回后继续；Worker 保留 Queue ownership。
   - 证据：本次 targeted/full test 和 race 全部通过；R5 测试覆盖该行为。它是已公开的 in-process contract boundary，不单独定性为生产 Bug。
   - 最小后续动作：在真实 Queue 实现和入口级 shutdown 测试中定义并验证 action context 合同；若要求 Stop 返回即全部 action 退出，需单独设计不可绕过的 wait/ownership contract。

2. **P0-08 生产入口和跨资源一致性仍是 evidence gap。**
   - 位置：`trpcservice/worker/`、`trpcservice/gateway/`、`cmd/trpc-service/main.go`。
   - 实际行为：P0-09B 已提供真实 PostgreSQL durable Queue，但 P0-08 Worker/Gateway 尚未接入生产入口；Queue Ack 与 Execution Commit 仍是独立事务。
   - 影响：不能证明生产异步装配、Commit/Ack 跨进程原子性、Outbox 一致性或 framework 全局退出。
   - 最小后续动作：后续阶段单独处理 Worker/Gateway/CMD 装配和跨资源协调，不把 P0-09B 证据外推。

无新的低严重度源码问题。

## 4. Runtime Integration Boundary

- **Queue：** 已有 transport-neutral `JobQueue`、`FakeQueue` 和 P0-09B PostgreSQL durable Queue；真实 Queue 覆盖跨连接 visibility、Ack/Nack、claim fencing、expiry recovery 和 connection-loss recovery，但没有 DLQ 或生产入口装配。
- **Repository/Lease：** P0-09A 已把 execution result commit 接入真实 PostgreSQL fenced Repository，并通过真实 Lease takeover/rollback/幂等 acceptance；通用业务 Repository、Queue Ack 联动和 P0-08 Worker 生产装配仍未完成。
- **Gateway：** `trpcservice/gateway.Gateway.Submit` 创建 Job 并调用 Queue，返回 accepted metadata；它是 transport-neutral contract。
- **Web/CMD：** `cmd/trpc-service/main.go` 当前创建 `platform.MemoryStore`、`platform.Runner` 和 `web.Server`；`POST /api/chat` 仍是同步兼容路径。没有 `NewWorker`/Gateway 的生产装配。
- **SIGTERM：** CMD 的 signal handler 只执行 HTTP `Shutdown` 和 migrator close；没有 Worker.Stop/Queue.Close 入口级端到端证据。
- **Outbox/Retry/DLQ：** 有 schema/interface 预留或测试命名，但没有本阶段真实业务实现和投递闭环。
- **IM：** webhook/channel 仍是简化协议壳，不是真实验签、解密、发送或重放保护实现。
- **Telemetry：** 没有本阶段可证明的生产 Telemetry 装配。
- **鉴权：** 现有少量 Context 权限检查不能宣称完整 API/管理/生产鉴权。
- **Framework ownership：** Queue/Execution/Worker/Gateway 无 tRPC-Agent-Go import；R1 adapter 只使用公开 event API，未访问 framework 私有字段/channel。全局 framework goroutine Wait/Done 仍是 residual limitation。

## 5. Residual Risks and Deferred Work

- 完整业务 Repository/Unit of Work：P0-09A 只关闭 execution result fenced commit，不包含 Tenant/Session/Event/Outbox 等完整事实源。
- Queue 的生产入口装配、远端操作 outcome contract 和 OS 进程级恢复演练；P0-09B 已覆盖数据库 durable Queue 和独立连接 recovery。
- Commit/Ack 跨进程原子性，以及 Repository/Outbox/Queue 的一致性方案。
- Retry/DLQ 业务策略、持久化状态和可观测性。
- 真实 Web/CMD asynchronous assembly、Worker lifecycle ownership 和 SIGTERM 到 Stop/Close 的入口级证据。
- 真实 IM 验签/解密/发送、鉴权和 Telemetry。
- tRPC-Agent-Go framework 内部 global goroutine Wait/Done：只能在上游提供公开稳定 API 后重新验证。
- R5 non-cooperating Queue action：当前 bounded Stop 返回错误并保留 ownership，finalizer 可能继续；真实 Queue 必须定义是否允许该行为。
