## 6. Repository 接口

`storage.OutboxRepository` 保持以下接口：

```go
type OutboxRepository interface {
    Enqueue(context.Context, tenant.TenantContext, OutboxMessage) error
    ClaimBatch(context.Context, tenant.TenantContext, string, int) ([]OutboxMessage, error)
    MarkCompleted(context.Context, tenant.TenantContext, string, string) error
    MarkRetry(context.Context, tenant.TenantContext, string, string, time.Time, string) error
    MoveToDLQ(context.Context, tenant.TenantContext, string, string, string) error
}
```

`postgres.OutboxRepository` 由 `NewOutboxRepository(pool, OutboxRepositoryConfig)` 创建。Repository config 提供有界的 `LockDuration` 和 `MaxBatchSize`；默认 batch size 为 100，不能通过 config 放大到无界值。具体实现另提供用于真实 acceptance 读取的 tenant-scoped `Get` 方法，但没有把它加入公共最小 contract。

## 7. Enqueue 和 dedup

- Tenant context 必须有效，message tenant 必须与 context 一致，否则返回 tenant mismatch。
- ID、Kind、AggregateID、dedup key 和 payload 均验证；空 payload 规范化为 `{}`，非空 payload 必须是 JSON，payload 上限为 1 MiB。
- 入队总是以 pending、attempt 1、数据库 clock timestamp 写入；调用方修改原始 payload 不会改变数据库记录。
- duplicate `(tenant_id, outbox_id)` 返回稳定 `ErrConflict`。
- tenant 内 duplicate `(tenant_id, dedup_key)` 返回同时可由 `errors.Is` 识别的 `ErrDedupConflict` 和 `ErrConflict`；相同 dedup key、不同 payload 仍返回 conflict。
- dedup key 的唯一性包含 tenant；不同 tenant 可以使用同一 dedup key。
- 接受成功只在 transaction commit 后返回；commit 前故障的 acceptance 确认无 durable row。

## 8. Claim、lock 和 reclaim

ClaimBatch 在一个 transaction 内：

1. 使用 PostgreSQL `clock_timestamp()` 将 tenant-scoped expired processing rows 转为 retry，清理 owner/lock 并递增 attempt；
2. 使用 `FOR UPDATE SKIP LOCKED` 选择到期的 pending/retry rows；
3. 将选中 rows 原子改为 processing，写入 owner 和配置提供的 locked-until；
4. commit 后才返回消息。

两个独立 pgx pool 并发 claim 的 acceptance 验证了每条消息最多一个 active owner、batch 不重复和 tenant-scoped 查询。active lock 在有效期内不会被重新领取；通过 SQL 受控设置 `locked_until` 到数据库当前时间之前后，新 owner 可以 reclaim，并且 attempt 递增。测试没有用几十毫秒 sleep 作为时间证据。

## 9. Complete、Retry 和 DLQ

Complete 只接受当前 tenant、processing 状态、当前 owner 和数据库时钟下未过期 lock；成功后设置 completed 并清理 lock。stale owner 被拒绝，expired owner 返回独立的 expired 分类；重复完成返回稳定 `ErrAlreadyCompleted`。

MarkRetry 只接受有效 owner、未来或过去的明确 `next_attempt` 和安全 failure code。它在同一 transaction 中设置 retry、next attempt、递增 attempt、last error code 并清理 lock。RetryPolicy 不在本阶段计算。next attempt 未到时不会 claim，到期后可重新 claim。

MoveToDLQ 在一个 PostgreSQL transaction 中完成：

1. 锁定并校验当前 processing owner；
2. 插入或确认 `(tenant_id, outbox_id)` 对应的 dead-letter row；
3. 把 outbox row 改为 dead 并清理 lock；
4. commit。

DLQ insert 后故意失败的测试确认 dead-letter row 和 outbox transition 一起 rollback；duplicate MoveToDLQ 返回稳定 `ErrAlreadyDead`。stale owner 不能写 DLQ，reason/last error 只能是安全 code。

## 10. Tenant isolation 和安全错误

所有真实读取、claim 和 mutation SQL 均带 tenant 条件。错误 tenant 不能读取或修改另一 tenant 的 Outbox row。schema 的 tenant-qualified primary key、dedup unique index、dead-letter unique constraint 和 FK 继续保留。

storage error contract 增加并区分：invalid argument、tenant mismatch、not found、conflict/dedup conflict、outbox lock lost、outbox lock expired、backend unavailable、transaction outcome unknown、unsafe failure code 和 already dead/already completed。`errors.Is`/`errors.As` 证据由 Fake/真实测试覆盖。

`MarkRetry` 和 `MoveToDLQ` 拒绝包含空格、任意文本或不安全字符的 durable failure code。数据库错误底层 cause 仍在 error chain 中，但 `OutboxError.Error()` 只输出固定 operation/category，不输出 SQL、DSN、payload、Prompt、Token、Authorization 或 Provider response body。测试验证 closed pool 错误不会泄露连接信息。

## 11. PostgreSQL restart 和 Docker fault evidence

`TestPostgresOutboxDockerRestartRecovery` 在 DockerLab 隔离 PostgreSQL 中完成：

- apply 当前 migration；
- Enqueue 并 Claim；
- 停止 PostgreSQL；
- repository operation fail-closed；
- 重启并等待健康；
- 通过恢复后的动态 PostgreSQL endpoint 重建 pool；
- 验证 pending/processing 数据存在、expired lock 可 reclaim、attempt 前进、stale owner 仍被拒绝；
- 新 owner 完成消息。

这只证明隔离 Docker 容器内的 PostgreSQL service stop/restart 和 repository recovery，不证明完整 OS Worker crash、生产集群 failover、SIGTERM 或 framework 全局 goroutine 退出。

Redis prerequisite 通过不改变 Outbox 事实源；Outbox payload 和状态仍只使用 PostgreSQL。
