# 跨主机高可用

## 测试目标与范围

验证一个独立主机发生整机故障或网络隔离后，位于其他故障域的服务能继续或恢复处理两个租户的企业微信消息，并防止失联旧节点与新节点同时拥有有效处理权限。

“不同主机”必须对应计划验证的故障域：同一物理机上的两个容器不能代表跨主机；同一物理机上的两个虚拟机也不能证明物理主机故障可用性。本文是测试步骤，不包含执行结果。

## 部署与前置准备

```text
主机 H1：应用节点 N1           主机 H2：应用节点 N2
         └──────── 可跨主机访问的状态与协调服务 ────────┘
                      按各自设计部署冗余或独立故障域
```

1. 固定 PR、镜像与配置；列出主机、虚拟化宿主、网络、磁盘、入口、模型访问路径、Bot 凭据来源及共享依赖位置。
2. 至少使用两个相互独立的应用主机。若要求承受物理主机故障，确认应用主机及关键副本不共用该物理宿主；若只测虚拟机故障，应明确范围。
3. 明确数据库、队列、协调服务及业务所需对象存储的容错能力。关键单点若位于受害主机，不能预设应用节点存活就能恢复业务。
4. 对依赖多数派仲裁的组件，按其实现安排副本、投票成员和故障域，保证目标故障后仍有法定多数。两个应用节点不自动意味着共享依赖能够容忍任意一台主机失效。
5. 两应用节点均具备处理两个租户所需的版本、配置、授权和共享会话访问能力；模型出口或凭据服务不得只存在于即将故障的主机。
6. 企业微信长连接检查各主机的实际出口和连接接管；HTTP/Web 入口如纳入范围，还需检查负载均衡、域名解析及入口自身的冗余。
7. 准备独立于受害主机的控制和观测通道，能够从虚拟化平台、云平台或带外管理确认整机状态。预先限定故障目标、网络规则和恢复操作，避免切断唯一恢复通道。
8. 按 [恢复后能继续对话](01-恢复后能继续对话.md) 准备两租户代号和逐级业务基线。统一时钟，在外部位置采集日志，防止主机故障同时带走证据。
9. 预设连接恢复、整体业务恢复、原任务完成、重复检查时限及探测间隔。确认故障节点在接管验收完成前不会被平台自动重建；自动重建另设子用例。

## 测试步骤

### 1. 建立跨主机业务基线

1. 仅运行 H1 上的 N1，两个 Bot 分别写入并回忆各自随机代号。
2. 启动 H2 上的 N2，观察预设稳定窗口，确认跨主机依赖连接、任务调度和 Bot 连接所有权符合设计。
3. 两租户继续原会话并安排并发请求，核对上下文和最终交付。记录每个 Bot 的连接所在主机、每个任务的执行主机，以及入口后端分配。
4. 验证采集系统能在 H1 不可达时继续观测 H2 和依赖服务。

### 2. 整机故障

1. 选择承担实际连接或执行职责的 H1 作为受害主机，使用外部控制面执行强制关机或等效整机终止。只杀一个容器不满足本子用例。
2. 记录 `t0`，从独立控制面确认 H1 停止，且所有该主机上的应用与辅助进程均不可继续服务。仅 SSH 失败不能证明整机已停止。
3. 保持 H1 停止，观察 H2、入口和共享依赖，记录连接接管、Worker 分配及业务探测恢复的时刻。
4. 两 Bot 按 [恢复后能继续对话](01-恢复后能继续对话.md) 进行接管后的原会话新消息验证和连续第二轮验证。
5. 如要验证整机故障下的原任务接管，重建基线后按 [在途任务接管](02-在途任务接管.md) 命中指定阶段再关闭主机，单独关联原任务完成情况。
6. 对计划内的每类关键依赖，确认其在本轮是否受到主机故障影响、是否仍有足够副本，以及是否发生自动切换。没有发生依赖切换时，结论仅覆盖该拓扑下的应用主机故障。

### 3. 网络隔离与旧节点失效

网络隔离与整机关机分别执行，每轮开始前恢复完整健康基线。

1. 根据部署网络，选择并准确记录隔离方向和端口：

   - H1 与所有业务依赖及外部服务完全断开，用于验证失联主机接管。
   - H1 无法访问协调或共享状态服务，但仍可访问企业微信、模型或部分存储，用于验证失去有效所有权后是否仍会处理或回复。
   - 仅 H1 与 H2 互不可达，用于观察实现是否依赖节点直连；若两者仍能正常使用共同协调服务，不应预设必然发生主备切换。

2. 在外部注入精确网络规则，保留恢复通道；通过不同方向的连接探测确认实际隔离范围，不能只检查一个端口。
3. 等待设计规定的租约或故障检测周期，观察哪个节点仍具有有效处理权。检查失效旧节点是否停止领取任务、提交状态和发送最终回复。
4. 两个 Bot 分别发送带唯一标记的新消息，核对最终回复、租户及会话。检查是否出现两个节点同时有效处理同一任务、互相抢占 Bot 连接或重复最终回复。
5. 如需覆盖旧节点上的在途写入，预先将任务暂停在结果提交或发送前，再隔离其协调路径并使新节点接管，最后释放旧任务；验证过期执行者不能覆盖新状态或重复产生业务效果。无法命中该阶段时，不能宣称已验证全部旧任务隔离。
6. 若因失去仲裁多数而选择停止服务，应分别记录“避免冲突写入”和“持续可用”是否满足要求；安全停止不能被判作持续可用。

### 4. 故障主机恢复与反向验证

1. 完成故障期间验收后，启动 H1 或撤销隔离规则，记录恢复动作。
2. 检查旧节点重新加入前能识别失效租约和过期任务；不应继续发送旧回复、覆盖新节点已提交的数据或导致连接反复迁移。
3. 观察完整稳定窗口，两个租户继续原会话，核对上下文和持续交付。
4. 重建基线后，对 H2 执行对称故障。若两个主机承担的关键依赖不同，应分别说明故障范围，不能用 H1 一轮推断 H2。
5. 若要声明共享依赖自身具备高可用，应进一步按各组件设计逐一故障其主副本或所在主机，验证自动切换、持久数据与业务恢复；这些操作单列子用例，每次仅注入一个预定故障。

## 验收标准与恢复时间

- 目标主机持续不可用时，原业务入口和存活服务在预设时限内恢复两个租户的有效请求，无需修改用户入口、重新绑定 Bot 或手工搬迁会话。
- 已提交的会话与业务状态符合预先约定的数据丢失目标（RPO）；本组聊天用例要求已确认写入的测试代号可回忆。需要更全面的数据保证时，另以确定性写入和持久记录核对。
- 每条输入归属正确租户和会话，没有重复最终回复；网络隔离期间旧节点的过期权限不能产生冲突写入或重复业务效果。
- 若纳入在途任务，其验收需满足对应注入点的独立要求，不能由接管后新消息成功替代。
- 主机恢复后服务稳定，反向故障也有独立证据；未覆盖的主机或共享依赖故障不得包含在结论中。

精确业务恢复时间应从 `t0` 起，通过外部持续探测确认两租户重新获得有效最终回复。提前设定探测频率，每条探测使用不同标记，关联服务端是否接收，并预先定义连续成功条件。需分别统计未接收的断线窗口消息、已接收在途消息和恢复后新消息。

探测需经过所声明的实际业务入口；企业微信链路应包含真实 IM 输入和最终回复，HTTP 业务探测只能证明 HTTP 链路。观测值应注明探测与采样间隔，不能宣称比采样精度更准确的恢复时间。

手工等到连接恢复后才发送的消息，只能给出其业务响应时间及一次恢复观测；健康检查、连接成功和队列恢复各自有独立计时，不能单独代表完整业务 RTO。

## 证据与结束操作

在独立运行目录保留拓扑和故障域清单、各轮故障及恢复动作、外部控制面状态、网络规则范围、依赖仲裁与切换、节点所有权、任务与投递关联记录、客户端最终回复。不要将实际执行数据、耗时或结论回填本文。

结束后撤销全部测试隔离规则、解除任务暂停，按计划恢复或关闭应用及依赖；核对没有遗留规则或过期测试任务。
