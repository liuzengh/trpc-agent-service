# 在途任务接管

## 测试目标与范围

验证系统已经持久接收、尚未完成最终回复的原始消息，在执行节点或发送节点故障后，能由存活节点自动继续处理或安全重试。用户无需重新发送消息，租户、会话和业务效果保持正确。

接管允许重新调用模型，不要求恢复模型生成到一半的内部状态；应分别检查任务重试次数、最终回复次数和外部副作用次数。本文只规定测试方法，不包含执行结果。

## 前置准备

1. 按 [恢复后能继续对话](01-恢复后能继续对话.md) 准备版本、两租户、两 Bot、不同随机代号、原会话和观测参数，完成单节点与双节点业务基线。
2. 明确被测实现的接收确认、消息持久化、队列确认、任务所有权、租约超时、结果提交和回复投递边界。企业微信“已发送”不代表服务端已持久接收。
3. 能用租户 ID、原始消息 ID、会话 ID、任务 ID、回复 ID、幂等键关联完整链路。不存在的字段使用实现的等价标识，不能只靠回复文本匹配。
4. 准备可控的暂停点，让任务停在指定阶段后再注入故障。优先使用已有调试设施或外部受控代理；代理应置于受害节点之外，透传真实上游请求，不代替应用接管、重试或补发。
5. 如必须增加测试钩子，应固定并标注测试补丁，区分原版本与辅助观测能力。无法可靠暂停或辨认阶段时，将该子用例标为未验证；仅要求模型“慢一点”或随机延时不足以证明故障发生在目标阶段。
6. 预先设定从故障时刻 `t0` 起算的原任务完成时限 `T_TASK`、最终可见回复时限 `T_DELIVER`，以及首条最终回复之后的重复检查窗口 `W_DUPLICATE`。主动暂停的时长应单独记录，不得事后从恢复耗时中随意扣除。`W_DUPLICATE` 至少覆盖实现的相关租约、重投及发送重试窗口；无法完整覆盖时应注明验证边界。
7. 关闭受害应用节点的自动重启和替换。明确任务执行者与 Bot 连接所有者可能位于不同节点，故障目标必须按该子用例的实际职责选择。

## 故障注入点

每个注入点都是独立子用例，必须重建健康基线并使用新输入标记，不能用一次故障推断全部阶段。

| 子用例 | 注入前必须确认的状态 | 故障目标 | 验证重点 |
|---|---|---|---|
| P1：已持久接收、尚未执行 | 原输入已持久化或可靠入队，尚未被执行 | 承担接收职责的节点，或已领取但尚未开始的执行节点；明确是哪一种 | 接收节点退出后输入仍可处理，或未完成的领取可被回收；两者分别判定 |
| P2：模型或工具执行中 | 原任务已由目标节点领取，模型或工具请求已发出，尚无完成结果 | 实际执行该任务的节点 | 执行权能被回收，原任务自动续处理或重试 |
| P3：结果已提交、最终回复未发送 | 结果和待发回复已持久化，下游尚未接受最终回复 | 待发回复的实际发送节点 | 存活节点能发送已保存的结果，无需用户补发输入 |
| P4：下游已接受、发送确认尚未持久化 | 发送已获下游接受证据，但应用尚未保存完成确认 | 实际发送节点 | 不确定投递窗口中的重试、去重及用户可见重复 |

P4 不能凭“客户端暂时没显示”判断。若协议不能提供可关联的接受证据，或无法区分接受与确认落盘，应记录覆盖缺口；不可将 P3 的验证替代 P4。下游接受记录也不能单独代替企业微信客户端最终可见性。

## 测试步骤

### 1. 为一个注入点安排两租户输入

1. 选择 P1～P4 中一个注入点，生成新的 `RUN_ID` 和两条消息标记。
2. Bot A 发送 `<RUN_ID>-P?-A：请回忆本会话的测试代号，说明你的租户，并回显本条标记。` Bot B 发送对应 B 标记，不再次提供代号。
3. 先对租户 A 的原任务设置目标暂停点，租户 B 作为并发对照，检查共享故障是否影响其他租户。
4. 采集暂停证据、原始输入的持久记录、任务状态及实际责任节点。确认最终回复还处于该子用例要求的阶段。

### 2. 故障并等待原任务自动处理

1. 非优雅终止目标应用节点，记录 `t0`，验证该节点保持停止。
2. 按预设方案释放存活节点后续请求所需的暂停条件。释放暂停只恢复外部依赖响应，不执行任务重投、租约删除或回复补发。
3. 保持原消息不变，用户不重复发送。观察队列重新分配、过期执行权回收、任务尝试次数、新执行者、回复状态及错误。
4. 在 `T_TASK` 内确认原任务完成，并在预定回复时限内核对原消息对应的最终可见回复。仅出现一条后续新消息的回复，不能证明原任务被接管。
5. 核对租户 A 及对照租户 B 的上下文和数据归属；再各发一条新消息，验证执行链路没有因接管长期堵塞。
6. 持续观察 `W_DUPLICATE`，查验迟到回复、重复完成、永久处理中任务以及无法释放的租约。

### 3. 覆盖另一租户与并发在途任务

1. 恢复双节点基线，用新标记对租户 B 执行同一个注入点，租户 A 作对照。
2. 在调度机制允许的情况下，让两租户各至少一个任务同时到达目标阶段，再故障其实际责任节点；记录每个任务是否受影响，不能默认两个任务都在受害节点。
3. 对剩余注入点重复上述步骤。缺乏可观测性、不能稳定命中或实现不支持的子用例分别记录，不合并为整体通过。

### 4. 验证有外部副作用的任务

1. 若被测应用支持工具写操作，使用独立测试资源，例如按业务幂等键创建一条测试记录；禁止以真实付款等不可逆操作作为探针。
2. 在工具操作前后设置可核对的暂停点，尤其覆盖“外部写入成功、应用结果尚未提交”的窗口。
3. 故障后检查最终业务记录数量及幂等键，区分模型重试、工具调用重试与实际重复写入。
4. 若只测普通聊天，应明确范围仅为聊天任务；不能从回复不重复推断工具副作用也不会重复。

## 验收标准

- 原消息在故障前有可靠接收证据，并确实命中选定注入点。
- 受害节点停止期间，原消息由系统自动续处理或重试完成；无需用户重发、手工重新入队或修改任务状态。
- 每个输入对应正确租户及原会话，最终答案能回忆各自代号，且无跨租户数据。
- 每个输入只产生一次用户可见最终回复；检查客户端表现及服务端发送记录，允许独立统计合法流式更新。
- 对外部写操作，按业务幂等键核对只产生一次预期业务效果。模型或 Worker 执行次数可以大于一次，应如实计数。
- 超时、丢失、串租户或重复最终回复均不满足对应验收项。投递协议不能保证去重时，应明确该限制，不能将“至少一次处理”写成“恰好一次交付”。

## 应采集的证据

在独立运行目录保存每个注入点的暂停条件、命中时间、原输入持久化证据、执行与投递状态流转、故障目标、接管者、重试次数、客户端最终回复，以及适用时的工具幂等记录。证据中需能关联同一原任务在故障前后的状态；本文不接收实际日志或测试结论。

结束每个子用例后解除暂停并清理测试工具数据；恢复健康基线再开始下一轮，全部验收结束后按计划关闭或恢复环境。
