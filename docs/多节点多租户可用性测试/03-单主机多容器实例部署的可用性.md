# 单主机多容器实例部署的可用性

## 测试目标与范围

验证同一主机内多个应用容器能正确共存，在某个应用实例故障后，其他实例能够维持或恢复两个租户的服务，并能在实例重新加入后保持稳定。

本用例检查部署与实例生命周期；[恢复后能继续对话](01-恢复后能继续对话.md) 提供业务验收步骤，[在途任务接管](02-在途任务接管.md) 提供处理中故障的子用例。它们可以组合执行，但各项需独立判定。本文不包含执行结果。

## 部署拓扑与前置检查

```text
测试主机 H1
├── 应用实例 N1：独立进程、节点身份和监听端口
├── 应用实例 N2：独立进程、节点身份和监听端口
└── 所需共享依赖：数据库、队列、协调服务等
```

1. 固定 PR 提交、镜像、配置、容器编排定义和持久卷映射。逻辑应用实例若由多个角色容器组成，应列明对应关系。
2. 检查两个实例均具备设计要求的两个租户配置，Bot 与租户映射一致；共享业务状态通过正确的租户键隔离。不得依靠两个彼此独立的完整环境冒充多实例接管。
3. 确认节点 ID、端口和本地临时目录不冲突。业务状态若要求共享，应使用实现支持的存储方式，不能任意共享一个不支持并发写入的本地文件。
4. 确认同一主机有足够资源容纳双实例，且单实例能够承担计划中的两租户流量；记录资源限制和测试负载。仅低流量验证时不得扩展为容量结论。
5. 记录实际入口：企业微信长连接由应用主动建立，应检查连接所有权与接管机制；若还有 HTTP/Web 入口，分别检查统一入口和后端健康摘除。
6. 准备独立故障命令、状态查询与清理流程。每次只停止计划中的应用实例，避免使用会连带关闭数据库和队列的整套停止命令。
7. 使用 [恢复后能继续对话](01-恢复后能继续对话.md) 的两租户代号、消息标记、稳定窗口和时限。测试证据保存在独立运行目录。

## 测试步骤

### 1. 单实例启动

1. 启动共享依赖和 N1，保持 N2 停止。
2. 检查健康状态、依赖连接和两个 Bot 的认证连接。
3. 两个租户分别写入并回忆自己的随机测试代号，核对原生租户、会话及最终交付记录。

### 2. 加入第二实例

1. 启动 N2，确认两容器使用相同版本、不同节点身份，重启计数稳定。
2. 检查服务发现、任务调度和连接所有权是否符合实现设计。主备连接只由一个实例持有是允许的；按设计应分摊的 Worker 职责须检查实际分配。
3. 在预设稳定窗口内，让两个租户分别连续交互，并安排重叠请求。每条输入使用不同标记，核对正确上下文、无重复回复和无持续积压。
4. 若存在 HTTP 统一入口，通过真实入口验证路由及会话延续，同时查询两实例状态；直接访问一个实例不能代替入口可用性检查。

### 3. 故障一个实例

1. 关闭应用实例自动重启和自动替换，确认共享依赖保持运行。
2. 优先选择实际持有 Bot 连接或执行任务的实例，非优雅终止，记录故障时刻和全部相关容器状态。
3. 确认剩余实例原进程持续运行，故障实例未被重建；观察连接、调度和入口路由的自动变化。
4. 按 [恢复后能继续对话](01-恢复后能继续对话.md) 的故障后步骤，验证两个租户在原会话发送新消息及连续第二轮消息。
5. 若本轮需要覆盖在途任务，另按 [在途任务接管](02-在途任务接管.md) 设置可确认的注入点；不可用新消息成功代替原任务完成。
6. 保持单实例承载预先规定的请求量与观察时间，检查资源、错误、队列积压及两租户是否都能完成请求。

### 4. 实例重新加入与反向故障

1. 完成故障期间的业务验收后，再恢复退出的实例。该恢复动作属于重新加入阶段，不能用于满足前一步的自动接管条件。
2. 等待完整稳定窗口，检查连接不会持续互相踢出、任务不会重复执行、旧任务不会再次回复，节点身份和租约状态一致。
3. 两个租户分别继续原会话并检查上下文。若实现支持创建新会话，再分别测试新会话的路由与会话数据隔离。
4. 重新建立双实例基线，故障另一实例，重复前述验证。注明每轮的连接持有者和任务执行者，区分连接主节点故障与备用节点故障。
5. 根据预定轮数重复“故障—验收—重新加入”，检查故障累积后的资源泄漏、僵尸节点或长期积压。未执行的轮次不纳入结论。

### 5. 区分不同恢复机制

| 独立子用例 | 配置与动作 | 判断内容 |
|---|---|---|
| 存活实例接管 | 关闭受害实例自动恢复，强杀后保持停止 | N2 是否能接管 N1 的职责，或反向接管 |
| 容器自动恢复 | 在前一子用例结束后，按部署策略启用重启或替换，再注入故障 | 运行时能否重建实例，以及恢复所需时间；不能代替接管验证 |
| 计划内停止 | 使用实现支持的优雅停止，核对停止接新任务、排空与退出 | 计划维护期间的行为；不能代替非优雅故障 |
| 单个共享依赖停止 | 独立子用例中停止非冗余数据库、队列或协调服务 | 观察影响范围、明确报错及恢复后的数据一致性；不能预设服务会持续可用 |

各子用例之间恢复基线，按实际机制解释恢复来源。某个容器重启成功不等于原任务已经完成，仍需进行对应业务验收。

## 验收标准

- 双实例能稳定共存，身份和监听资源无冲突，两租户路由、会话及最终交付正确。
- 在单个应用实例持续停止、依赖正常的条件下，存活实例能在预设时限内接管受影响职责并服务两个租户。
- 重新加入和反向故障不导致连接振荡、跨租户访问、重复最终回复或不可恢复积压。
- 若覆盖 HTTP 入口，故障后请求能经原入口到达存活实例，无需用户改地址。
- 对自动重启、优雅停止和依赖故障分别判定，不混合计算恢复时间。

## 适用边界与结束操作

单主机多容器只能隔离部分进程和容器故障。主机电源、内核、容器运行时、磁盘或整机网络故障可能同时影响全部实例及依赖；本用例不证明这些故障下仍可服务。跨主机验证使用 [跨主机高可用](04-跨主机高可用.md)。

结束后保存容器状态、入口观测、连接/执行者变更和业务关联证据；按计划关闭或恢复环境，保留需要复查的数据卷。不要把运行日志、实际时延或通过结论写入本文。
