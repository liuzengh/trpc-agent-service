# 恢复后能继续对话

## 测试目标与范围

验证一个应用节点故障、其余节点完成接管后，两个企业微信 Bot 都能处理新消息，并保持正确的租户归属和原会话上下文。

本文及同目录文件是可复用的测试流程，不包含执行结果。具体 PR 的部署命令、状态字段和接管机制应从被测版本确认；下文的消息、任务、租约、投递记录均指实现中的对应概念，不要求固定表名或中间件。

本用例在确认接管完成后发送业务消息。在处理过程中故障应使用 [在途任务接管](02-在途任务接管.md)；部署层面的检查分别见 [单主机多容器实例部署的可用性](03-单主机多容器实例部署的可用性.md) 和 [跨主机高可用](04-跨主机高可用.md)。

## 前置准备

1. 固定被测 PR、完整提交 SHA、镜像摘要与配置版本。两个节点使用同一版本；记录部署适配和观测工具，不通过临时修复被测业务代码获得接管能力。
2. 准备两个独立应用节点 N1、N2，以及实现要求的共享存储、队列、协调服务。明确每个节点的入口、Worker、IM 连接和回复发送职责。
3. 将 Bot A 绑定到租户 A、Bot B 绑定到租户 B。两个节点均应具备按设计接管两个租户的配置；凭据由部署环境注入。
4. 使用同一企业微信用户分别与两个 Bot 单聊，使用真实模型服务。模型是否共用上游 Key 不作为租户隔离的判据。
5. 为每次执行生成唯一运行标记 `RUN_ID`，并随机生成两个不同测试代号 `TOKEN_A`、`TOKEN_B`。代号仅通过各自 Bot 的聊天消息写入，不放进系统提示词、知识库或后续提问。下文尖括号内容均须替换成当次值。
6. 设置可辨认的租户回复前缀，并准备服务端租户、会话、消息、执行者、最终投递记录的查询方式。不能仅根据模型自报身份判断租户路由。
7. 关闭两个应用节点的自动重启和自动替换，保留人工恢复手段；本用例要求故障节点在验收前一直停止。依赖服务保持正常。
8. 统一观测时钟和时区。执行前填定以下参数，超时后不得通过延长阈值将本轮改判为通过。

| 参数 | 含义与设定依据 |
|---|---|
| `W_BASELINE` | 双节点稳定观察窗口，覆盖多个连接心跳、租约续期及任务调度周期 |
| `T_CONNECT` | 允许的 Bot 连接接管时限，结合租约过期、断线检测及重连退避设定 |
| `T_READY` | 允许的整体接管时限，包含执行者重新分配和共享依赖就绪 |
| `T_REPLY` | 新消息到最终可见回复的最大等待时间，考虑实际模型延迟 |
| `W_REPEAT` | 首轮成功后持续观察和重复验证的窗口 |
| `DELTA_POLL` | 状态采样间隔；计时结论需包含该采样误差 |

## 测试步骤

### 1. 建立单节点业务基线

1. 只启动 N1，确认 N2 未运行。确认依赖就绪、两个 Bot 已连接且没有其他测试环境占用相同 Bot 凭据。
2. 分别发送：

   - Bot A：`<RUN_ID>-S1-A：请说明你的租户。本次会话的测试代号是 <TOKEN_A>，请记住并回显本条标记。`
   - Bot B：`<RUN_ID>-S1-B：请说明你的租户。本次会话的测试代号是 <TOKEN_B>，请记住并回显本条标记。`

3. 两边再分别问：`请说明你的租户，并回忆我刚才告诉你的测试代号。` 不再次提供代号。
4. 核对企业微信最终回复及服务端的租户、会话、处理完成、最终交付记录。两边都满足条件后才进入下一阶段。

### 2. 逐渐建立双节点健康基线

1. 启动 N2，确认两个节点健康，版本一致、节点身份不同，均能访问所需共享依赖。
2. 观察完整的 `W_BASELINE`：无意外重启、持续报错、反复抢占连接或任务积压。主备架构允许备用节点不持有 Bot 连接，但必须有可核对的候选接管状态。
3. 分别向两个 Bot 发送 `<RUN_ID>-S2-A/B：你属于哪个租户？我之前告诉你的测试代号是什么？请回显本条标记。`
4. 核对两个最终回复、各自原会话及服务端归属；确认期间没有更换会话来绕过上下文恢复问题。
5. 通过租约、连接日志或管理状态，将两个 Bot 的实际连接所有者映射到具体节点和进程启动时间。不能根据节点名称推测所有者。

### 3. 注入应用节点故障并观察接管

1. 确认基线消息均已最终交付，没有待完成的测试任务。选择实际持有 Bot 连接的节点作为受害节点；若两个 Bot 分属不同节点，注明本轮受影响的 Bot，另一 Bot 作为对照。
2. 对受害节点执行非优雅终止，并记录故障时刻 `t0`。容器部署可在确认目标名称后使用 `docker kill --signal=KILL <受害应用容器>`。若一个逻辑应用节点由多个容器构成，应按预定故障范围停止该节点的全部应用组件，并记录每个动作时间。
3. 确认受害节点确已退出且没有自动恢复；存活节点及共享依赖仍正常。保持受害节点停止直到本轮验收结束。
4. 持续查询连接所有者、两个 Bot 的认证连接、Worker 分配和任务积压。分别记录连接恢复 `t_connect`、执行者就绪 `t_worker`、整体可接收业务 `t_ready`。
5. 不手工删除租约、重绑 Bot、重启存活节点或重投消息。超过预设时限仍未恢复，结束自动接管判定；后续人工排障另行处理。

### 4. 接管后发送新消息

1. 确认两个 Bot 和执行链路均已就绪，再分别发送 `<RUN_ID>-S3-A/B：你属于哪个租户？我之前告诉你的测试代号是什么？请回显本条标记。`
2. 分别记录发送、服务端接收和最终回复可见时刻。两条消息必须进入各自原有会话；不得在问题中提示测试代号。
3. 核对正确租户和代号、无另一租户内容、消息完成、最终交付，以及实际接管节点。流式占位消息或“正在处理”不能算最终回复。
4. 在 `W_REPEAT` 内，以新的消息标记至少再执行一轮，并让两个租户的请求有重叠，检查持续可用性和重复回复。
5. 如需验证全新服务端会话，使用被测实现提供的创建方式单列一轮：新会话应正确路由，且不应读取仅限旧会话的测试代号。单纯关闭企业微信聊天窗口不等于创建新会话。

## 验收标准

- 单节点、双节点两个业务基线都满足条件，故障发生在基线之后。
- 受影响的连接和执行链路在预定时限内自动恢复；受害节点始终停止，存活节点不依赖人工修复。
- 两个 Bot 的每轮新消息在 `T_REPLY` 内得到正确最终回复；客户端可见回复与服务端租户、会话及投递记录一致。
- 原会话测试代号不丢失、不串租户；每个输入只对应一条用户可见最终回复。合法的流式更新与重复最终回复应分别统计。
- 持续观察期间没有连接反复迁移、持续积压或迟到的重复回复。

## 应采集的证据与计时口径

执行证据保存在独立运行目录，不回填本文。至少采集版本与拓扑、参数、节点启停及重启次数、故障时间、连接所有者变化、两租户消息关联 ID、最终回复及投递记录；凭据和完整个人标识应脱敏。

`t_connect - t0` 是连接恢复时间，`t_ready - t0` 是观测到的执行链路恢复时间。接管后每条消息的接收至最终回复耗时是该请求的响应时间。人工等待后才发送消息，不能据此得出精确的端到端业务恢复时间（RTO）。断线窗口内发送但未被服务端接收的消息，不属于本用例的通过依据。

验收结束后按测试计划恢复或关闭环境并保留证据；这一步不能计入此前的自动接管过程。
