## 1. 当前事实与目标

当前主干为：AgentVersion + ProfileRevision → DeploymentRevision / RuntimeManifest →
ChannelBinding → Gateway 收信 → 持久 RunRequested。真实 Worker 执行与完整回复仍待接线。
现有 Web 已有 Agent、Profile、Deployment 工作台，但当前 Control 工作树未接入 Channel 页面。
“配置已保存”“版本已发布”“渠道已连接”“路由已应用”“Run 已完成”不是同一个状态。

本 TODO 的目标是减少用户理解对象和技术字段的成本，不增加 Environment、用户 Slot 映射表、
Secret 产品、动态工具注册中心或调度平台。改善表单体验不改变后端授权、版本不可变性、
节点级最小工具分配、CAS 和幂等规则。

## 3. UX-01：从 Agent 需求生成同名资源表单骨架

### 用户目标

用户先选确定的 AgentVersion，系统按其 requirements 生成 Profile 资源表单，用户只补实际
模型、服务地址和凭据，不再手工抄写逻辑资源名称。该骨架是可编辑草稿，不自动发布。

### 待办

- [ ] 读取固定 AgentVersion 的 models / tools / knowledge 需求，按类别和精确名称生成表单。
- [ ] 显示所需 Capability、被哪些节点使用、哪些声明尚未被节点引用。
- [ ] 复用现有 Profile 编辑/保存能力；有同名资源时保留已填值并展示差异，不覆盖用户草稿。
- [ ] 依据平台静态支持的关闭 Kind 显示合法选项；未知能力或缺少可用实现时给出明确诊断。
- [ ] 新骨架不复制或推测其他 Profile 的凭据关联，不自动填写真实凭据。
- [ ] 用户更新来源 AgentVersion 时先预览新增/变化项；不自动删除已有资源或重命名冲突项。

### 不变量与验收

- models.primary、tools.search、knowledge.docs 原名进入表单，无额外绑定映射表、Alias 或模糊匹配。
- 生成工具表单不等于挂载工具；Manifest 和 Worker 仍只向选择了该工具的节点提供入口。
- Profile 含额外资源时不擅自删除，也不把额外工具自动分配给 Agent。
- 无匹配 Kind 的声明仍形成待补配置提示，不通过猜测任意候选制造“可发布”假象。
- Storage 不属于 AgentSpec Slot，不生成 storage_slot，另按 UX-02 和现有运行角色规则处理。

## 4. UX-02：平台提供托管 Session Storage

### 用户目标与当前差距

普通用户不必自行部署 PostgreSQL、组织 DSN 或录入数据库密码，就能获得 Agent 的会话存储。
当前 Compiler 明确要求 storage.session，可选 storage.memory；当前 Profile 接受用户提供的
postgres_state 配置。仅把 DSN 输入框隐藏，不构成托管存储能力完成。

### 待办

- [ ] 冻结托管存储的身份、租户隔离、连接资源、容量/保留/清理以及故障处理职责。
- [ ] 通过平台配置供应真实后端；通过 Profile 拥有方的受控用例产生明确的 storage.session
  配置与内部凭据关联，不由 Web 或其他模块直接写 Profile 表。
- [ ] 表单清楚显示“使用平台托管会话存储”及关键限制；避免用户手工创建业务 Environment。
- [ ] Deployment 发布仍固定确定配置及关联；Worker 不临时挑选默认数据库或跟随可变 latest。
- [ ] 定义平台服务身份代用户准备托管资源的授权规则；不以自动化路径绕过 OWNER 凭据权限。
- [ ] 明确普通用户是否还能选择自带 PostgreSQL，以及切换存储的生效和数据迁移语义。
- [ ] 使用真实 PostgreSQL 与后续 Worker 验证跨租户隔离、并发、恢复和存储不可用行为。

### 必须先决定

1. 一个托管资源按 Tenant、Profile 还是其他明确作用域配置；连接池与数据隔离如何对应。
2. 会话键与 Tenant / Agent / Deployment / Channel / 外部会话的关系，跨部署版本是否延续。
3. 后端地址变化、密码轮换、停用/删除、保留期限与历史 Run/Session 的处理。
4. 是否复用当前 postgres_state 协议；如需调整，直接完善当前未稳定 V1，不为开发期旧数据新建 V2。

### 验收

- 用户无需填写数据库 host、用户名、密码、DSN 即可完成部署准备，并能看到所用存储及限制。
- 不新增 Environment、Secret 管理页面或可被用户随意填写的底层数据库标识。
- 同名资源和托管底层设施不会导致两个租户访问彼此会话；使用凭据与配置仍按拥有方授权。
- 新的托管资源选择不改变既有不可变 Manifest；历史会话迁移不得隐含发生。
- “托管可用”必须由真实存储接线与 Worker 验证证明，不以占位 DSN 或配置发布成功替代。

## 5. UX-03：资源模板与独立“测试连接”

### 用户目标

用户从少量明确资源模板开始，只填写必要字段，并能主动测试当前配置，而不必先多次发布。
模板与测试属于配置辅助，不自动修改已经发布的配置，也不代替 Deployment 静态校验。

### 资源模板待办

- [ ] 先覆盖现有 openai_compatible、mcp_streamable_http + web.search、qdrant_openai、
  postgres_state；不将内建工具、命令执行或任意 SDK Option 标成已接入能力。
- [ ] 模板使用显式名称、说明和非秘密默认值；选用后产生普通草稿配置，不建立隐藏继承。
- [ ] 不内置真实凭据、共享 CredentialID 或跨租户关联；模板更新不静默覆盖已有草稿和 Revision。
- [ ] 与 UX-01 联动时保留 Agent 要求的资源名称；远程工具名与本地资源名称分别展示。

### 独立连接测试待办

- [ ] 定义单资源、显式触发的测试用例与结果契约；接口形状未冻结，不加入“当前已实现 API”。
- [ ] 明确测试已保存 Draft / 已发布 Revision / 未保存输入中哪一种，以及所需凭据授权。
- [ ] 通过 Profile 拥有方与类型化 Adapter 取用必要凭据；客户端不得得到原值，日志不保存秘密。
- [ ] 限定目的地址、协议、网络范围、超时、并发与频率；不提供任意 URL 探测或通用命令入口。
- [ ] 先采用最小、非破坏性探测；可能计费的真实模型请求单独说明并由用户显式触发。
- [ ] 不写业务数据、不建索引或修改用户数据库；必要权限和资源存在性检查与写入测试分开。
- [ ] 返回认证失败、网络不可达、资源不存在、协议不匹配、超时等稳定分类，不返回秘密值。
- [ ] 标记对象、配置指纹/版本、凭据版本（非凭据值摘要）及时间；配置或凭据变化后结果标记过期。

### 验收

- 测试只影响诊断结果，不创建 ProfileRevision、DeploymentRevision、Manifest 或路由事件。
- 在线测试失败不回滚合法草稿，不自动成为发布事务的必经网络步骤。
- 连接成功只证明该时间、该目标与该项探测成功，不保证 Worker、全部能力或未来调用一定成功。
- 成员没有测试授权时，后端拒绝调用；按钮隐藏不是权限实现。

## 6. UX-04：连接测试与发布静态校验分开展示

### 待办

- [ ] 显示两组独立结果：“发布兼容性校验”和“在线连接测试”，不给一个混合绿灯。
- [ ] 静态结果显示来源 AgentVersion / ProfileRevision、字段与资源定位、稳定诊断和修复入口。
- [ ] 在线结果显示最近测试时间、对象、覆盖范围、成功/失败/未测/过期；测试中状态单独显示。
- [ ] 配置、凭据或来源版本变化后，使不再匹配的结果失效；不能展示旧的成功为当前通过。
- [ ] 保存、发布、Gateway 连接观测、路由传播、Run 完成分别呈现，不把 READY 当作 Agent 已回复。

### 必须覆盖的组合

| 静态校验 | 在线测试 | 产品含义 |
| --- | --- | --- |
| 通过 | 未测试 / 过期 | 满足发布契约；当前连通性未知，不假装已上线 |
| 通过 | 失败 | 静态兼容，但存在运行诊断；不把网络探测塞入发布 SQL 事务 |
| 失败 | 成功 | 地址可达不代表可发布，例如同名资源能力不匹配；仍需修复静态错误 |
| 通过 | 成功 | 展示两项及各自时间/范围；仍不代表 Worker 或完整回复验收完成 |

后端 Publish 每次重新执行确定性校验，不能使用前端旧报告或在线测试成功凭证跳过检查。

## 7. UX-05：客户端处理并发、幂等与技术字段

### 用户目标

用户只操作“保存、发布、启用、切换版本、更新凭据”，不填写 CAS、Idempotency-Key、
CredentialID、account_revision、connection_revision 或 route generation。

### 待办

- [ ] 客户端读取当前版本并携带对应 expected 字段；不能自行递增当作权威值。
- [ ] 一次逻辑提交生成一个幂等键，双击、超时、断线重试复用原键与完全相同的请求内容。
- [ ] 内容改变视为新提交，先解决不确定结果，再生成新键；不自动换键重试造成重复副作用。
- [ ] 定义响应丢失后的恢复策略，尤其凭据命令：含秘密正文不持久化到 localStorage、URL
  或日志；页面重载后的元数据核实/重新输入流程需冻结，不盲目重发凭据轮换。
- [ ] CAS 冲突展示“配置已被更新”，保留本地输入，提供刷新和差异确认；不自动覆盖他人改动。
- [ ] Binding 改版由服务器生成 generation；客户端展示传播状态，不构造更高 generation 冒充生效。
- [ ] 普通页面显示业务状态、所选发布版本与时间；内部版本保留在只读高级诊断中。
- [ ] 区分“修改下一版草稿凭据”和“更新已发布配置使用的凭据”，展示后者的影响范围。
- [ ] 区分账户与 Binding 启用；重新启用账户可能恢复保留的 Binding 意图时明确提示。

### 验收

- 用户不填写并发/幂等/内部身份字段，但服务端校验和 OWNER 权限保持有效。
- 双击、成功响应丢失后重试、并发编辑、同 key 异正文、发布后切换失败均有自动化测试。
- 重试不重复发布或轮换凭据；过期页面不覆盖新版本；请求日志没有秘密输入。
- 服务器保存与 Gateway 应用分开展示；查不到传播结果显示“待确认”，不显示“已上线”。

1. 先冻结 UX-02 的存储隔离/会话语义，以及 UX-03 的测试对象、授权与返回契约。

3. 实现 UX-01 骨架与 UX-03 模板，复用 Profile 真实保存接口；再接入独立连接测试。
4. 将托管 Storage 与后续 Worker、Channel Web 接线；完成“最小 LLM + Session + Telegram 回复”真实验收。

Profile 拥有资源与凭据，Deployment 拥有编译和发布，Channel 拥有机器人账户与路由，
Gateway 拥有渠道连接/收信/投递，Worker 拥有执行。跨任务共享文件先协调，禁止分别覆盖。
平台运维负责 mTLS 证书、公共 Webhook origin、NATS、执行网络与资源上限；这些不转嫁为租户表单。
