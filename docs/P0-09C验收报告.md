## 3. Atomic Completion interface

当前 storage-neutral contract 为：

```go
type DeliveryAckRecord struct {
    TenantID    string
    JobID       string
    ExecutionID string
    SessionID   string
    DeliveryID  string // job_queue.delivery_id；同时是当前 delivery token
}

type AtomicCompletionRequest struct {
    Commit   ExecutionCommitRecord
    Delivery DeliveryAckRecord
}

type AtomicCompletionCoordinator interface {
    CommitResultAndAck(context.Context, AtomicCompletionRequest) error
}
```

`ExecutionCommit` 仍是执行层的完整 fenced commit 输入；`AtomicCompletionRequestFor` 在进入 coordinator 前校验 JobID、ExecutionID、TenantID、SessionID、owner/epoch/FenceToken、Lease identity 和 Delivery identity，并序列化 `AgentResult`。PostgreSQL coordinator 再在数据库 transaction 内重新校验，前置转换不是数据库 fencing 的替代品。

`ExecuteWithCompletion` 只在原有执行 Lease/Runtime 完成、提交前 `Lease.Validate` 成功后调用 completion callback。callback 返回错误时 Executor 不报告成功，Worker 不进入成功路径。

## 4. Transaction ownership 和 SQL 边界

`postgres.AtomicCompletionCoordinator` 从同一个 `*pgxpool.Pool` acquire 一个 `*pgxpool.Conn`，显式创建一个 `pgx.Tx`。transaction ownership 留在 PostgreSQL storage coordinator，`pgx.Tx` 不逃逸到 Worker、Execution 或 Queue 上层。

transaction 顺序为：

1. `SELECT ... FROM job_queue ... FOR UPDATE`，按 `(tenant_id, job_id)` 锁定当前 Queue row。
2. 从持久化 payload 解析并校验 JobID、ExecutionID、TenantID、SessionID，避免只相信调用方传入的 Delivery。
3. 读取已有 `execution_result`，识别重复完成或历史 result-only 状态。
4. 对活动 delivery 执行 `SELECT ... FROM session_lease ... FOR UPDATE`，重新校验当前 owner、epoch、fencing token 和 Lease expiry。
5. 若 result 尚不存在，执行 `execution_result INSERT ... ON CONFLICT DO NOTHING`。
6. 检查 result `RowsAffected()`；0 不能视为成功，必须重新读取并证明相同的 result，否则返回 conflict。
7. 执行条件 Queue Ack update：当前 tenant/job、`status='in_flight'`、当前 `delivery_id`、Lease visibility 未过期。
8. 检查 Queue Ack `RowsAffected()==1`；否则 transaction rollback，不能留下 result。
9. 只有 `tx.Commit` 明确成功后才返回 nil。

Queue row 先锁、Lease row 后锁；Queue 和 Lease 的数据库操作都在同一 transaction。结果写入和 Queue `acked` 状态在同一 PostgreSQL commit 边界可见。

已 Ack 的相同 delivery token + 相同 result 是重复调用的幂等成功，可以在 Worker release Lease 后识别；此路径不产生新写入。已 Ack 但 result 缺失被明确拒绝为 conflict，不使用非原子的补写。

## 5. Fencing、tenant 与 delivery 校验

transaction 内重新校验：

- `TenantID`：Queue row、Session/Lease、Execution result 均使用 tenant 条件。
- `SessionID`：Lease row、result record、Queue durable payload 一致。
- `OwnerID`、`Epoch`、`FenceToken`：与当前 `session_lease` 行锁定读取的值完全匹配。
- Lease expiry：使用 PostgreSQL `clock_timestamp()` 读取和条件检查，过期返回 `storage.ErrLeaseLost` 或 delivery expiry 分类。
- `JobID`、`ExecutionID`：请求 Delivery、Queue row、Queue payload 和 result identity 一致。
- `DeliveryID` / token：必须等于当前 Queue row 的 `delivery_id`；旧 token、错误 token、已完成 token 不能改变 Queue。
- Queue 当前状态：只允许活动 `in_flight` delivery 完成；`queued`、`discarded`、错误 holder 和错误 last token 均拒绝。

真实 acceptance 覆盖 owner、epoch、fence token、tenant、session、job、execution、错误 delivery ID、过期 delivery、已 discarded delivery 和 reclaim 后旧 token。错误条件均在 result insert 前阻断，或在 transaction rollback 后不留成功 result。

PostgreSQL coordinator 不依赖 `queue` runtime 包，delivery 错误使用 storage-neutral sentinel，避免 Queue integration test package 与 PostgreSQL package 形成 import cycle。

## 6. Result 与 Queue Ack 原子性证据

真实 PostgreSQL acceptance `TestPostgresAtomicCompletionCommitsResultAndAckTogether` 通过：

- 有效 Session Lease 和有效 Queue delivery；
- coordinator 成功；
- `execution_result` 只有一行，tenant/session/job/execution/owner/epoch/token/result 正确；
- `job_queue.status='acked'`，active delivery 清空，`last_delivery_id` 为当前 token；
- Worker integration 额外断言 legacy `FencedExecutionSink.Commit` 次数为 0，Queue 独立 `Ack` 次数为 0。

真实 Worker 使用 `NewWithAtomicCompletion`。成功路径为：

```text
Receive
  -> Execute runtime
  -> Lease Validate
  -> AtomicCompletionCoordinator.CommitResultAndAck
  -> Release
```

`New` 保留的是显式 legacy in-process/Fake contract 路径，提供既有 `Execute -> Commit -> Ack` 行为；真实 PostgreSQL Worker acceptance 不使用该构造，而使用强制要求 coordinator 非空的 `NewWithAtomicCompletion`。代码中没有类型断言后 fallback，也没有 coordinator 失败后回退到独立 Commit/Ack。

## 7. Rollback、错误注入和 commit unknown

### Result write failure

真实 PostgreSQL trigger 在 `execution_result BEFORE INSERT` 阶段抛出 `pgconn.PgError`。验收通过：

- coordinator 返回错误且 `errors.As` 可取得 `*pgconn.PgError`；
- result 行数为 0；
- Queue 仍为 `in_flight`，没有 Ack；
- 移除 trigger 并让 visibility 到期后，真实 Queue 获得新 delivery token，支持后续 recovery。

### Ack update failure

真实 PostgreSQL trigger 只在 Queue row 转为 `status='acked'` 时抛出 `pgconn.PgError`。验收通过：

- result insert 已在同 transaction 中发生，但 Ack update 错误使整个 transaction rollback；
- result 行数为 0；
- Queue 不进入 acked；
- 移除 trigger、让 visibility 到期后可以重新领取新 token；
- 不是 fake Ack 返回 error。

### Rollback

result INSERT、Queue Ack update 任一语句失败都由同一 transaction rollback；不会产生 result-only 或 ack-only 的新半提交状态。测试中的 result-only reconciliation 是显式历史数据 setup，不是本阶段 Worker 成功路径。

### Commit outcome unknown

`TestPostgresAtomicCompletionUnknownCommitOutcomeIsReported` 使用真实 PostgreSQL pool connection，在 transaction commit 前关闭底层 `pgx.Conn`，模拟 commit 附近连接中断。验收通过：

- 不返回 clean success；
- 返回可 `errors.Is(err, storage.ErrCompletionOutcomeUnknown)` 的 `*CompletionOutcomeError`；
- 错误包含只读 reconciliation outcome；
- reconciliation 区分 `neither_committed`、`both_committed`、`result_only`、`ack_only` 或 `delivery_token_taken_over`；
- 不立即执行 Ack/Nack；
- 不把连接关闭简单当作 rollback；
- 测试只证明数据库连接/transaction 故障，不证明 OS 进程 crash 或 SIGTERM。

Worker 对 `ErrCompletionOutcomeUnknown` 只标记 delivery unresolved，不调用 Queue Ack 或 Nack。后续 Stop/recovery 才按既有 Worker unresolved ownership 规则处理，不能伪造成功。

## 8. Duplicate、历史状态和并发 owner 证据

`TestPostgresAtomicCompletionDuplicateAndResultOnlyReconciliation` 通过：

- 同一有效 request 重复提交只有一份 result；Queue 只 ack 一次；在 Lease release 后重复调用仍幂等成功。
- 显式历史 result-only 状态可以在当前有效 delivery、当前有效 Lease 下安全补 Ack，不重写 result。
- 显式 queue ack-only 状态没有 result 时返回 conflict，不继续写 result。

`TestPostgresAtomicCompletionTakeoverAndConcurrentWinner` 通过：

- takeover 后旧 owner 的 request 返回 fence/epoch/lease 拒绝；新 owner 使用新 epoch/token 成功；最终 result 属于新 owner。
- 旧、新 owner 并发提交时只有一个成功；新 owner result 只有一行；Queue 只有一个 Ack。
- 即使旧 request 在新 request 已 Ack 后到达，result fence 不匹配也不会报告成功。

真实 Worker acceptance `TestPostgresWorkerFenceLossPreventsAtomicCompletion` 通过：epoch bump 后旧执行不产生 result、不调用 legacy sink，Queue 按当前 Worker contract requeue。
