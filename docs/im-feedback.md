# IM 回执、失败与媒体处理规则

## 1. 重复审批有提示，但不重复执行

同一条 Webhook 被平台重投，仍然复用已有回执；用户自己另发一条相同的批准/拒绝命令，则收到新的固定状态提示。两者通过外部消息 ID 区分，不由模型判断。

审批决定与执行任务仍然各只有一份。批准的续执行任务沿用第一次决定的消息 ID，新提示不会生成第二份工具授权。若前次进程中断，新请求可以补齐原任务/回执，但不会新增另一笔逻辑操作。

新增 `approval_decision_message` 记录所有已接受的决定消息，包括重复确认。一个外部消息 ID 不能再用于决定另一张审批单。migration `013_approval_decision_messages.sql` 会补入历史首次决定的映射，不修改历史审批状态。

重复确认的回复来自平台，不经过 LLM。例如：

> 平台提示：审批 … 已批准，本次重复确认不会额外创建执行任务；批准不等于执行成功，请查看原任务的执行结果。

反向决定、其他用户、其他 Topic、其他租户、过期审批仍被拒绝。所有通过验证的回调，包括审批和媒体提示，都经过一次入站频率检查；不会因为不调用模型就绕过限流。

## 2. 执行失败后不再静默结束

Worker 的模型执行重试耗尽后，在同一事务里将 `agent_run` 标记为 `dead`，并插入固定失败回执。只有回执持久化后才 ACK 队列；回执写入失败会继续尝试保存，不再额外执行模型。

```text
执行失败 → 有重试额度：重新调度
        → 额度耗尽：dead + outbound 回执原子提交 → ACK
                   → 写入失败：保留队列交付，重试保存回执
```

这不是把失败的 Run 改成 `completed`。回执包含请求编号，并提醒用户先核对工具记录，不声称工具已回滚。重投已结束的消息不会再调用模型或发送第二条失败提示。旧 Worker 的失败、完成或终态写入会检查当前归属，不能覆盖其他 Worker 正在处理的状态；已经完成的 Run 仍允许幂等补齐后续记账。

`dead` Run 与 `dead` 出站投递是不同状态。模型执行失败的提示仍需要 Sender 和 IM 平台正常工作；Bot 被封禁、网络持续不可用或接收人无效时，不能保证同一通道还能发出失败通知。发送失败仍走现有退避、dead 记录与审计，实际告警通知属于后续运维交付。

进程取消时不把中断误判成最终业务失败，也不提前 ACK；由持久化队列后续接管。完整跨节点故障矩阵和长时间故障恢复仍需生产阶段演练，不能只凭这些单测承诺所有分布式交错均已验证。

## 3. 媒体与编辑消息明确拒绝

当前平台对 IM 的可执行输入仅支持文本。图片、文件、语音、视频等已识别媒体收到固定说明，告诉用户尚未下载或读取附件。附件说明也不会被当作批准命令。这条提示通过 Inbox/Outbound 持久化，绕过 Runner，不产生工具调用。

Telegram 的 `edited_message` 被显式标记：修改原消息不会修改已提交任务、不会撤销审批，也不会再次执行 Agent。需要新请求时应另发文本消息。群聊的白名单、mention/reply 过滤仍先执行，不会向未触发 Bot 的群消息刷提示。

这一阶段没有实现附件下载。后续 rc.4 已增加显式开启的 Telegram 附件下载、大小/MIME/图片尺寸检查、Artifact 转存和同会话文本读取，见[附件实现](reliability-followup.md#最小安全附件链路)。默认仍拒绝媒体；没有完整杀毒、多模态理解、媒体发送或消息编辑 API，不应写成“已支持图片理解”。

## 4. 验证与生效

Memory 与隔离 PostgreSQL 测试覆盖：重复决定消息不能跨审批复用、失败状态/回执原子性、插入失败的事务回滚、旧 Worker 写入拒绝；Worker 测试覆盖回执写失败及提交响应丢失，确认模型调用次数不再增加。Telegram 模拟协议链路覆盖两种重复消息及固定回复，媒体/编辑入口验证不会进入审批或模型。

这些是本轮自动测试与本地数据后端验证，不等同于新版本已再次使用真实 Telegram/企业微信账号联调。日常服务、Bot Binding 与现有发布指针未改动；新行为需要部署新 binary 并应用 migration 012、013 后生效。
