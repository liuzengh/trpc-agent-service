# 存储与数据访问设计

> 状态：已确认（阶段 18，grill-with-docs 对齐：动机=统一数据访问抽象 + 说清每域如何存储；范围=轻量聚合 + 文档，非六域 Router 化）
> 关联：`CONTEXT.md`「数据访问与存储域」分组；`AGENTS.md` 阶段 18；代码 `trpcservice/storage/stores.go`

## 1. 目的与范围

本文给出平台**存储层的权威说明**：数据划分成哪些**数据域**，每域由什么抽象承载、落在哪个后端、数据如何布局、一致性边界是什么；以及「统一数据访问抽象」`DataStores` 如何收敛装配。

管理域（tenant/agent/model-endpoint/tool/skill 的注册表与配置，各自走独立 MySQL store 或内存）不属于本文的存储域范畴——它们是「元数据」，随 `db` 是否为 MySQL 决定存储，不经 `storage.Router`。

## 2. 数据域总览

| 数据域 | 承载内容 | 抽象接口 | 实现后端 | 数据布局 | 一致性 | 当前状态 |
|---|---|---|---|---|---|---|
| session | 会话状态/事件/路由锁 | `storage.Sessions` | inmemory / MySQL / Redis（逐租户可选） | 内存 map；`session_states` 等表；Redis key | 跨节点共享、MySQL 权威 / Redis 加速 | Router 注册 |
| memory | 长期记忆 | `storage.Memories` | inmemory / MySQL / Redis（逐租户可选） | 同 session 风格 | 同上 | Router 注册 |
| summary | 会话摘要 | 无独立接口 | **随 session 后端**（框架 session/mysql 自建 `session_summaries` 表） | — | — | **非独立域**（无第二实现、无独立存储诉求） |
| knowledge | 知识库元数据 + 向量 | `knowledge.Manager` + 框架 VectorStore | MySQL 元数据 + Milvus 2.5（或内存向量库回落） | 006 表族；Milvus collection `{tenant}_kb_*` | 摄入写入 Bounded 一致（写后短暂不可见属正常） | 全局单后端，工厂由 main 注入 |
| artifact | 命名版本化产物（字节） | `artifact.Service`（框架契约） | MinIO（S3 兼容） | 对象键 `{tenant}/{user}/{session}/{filename}/{rev}`（`user:` 前缀跨会话） | 单写者低频；版本不可变 | 全局单后端（阶段 14） |
| audit | 治理决策/用量记账 | `audit.Recorder` | MySQL（异步批量） | 009 `audit_logs`/`usage_records`/`artifacts` 表 | 异步批量、优雅关停、溢出计数 | 全局单后端（无 MySQL 时禁用） |

## 3. 各域存储细节

### 3.1 session / memory —— 唯一「逐租户可选后端」的域

- 抽象：`storage.Sessions` / `storage.Memories`，实现 inmemory / MySQL / Redis 三种后端（`storage/sessions.go`、`memories.go`、`mysql.go`）。
- 路由：`storage.Router.Sessions(ctx, tenantID)` / `.Memories(ctx, tenantID)` —— 先读该租户 `Tenant.DataBackend`（map：domain→backend 值），未显式配置用启动默认；解析结果按 backend id 缓存单实例，租户隔离靠调用链上的 tenant key（框架 AppName）。
- 一致性：跨节点共享状态以 MySQL 为权威、Redis 加速；框架 session 后端独立 module（`session/mysql`、`session/redis`）。

### 3.2 summary —— 有意不设独立域

详细设计曾列 summary 为六域之一。平台落地判定：摘要当前随会话后端（框架 `session/mysql` 的 `session_summaries` 表）；平台没有独立摘要存储功能、没有第二实现。**结论：Summary 不是独立数据域**（见 `DataStores` 无 summary 字段、`stores_test.go` 有显式注释）。若未来出现"摘要须独立落库"的真实需求再评估。

### 3.3 artifact —— MinIO（S3）

- 框架 `artifact.Service` 契约（Save/Load/List/Delete/ListVersions），平台实现 `storage.MinioArtifactService`（阶段 14）。
- 版本信息编码在对象键内（`.../{filename}/{revision}`），revision 首个保存为 0、逐次 +1；无额外索引。
- 注入点：`runner.WithArtifactService`（worker.run），代码执行工具产物自动保存。

### 3.4 knowledge（向量库域）

- 元数据：MySQL 006 表族（`knowledge` 元数据 + 文档分块）；向量：Milvus collection（`{tenant}_{kb}_{id}` 清洗后名）或内存向量库回落。
- 工厂由 main 按 `cfg.Milvus.Address` 选择（`knowledge/milvus.go` `vectorStoreFactory`）；embedder 复用模型端点。
- 一致性：Bounded（写入后短暂不可见属正常，不做强一致）。

### 3.5 audit

- 单一 `audit.MySQLRecorder`：channel buffer + 批量 flush + 优雅关停 + 溢出计数；读侧 `List` 供 admin。
- 无 MySQL 时 auditor 为 nil（禁用）。

## 4. 统一数据访问抽象：DataStores

`storage.DataStores`（`storage/stores.go`）是数据域**装配聚合点**：

```go
type DataStores struct {
    Router    *storage.Router     // session / memory（逐租户）
    Knowledge *knowledge.Manager  // knowledge（向量）域
    Artifacts artifact.Service    // artifact 域（MinIO）
    Auditor   audit.Recorder      // audit 域
}
```

- main 在 worker 分支**单点组装**一次（`storage.NewDataStores(router, kbMgr, artSvc, auditor)`），worker 构造从 `dss.*` 取值，域名与代码字段一一对应。
- 取舍：**不为没有第二实现的域造可选接口**（artifact/knowledge/audit 目前只有单一生产后端）。`Tenant.DataBackend`（domain→backend）是保留的扩展点。
- 若某一域将来出现第二个后端实现（例如 audit 文件后端、知识库 PostgreSQL pgvector），则按第 5 节扩展步骤把该域注册进 Router。

## 5. Router 扩域准则与步骤

**准则（阶段 18 拍板）**：一个域只有在**确实存在第二个后端实现**时才纳入 `Router` 的逐租户后端选择。当前满足的只有 session/memory。

未来扩展某域（以 audit 举例）的步骤：
1. `tenant` 增加 domain 常量（如 `DomainAudit = "audit"`）——现在只有 `DomainSession`/`DomainMemory`；
2. 为该域定义抽象接口 + ≥2 个实现（如 `audit.MySQLRecorder` 与文件后端）；
3. `Router` 增加 `Audits(ctx, tenantID)` 方法（domain 解析 + 实例缓存，与 `Sessions` 同构）；
4. `DataStores` 相应调整字段；main 装配；文档本表更新。
「没有代码改动即换后端」的机制已存在，等待的是真实需求而非预埋抽象。

## 6. 与详细设计 §5.8 的对照说明

详细设计 §5.8/§21 ⚠️ 曾按六域设想 Router 全覆盖。实际落地收敛为：**Router 覆盖 session/memory；summary 不独立；artifact/vector/audit 各持全局单后端并纳入 DataStores 装配聚合**。差异源于「领域包内嵌内存态、storage 回归会话域」与「只在出现第二实现时才抽象」的既定架构原则（AGENTS.md §4/存储架构约定）。
