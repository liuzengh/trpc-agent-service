# P1-09 运行文档：本地 Docker/Compose 部署边界

本文档描述 P1-09 交付的可重复本地容器部署边界。它只覆盖本地
Docker/Compose 部署、生命周期和依赖健康检查，不代表生产部署、
云 IAM/TLS、HA/failover 或任何 production rollout。

## 1. 范围与边界

- 权威计划（`docs/implementation-plan.md`）对 P1-09 的定义：
  `Docker Compose、readiness/liveness、依赖健康检查和运行文档`。
- 不包含：Production Embedder、Production Milvus、云 PostgreSQL/Redis、
  云 OTel Collector、Kubernetes、生产 secret manager、HA/failover 证明。
- `P1-06 production rollout: BLOCKED` 状态不变：Compose 中没有任何
  vector/retrieval/rebuild/Milvus 服务或开关，`VECTOR_BACKEND` 保持
  默认 `none`。
- telemetry 保持 P1-07 默认 `no-export`：默认 profile 不设置任何
  OTLP endpoint，应用不构造 collector client；本地 collector 只存在于
  显式 `--profile telemetry` 中，且不参与业务 readiness。

## 2. 前置条件

- Docker daemon 与 `docker compose` 可用（本边界在 Docker 29.7.2、
  Compose v5.5.0 上验证）。
- 基础镜像（固定 tag + digest，见验收报告）：
  - `golang:1.26.3-alpine`（builder）
  - `alpine:3.20`（runtime）
  - `postgres:16-alpine`、`redis:7-alpine`
  - `otel/opentelemetry-collector-contrib:0.111.0`（仅 telemetry profile）

## 3. 构建镜像

```bash
docker build -t p109-deploy-app:local .
```

镜像内只包含 `trpc-service`、`trpc-migrate`、`/app/migrations` 和 CA
证书；默认 `USER app`（非 root）；不包含 `.env`、secret、git 元数据、
测试文件或报告。

## 4. 配置与 secret

1. 参考 `.env.example` 建立 env 文件（非敏感占位值）。
2. 在仓库外的目录（0700）生成 PostgreSQL 密码文件：

```bash
mkdir -m 700 -p /tmp/p109-deploy-<run-id>/secrets
printf '%s' '<local-password>' > /tmp/p109-deploy-<run-id>/secrets/pg_password
chmod 600 /tmp/p109-deploy-<run-id>/secrets/pg_password
export P109_SECRET_DIR=/tmp/p109-deploy-<run-id>/secrets
export P109_RUN_ID=<run-id>
```

- 密码通过 Docker secret（`/run/secrets/pg_password`）进入容器；
  Compose 文件、`docker compose config` 输出、镜像层和
  `docker inspect` 环境中均不出现密码或完整 DSN。
- 容器内由 wrapper 读取 secret 组装 `DATABASE_URL` 后，通过
  `su-exec` 以非 root `app` 用户执行服务进程。

## 5. 启动

```bash
# 核心边界（postgres + redis + migrate + app）
docker compose --env-file <env-file> up -d

# 显式本地 telemetry profile（可选，默认不启动）
docker compose --env-file <env-file> --profile telemetry up -d
```

- `migrate` 是独立 migration 生命周期步骤：`depends_on` 要求
  PostgreSQL healthy；`app` 要求 `migrate` 成功退出
  （`service_completed_successfully`）。
- 发布端口仅绑定 `127.0.0.1`（默认 app `18080`、postgres `15432`、
  redis `16379`、collector `14317`，可通过 env 覆盖）。

## 6. 健康与诊断

- `GET /livez`：liveness，进程存活即 200，不依赖数据库/Redis 状态。
- `GET /healthz`：readiness，依赖装配与 migration 正确后才 200；
  drain 中、PostgreSQL outage 中返回 503。合同未在本阶段修改。
- 容器 healthcheck：postgres `pg_isready`、redis `redis-cli ping`、
  app `wget /healthz`，均为有界 interval/timeout/retries。

## 7. 停止与恢复

```bash
docker compose --env-file <env-file> stop app     # SIGTERM，有界（30s grace）
docker compose --env-file <env-file> start app    # 重新拉起
docker compose --env-file <env-file> down -v      # 停止并删除本轮资源
```

- SIGTERM：应用有界反向关闭，stderr 记录 `service stopped status=clean`，
  退出码 0。
- SIGKILL：`docker kill` 按设计不触发 restart policy；操作员
  `docker compose start app` 后，应用从 PostgreSQL durable 状态恢复并
  重新 ready。`restart: unless-stopped` 覆盖容器自身异常退出。
- migration mismatch（checksum/缺失/超前）：`trpc-migrate` 与服务启动
  gate fail closed，应用不能进入 ready，Compose 拒绝启动 app。

## 8. 独立 migration 命令

```bash
docker compose --env-file <env-file> run --rm migrate
```

退出码：`0` 已应用或已最新；`2` 配置非法；`3` 依赖不可达；
`4` checksum mismatch；`5` 缺失版本；`6` 未知未来版本；
`7` migration 源非法；`8` 执行失败/超时。stderr 只输出稳定类别
（如 `category=checksum_mismatch`），不输出 DSN 或原始数据库错误。

## 9. 资源所有权与清理

- 所有资源带 label：`owner=p109`、`run_id=<run-id>`、
  `component=deployment`、`created_by=pi`；名称内嵌 run id。
- 清理仅针对本轮资源（`down -v` 按 project 名），并按 label 过滤核对
  归零；不使用 `docker system/volume/network prune`，不删除历史资源。
