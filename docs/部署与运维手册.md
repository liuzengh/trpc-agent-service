# 部署与运维手册

> 本文回答四件事，每一条都以**本机真实部署实测**为准（数据标注了日期与条件）：
> ①故障恢复与降级策略 ②平台版本灰度发布与租户配置回滚 ③容量评估 ④最小可运行部署与生产推荐部署。
>
> 实测环境：Windows + Docker Desktop / Docker Compose v2，单机 8 vCPU 级别；
> 平台版本 `v1`（`GET /version` 可见），模型端点 `endpoint001`（deepseek chat 协议），
> Agent `agent001`，租户 `t-demo`。所有命令均在仓库根目录执行。

## 0. 结论速览

| 问题 | 结论（实测） | 章节 |
| --- | --- | --- |
| 节点/依赖故障会不会丢消息 | **不会丢**：Redis 停机 30s、消息仍可重投；进程不需要重启，自愈后继续消费 | §2.2 §2.5 |
| 故障期用户看到什么 | Redis 不可用：`POST /chat` → **500**（拒绝而不是假装接受）、`/healthz` → **503 + 原因**；恢复后 ≤6s 回到 200 | §2.5 |
| 灰度发布怎么做 | 入口层按**权重 + 试点租户白名单**分流新构建，`GET /version` 可外部验证，回滚一条命令；实测 10% 权重 → 观测 11.0%，试点租户 → 100% | §3.1 |
| 租户配置怎么回滚 | 平台内 `POST /tenants/{id}/config-rollback`；平台外 `cmd/configctl rollback`（平台不可用时用） | §3.5 |
| 单节点能扛多少 | 入站 **3.2k~4.3k msg/s**（HTTP+XADD）；稳态回合 **12.75 turns/s**（16 并发）；干净队列下单回合 p50 **1.0s**、p90 1.5s | §4.1 |
| 最小部署 | 4 个容器（mysql/redis/backend/frontend），一条 compose 命令，单进程 `role=all` | §1.1 |
| 生产推荐部署 | edge(TLS) + admin/worker×N/gateway 分角色 + 观测栈，`role` 隔离爆炸半径，可滚动扩容 | §1.2 |

## 1. 部署方案

### 1.1 最小可运行部署（core profile）

适用：验收演示、单租户试运行、开发联调。全部状态在 4 个容器里，无外部依赖。

```bash
cp deployments/.env.example deployments/.env      # 至少改 TRPC_SECRET_MASTER_KEY
cd deployments
COMPOSE_PROFILES= docker compose up -d --build     # 只起 mysql/redis/backend/frontend
docker compose ps                                   # 4 个服务 + healthcheck
```

| 项 | 值 |
| --- | --- |
| 容器 | `deployments-mysql-1`(3307→3306)、`deployments-redis-1`(6379)、`deployments-backend-1`(8080)、`deployments-frontend-1`(5173→80) |
| 后端角色 | `all` = Admin API + Chat API + Worker 消费 + IM 网关（单进程） |
| 数据 | MySQL 卷 `deployments_mysql-data`（DDL 由 `deployments/mysql/init/*.sql` 首次启动执行）、Redis 卷（stream/锁/幂等） |
| 登录 | `.env` 的 `ADMIN_USER_ID/ADMIN_PASSWORD`（未设时 dev 默认 `admin/admin123`，生产 profile 下强制显式设置） |
| 验证 | `curl -s localhost:8080/healthz` → `{"status":"ok"}`；`curl -s localhost:8080/version` → `{"version":"v1","role":"all",...}` |
| 代码执行 | backend 容器挂载宿主 `docker` CLI 能力才能用 `code-exec`（`deployments/docker-compose.yml` 已按需配置）；不挂则工具报传输错误，平台其余功能不受影响 |
| 资源实测 | backend 空载 ~33 MiB，重载峰值 ~101 MiB / 28% CPU（§4.1） |

**core 的能力边界（如实）**：向量知识库（Milvus）、对象存储（MinIO）、追踪/指标
（Jaeger/Prometheus）都不在 core 里；`COMPOSE_PROFILES=full` 才拉起它们。
core 下 `knowledge` 回落内存、artifact 不落对象存储、无 trace 导出。

### 1.2 生产推荐部署（分角色 + TLS 入口）

`deployments/docker-compose.prod.yml` 把单进程拆成按职责隔离的角色，并用 edge 统一入口：

```bash
# 1) 证书（自签仅用于内网/演示；对外用正式证书替换 deployments/prod/certs/）
bash scripts/gen-selfsigned.sh

# 2) 必需变量（缺失直接拒绝启动，见 compose 的 ${VAR:?}）
export ADMIN_PASSWORD='<强口令>'
export TRPC_JWT_SECRET='<32B+ 随机串>'
export TRPC_SECRET_MASTER_KEY='<32B+ 随机串>'
export WORKER_REPLICAS=2

# 3) 起栈（legacy profile 关闭 all-in-one 后端，避免抢同一份 Redis 消费组）
cd deployments && docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile prod up -d --build
```

| 服务 | 角色 | 说明 |
| --- | --- | --- |
| `edge` | nginx + TLS | `${EDGE_HTTP_PORT:-80}`→301、`${EDGE_HTTPS_PORT:-443}`（HTTP/2、HSTS）、`/api/(chat\|sessions\|dlq)` → `backend-worker`，其余 `/api/` → `backend-admin`，静态前端 |
| `backend-admin` | `role=admin` | 管理面：租户/Agent/端点/工具/KB/Skill/审计/用量/通道配置。**不消费消息** |
| `backend-worker` | `role=worker` | 数据面：Chat API + SSE + Worker 消费 + Outbox 派发。`WORKER_REPLICAS` 可扩 |
| `backend-gateway` | `role=gateway` | 仅 IM 长连接与出站投递。**全平台只允许一个实例** |
| mysql / redis / milvus / minio / otel / jaeger / prometheus | 基础设施 | 与 core 相同，生产建议外置托管（见下） |

**为什么要拆角色**（实测证据）：

- 路由矩阵：生产拓扑隔离项目实测 —— 停掉 worker 后 `GET /api/sessions` 返回 **502**（edge 找不到上游），
  而 `GET /api/version` 仍 **200**（admin 存活）；说明角色确实各管一摊，**管理面不会因为数据面挂了而不可用**。
- 爆炸半径：Worker 是唯一会执行模型/工具/代码的进程，把它与管理面分开，模型或工具故障不会
  连带管理 API 不可用。
- 单点约束：IM 网关**必须单实例**（一个 bot 账号只能被一条 WSS 长连接持有）。
  `backend-gateway` 因此固定 1 副本；升级时蓝绿切换（§3.3）。
- 无状态扩容：`backend-worker` 无本地状态（会话/记忆/锁/幂等都在 Redis，回复走 MySQL outbox），
  直接加副本即可线性扩容。

**`role` 的语义**（`cmd/trpc-service/role.go`，未知角色直接 `exit 2`，不静默降级）：

| role | 注册内容 |
| --- | --- |
| `all` | Admin API + Chat API + WorkerLoop + IM 网关（dev/最小部署） |
| `admin` | 仅 Admin API（管理面） |
| `worker` | Chat API + WorkerLoop（数据面，可多副本） |
| `gateway` | 仅 IM 网关（有状态，单副本） |

**密钥与配置**：平台只读一个 YAML（`/etc/trpc-service/config.yaml`），敏感值全部走环境变量
注入（`TRPC_MYSQL_DSN`、`TRPC_SECRET_MASTER_KEY`、`TRPC_JWT_SECRET`、`ADMIN_PASSWORD`），
配置文件里用 `${ENV}` 展开，**仓库不存明文**。模型 API Key 与 IM 凭据存 MySQL（AES-256-GCM，
主密钥只存在于环境变量），`GET /secrets` 只返回 key 名不返回明文。

### 1.3 两种方案取舍

| 维度 | 最小（core） | 生产（分角色 + edge） |
| --- | --- | --- |
| 容器数 | 4 | 9~12（含观测） |
| 故障域 | 单进程，数据面挂了管理面一起挂 | 角色隔离，管理面独立存活 |
| 扩展 | 垂直（加 CPU/内存） | 水平（`WORKER_REPLICAS`） |
| 入口 | 直连 8080/5173，无 TLS | edge TLS/HTTP2/HSTS，路径分流 |
| 灰度 | 不易（单容器换版即全量） | 可（新构建挂 edge 权重，§3） |
| 何时升级 | 演示/试运行 | 有多租户真实流量、需要不停机发布时 |

### 1.4 上线前检查清单

1. `TRPC_JWT_SECRET`：**每个会响应 HTTP 的节点都必须有**（曾经只在 admin 上配置，导致
   worker 路由返回 401「invalid or expired token」，生产拓扑实测时才发现）。
2. `TRPC_SECRET_MASTER_KEY` 已改：缺失时 credential store 不启用，模型 Key 无法落库。
3. `ADMIN_PASSWORD` 已改：`server.production` 下缺失口令直接拒绝启动（`exit 1`）。
4. MySQL 字符集/时区：`OpenMySQL` 已把会话时区钉到 UTC；外部托管 MySQL 时确认
   `MAX_CONNECTIONS`、`wait_timeout` 高于平台连接池需求。
5. Redis：开启持久化（`appendonly yes` 或合理 RDB 策略）。Redis 同时承载 stream、会话锁、
   幂等键、审批状态——**丢 Redis = 丢在途消息与锁**（outbox 回复是 MySQL，不受影响）。
6. 备份：MySQL 定时 dump（租户/Agent/审计/用量/outbox/配置版本都在这里）；Redis 可丢但
   建议开 AOF，避免停机时在途消息需要人工补发。
7. 观测：`prometheus.yml` 已挂 `alerts.yml`（11 条规则），确认 Prometheus 能抓到
   `otel-collector:8889`，并在告警通道接上 `PlatformIMInboundWithoutDelivery` 等关键规则。
8. 演练：至少跑一次 `bash scripts/faults/redis-outage.ps1`（Windows 用 pwsh）确认自愈行为
   与本文一致。

## 2. 故障恢复与降级

### 2.1 总矩阵

| # | 故障 | 检测方式 | 平台行为（降级） | 恢复 | 用户感受 | 实测证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Worker 节点崩溃 / 被 kill | 消息未 ack 留在 PEL | 消息**不丢**：`XAUTOCLAIM` 认领重投；幂等键是 90s **租约**（回合内每 10s 续期），崩溃后到期即允许重跑；MySQL outbox `message_id` 唯一标记保证不重复回复 | 新副本起来即接管（无状态） | 该回合延迟到重投后完成，可能重复计一次模型调用 | §2.2 |
| 2 | IM 重复回调 / 平台重推 | 入站 ID = `channel:platformMsgID` | Redis 幂等键两段式（`SetNX` 抢占 → 成功 `CommitIdem` / 失败 `ClearIdem`）→ 重复回调只产生一次回合 | 无需恢复（幂等即最终一致） | 用户只收到一条回复 | §2.3 |
| 3 | MySQL 短暂不可用 | 连接错误 / 语句失败 | 入站消息**仍被接受**（在 Redis），但**回复持久化失败 → 消息保持 pending 重投**；审计/账本/用量（best-effort）丢弃并告警；启动时另见 §2.4 | MySQL 回来后重投成功，回复补投 | 停机期间无回复；恢复后收到回复 | §2.4 |
| 4 | Redis 短暂不可用 | 阻塞读失败 | 消费循环/出口跟随者**退避重连**（1s→30s），依赖沉默 >5s 时 `/healthz` **503**；`POST /chat` 返回 **500**（拒绝，不假装接受） | 总线重新应答读 → 自动清 503，继续消费 | 停机期间发消息报错；恢复后 ≤6s 正常 | §2.5 |
| 5 | 模型超时 / 上游挂起 | HTTP 超时 | 单次调用 **120s** 超时，整个回合 **300s** 硬超时 → 审计 `error_type=timeout`、指标 `agent_run_errors`，消息重投（最多 5 次后进 DLQ） | 上游恢复即自动成功 | 该回合失败（可见错误），后续正常 | §2.6 |
| 6 | 工具执行失败 | 工具返回错误 | 容器非零退出（语法错误/异常）算**工具输出**交模型自修复；传输层失败（CLI 缺失/镜像拉取/超时）才是 tool error → 审计 `run_error` | 模型改写代码重试 | 用户看到 Agent 自我修正后的结果 | §2.7 |
| 7 | IM 发送失败 | 平台返回错误码/超时 | Outbox 事件指数退避 2s→60s，**10 次后置 `dead` + `last_error`**（不再无限重试） | 修好凭据后用 SQL/接口重放 | 该条回复丢失，其余正常 | §2.8 |
| 8 | 消息反复失败 | 失败计数（Redis，24h TTL） | 5 次业务失败 → DLQ（`stream:inbound:dlq` + `dead_letters` 表），`GET /dlq` 可见、`POST /dlq/{id}/replay` 重放 | 人工修复 + 重放 | 该消息长时间无回复，运维可见 | §2.8 |
| 9 | 中毒消息（无法解码） | 反序列化失败 | 入站直接 ack（不成毒丸）；出站事件 `park` 成 `dead` 并记原因 | 无需恢复 | 无影响（该条丢弃） | §2.8 |
| 10 | 依赖启动竞态（容器乱序起） | 启动连接失败 | 启动等待 MySQL/Redis 就绪 **60s（2s 轮询）**；MySQL 超时 → `health.Report("mysql","unavailable")` → `/healthz` 503 且数据面不启动（不静默回落内存） | 重启节点 | 部署期短暂不可用 | §2.4 |

> **时钟一致性（历史真实事故）**：outbox 到期判断曾比较"数据库写入的 `created_at`"与
> "进程时钟"，驱动按 UTC 解析而 MySQL 会话是本地时区（UTC+8）→ 所有回复静默停在
> pending。修法是**让数据库自己算年龄**（`TIMESTAMPDIFF(SECOND, created_at, NOW())`）
> 并把会话时区钉到 UTC（`OpenMySQL` 注入 `time_zone='+00:00'`），回归测试
> `TestOutboxDeliversWhenServerZoneDiffersFromTheDriver`。

### 2.2 节点故障（进程被杀）

机制（三段）：

1. **认领**：消息被消费后进入 Redis PEL；消费循环每次 `XAUTOCLAIM` 认领空闲超过 30s 的条目，
   所以崩溃节点的在途消息会被其他节点（或重启后的自己）接管。
2. **幂等租约（三态）**：处理前 `Idempotent` 原子认领 `idem:{msgID}`（**租约 90s**，回合内
   `startTurnHeartbeat` 每 10s 续期）；回合成功且回复落 outbox 后才 `CommitIdem`（24h 持久标记）。
   关键是**"进行中"与"已完成"必须是两个答案**：
   - 已完成 → ack 丢弃（平台重推的正常路径）；
   - 进行中 → **`ErrRequeue`，绝不 ack**：对方要么提交（下次看到"已完成"再 ack），
     要么已死（租约到期后下次认领才真正执行）。
3. **会话锁**：同一 session 30s 锁 + 心跳续期，保证跨节点只有一个回合在跑；锁被别的节点占住时
   返回 `bus.ErrRequeue`，**不计入失败次数**（否则繁忙会话会把健康消息推进 DLQ）。

**实测（`scripts/faults/node-failure.ps1`，真实多消费者集群：all-in-one + admin + 2×worker）**：

| 观测 | 结果 |
| --- | --- |
| 发布 20 条后 SIGKILL 一个 worker（`docker update --restart=no` + `docker kill`） | 杀前 `pending=15`、杀后 `pending=8`（死者 PEL 里的在途消息） |
| 同时滚动重启另一个 worker | 重启后自动重新加入消费组，队列继续被消费 |
| 最终结果 | **每条消息恰好一条回复：无丢失、无重复** |
| 崩溃消息的恢复延迟 | 死者认领的那条消息在**幂等租约到期后**被重跑（实测 88s 后回复落库），上限 = 租约 90s + 认领窗口 30s |

> **这个演练抓到过一个真实缺陷，值得写进运维知识**：`Idempotent` 早期只返回布尔值，
> 于是"别人正在处理"与"已经处理完"看起来一样。节点被 SIGKILL 后，`XAUTOCLAIM` 在死者的
> 90s 租约仍然有效时就把消息交给了存活节点，存活节点读到"标记存在"→ 当成"处理过了"→
> **ack**。表现极具欺骗性：`lag=0`、`pending=0`、`/healthz` 200，消息却凭空消失
> （演练实测丢 3/20）。现在 `Idempotent` 返回三态、`ErrRequeue` 保持 pending；
> 回归测试 `TestBusIdempotencyDistinguishesLeaseFromCompletion`、
> `TestWorkerLeavesAnInFlightMessagePending`。

验证方式：

```bash
pwsh scripts/faults/node-failure.ps1 -Messages 20 -Workers 2   # 建 2 个 worker，杀进程 + 滚动重启演练
docker exec deployments-redis-1 redis-cli XPENDING stream:inbound workers   # 有 pending 说明有在途消息
docker exec deployments-redis-1 redis-cli XINFO GROUPS stream:inbound       # lag / consumers
```

> 运维提示：`XINFO GROUPS` 的 `consumers` 随每次进程重启累积（消费名是 `host-pid`），
> 实测一天下来攒到 50+。它们是空 PEL 的元数据，不影响正确性；需要清理时用
> `XGROUP DELCONSUMER stream:inbound workers <name>`（先确认其 PEL 为空）。

**崩溃恢复的代价（如实）**：崩溃节点的在途消息要等幂等租约过期才会被重跑，恢复上限约
**2 分钟**（90s 租约 + 30s 认领窗口）；这段时间消息一直 pending、不丢，但用户会等。
要缩短只能调小租约，代价是并发重投时更容易重复执行（由 outbox 唯一键兜底，用户不会收到重复回复）。

### 2.3 IM 重复回调（实测）

- 入站 ID 是 `channel:platformMsgID`（企业微信/飞书的消息 ID），消费者按它做幂等；
- 企业微信 SDK 不 ack 会重推，因此连接层收到消息立即发**空流式占位**（`finish=false`）
  以满足回调超时，同时 worker 侧两段式幂等保证只跑一次。

实测（`scripts/faults/im-redelivery.ps1`：把同一信封 id 两次 `XADD` 进 `stream:inbound`，
即"同一条平台回调被推两次"的真实形状）：

| 观测 | 结果 |
| --- | --- |
| 两次投递的流水记录 | `chat_messages`: USER=1 ASSISTANT=1；`audit_logs` executed=1；`idempotency_keys`=1 |
| 第二次投递的处理方式 | 日志 `worker: delivery already completed, acking`（`IdemCompleted` → ack 丢弃） |
| 结论 | **重复回调不产生第二次回合、第二条回复、第二份计费** |

### 2.4 MySQL 短暂不可用（实测）

行为分层（按影响从大到小）：

| 面 | 行为（实测） |
| --- | --- |
| 入站接收 | **正常**：`POST /chat` 返回 **202**（消息进 Redis stream） |
| 运行期健康探针 | `/healthz` **保持 200**：MySQL 只参与**启动期**判定（启动等待 60s，超时才 503 且数据面不启动） |
| 管理 API | **降级**：`GET /tenants` 返回 **500**（管理面确实读 MySQL） |
| 回合执行 | 会话/记忆在 Redis 时可继续；**需要 MySQL 的步骤（如 agent 查询）失败 → 消息保持 pending 重投**（实测日志 `bus: inbound handling failed ... attempt=1 max=5 err="worker: agent agent001 not found: dial tcp: lookup mysql ... no such host"`） |
| 回复持久化 | outbox 写不进 → 不 ack，靠重投补齐 |
| 审计 / 会话账本 / 用量 | best-effort：失败只记日志不阻断回合（账本按 `message_id` 幂等） |

实测（`scripts/faults/mysql-outage.ps1 -DownSeconds 25`）：停库期间入站 202、`/healthz` 200、
管理 API 500、`pending=1`（在途不丢）；**MySQL 恢复后 10s 内回复落库，USER=1/ASSISTANT=1
（重投过、但只回复一次）**。

> 为什么不停机也"看起来没事"：数据面不依赖 MySQL 的**实时读**（会话在 Redis），
> 所以停库的直接影响是"回复暂时发不出去 + 管理面报错"，而不是"消息丢失"。
> 代价是重投会**重跑该回合**（多花一次模型调用），由 outbox 唯一键保证用户不会收到两条回复。

### 2.5 Redis 短暂不可用（完整实测记录）

脚本：`pwsh scripts/faults/redis-outage.ps1 -DownSeconds 30`（退出码 0 = 全部不变量成立）。

| 时间点 | 观测 |
| --- | --- |
| 基线 | `/healthz` 200；一个真实回合 **2.086s** 成功 |
| 停 Redis | t+0s 仍然 200（失败探测需要一次阻塞读失败） |
| t+21s | `/healthz` → **503**，`reason` 同时列出两个消费者：<br>`worker: consumer lost the bus: ... xautoclaim: dial tcp: lookup redis ... no such host`<br>`channels: outbound follower lost the bus: ... resolve outbound tail: ...` |
| 停机期间 | `POST /chat` → **500**（拒绝而不是假接受，避免"消息被吞"的黑洞） |
| 重新启动 Redis | t+3s 仍 503 → **t+6s 恢复 200**（无需重启进程） |
| 恢复后 | 一个真实回合 **1.519s** 成功；容器 `StartedAt` 与 `Pid` **完全未变** |

日志节奏（真实日志，说明"沉默判定"为什么必要）：

```
attempt=1 silent_for=571ms  err="xreadgroup: dial tcp 172.20.0.2:6379: connect: connection refused"
attempt=2 silent_for=21.1s  err="xautoclaim: dial tcp: lookup redis on 127.0.0.11:53: no such host"
... 20s 后 ...
INFO worker: consumer reattached      # 总线重新应答读的那一刻
```

**这里有一个必须记住的教训**：第一版自愈实现用"消费循环还在跑"判断恢复，结果在 Redis
仍然停机时打印 `reattached` 且 `/healthz=200`——被本演练脚本当场抓住。真正的证据是
**总线回答了一次读**（`RedisBus.SetConsumeReady` / `Gateway.SetReady` → `health.Supervisor.Attached`），
而失败次数判定同样不可靠：一次失败可能耗掉 19s（容器名解析超时），所以现在的规则是
**依赖沉默超过 5s 即判降级**（正常时总线每秒都会应答一次阻塞读）。

### 2.6 模型超时（实测，含一个被演练改掉的误判）

护栏有两层：

| 层 | 值 | 作用 |
| --- | --- | --- |
| 单次模型 HTTP 调用 | `llm.DefaultHTTPTimeout` = **120s**（openai/anthropic/gemini 三个协议） | 一次请求的读超时 |
| 整个回合 | `worker.runTimeout` = **300s**（含多轮工具调用） | 端到端预算，超时即取消 runner |

**实测（`scripts/faults/model-timeout.ps1`，临时端点 + 临时 Agent，用完即删）**：

| 上游故障形态 | 结果 |
| --- | --- |
| 黑洞地址（TCP 不可达） | **68s** 失败，审计 `error_type=run_error` —— 这是**连接层**失败，不是超时，分类正确（说明分类有区分度） |
| 连上但永不应答（stall 上游） | 单次调用 120s 超时后 SDK 会重试，累计把回合拖到 **~283s**，最终由**回合级 300s 护栏**切断 |
| 故障后的节点 | `/healthz` 仍 200、下一个正常回合照常完成（无 goroutine/槽位泄漏） |

> **这个演练抓到一个真实误判（已修）**：回合被我们自己的 300s 护栏切断时，框架用自己的
> 措辞报告"模型调用被取消"，`errors.Is(err, context.DeadlineExceeded)` 为假，于是审计写成
> `run_error`——和"上游返回错误"完全分不清，运维无法据此判断该找上游还是该调预算。
> 修法：`run()` 回传错误时用 `timeoutAware(runCtx, err)` 把平台自己的 deadline 一并包装进去
> （`fmt.Errorf("%w: %w", …)`，框架错误仍可在日志里读到），审计因此记为 **`timeout`**；
> 单测 `TestTimeoutAwareKeepsThePlatformDeadlineVisible` 覆盖"deadline 被切断→timeout"
> 与"普通上游错误→run_error"两侧。
>
> **如实说明未闭合的部分**：用"连上但永不应答"的上游反复演练时，同一脚本观察到过两种结果
> （~283s 被回合护栏切断 / 几秒内以空回答结束并被记为 `executed`），差异来自 SDK 重试、
> 读超时与"模型返回空文本"三条路径的交错，仅靠外部观察无法稳定复现单一结论。
> 已确定的是：**平台自己的预算被触发时一定记为 `timeout`（单测保证）**；
> 待办（非本轮范围）是用框架级埋点确认 openai 路径下单次 120s 读超时在重试下的真实边界。
>
> 运维口径：**真正的兜底是回合级 300s**，单次 120s 会被 SDK 重试放大；
> 因此 `PlatformTurnLatencySevere`（p99>180s）比任何单次超时都更早预警。
> 另外，"模型返回空文本"会让该回合以 `executed` 结束但用户收不到回复——
> 这是一条真实的产品缝隙，现在至少会打 WARN 日志（`worker: agent produced no text, acking without a reply`），
> 不再静默。

## 3. 灰度发布与配置回滚

> **口径**：本平台的"灰度发布"指**平台项目版本**（新构建）的灰度，不是 Agent 资产的灰度。
> Agent 侧只有不可变版本 + 原子回滚（§3.6）。

### 3.1 平台版本灰度（权重 + 试点租户白名单）

资产：`scripts/canary.sh`、`deployments/docker-compose.canary.yml`、`deployments/canary/edge.conf`、
`deployments/canary/weight.conf`（脚本生成）、每个进程的 `GET /version`。

```bash
bash scripts/canary.sh up                    # 构建并启动 v2（role=worker，不暴露宿主端口）
bash scripts/canary.sh weight 10             # 10% 流量走 v2（其余仍走 v1）
bash scripts/canary.sh weight 10 t-demo,t-a  # 试点租户钉死走 v2（优先于百分比）
bash scripts/canary.sh check 200             # 采样 200 次，给出真实占比
bash scripts/canary.sh tenant-check t-demo 50 # 单租户验证
bash scripts/canary.sh rollback              # 权重归零 + reload（v2 容器留着排障）
bash scripts/canary.sh promote               # 用新构建重建主服务、移除 v2
```

分桶与判定细节：

- 权重用 nginx `split_clients "${cookie_dsh_uid}${remote_addr}"`：**同一浏览器稳定命中同一版本**
  （没有 cookie 时退回客户端 IP，仍然稳定）；
- 试点租户用 `map $http_x_tenant_id` 白名单，**优先于百分比**（白名单命中即走新版本），
  两者合成 `map "$forced_v2$weighted_v2" $backend_upstream`；
- `weight.conf` 是唯一事实来源，`canary.sh status` 直接打印它 + 两个服务的 `/version`；
- 0% 不写百分比行（nginx 拒绝 `0%` 条目），完全回滚即"没有百分比条目"；
- nginx reload 是优雅的，采样前脚本会等 2s（`RELOAD_SETTLE`），否则会观测到上一版权重。

**实测数据**（本机真实 edge，每次都实采样，非估算）：

| 步骤 | 期望 | 实测 |
| --- | --- | --- |
| 基线（v2 已起，权重 0） | 0% | 200 次采样：v2 **0/200** |
| `weight 10` | ≈10% | 400 次采样：v2 **44/400 = 11.0%** |
| 试点租户 `t-demo` | 100% | **50/50** 全部 v2；同时另一租户 200 次采样 v2 **17/200 = 8.5%**（未被白名单影响） |
| `weight 100` | 100% | **200/200** |
| `rollback` | 0% | **100/100** 回到主构建，v2 占比 0% |

### 3.2 蓝绿与提升

- 生产（§1.2）里新版本以新容器出现，edge 用权重/白名单引流；观察 `GET /version`
  与告警（§2.9）后再加大权重。
- 提升 = 让主服务跑新构建（`canary.sh promote`）。生产上等价于 "把 `backend-worker/admin`
  指向新镜像 tag，然后移除临时服务"。
- 回滚 = 权重归零（秒级），**不需要重新构建**；已进入新版本的会话不受后续切换影响
  （回合内一致性由会话锁保证）。

### 3.3 为什么 IM 网关只能蓝绿

一个 bot 账号（企业微信/飞书）只能由**一条长连接**持有；按百分比给网关分流会让两条连接
各自收到一半回调，而幂等键挡不住"两条流各自收到不同消息"（它们是不同的消息 ID）。
所以网关的发布方式是：

1. 停旧节点网关（`docker compose stop backend-gateway`，或先只停它的 adapter）；
2. 起新节点网关（新构建）；
3. 用一条真实消息验证往返（`/version` 显示新版本，IM 侧收到回复）。

网关是**有状态**的，因此不在"按比例灰度"的范围内，也不参与 `WORKER_REPLICAS` 扩容。

### 3.4 前端

前端是静态产物 + nginx；灰度期间**只对 `/api/` 分流**，页面本身随平台版本整体切换。
理由：界面与 API 契约保持向后兼容，做不到"半新半旧的前端"这种有意义的状态。

### 3.5 租户配置版本与回滚（平台内 + 平台外）

**平台内**（有 MySQL、平台可用时）：

```bash
# 每次 PUT /tenants/{id} 都会写一条 tenant_config_versions 快照
curl -s localhost:8080/tenants/t-demo/config-versions -H "Authorization: Bearer $TOKEN"
curl -s -X POST localhost:8080/tenants/t-demo/config-rollback \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"version":3}'     # 回滚到第 3 版（配额/审计策略/工具白名单/force_approval 一并恢复）
```

前端「租户 → 配置历史/回滚」提供同样的能力。

**平台外**（平台不可用、或要留档/做变更评审时）：`cmd/configctl`

```bash
go run ./cmd/configctl -dsn "$TRPC_MYSQL_DSN" export   -tenant t-demo -out t-demo.json
go run ./cmd/configctl -dsn "$TRPC_MYSQL_DSN" diff     -tenant t-demo -file t-demo.json   # 漂移则退出码 2
go run ./cmd/configctl -dsn "$TRPC_MYSQL_DSN" apply    -tenant t-demo -file t-demo.json --dry-run
go run ./cmd/configctl -dsn "$TRPC_MYSQL_DSN" versions -tenant t-demo
go run ./cmd/configctl -dsn "$TRPC_MYSQL_DSN" rollback -tenant t-demo -version 3
```

它直接读写同一张表（不经过 HTTP），因此**平台进程挂了也能回滚**；`diff` 的退出码可接进 CI。
两端共用同一个版本序列，不会出现"两套版本号"。

### 3.6 Agent 版本与资产变更

- Agent 资产：publish 生成不可变 `agent_versions` 行，回滚是原子切 `agents.current_version`；
  **没有按比例/按会话分流**（历史上实现过，已连代码一起移除，理由见《架构设计文档》§10.4）。
- 资产（KB/Skill/端点/通道/Agent）的改动都落审计（`audit_logs`，`decision=executed/deny`），
  前端可按"来源/资产种类/决策/操作者"筛选，便于回答"这次变更是谁在什么时候做的"。

### 3.7 发布检查清单

1. `canary.sh up` 后先 `status` 确认 v2 的 `/version` 与预期一致（构建号、role）；
2. 先白名单租户（`weight 0 t-pilot`）跑真实业务，看审计与告警，再放开权重（10→30→60→100）；
3. 每步 `check` 采样确认占比；不要靠"应该生效了"；
4. 观察 15min：`PlatformIMInboundWithoutDelivery`、`PlatformRunErrors`、回合 p99；
5. 出问题 `rollback`（秒级），保留新容器现场再排查；
6. 稳定后 `promote`，并删除临时服务与 `weight.conf` 的百分比条目。

| 节点资源（backend） | CPU 峰值 **28.4%**，内存 33→101 MiB | `docker stats` 采样 4 次 |

> 入站峰值那两行的 MySQL QPS 是 0.2s 窗口的差值（含审计批量刷盘等噪声），只用于量级判断；
> 稳态排空期的 386 q/s 是 7.8s 窗口，更可信。

### 4.2 每节点并发 Session 数

- **有界并发回合数 = `consumeWorkers` = 16**（`infra/bus/bus.go`）。这是单节点同时执行
  的回合上限，也是"每节点并发会话数"的真实含义：一个会话同时只有一个回合（会话锁），
  所以**并发会话数上限 = 并发回合数 = 16**。
- 依据：16 并发下实测 12.75 turns/s，与"16 ÷ 平均回合 1.0~1.25s"吻合，说明 16 槽确实被打满，
  再高的排空速率需要更多槽位或更多节点。
- 调节方式：代码里 `WithConsumeWorkers(n)`（当前未暴露为配置项，改需重建镜像）；
  扩容优先用**多副本**（`WORKER_REPLICAS`）而不是无限加槽——单进程槽位越多，
  一个坏回合（如 300s 超时）占用的资源越多。

### 4.3 平均 token 消耗（成本口径）

`usage_records` 按维度记账（token / tool / skill / sandbox / artifact），`record_id` 幂等：

| 维度 | 行数 | 合计 | 说明 |
| --- | --- | --- | --- |
| token | 424 | 1,223,625 | 平均 **2,886 tokens/回合**（含输入+输出，框架 `Usage` 口径） |
| skill | 424 | 424 | 每回合注入的 skill 数（0/1） |
| tool | 3 | 3 | 本组测试几乎不触发工具（提示词是 `ping`） |

容量换算（以 1 万回合/天为例）：约 **2,886 万 tokens/天**，单节点 12.75 turns/s 的理论
上限是 110 万回合/天——**瓶颈是模型配额与成本，不是平台进程**。按租户查看：
`GET /usage?tenant_id=…&dimension=token`（前端「用量」页同样展示）。

### 4.4 Redis / MySQL QPS 与容量起点

| 负载 | Redis | MySQL |
| --- | --- | --- |
| 入站（20 并发 POST） | 3.5k~4.4k cmd/s（XADD + 幂等 SETNX + 路由查询） | 1.5k~1.7k q/s |
| 稳态排空（16 并发回合） | **455 cmd/s** | **386 q/s** |

容量起点建议（按实测外推，留 3 倍余量）：

- 单节点 10 turns/s 稳态 → Redis 约 **360~500 cmd/s**、MySQL 约 **300~400 q/s**；
- Redis 单实例（本机容器）轻松支撑数千 cmd/s，因此**它不是瓶颈**，但要开持久化并监控
  内存（stream + 幂等键 + 锁 + 审批状态）；
- MySQL 是"回复持久化 + 审计批量写 + 账本"的路径，语句速率是主要观察点；
  外部托管 MySQL 时按 `QPS ≈ 400 × 节点数` 预留连接与 IOPS。

### 4.5 IM 回调峰值

- 平台侧上限 = §4.1 的入站峰值（**3.2k~4.4k msg/s**，单节点），远高于两家 IM 平台的推送速率；
- 真正的上限在 IM 平台侧（企业微信/飞书对回调与主动推送都有频控），因此生产按
  **平台侧限额**做容量规划，并用 `rate_limit` 配置（固定窗口，fail-open）做保护；
- 长回复会被平台截断（企业微信 2000 字、飞书 4000 字，按 rune 安全截断并加 `…`），
  所以出站不需要额外分片；
- 峰值保护：消费者有界并发（16）自然形成背压，积压留在 stream 中不丢（§2.5 已验证）。

### 4.6 扩容判断

| 信号 | 含义 | 动作 |
| --- | --- | --- |
| `xleng(stream:inbound)` 持续增长（`lag>0`） | 消费跟不上 | 加 `WORKER_REPLICAS` |
| 回合 p99 上升但 CPU < 50% | 在等模型/工具 | 先查上游，不是加机器 |
| `PlatformSessionBackendSlow` | Redis/MySQL 争用 | 升级实例或分离数据面 |
| Redis 内存 > 70% | stream/幂等键堆积 | 缩短幂等 TTL、清理已 ack 条目、扩容 |
| MySQL `Questions` 接近实例上限 | 回复持久化变慢 | 提升实例或分库（outbox/审计可分离） |

### 4.7 压测方法（可复现）

```bash
# 入站峰值（不跑模型，只测接收路径）
go run ./cmd/loadtest -mode publish -n 1000 -c 50 -agent agent001
# 端到端回合（真实模型，测用户感知时延）
go run ./cmd/loadtest -mode turn -n 8 -c 4 -agent agent001 -timeout 6m
# 一次性采集全部指标
pwsh scripts/capacity-probe.ps1
```

注意两点（都会影响结论的可比性）：
① `publish` 模式入队后**仍会被真实执行**（每条消息都会跑一个回合并计费），
所以用它测入站峰值要有成本预期；② 测回合延迟前必须**等队列排空**
（`redis-cli XINFO GROUPS stream:inbound` 的 `lag`/`pending` 归零），否则测到的是排队时间。

### 4.8 已知瓶颈与不适用场景

- 单进程槽位 16：超高并发需要多副本（线性扩展，共享 Redis/MySQL）；
- 模型上游不可控：实测有 10~15% 回合拖尾到十几秒甚至接近 300s（阶段 36 数据），
  它是**上游抖动**，平台只能靠超时护栏兜住；
- 未压测项（如实）：Milvus 向量检索、MinIO 制品读写、代码执行容器冷启动、50+ 节点集群；
- 本机单机 Docker Desktop 的网络/磁盘与生产裸机不同，绝对值仅供参考，**方法**才是交付物。

## 5. 日常运维

### 5.1 探针

| 端点 | 用途 | 语义 |
| --- | --- | --- |
| `GET /healthz` | 存活/降级 | 200 = 全部正常；**503 + reason** = MySQL 启动失败、消费循环或 IM 出口跟随者与总线断开（原因按生产者聚合，互不覆盖） |
| `GET /version` | 版本身份 | `{version, git_sha, role, instance, started_at}`，无需鉴权，灰度/回滚时用它判断"谁在服务" |

### 5.2 日志与追踪

- 日志是结构化 JSON（`slog`），敏感属性自动脱敏（`infra/log` 的 `Mask/redactHandler`）；
- 关键行：`worker: consumer lost the bus, reconnecting`（含 `attempt`/`silent_for`/`in`）、
  `worker: consumer reattached`、`bus: message dead-lettered`、`worker: chat ledger write failed (best-effort)`；
- 追踪：一条消息从 `im.callback` → `agent.run` → 工具 → `im.reply` 共用一个 trace id，Jaeger 可见。

### 5.3 备份与恢复

| 数据 | 位置 | 丢失后果 | 备份 |
| --- | --- | --- | --- |
| 租户/Agent/端点/工具/KB/Skill/通道 | MySQL | 管理域丢失 | `mysqldump` 定时全量 |
| 审计/用量/会话账本 | MySQL | 合规与计费缺口 | 同上（可按月分区归档） |
| outbox（待投递回复） | MySQL | 回复丢失 | 同上；恢复后 dispatcher 会自动续投 |
| 租户配置版本 | MySQL | 无法回滚到历史配置 | 同上 |
| stream/锁/幂等/审批 | Redis | 在途消息与锁丢失 | 开 AOF；极端情况下用 DLQ + 账本人工核对补发 |
| 制品 | MinIO | 代码产物丢失 | bucket 版本化已开启（`MinioArtifactService`） |

### 5.4 升级与回滚流程

1. 备份 MySQL（§5.3）与 `cmd/configctl export` 关键租户配置；
2. `canary.sh up` 起新版本 → 白名单租户验证（§3.1）；
3. 观察 15min 告警与 `/version`；
4. 逐步放大权重 → `promote`；
5. 出问题：`canary.sh rollback`（秒级）→ 若已 promote，则用上一镜像 tag 重建并
   `migrate`/DDL 回退（DDL 都是向后兼容的新增列，回滚镜像不需要改库）。

### 5.5 常见故障排查

| 症状 | 可能原因 | 定位 | 处置 |
| --- | --- | --- | --- |
| 用户发消息没人回，`/healthz` 200 | 消费循环已断开但尚未超过沉默阈值；或 Agent 未绑定 | `docker logs … \| grep 'lost the bus\|no agent bound'`；`redis-cli XINFO GROUPS stream:inbound`（`lag` 增长即没人消费） | 等自愈（≤30s）或重启该节点；绑定 Agent |
| `/healthz` 503 | MySQL 启动失败 / Redis 断开 | `GET /healthz` 的 `reason` 直接说明是哪个生产者 | 恢复依赖，观察 `reattached` |
| `POST /chat` 500 | 总线不可用（Redis 断） | 同上 | 恢复 Redis；客户端重试 |
| 回复一直不到 IM | outbox 事件失败重试中或已 `dead` | `SELECT status,retries,last_error FROM outbox …` | 修凭据/配置后重放该事件 |
| 单条消息反复失败 | 业务错误（模型/工具/参数） | `GET /audit?kind=agent_run&decision=failed`；`GET /dlq` | 修因后 `POST /dlq/{id}/replay` |
| 同一问题回复两遍 | 幂等键被清（Redis 数据丢失）或 IM 平台重推 | 查 `audit_logs` 同 `session_id` 是否两条 `executed` | 检查 Redis 持久化；确认消息 ID 来自平台 |
| 管理 API 401 | 该角色未配置 `TRPC_JWT_SECRET` | 对比各服务环境变量 | 补齐后重建该服务 |
| 前台页面反复跳登录 | 中间件顺序导致预检 401（历史缺陷，已修）/ token 失效 | 浏览器 Network 看 OPTIONS 与 `/auth/me` | 升级到最新前端产物（CORS 在最外层） |
| 升级后 `Unknown column` | 旧数据卷没跑新增列的 DDL | `SHOW COLUMNS FROM <table>` | 按 `deployments/mysql/init/014_*.sql` 手动 `ALTER` |
