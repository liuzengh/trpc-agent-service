## 1. 输入假设与目标公式

容量目标：**IM 回调峰值下，端到端（入站→回复）延迟满足 SLO，且不 OOM/不雪崩**。

关键链路与消耗：

| 环节 | 单位成本 | 影响因素 |
| --- | --- | --- |
| 入站回调 | 1 消息 | 平台推送峰值（企微/飞书回调突发） |
| worker 回合 | ~1 goroutine ×（模型调用+工具+memory） | 模型延迟、工具执行、上游 SDK |
| 模型调用 | token | 上下文长度、agent 轮数 |
| Session 后端 | 每回合 1+N 次读/写 | Redis QPS 或 MySQL 行数 |
| 回复投递 | 1 消息 | outbound 流 + adapter SDK |

**经验公式**（单节点）：

```
单节点并发回合 ≈ consumeWorkers（默认 16）
支撑 IM 峰值      ≈ 单节点并发回合 / 平均回合耗时(秒)
每回合 token      ≈ (输入上下文 + 输出) × 轮数     → 汇总为 QPS × token/回合
Redis QPS         ≈ IM 峰值 × (锁 1~2 + 幂等 1 + session 读 1 + 写 1 + memory)
SQL QPS（如 session 走 mysql）≈ IM 峰值 × 行读写系数(5~10)
```

## 2. 逐域评估要点

- **每节点并发 session**：受 goroutine 与内存限制，模型延迟/token 吞吐主导；
  详细设计文档容量表取 200~500 并发/节点（有状态后端），但 worker 实际并发受
  `consumeWorkers`（16）限制 → 扩容 = 加节点（水平，无 sticky）或调大该值并
  观察后端延迟。
- **平均 token 消耗**：从 `usage_records`（audit 包 usage 维度）实测；预算由
  tenant quota 兜底。
- **Redis / SQL QPS**：session 锁 + 幂等 + session/memory 读写都打共享后端；
  用 compose 的 Prometheus（redis/metrics）+ 平台指标 `session_latency` 实测。
- **IM 回调峰值**：从平台侧看 `platform.inbound_messages`（按租户/通道）历史峰值，
  预留 3~5× 突发；`rate_limit.per_minute` ≥ 峰值 × 60。

## 4. 压测方法（推荐）

1. **mock adapter 冒烟**（见《IM联调手册》§2）确认链路后，用脚本向
   `POST /chat`（admin SSE 同管道）注入 N 并发文本消息；
2. 观察三组数：`agent_run_duration` p95、`session_latency`、Redis/MySQL QPS；
3. 找到延迟拐点 = 后端极限；对比 `rate_limit.per_minute` 与 `quota.token_quota`
   确认治理上限不误伤业务峰值；
4. 整节点 kill 测试 XAUTOCLAIM 重投不丢消息。

> **实测口径警示（2026-09 真实模型栈验证）**：`POST /chat` 是**异步入队**（入队
> 即回 `202`），压测脚本直接统计它得到的是**入队侧延迟**（实测 p50≈2ms /
> p95≈34ms、千级 req/s），**不是端到端回合延迟**。端到端容量由
> `consumeWorkers`（默认 16/节点）× 平均模型回合时长决定（真实模型回合
> 60~250s，模型延迟主导吞吐）。因此：
> - 「并发注入」只测平台入队/总线/HTTP 侧余量；端到端吞吐 = 并发会话数 /
>   回合时长，扩容意义 = 加节点并行数；
> - 端到端延迟观测应以 **audit_logs.latency_ms 分布**（每回合真实耗时）与
>   Prometheus `platform_agent_run_duration` 直方图 p95/p99 为准；
> - 实测步骤：以 16 并发会话（每会话串行多轮）灌满 worker，统计 audit 回合数
>   与 latency_ms 分布、usage token 总量；脚本见 `scripts/loadtest/chat_load.go`，
>   操作手册见 `tempdocs/边界演示与压测实操手册.md`。

### 4.1 实测记录（2026-09-09，真实模型栈）

> 环境：Docker Compose 全栈单节点；后端 `-role=all`；真实模型
> deepseek-v4-flash（anthropic 协议，cn.meai.cloud）；agent 仅挂时间工具
> （"hi" 消息不触发）。注入 = `scripts/loadtest/chat_load.go`。

| 档位 | 注入 | 入队侧 | 端到端回合延迟 (audit latency_ms) | 结果 |
| --- | --- | --- | --- | --- |
| 8 并发 × 2 轮 | 16 | p50 5ms / p95 50ms | n=14 完成，0 failed；min 2.9s、**p50 4.3s**、**p95/p99/max 300s** | token ≈7908（≈565/回合） |
| 4 并发 × 3 轮 | 12 | p50 3ms / p95 39ms | n=14(含前档 2 迟到)，0 failed；min 2.7s、**p50 5.0s**、p95/p99/max 300s | token ≈9469 |

**结论（回填容量表的关键实测）**
1. 入队侧（HTTP+总线）远不是瓶颈：p50≈3~5ms、数百 req/s 轻松，与并发无关。
2. 端到端 p50≈4~5s（min≈2.7s），**与并发 4/8 基本无关**——worker 无争用放大；
   `consumeWorkers=16` 下单节点稳态吞吐理论值 ≈ 16 ÷ 平均回合时长。
3. **拖尾是模型侧特性，不是平台缺陷**：低并发下仍约 10~15% 回合飙到 ~300s
   （上游模型慢响应/重试），被平台护栏（模型 HTTP 120s + 整轮 300s）兜住，
   **0 失败、无泄漏**。规划 SLO 时 p95 应按数百秒量级设防（或对模型网关做
   更激进的上游超时/快速失败），不能按 p50 乐观规划。
4. 保守容量估算：若 15% 回合拖 300s、85% 回合 5s，单节点 16 槽实际吞吐
   ≈ 16/(0.85×5 + 0.15×300) ≈ **0.33 回合/s**；水平扩容（无状态 worker）
   可线性提升——这正是平台无 sticky + 总线路由的价值所在。
5. token 成本 ≈565/回合（"hi" 短上下文），长上下文/多轮按 usage_records 实测。

## 5. 治理兜底与降级（无自动扩缩时的护栏）

- 运行上限护栏：`consumeWorkers`、`runTimeout`、模型 HTTP 120s、租户 token 预算、
  IM 入站限流（可选）——不会无界消耗；
- DB 抖动：管理域回落内存（main.go OpenMySQL fail→内存）；session 后端不可用 →
  worker 记 Warn 并以无状态方式跑（worker.go）；budget 计量失败放行；
- **无自动扩缩**：当前是 Docker Compose 单机/水平加节点的部署模型（阶段 25 决策）；
  上 K8s 后再谈 HPA（观测指标已齐备，接入成本低）。

## 6. 结论

“容量评估”是可执行方法论 + 观测体系：输入假设（§1）、分域估算（§2）、指标观测
（§3）、压测（§4）、治理护栏（§5）五步闭环。代码支撑点均已落地；**真实模型
栈的实测数值已回填**（§4.1，2026-09-09）：入队侧非瓶颈（p50≈3~5ms），端到端
回合 p50≈4~5s 与并发无关，~10~15% 回合因上游模型抖动拖尾到 ~300s（护栏内，
0 失败），单节点 16 槽保守吞吐 ≈0.33 回合/s、可水平扩容线性提升。其余账号级
联调（IM 真实收发）结论见《IM联调手册》。
