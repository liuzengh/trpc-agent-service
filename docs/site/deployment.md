# 部署与生命周期

Deployment 是一份确定的上线方案：选择哪一版 Agent，配合哪一版运行配置，再经过校验形成固定版本。它不是启动或停止服务器的按钮。

## 发布前的准备

- 已发布的 AgentVersion。
- 已发布的 ProfileRevision。
- 同类别、同名的资源槽位，例如 `Models.primary`。
- 必要凭据已经由 OWNER 填写。
- V1 执行形态为单 LLM，且包含 `session` 会话存储。

## 从页面完成发布

1. 当前租户 → **部署** → 新建部署。
2. 填写名称，选择 Agent 及其版本。
3. 选择运行配置及其 Revision。
4. 保存并校验。按诊断中的资源名称与原因修正来源配置。
5. 由 OWNER 发布，得到 Deployment r1。
6. 在版本详情确认 Agent、Profile 来源与发布内容。

MEMBER 可以准备和校验部署；发布部署需要 OWNER。

## 如何理解状态

| 你看到的状态或结果 | 它能证明什么 | 还需要做什么 |
| --- | --- | --- |
| 草稿已保存 | 当前编辑已写入服务器 | 校验并发布 |
| 校验通过 / READY | 配置满足相应校验要求 | 发布固定版本、接入渠道 |
| PUBLISHED | 固定部署版本已生成 | 保存渠道目标、启用接入与路由 |
| 连接观测已更新 | 有接入侧运行观测 | 用真实消息确认执行与回复 |
| 真实消息收到回复 | 本轮消息完成收发 | 再验证会话连续性和业务质量 |

**新发布的部署不会自动替换现有渠道目标。** 渠道绑定的是明确的 Deployment Revision。

## 升级、回退与维护

- **升级**：发布新的 Agent 或 Profile → 新建部署版本并校验发布 → 修改渠道目标 → 发送真实消息验证。
- **回退**：把渠道目标切回已知可用的旧部署版本。版本是固定的，凭据与外部资源仍可能变化；回退后也要验证。
- **维护**：先暂停路由，再决定是否停用渠道接入。这样恢复接入时不会意外恢复消息路由。
- **请求超时**：先刷新并确认服务器是否已保存或发布成功，再决定是否重试，避免重复创建。
