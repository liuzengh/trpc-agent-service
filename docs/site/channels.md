# Telegram 与企业微信

渠道把外部机器人收到的消息，交给一个明确的部署版本。页面入口：当前租户 → **渠道接入**。创建、凭据、启停与诊断由租户 OWNER 操作。

## 通用接入顺序

创建停用的渠道账户 → 填写身份与凭据 → 预检或诊断 → 保存固定部署目标（路由关闭）→ 启用接入 → 开启路由 → 发送真实消息。

V1 一个渠道账户对应一个 Binding，目标是具体的 Deployment Revision，不是“自动跟随最新版本”。Provider、机器人身份和自动生成字段只读；Telegram 接收方式可在账户停用后独立切换，并确认影响。修改凭据不会更改接收模式。

## Telegram：优先使用长轮询

准备数字 Bot ID 和 Bot Token。长轮询 `long_polling` 由 Gateway 主动获取消息，**不需要公网 IP 或入站 HTTPS 回调**，但服务器仍需要能够访问 Telegram。

- 长轮询和 Webhook 是两种不同接收方式。已有 Webhook 或另一个轮询进程可能冲突。
- 首次使用长轮询，先运行接入预检，查看身份与接收方式诊断。
- 预检通过后，完成接入与路由启用，再给机器人发送私聊文本。
- 使用 Webhook 时，还需公网 HTTPS 回调与 Webhook Secret；不能把回调地址填成本机内网地址。

### 预检能做什么

Telegram 预检是只读检查，查询机器人身份与 Webhook 状态。它不会发送测试消息，不会拉取更新，也不会修改 Webhook 或启用账户。

“通过”不等于入站与回复已验收。真实消息投递仍需单独验证；结果中的 UNKNOWN 不应被当作失败或成功回复。

## Channel Lab：本地模拟 Telegram

不准备官方 Bot、也不需要公网 IP 时，可以使用独立的 **Channel Lab** 测试文本消息。默认本机入口是 `http://127.0.0.1:18090`，包含聊天测试、Bot 接入、模型设置、投递记录四个页面。

接入顺序：在 Lab 创建 Bot → 在控制台选择 **测试 Telegram（Channel Lab）** 与长轮询 → 填写 Lab Bot ID / Token → 预检 → 绑定已发布的 Deployment Revision → 启用接入和消息路由 → 回到 Lab 发消息、观察真实回复。

Gateway、Worker 与 Lab 应共享可解析 `channel-lab` 的网络。模拟平台不生成 Agent 回复；需要真实执行链路。可直接使用 Profile 中的真实模型，也可将 Profile 指向 Lab 模型端点，使用本地回显或上游代理。回显只验证链路，代理设置影响使用该端点的所有 Bot 后续请求。

Update 的 ACK 不等于 Agent 执行成功。没有回复时，依次检查网络与凭据、接收状态、路由与部署目标、Worker 执行和回复投递。测试账户与官方账户分开，当前仅支持文本。

完整启动、逐页操作、模型配置与排查步骤见 [使用指南第 7.6 节：Channel Lab](/docs/guide.html#chapter-7)。

## 企业微信：使用智能机器人长连接

准备**智能机器人长连接专用 Bot ID 和 Bot Secret**，不是群机器人 Webhook，也不是旧回调模式的 URL、Token、AESKey。

接入诊断需要账户处于停用状态，并明确确认影响。诊断会临时建立真实连接，可能替换同一机器人已有客户端；期间收到的消息不会交给 Agent，也不会回复。结束后诊断连接断开，不会自动恢复其他客户端。

查看凭据和鉴权检查结果。真实消息投递可能标为 NOT_TESTED；完成正式接入与路由后再验收。

### 预检一直等待时检查什么

如果账户已停用、凭据已保存，但诊断没有开始，请让部署维护者检查 Control 中对应 Gateway workload 的 `consumers` 是否包含 `wecom_preflight`。普通连接权限 `wecom_connection` 不包含诊断权限；登录用户是 OWNER 也不能代替服务身份授权。补齐后需重启 Control 使配置生效，不需要修改机器人凭据。

### 群聊如何使用

把智能机器人加入允许使用它的企业微信群，在输入框中通过成员选择器真正 **@机器人** 后发送文本。仅手动输入同名字符串不作为有效提及的验收依据。企业微信客户端会提示机器人在群内仅可获取和回复 @ 它的消息；不要将它当作全群消息监听器。

同一机器人复用已有渠道账户和固定 Deployment，无需为每个群重复填写 Secret。验证时检查回复是否留在原群，并核对群聊与私聊是否分配到不同 Session。多人群、跨群和非文本消息需要分别验收，不能用一次群 @ 成功代替。

如果回复以 `lab echo:` 开头，当前使用的是回显模型：能证明渠道和 Worker 收发链路，不证明真实模型回答、上下文理解或工具执行。要验收这些能力，应发布使用真实模型的 Profile / Deployment 版本，并显式切换目标。

## 两个开关的影响

| 操作 | 接入意图 | 路由意图 | 恢复时的含义 |
| --- | --- | --- | --- |
| 停用接入 | 关闭 | 保留原值 | 重新启用后，原本开启的路由可能恢复 |
| 暂停路由 | 保留原值 | 关闭 | 只恢复接入不会自动打开路由 |
| 启用接入并开启路由 | 开启 | 开启 | 新消息进入绑定的固定部署目标 |

计划维护时，先暂停路由，再停用接入。页面中的意图状态不是远端连接健康或消息已回复的证明。

## 做一次两轮验收

第一条：请机器人介绍自己。第二条：围绕上一条内容继续追问。两轮都收到合适的文本回复，再确认会话能承接上文。保留时间、渠道与部署版本，便于排查。
