# RuntimeProfileSpec Canonical Schema v1

This directory owns the current **internal Canonical RuntimeProfileSpec** schema.
It is not the public write request or public read-response schema.

- `runtime-profile-spec.schema.json` is the strict Draft 2020-12 JSON Schema.
- `embed.go` exposes the same schema to Go validation.
- `examples/valid/` and `examples/invalid/` are internal canonical fixtures shared
  by schema and domain tests, not payloads to send directly to the public API.

## One current V1, three representations

The implementation directly uses `/v1`, `schema_version=v1`, and
`credential_protocol_version=v1`. There is no reference-only compatibility stack.

| Representation | Contents and boundary |
| --- | --- |
| ProfileWrite | Public `config` plus write-only `credentials` actions; never persisted as raw Spec |
| Canonical Spec | Non-secret resource configuration and server-generated internal CredentialIDs |
| ProfileRead | Public redacted `config` and, for detail GETs, current `credential_states`; no `spec` or internal IDs |

Ordinary Draft credential replacement uses copy-on-write (COW): a new internal
ID does not alter published associations. Explicit live updates change the
current value/status under independent Credential CAS; published content and
Digest remain immutable. Draft CAS and idempotency receipts remain separate.

Canonical Spec never contains credential values, ciphertext, mutable status,
Credential Revision, association tokens, or write receipts. Encrypted current
values belong to the Profile-owned credential table. Public read projections
cannot be used to recompute the internal Spec Digest. Publication responses omit
mutable credential states so idempotent publication does not change after rotation.

## Canonical fields and resource boundaries

The required top-level fields are `schema_version`, `credential_protocol_version`,
`models`, `tools`, `knowledge`, and `storage`. Both versions are `v1`. Each collection
may be empty. Limits are 16 models, 64 tools, 32 knowledge resources, and 16 storage
resources. Canonical raw documents and complete credential HTTP requests are
limited to 512 KiB; each write-only credential value is limited to 64 KiB.

Resource keys match `^[a-z][a-z0-9_-]{0,63}$`. Internal CredentialIDs match
`^crd_[0-9a-f]{32}$` and are generated by the server, not entered by users.

| Category | Kind | Canonical credential fields and capabilities |
| --- | --- | --- |
| Model | `openai_compatible` | required `api_key_credential_id`; `chat`/`tool_call`, requiring `chat` |
| Tool | `mcp_streamable_http` | bearer `auth.credential_id`, absent for `none`; fixed `web.search` |
| Knowledge | `qdrant_openai` | optional `qdrant_api_key_credential_id`, required `embedding.api_key_credential_id`; derived `knowledge.search` |
| Storage | `postgres_state` | required `dsn_credential_id` and fixed `destination`; derived `storage.session` and `storage.memory` |

Storage destination is exactly `{host, port, database, username, sslmode}`.
Write-only DSNs accept PostgreSQL URI syntax only, require explicit `sslmode` from
`disable`, `require`, or `verify-full`, and accept no other driver options.
The parser separates the password for encryption; Canonical retains only its
CredentialID plus non-secret destination. Port omission normalizes to 5432.
A live password replacement must preserve the complete destination.

## Resource names and publication boundary

Deployment matches each AgentVersion requirement by **exact category and name**:

```text
AgentSpec.requirements.models.primary -> RuntimeProfile.models.primary
AgentSpec.requirements.tools.search   -> RuntimeProfile.tools.search
AgentSpec.requirements.knowledge.docs -> RuntimeProfile.knowledge.docs
```

There is no capability search, fuzzy name matching, or user-supplied mapping table.
`tools.search` can use MCP `tool_name = search_web`; the remote name is not the
logical resource name. Profile publication does not read AgentVersion, decrypt
credentials, check live credential state, or call providers. Extra Profile
resources do not automatically become available to an Agent.

V1 has no Environment entity/API, `environment_id`, hidden default, overlay,
inheritance, or layered merge. Test and production use separate Profiles and
Profile-owned credentials. Profile does not grant platform network, execution,
or resource-limit permissions. AgentSpec V1 has no storage requirements;
`storage.session` in a fixture is not a required or automatically selected resource.

## Validation, integrity, and current implementation status

Canonical objects reject unknown fields, plaintext credential fields, old `*_ref`
fields, arbitrary option blobs, and internal-framework options. The public Write
DTO separately validates the only permitted credential-value positions, actions,
size bounds, and field shapes. It is not accepted by the Canonical validator.

Domain validation supplements JSON Schema with HTTP/HTTPS URL rules, no userinfo,
query or fragment, the required model `chat` capability, duplicate-key/UTF-8 checks,
and document limits. Fixtures prove static protocol behavior, not that an internal
credential record exists, is active, or can authenticate with a provider.

Full internal Revision reads and public redaction sources are re-canonicalized and
checked against stored Schema Version and Digest. Revision lists use Summary-only
columns, never load `spec_jsonb`, and do not materialize credential states.

Canonical/Write/Read separation, Profile-owned encrypted storage, and consumer
application methods now exist in code. Final test coverage/results are recorded by
the current verification run. Real Deployment, trusted Run/Attempt authorization,
and Worker execution wiring remain follow-up work; missing execution authorization
never receives permissive defaults.

The tool protocol remains `mcp_streamable_http` with fixed `web.search`. Built-in
and workspace tools remain future typed protocols. Agents declare requirements,
nodes select `tool_slots`, and Workers assemble only Manifest/node requirements.
Implementation identifiers are platform names, not Go imports or arbitrary SDK
options. Workspace execution may reuse the Worker's tRPC CodeExecutor without a
standalone Sandbox Manager; this change adds no new tool kind or capability.

### Managed PostgreSQL / Redis Memory password

`managed_memory` and `managed_session` may carry the server-generated paired canonical fields
`dsn_credential_id` and `credential_audience_digest`. The latter is the exact
role-bound PostgreSQL/Redis Memory or Redis Session backend Snapshot digest, obtained through a trusted platform port.
Neither field is accepted or returned in public config. Public write actions and
credential state use `storage.<name>.dsn_password`; the value is a password, not
a DSN. Deployment requires a configured, matching association for active managed
Memory. Changing backend identity/revision requires replacement, not implicit keep.
Published credential rotation uses the immutable association without consulting
current backend availability. Managed Session only enables Redis/session_runtime; Memory retains memory_runtime. Other managed roles do not gain this
credential purpose.

Managed Artifact uses optional canonical access_key_id_credential_id and
secret_access_key_credential_id with one fixed S3 Snapshot audience digest.
Draft may be partial; new Worker compilation requires both associations.
Public write/state purposes are access_key_id and secret_access_key under
storage.artifact. Public config never accepts internal IDs or audience fields.

Managed Knowledge now accepts optional paired canonical
qdrant_api_key_credential_id and credential_audience_digest from the trusted
Qdrant Snapshot resolver. Public config remains unchanged; write/state use
qdrant_api_key. Embedding credential audience retains its existing kind/BaseURL
algorithm. New Worker publications require the explicit Qdrant association;
historical descriptors without it remain readable, not executable.
